## 三、分阶段详细分析

### 3.1 B-1 基线向量检索（最优阶段）

**配置**: ChromaDB + DashScope text-embedding-v2, k=10

**Hit@5 = 31/38 (81.6%)** | 平均延迟: 369ms

**命中情况**:
- 高度匹配(文档在Top3内): 24条查询
- 边缘命中(文档在Top5内): 7条查询
- 完全未命中: 7条查询

**未命中查询分析** (7条):

| 查询 | 目标文档 | 失败原因 |
|------|---------|---------|
| 试用期多长时间？ | 员工手册 | "试用期"与员工手册中"3个月"的表述在向量空间距离远 |
| 公司是哪一年成立的？ | 公司简介 | 短查询+事实性答案，Embedding泛化差 |
| 公司发展历程 | 公司简介 | 同上 |
| 公司的核心价值观是什么？ | 公司简介 | 抽象概念难以精确匹配 |
| 公司有哪些部门？ | 公司简介 | 短查询与文档片段语义不匹配 |
| 公司的联系方式 | 公司简介 | 电话号码类事实检索非向量所长 |
| 访客如何进入公司？ | 行政办公管理制度 | 短口语化查询与正式文本不匹配 |

**核心问题**: 公司简介类文档（短段落、事实陈述、专有名词）普遍检索困难，是当前系统的主要瓶颈。

### 3.2 B-2 BM25+向量混合检索

**配置**: α(vector)=0.5, α(BM25)=0.5, score-level fusion

**结果: R@5=0.684, 显著低于基线 (-16.1%)**

**根本原因**: 
1. BM25对短查询（如"试用期多久"）给出高分，但目标文档在向量空间中排名靠后
2. Score-level fusion导致BM25高分配上前几名，但这些文档在向量检索中本来排名就低
3. 缺少RRF（Reciprocal Rank Fusion）这样的rank-level融合方法

**Top10来源分布**: vector=100%, bm25=0%, vector+bm25=0%

这说明即使在fusion后，BM25对Top10的贡献也基本为零——因为BM25高分的文档在向量空间中普遍得分低，最终fusion score被向量分数主导。

### 3.3 B-6 候选文档过滤率分析

**精排过滤率**: 74.7% (150候选 → 38精排)

**来源分布**: 100%来自向量检索，BM25完全没有贡献

**Hit@5=68.4%**，在k=10时与B-2完全一致，验证了向量主导的结论。

### 3.4 B-3 多阶段+Rerank精排

**配置**: 混合检索候选(15个) → Qwen gte-rerank-v2 → Top5

**结果**: R@5=0.700, MRR=0.700 (精简10条测试集)

**关键观察**:
- Top1 rerank分数对最终命中有决定性作用
- 高分案例: "公司发展历程" → Top1得分0.790，远超其他
- 低分案例: "试用期多长时间" → Top1仅0.205，说明reranker也识别出该查询检索质量差
- "公司简介"类查询全部返回0-4个结果，reranker直接过滤掉了不相关候选

**精排过滤率**: 74.7%，reranker将150个候选缩减到38个，大幅降低下游LLM调用量。

### 3.5 B-4 CRAG正确性反馈（Corrective RAG）

**配置**: top_k=5, rerank_before_grade=True, max_retries=1

**结果** (5条精简测试):

| 查询 | 决策 | 高相关 | 均分 | R@5 | 命中 |
|------|------|--------|------|-----|------|
| 新员工入职流程是什么？ | HIGH | 5/5 | 0.80 | 1.00 | ✓ |
| 试用期多长时间？ | HIGH | 2/2 | 0.75 | 0.00 | ✗ |
| 公司工作时间是怎么规定的？ | HIGH | 4/5 | 0.65 | 1.00 | ✓ |
| 年假有多少天？ | NO_RESULTS | 0/0 | 0.00 | 0.00 | ✗ |
| 工资什么时候发放？ | HIGH | 5/5 | 0.55 | 1.00 | ✓ |

**HIGH比例**: 80.0% | 平均高相关文档比例: 76.0% | 平均延迟: 45s

**CRAG关键价值**:
1. **正确识别无结果场景**: "年假有多少天？"触发了NO_RESULTS判断（检索为空），触发1次重写
2. **量化相关性评分**: LLM-as-judge给出0.55~0.80的相关性评分，提供了可解释性
3. **减少LLM生成浪费**: HIGH决策直接用于生成，LOW/NO_RESULTS提前拦截

**当前问题**:
- "试用期多长时间？"虽然HIGH(5/5)，但R@5=0，因为员工手册在向量检索中根本没有被召回到候选集
- CRAG评估的是"检索到的文档是否相关"，而非"相关文档是否被检索到"

### 3.6 B-5 Query Expansion

**配置**: ExpandStrategy.HYBRID (Rule-first → LLM fallback)

**结果** (5条复杂查询):

| 查询 | 规则分解 | LLM分解 | 策略 | 耗时 |
|------|---------|---------|------|------|
| 新员工入职流程是什么？ | 3个子查询 | 3个 | rule | 1ms |
| 公司工作时间是怎么规定的？ | 3个子查询 | 3个 | rule | 1ms |
| 公司有哪些福利？ | 1个子查询 | 1个 | rule | 89ms |

**规则分解率**: 100% (5/5) | **LLM分解率**: 100% (5/5) | **LLM实际调用**: 0次 (规则全部覆盖)

**核心发现**:
1. 规则引擎（正则匹配）已经能覆盖全部复杂查询，无需LLM介入
2. "公司有哪些福利？"被分解为"公司政策"（过度泛化），但与LLM分解结果一致
3. 唯一一次LLM调用发生在"公司有哪些福利？"，耗时89ms，结果与规则相同

**Query Expansion对"公司简介"类问题的局限**:
- "公司是哪一年成立的？" 短查询，无关键词触发规则分解
- "公司的核心价值观是什么？" 同上
→ **建议**: 扩展规则引擎，增加"什么/哪一年/哪个"类短查询的规则处理

### 3.7 C 分块策略测试

**测试文档**: 员工手册.md

| 策略 | 块数 | Token范围 | 平均Token | 超限比例 | 适用场景 |
|------|------|----------|----------|---------|---------|
| recursive | 2 | 178~481 | 330 | 0% | 通用首选 |
| semantic | 1 | 631 | 631 | 0% | 大段落保留 |
| hybrid | 3 | 82~413 | 220 | 0% | 平衡质量 |
| **markdown** | **10** | **25~72** | **51** | **0%** | **标题结构化** |

**句子分割验证**: 3/4 通过 (75%)
- ✓ 省略号: 1句
- ✓ 分号列表: 3句
- ✓ 圆圈序号: 3句
- ✗ 数字列表: 期望3句, 实际6句 (识别精度问题)

**Token估算精度**:
- 中文: ~1.0字符/token
- 英文: ~4.7字符/token
- 混合: ~0.9字符/token

**分块策略推荐**:
- **推荐 `hybrid`**: 块数适中(3块)，Token分布均衡(82~413)，适合大多数场景
- **推荐 `markdown` 作为备选**: 对于有清晰标题结构的文档，10块更精细，有利于精排

## 五、核心问题总结与优化建议

### 问题1: 公司简介类文档检索失败（严重）

**现象**: 7/38 查询未命中，其中5条来自"公司简介"文档

**根因**: Embedding模型对以下内容泛化差：
- 短查询（"公司是哪一年成立的？"仅8字）
- 事实性陈述（年份、数字、专有名词）
- 抽象概念（"核心价值观"）

**建议优化**:
1. [高优先级] 对"公司简介"类文档降低分块阈值（当前语义分块产生了1个631token的大块，导致关键信息被淹没）
2. [中优先级] 增加Query Expansion对短查询的规则覆盖
3. [低优先级] 考虑混合方案：对短查询增加BM25权重或启用精确匹配

### 问题2: BM25混合检索降低效果（中等）

**现象**: B-2比B-1的R@5下降了16.1%

**根因**: Score-level fusion在当前配置下BM25反而引入噪声

**建议优化**:
1. [高优先级] 改为Rank-level fusion（RRF）而非score-level fusion
2. [中优先级] 对短查询（<10字符）降低BM25权重
3. [中优先级] 调整fusion权重：推荐 α(vector)=0.8, α(BM25)=0.2

### 问题3: CRAG评估的是相关性而非召回（中等）

**现象**: "试用期多长时间？"被CRAG评为HIGH，但R@5=0

**根因**: CRAG评估的是"召回了什么文档的相关性"，而非"应该召回什么文档"

**建议**: CRAG + Recall-oriented evaluation需要同时监控两个维度

### 问题4: Rerank分数区分度不足（轻微）

**现象**: Top1分数0.790 vs Top2分数0.152（好），但"试用期"类查询Top1仅0.205

**建议**: 调整rerank threshold从0.1到0.15，避免低质量候选进入精排

## 六、推荐的生产配置

基于测试结果，推荐以下生产配置：

```
检索阶段:
  - 启用: 向量检索 (RetrieverManager)
  - 启用: Rerank精排 (Qwen gte-rerank-v2, top_n=5, threshold=0.15)
  - 可选: BM25 (α=0.2, 仅用于短查询)
  - 可选: CRAG (HIGH时直接生成, LOW时启用Query Expansion)

分块策略:
  - 默认: hybrid (3块, 平均220token)
  - 结构化文档: markdown (更细粒度)

Query Expansion:
  - 默认: Rule-based (0 LLM消耗, 100%覆盖)
  - 规则无法处理时: LLM HYBRID fallback

CRAG:
  - rerank_before_grade=True (减少50% LLM评估调用)
  - max_retries=1 (平衡质量与延迟)
```
