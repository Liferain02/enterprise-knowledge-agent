# 全局变量设计与测试总结

## 1. 这份报告怎么讲

这次不再按“模块介绍”的方式讲，而是只抓一条最核心的主线：

- 以 `test/gvar_test.cc` 里的 `test_scalar_types()` 为例
- 只看简单标量全局变量，如 `GLOBAL_INT(sa)`、`GLOBAL_INT(sb)`
- 按一个全局变量从“程序启动”到“声明”到“第一次写入”到“所有节点读取/计算”再到“第二轮更新”的生命周期来讲

这样能把下面这些问题一次讲透：

- 全局变量声明时到底发生了什么
- 它什么时候真正分配内存
- master 和 worker 分别做了什么
- 变量是怎么绑定到真实全局地址上的
- 读取、写入、表达式计算到底走了哪些代码路径

文中主要对应这些源码：

- `test/gvar_test.cc`
- `include/global_var.h`
- `src/global_registry.cc`
- `src/global_runtime.cc`
- `include/global_meta.h`
- `include/gallocator.h`
- `src/gallocator.cc`

---

## 2. 先看测试程序里的这段代码

`test_scalar_types()` 是整个生命周期最典型的例子：

```cpp
GLOBAL_INT(sa);
GLOBAL_INT(sb);

if (node_id == 1) {
    sa = 7;
    sb = 4;
}
rt->Fence();

int a = sa;
int b = sb;
ASSERT_EQ_INT(node_id, a, 7);
ASSERT_EQ_INT(node_id, b, 4);
ASSERT_EQ_INT(node_id, (int)(sa + 5), 12);
ASSERT_EQ_INT(node_id, (int)(sa + sb), 11);
```

后面还有第二轮：

```cpp
if (node_id == 1) {
    a = sa;
    sa = a;
    sa = sb;
    sa = sb + a;
    sb = sa;
}
rt->Fence();
```

我们下面就只围绕这段代码说明 `sa` 和 `sb` 的完整生命周期。

---

## 3. 生命周期第 0 阶段：程序启动，先把运行时搭起来

在进入 `test_scalar_types()` 之前，`main()` 已经先调用了：

```cpp
GlobalRuntime::Init("../scripts/slaves");
```

这一步不是全局变量对象自己的生命周期，但它决定了后面变量能不能工作。

### 3.1 master 做了什么

master 节点在 `GlobalRuntime::Init()` 里做了这些事：

1. 读取 `slaves` 文件，得到所有节点 IP。
2. 根据本机 IP 找到自己的 `node_id`，master 的 `node_id = 1`。
3. 构造 `Conf`，初始化底层 GAM allocator：
   ```cpp
   instance_->alloc_ = GAllocFactory::CreateAllocator(conf);
   ```
4. 生成本轮运行唯一的 `run_id`：
   ```cpp
   PublishRunId();
   ```
5. 用 `Put()` 把 `run_id` 发布到全局 bootstrap key。
6. 进入 `SyncAllWorkersReady()`，等待所有 worker 也完成 allocator 初始化。
7. 调用 `InitRegistry()` 创建 `GlobalRegistry`。

### 3.2 worker 做了什么

worker 做的事情和 master 类似，但有两个关键差异：

1. worker 不负责生成 `run_id`，而是通过：
   ```cpp
   FetchRunId();
   ```
   从 bootstrap key 里读到 master 发布的 `run_id`。
2. worker 不负责建立“本轮运行的主身份”，它只是在同一个 `run_id` 下加入本次运行。

### 3.3 这一步为什么重要

后面所有全局变量注册和查找，都依赖下面两个运行时前提：

- 所有节点已经有可用的 `GAlloc*`
- 所有节点使用的是同一个 `run_id`

如果没有 `run_id`，不同轮程序运行的 registry key 会混在一起。

---

## 4. 生命周期第 1 阶段：声明 `GLOBAL_INT(sa)` 时到底发生了什么

先看宏定义：

```cpp
#define GLOBAL_INT(name) Global<int> name(#name)
```

所以：

```cpp
GLOBAL_INT(sa);
```

展开后其实就是：

```cpp
Global<int> sa("sa");
```

### 4.1 这时候只做了“本地对象构造”

`Global<int>` 继承自 `GlobalBinding`，构造时只会初始化这些本地成员：

- `meta_addr_ = 0`
- `data_addr_ = 0`
- `bound_ = false`
- `type_size_ = 0`
- `count_ = 0`
- `total_bytes_ = 0`
- `name_ = "sa"`

也就是说，**声明时没有发生下面这些事**：

- 没有远端分配内存
- 没有访问 registry
- 没有访问 master
- 没有把变量名广播到其他节点

这一步只是告诉当前进程：

“我这里有一个叫 `sa` 的全局变量代理对象，以后如果有人第一次读/写它，就按名字 `sa` 去绑定。”

### 4.2 master 和 worker 在声明阶段是一样的

因为所有节点跑的是同一份程序，master 和 worker 都会执行：

```cpp
Global<int> sa("sa");
Global<int> sb("sb");
```

但此时双方手里都只是**尚未绑定的代理对象**。

区别不在声明，而在第一次使用时。

---

## 5. 生命周期第 2 阶段：master 第一次写入 `sa = 7`，真正触发变量创建

测试中第一轮只有 master 执行：

```cpp
if (node_id == 1) {
    sa = 7;
    sb = 4;
}
```

这里以 `sa = 7` 为例。

### 5.1 语法层调用链

`sa = 7` 会走这条 C++ 调用链：

1. `Global<int>::operator=(const int& value)`
2. `Global<int>::Write(value)`
3. `EnsureBoundOrDie(sizeof(int), 1, sizeof(int))`
4. `WriteBytes(&value, sizeof(int))`

也就是说，**第一次写入并不是直接写内存，而是先强制绑定**。

### 5.2 `EnsureBoundOrDie()` 先发现：这个变量还没绑定

因为刚声明时 `bound_ = false`，所以第一次写入时会进入绑定流程。

它首先计算：

- `expected_type_size = 4`
- `expected_count = 1`
- `expected_total_bytes = 4`
- `expected_hash = HashName("sa")`

这些参数代表 master 对变量 `sa` 的预期：

- 它是一个 `int`
- 只有 1 个元素
- 总共占 4 字节

这些预期之后会被写进元数据，并在其他节点绑定时校验。

### 5.3 master 发现本地 registry 还没有 `sa`

因为当前节点是 master，所以 `EnsureBoundOrDie()` 走的是：

```cpp
if (rt->IsMaster()) {
    if (!reg->LookupLocal(name_.c_str(), &existing)) {
        existing = reg->Register(...);
    }
}
```

第一次访问 `sa` 时，本地缓存里还没有 `sa`，所以进入：

```cpp
GlobalRegistry::Register("sa", 4, 1, 4)
```

这一步才是 `sa` 真正“出生”的时刻。

---

## 6. 生命周期第 3 阶段：master 为 `sa` 分配元数据和数据内存

`GlobalRegistry::Register()` 负责完成全局变量从“名字”到“真实内存”的创建。

### 6.1 先分配一块元数据地址 `meta_addr`

代码：

```cpp
GAddr meta_addr = alloc_->Malloc(sizeof(GlobalVarMeta));
```

这块地址用于存一个 `GlobalVarMeta` 结构体。

它不是用户数据本身，而是变量的“说明书”。

### 6.2 再决定数据真正放在哪个节点

代码：

```cpp
GAddr home_base = ChooseDataHomeBase();
```

`ChooseDataHomeBase()` 会轮询节点，把数据 home 分散到不同节点。

所以即使是 master 创建变量，`sa` 的真实数据也**不一定**放在 master 本机。

例如：

- 第一个变量可能落到 node 1
- 第二个变量可能落到 node 2
- 第三个变量可能落到 node 3

这取决于 `next_home_node_` 当前轮到谁。

### 6.3 为 `sa` 分配真正的数据块 `data_addr`

代码：

```cpp
GAddr data_addr = alloc_->AlignedMalloc(BLOCK_SIZE, home_base);
```

这里非常关键：虽然 `sa` 只是一个 4 字节的 `int`，但系统不是分配 4 字节，而是分配**整整一个 block**。

原因是当前 GAM 的锁和缓存一致性都是按 block 粒度工作的。

所以设计上做了这个选择：

- 一个全局变量占一个完整 block
- 避免两个变量落在同一个 block 里产生伪共享
- 让 `RLock/WLock` 与变量边界对齐

### 6.4 为什么说这是“分配内存”

到这一步，`sa` 已经拥有两块真正的全局内存资源：

1. `meta_addr`
   用来存变量元信息。
2. `data_addr`
   用来存变量真实值。

这是全局变量生命周期中第一次真的“占用了远端内存”。

---

## 7. 生命周期第 4 阶段：master 初始化 `sa` 的底层存储和元数据

变量分配完内存以后，master 还要把内容填好。

### 7.1 先把 `data_addr` 整块清零

代码：

```cpp
char zero_buf[BLOCK_SIZE] = {0};
alloc_->Write(data_addr, zero_buf, BLOCK_SIZE);
```

这一步的意义是：给这个全局变量一个干净的初始物理状态。

对于 `sa` 这种 `int` 来说，清零以后，逻辑初始值就是 `0`。

### 7.2 再构造 `GlobalVarMeta`

代码：

```cpp
GlobalVarMeta meta;
meta.Init(hash, type_size, count, total_bytes, data_addr);
```

这里写进去的内容包括：

- `magic`
- `name_hash = HashName("sa")`
- `type_size = 4`
- `count = 1`
- `total_bytes = 4`
- `data_addr = 刚分配的数据块地址`
- `initialized = 1`

这份元数据的作用是：

- 告诉所有节点 `sa` 真正的数据地址在哪
- 告诉所有节点 `sa` 应该按什么类型、什么大小访问

### 7.3 把元数据写到 `meta_addr`

代码：

```cpp
alloc_->Write(meta_addr, &meta, sizeof(GlobalVarMeta));
alloc_->MFence();
```

这里有个顺序要求：

1. 先写元数据内容
2. 再 `MFence()`，保证写已经发布

因为后面 worker 会先通过 registry key 找到 `meta_addr`，然后马上去读 `meta_addr`。

如果这里不先把元数据写稳，worker 可能会拿到一个还没初始化完的元数据块。

### 7.4 再把名字发布到 registry

最后：

```cpp
uint64_t key = MakeRegistryKey(run_id, hash);
alloc_->Put(key, &meta_addr, sizeof(GAddr));
```

也就是说，registry 里存的不是变量值，也不是 `data_addr`，而是：

- `run_id + name_hash` -> `meta_addr`

worker 之后就是靠这条映射找到 `sa` 的。

### 7.5 master 本地缓存

master 还会做：

```cpp
CacheEntry(hash, meta_addr);
```

这样当前进程里以后再次访问 `sa` 时，就不用再重新注册了。

---

## 8. 生命周期第 5 阶段：master 完成 `sa` 自己的绑定

`Register()` 返回后，`EnsureBoundOrDie()` 还没有结束。

master 会继续做：

```cpp
reg->ReadMeta(meta_addr_, &meta)
```

也就是说，虽然元数据是它自己刚写进去的，它还是会再读一遍。

读回来以后再校验：

- `meta.name_hash == HashName("sa")`
- `meta.type_size == 4`
- `meta.count == 1`
- `meta.total_bytes == 4`
- `meta.data_addr != 0`

全部通过以后，把下面这些成员写入 `sa` 这个本地代理对象：

- `meta_addr_`
- `data_addr_`
- `type_size_ = 4`
- `count_ = 1`
- `total_bytes_ = 4`
- `bound_ = true`

到这里，master 手里的 `sa` 才真正从“仅有名字的代理对象”变成“已绑定到真实全局内存地址的数据对象”。

---

## 9. 生命周期第 6 阶段：master 执行真正的写入 `sa = 7`

绑定完成以后，`Global<int>::Write(7)` 会继续进入：

```cpp
WriteBytes(&value, sizeof(int))
```

### 9.1 写入路径

`WriteBytes()` 对 `sa` 执行的是：

1. `alloc->WLock(data_addr_, 4)`
2. `alloc->Write(data_addr_, &value, 4)`
3. `alloc->MFence()`
4. `alloc->UnLock(data_addr_, 4)`

### 9.2 为什么要先加写锁

当前系统的最小一致性/锁粒度是 block。

因为 `sa` 独占一个 block，所以这把写锁本质上就是：

- 锁住 `sa` 所在 block
- 阻止并发读/写冲突

### 9.3 为什么 `Write()` 之后还要 `MFence()`

要看 `GAlloc::Write()` 的实现。

在非本地 mock 模式下，底层会构造一个 `WorkRequest`，并且：

```cpp
wr.op = WRITE;
wr.flag = flag | ASYNC;
```

也就是说，底层写是**异步写请求**。

所以 `Write()` 返回，不等于远端一定已经全局可见。

为了把这个异步写真正冲刷出去，变量层强制做：

```cpp
alloc->MFence();
```

这一步是变量写语义成立的关键。

### 9.4 `sb = 4` 的生命周期完全相同

只不过名字变成 `"sb"`，哈希不同，元数据不同，数据块地址也不同。

`sb` 会重复经历：

- 懒绑定
- 注册
- 分配元数据
- 分配数据块
- 写元数据
- 发布 registry key
- 绑定完成
- 写入值 4

---

## 10. 生命周期第 7 阶段：worker 什么时候知道 `sa` 存在了

注意，worker 在声明 `GLOBAL_INT(sa)` 时并不知道：

- `sa` 有没有被 master 创建
- `sa` 的 `meta_addr` 是多少
- `sa` 的 `data_addr` 是多少

worker 真正知道 `sa` 存在，是在它第一次访问 `sa` 时。

测试里第一次访问发生在：

```cpp
int a = sa;
```

但这一步之前还有：

```cpp
rt->Fence();
```

这意味着在测试设计上，worker 只有在 master 已经完成第一轮写入后，才开始读。

---

## 11. 生命周期第 8 阶段：`Fence()` 保证大家进入“可读阶段”

master 写完 `sa = 7; sb = 4;` 之后，所有节点执行：

```cpp
rt->Fence();
```

### 11.1 master 在这轮 `Fence()` 里做了什么

master 进入 `SyncFenceRound()` 后：

1. 先执行 `alloc_->MFence()`
   目的是确保本节点在 fence 之前发出的写都已经发布。
2. 构造自己的 fence key：
   ```cpp
   MakeSyncFenceKey(run_id_, fence_seq, node_id_)
   ```
3. `Put()` 自己已到达该轮 fence 的标记。
4. 轮询等待所有节点都写入同一轮 fence 标记。
5. 再做一次 `alloc_->MFence()` 后返回。

### 11.2 worker 在这轮 `Fence()` 里做了什么

worker 做完全一样的事情，只是 `node_id_` 不同。

### 11.3 这一步到底保证了什么

它保证的是：

- master 在 fence 之前写入的 `sa = 7`、`sb = 4` 已经完成发布
- 所有节点都已经到达“现在可以开始读”的阶段边界

它**不等于**每次读都自动同步，而是显式定义了阶段。

---

## 12. 生命周期第 9 阶段：worker 第一次读取 `int a = sa`

现在进入 worker 第一次真正访问 `sa` 的时刻。

### 12.1 语法层调用链

`int a = sa;` 会走：

1. `Global<int>::operator T() const`
2. `Read()`
3. `EnsureBoundOrDie(4, 1, 4)`
4. `ReadBytes(&value, 4)`

因为 worker 手里的 `sa` 还没有绑定，所以这里也会先进入绑定流程。

### 12.2 worker 不注册，只查找

worker 在 `EnsureBoundOrDie()` 里走的是：

```cpp
reg->LookupOrWait("sa", 5000, 1000, &meta_addr_, &meta)
```

这一步和 master 最大的差异是：

- master 负责创建变量
- worker 只负责查找已经由 master 创建好的变量

### 12.3 worker 怎么查找到 `sa`

`LookupOrWait()` 先做：

```cpp
uint64_t hash = HashName("sa");
uint64_t key = MakeRegistryKey(run_id, hash);
alloc_->Get(key, &meta_addr);
```

也就是说，worker 先用：

- 当前运行的 `run_id`
- 变量名 `"sa"` 的 hash

组成 registry key，再去全局键值表里查。

如果 master 已经发布了这个 key，worker 就能拿到 `meta_addr`。

### 12.4 worker 再去读元数据

拿到 `meta_addr` 后，worker 并不会直接开始读变量值，而是先循环读元数据：

```cpp
ReadMeta(meta_addr, meta_ptr)
```

直到校验通过：

- `magic` 正确
- `initialized == 1`
- `data_addr != 0`

### 12.5 worker 完成绑定

然后 worker 再进行和 master 一样的元数据一致性校验：

- `type_size == 4`
- `count == 1`
- `total_bytes == 4`
- `name_hash` 匹配

如果都通过，就把 `data_addr_`、`meta_addr_` 等写入本地对象，并置：

- `bound_ = true`

到这里，worker 手里的 `sa` 也正式从“名字代理”变成“绑定到真实全局地址的对象”。

注意：worker 没有分配任何新内存，它只是绑定到了 master 已经创建好的那一份 `sa`。

---

## 13. 生命周期第 10 阶段：worker 执行真正读取

绑定完成以后，worker 的 `Read()` 才继续进入：

```cpp
ReadBytes(&value, sizeof(int))
```

### 13.1 读取路径

`ReadBytes()` 做的是：

1. `alloc->RLock(data_addr_, 4)`
2. `alloc->Read(data_addr_, &value, 4)`
3. `alloc->UnLock(data_addr_, 4)`

### 13.2 这一步读到的是什么

读到的是 master 在前面第一轮写入阶段写进去的值 `7`。

所以 worker 本地变量：

```cpp
int a = sa;
```

最终拿到的是一个普通的本地 `int a = 7`。

从这一步开始，`a` 与全局变量 `sa` 就没关系了。后面对 `a` 的操作都只是本地栈变量操作。

### 13.3 `int b = sb` 也是同样的生命周期

只不过绑定和读取的是 `sb` 的那一份元数据和数据块。

---

## 14. 生命周期第 11 阶段：表达式计算 `sa + 5` 和 `sa + sb` 怎么实现

这部分最容易被写得太抽象，这里直接按代码行为说。

### 14.1 `sa + 5`

测试里有：

```cpp
ASSERT_EQ_INT(node_id, (int)(sa + 5), 12);
```

运算符重载定义是：

```cpp
template <typename T>
T operator+(const Global<T>& a, const T& b) {
    return static_cast<T>(a) + b;
}
```

所以 `sa + 5` 的真实过程是：

1. `static_cast<int>(sa)`
2. 这会触发 `sa.Read()`
3. 再走一次 `RLock -> Read -> UnLock`
4. 得到一个普通本地整数 `7`
5. 最后在本地 CPU 上执行 `7 + 5`

结论：

- 计算发生在本地
- 全局变量只负责把值读出来

### 14.2 `sa + sb`

测试里还有：

```cpp
ASSERT_EQ_INT(node_id, (int)(sa + sb), 11);
```

对应重载是：

```cpp
template <typename T>
T operator+(const Global<T>& a, const Global<T>& b) {
    return static_cast<T>(a) + static_cast<T>(b);
}
```

所以 `sa + sb` 的真实过程是：

1. 读取 `sa`
2. 读取 `sb`
3. 在本地做加法

这说明当前系统没有远端表达式执行引擎，也没有“把加法下推到数据所在节点”。

它的模型非常明确：

- 读是分布式的
- 算是本地的

---

## 15. 生命周期第 12 阶段：master 第二轮更新时做了什么

测试第二轮：

```cpp
if (node_id == 1) {
    a = sa;
    sa = a;
    sa = sb;
    sa = sb + a;
    sb = sa;
}
```

这几句正好覆盖了“读取、写入、计算”最核心的几种形式。

### 15.1 `a = sa`

这一步是读取：

- `sa` 已经在第一轮绑定过了，所以这次不会再注册、不会再查找
- 直接执行 `RLock -> Read -> UnLock`
- 得到本地变量 `a = 7`

### 15.2 `sa = a`

这一步是把本地变量写回全局变量：

- `a` 已经是本地整数
- `sa` 已经绑定完成
- 直接执行 `WLock -> Write -> MFence -> UnLock`

### 15.3 `sa = sb`

这一步的真实过程是：

1. 先读 `sb`
2. 得到本地整数 `4`
3. 再把 `4` 写入 `sa`

所以这里不是“让 `sa` 指向 `sb`”，而是“把 `sb` 当前值拷贝给 `sa`”。

### 15.4 `sa = sb + a`

真实执行顺序是：

1. 读取全局变量 `sb`，得到 `4`
2. 读取本地变量 `a`，值是 `7`
3. 在本地算出 `11`
4. 把 `11` 写回全局变量 `sa`

### 15.5 `sb = sa`

由于上一句已经把 `sa` 写成 `11`，这里又会：

1. 读取 `sa`，得到 `11`
2. 写入 `sb = 11`

所以第二轮结束后：

- `sa = 11`
- `sb = 11`

这正是后面断言检查到的结果。

## 16. 生命周期第 13 阶段：第二轮 `Fence()` 之后所有节点再次读取

master 第二轮写完以后，所有节点再次执行：

```cpp
rt->Fence();
```

然后每个节点继续：

```cpp
a = sa;
b = sb;
ASSERT_EQ_INT(node_id, a, 11);
ASSERT_EQ_INT(node_id, b, 11);
ASSERT_EQ_INT(node_id, (int)(sa + sb), 22);
```

### 16.1 master 这一轮做什么

master：

- 先把第二轮写请求通过 `MFence()` 发布
- 进入 fence 汇合
- fence 返回后再进行本地读取

### 16.2 worker 这一轮做什么

worker：

- 进入同一轮 fence
- fence 返回后直接读取

注意，worker 在这一轮读取时，不会重新走绑定流程，因为 `bound_` 已经是 `true`。

所以这一轮读取是纯粹的：

- `RLock`
- `Read`
- `UnLock`

这也体现出生命周期里的一个重要特点：

- 注册和绑定只发生在第一次访问
- 后续访问都走快路径

## 17. 把 `sa` 的整个生命周期浓缩成一条时间线

下面把 `sa` 在这段测试中的一生串成一条时间线。

### 17.1 程序启动前期

master：

- 初始化 allocator
- 生成 `run_id`
- 初始化 registry

worker：

- 初始化 allocator
- 获取 `run_id`
- 初始化 registry

### 17.2 声明阶段

所有节点都执行：

```cpp
Global<int> sa("sa");
```

这时只有名字，没有远端内存，没有绑定。

### 17.3 第一次写入阶段

只有 master 执行：

```cpp
sa = 7;
```

master 会：

1. 发现 `sa` 尚未绑定
2. 计算 `HashName("sa")`
3. 调用 `Register("sa", 4, 1, 4)`
4. 分配 `meta_addr`
5. 分配 `data_addr`
6. 清零 `data_addr`
7. 写入 `GlobalVarMeta`
8. 发布 registry key
9. 回到 `sa` 对象，完成本地绑定
10. 对 `data_addr` 执行真正的写入 `7`

worker 这时还什么都没做，因为它还没访问 `sa`。

### 17.4 第一次同步阶段

所有节点执行 `Fence()`。

作用：

- 保证第一轮写已发布
- 保证所有节点在同一阶段点后再开始读

### 17.5 第一次读取阶段

worker 第一次执行：

```cpp
int a = sa;
```

worker 会：

1. 发现 `sa` 尚未绑定
2. 通过 `run_id + HashName("sa")` 查 registry
3. 拿到 `meta_addr`
4. 读元数据，得到 `data_addr`
5. 校验元数据和本地类型预期一致
6. 完成本地绑定
7. 对 `data_addr` 做 `RLock -> Read -> UnLock`
8. 拿到本地整数 `a = 7`

master 读取时就更简单，因为它已经绑定过了，直接走读路径。

### 17.6 第一次计算阶段

所有节点执行：

- `sa + 5`
- `sa + sb`

流程统一都是：

1. 先读取全局变量值到本地
2. 再由本地 CPU 执行加法

### 17.7 第二次写入阶段

只有 master 执行：

- `a = sa`
- `sa = a`
- `sa = sb`
- `sa = sb + a`
- `sb = sa`

这些操作都不再涉及注册或分配，只在已绑定地址上做：

- 读取
- 本地计算
- 写回

### 17.8 第二次同步与读取阶段

所有节点再次 `Fence()`，然后再次读取验证：

- `sa == 11`
- `sb == 11`
- `sa + sb == 22`

到这里，`sa` 在这段测试里的生命周期就完整闭环了。

## 18. 从生命周期角度总结几个最关键的实现结论

### 18.1 声明不是创建

`GLOBAL_INT(sa)` 只是创建了一个带名字的本地代理对象，不会立刻注册变量，也不会分配全局内存。

### 18.2 第一次访问才会触发绑定

真正触发“创建/查找/绑定”的入口是第一次：

- 写
- 读
- 表达式求值中的隐式读取

### 18.3 只有 master 负责创建变量

master 第一次访问变量时，如果 registry 里没有该变量，就会：

- 分配元数据
- 分配数据块
- 初始化元数据
- 发布 registry key

worker 永远不负责创建变量，只负责查找和绑定。

### 18.4 内存分配是“两块”

一个全局变量实际对应两块内存：

1. `meta_addr`
   存变量说明书。
2. `data_addr`
   存变量真实值。

### 18.5 绑定是“名字 -> 元数据 -> 数据地址”

worker 不是直接按名字找到数据地址，而是先通过名字查到 `meta_addr`，再从元数据里拿到 `data_addr`。

### 18.6 读取和写入都是显式协议动作

读取不是普通内存 load，而是：

- `RLock`
- `Read`
- `UnLock`

写入不是普通内存 store，而是：

- `WLock`
- `Write`
- `MFence`
- `UnLock`

### 18.7 计算发生在本地，不发生在远端

`sa + sb`、`sa + 5`、`sa = sb + a` 的核心模式都是：

- 先把全局变量读成本地值
- 在本地 CPU 计算
- 必要时把结果再写回全局变量

### 18.8 `Fence()` 负责阶段边界，不负责变量创建

变量的创建、绑定、读写是 `Global<T>` 自己完成的；
`Fence()` 只负责定义“什么时候可以从写阶段进入读阶段”。

## 19. 最后一句话概括 `test_scalar_types()` 里的全局变量生命周期

在这段测试里，一个简单全局变量 `sa` 的生命周期可以概括为：

**先在每个节点本地声明成一个未绑定代理对象；第一次由 master 写入时完成注册、分配元数据与数据块、发布名字到 registry 并写入真实值；worker 第一次读取时再通过 registry 找到同一份元数据和数据地址完成绑定；之后所有读写和表达式计算都围绕这同一份全局地址进行，其中读写由锁和 `MFence` 保证协议正确，阶段切换由 `Fence()` 保证。**
