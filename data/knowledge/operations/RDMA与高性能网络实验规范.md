# RDMA 与高性能网络实验规范

## 文档目的

本规范用于统一实验室中与 RDMA、高性能网络、低延迟 RPC、远程内存访问相关实验的记录与执行方式，降低实验不可复现、配置不一致和结果缺失的问题。

## 一、实验前检查清单

在开始 RDMA 相关实验前，必须确认以下内容：

1. 网卡型号、驱动版本、固件版本已记录
2. 内核版本与 OFED / rdma-core 版本已记录
3. 节点拓扑已记录，包括 CPU socket、NUMA node、NIC 所在 PCIe 根
4. 是否开启 SR-IOV、IOMMU、HugePages 已记录
5. 测试使用的网线、交换机端口、速率与链路状态已确认
6. 所有实验节点的时钟已同步

## 二、必须记录的环境信息

每次实验至少记录以下字段：

- 实验日期
- 实验负责人
- 参与节点列表
- CPU 型号与核心数
- NUMA 拓扑
- NIC 型号与速率
- 驱动版本
- 内核参数
- 编译选项
- 代码 commit id
- 数据集或请求模式

## 三、网络与 NUMA 拓扑记录要求

RDMA 实验高度依赖拓扑位置，因此必须明确写清楚：

- 网卡挂在哪个 NUMA node
- 发送线程绑定在哪个核心 / NUMA node
- 接收线程绑定在哪个核心 / NUMA node
- 内存 buffer 分配在哪个 NUMA node

如果线程与 NIC 不在同一 NUMA node，必须单独标注，因为这会显著影响测得的延迟和带宽。

## 四、基准测试最少项

每个 RDMA 相关系统至少应包含以下测试：

1. 单连接延迟测试
2. 多连接吞吐测试
3. 不同消息大小下的延迟 / 吞吐曲线
4. 不同线程数下的扩展性测试
5. 不同 NUMA 绑定策略下的对比测试
6. 长时间运行下的尾延迟测试

## 五、结果呈现要求

实验报告中至少包含：

- 平均延迟
- P95 / P99 / P99.9 延迟
- 吞吐量
- CPU 使用率
- 每核负载分布
- 是否存在跨 NUMA 远端访问

对异常结果，必须给出初步解释，例如：

- 网卡与线程跨 NUMA
- QP 数量过多导致缓存失效
- 消息过小导致 doorbell / polling 开销占主导
- 远端内存访问引入额外尾延迟

## 六、常见错误

### 1. 只记录平均值，不记录尾延迟

对于低延迟系统，平均值通常无法反映系统真实行为，尾延迟必须保留。

### 2. 不记录 CPU 绑定与内存绑定

NUMA 和 RDMA 组合下，绑定策略经常直接决定实验结论。

### 3. 不记录 commit id

没有 commit id 的结果不能视为可复现实验。

### 4. 混用不同驱动和不同固件版本

这会导致同一实验在不同节点上出现不可解释的差异。

## 七、建议输出目录结构

推荐按如下方式组织实验输出：

```text

    rdma-latency/
      config.md
      env.txt
      commit.txt
      raw/

```

## 八、与分布式 NUMA 研究的关系

对于分布式 NUMA 方向，RDMA 实验不只是“网络实验”，而是“远端资源访问路径实验”。因此需要同时关心：

- 远端访问抽象是否稳定
- 延迟代价是否可预测
- 数据布局与线程布局是否协同
- 远端访问是否破坏应用本地性
