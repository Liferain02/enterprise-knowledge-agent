# Deep Research 答案级盲评表

> 评分前不要打开 `深度研究盲评映射.json`。候选顺序已逐题固定随机化。
> 每个维度 0～2：正确性、完整性、证据依据。不要按文风、篇幅或是否像多 Agent 评分。

- 正确性：0=关键结论错误；1=大体正确但有实质问题；2=关键结论正确。
- 完整性：0=大部分关键点缺失；1=覆盖部分；2=覆盖全部或绝大多数预设关键点。
- 证据依据：0=无依据/引用错；1=部分事实有依据；2=主要事实均有有效、就近依据且推断有标记。

## H01 · multi_evidence

问题：综合新人清单、常见问题和 RDMA 实验规范，说明新成员第一次上共享节点做实验前应建立怎样的可复现证据包

预设关键点：账号与权限准备；硬件/软件环境版本；NUMA 与 NIC 拓扑；代码与参数记录

参考资料范围：新生入组第一周任务清单；实验室常见问题FAQ；RDMA与高性能网络实验规范

### 候选甲

新成员首次上共享节点进行 RDMA 实验前，应建立包含以下核心要素的“可复现证据包”，以确保实验环境一致性与结果可追溯性：

1. **基础环境快照**
   - 记录网卡型号、驱动版本（OFED/rdma-core）、固件版本及内核版本 [文档1]。
   - 确认并记录是否开启 SR-IOV、IOMMU、HugePages 等关键开关 [文档1]。
   - 明确 CPU 型号、核心数、NUMA 拓扑结构及 NIC 所在的 PCIe 根与 NUMA 节点位置 [文档1]。

2. **线程与数据绑定策略**
   - 详细记录发送/接收线程绑定的具体核心及 NUMA 节点 [文档1]。
   - 注明内存 Buffer 分配的 NUMA 节点位置，若存在跨 NUMA 访问需特别标注 [文档1]。
   - 说明编译选项、代码 Commit ID 及测试使用的数据集或请求模式 [文档1]。

3. **网络与运行状态**
   - 记录网线类型、交换机端口、链路速率及状态 [文档1]。
   - 确认所有实验节点的时钟已同步 [文档1]。
   - 保留完整的日志目录与参数记录，特别是长时间运行的任务 [文档2]。

4. **新人必备准备**
   - 完成本地及服务器开发环境配置，并跑通最小示例 [文档4]。
   - 熟悉共享目录结构与日志归档方式，确保能正确保存结果 [文档4]。
   - 若遇平台冲突或环境异常，及时联系平台维护负责人而非自行排查 [文档5]。

该证据包旨在消除因配置不一致导致的不可复现问题，符合实验室对高性能网络实验的统一规范要求 [文档1][文档2]。

### 候选乙

**前提核验**：当前证据支持该前提成立。

1. 研究问题
新成员首次使用共享节点进行 RDMA 或高性能网络实验前，应构建包含哪些核心要素的“可复现证据包”，以确保实验环境、参数及拓扑信息的完整记录与后续复现。

2. 已有证据
- 新人入组第一周需完成服务器账号开通、环境配置并跑通最小示例，熟悉共享目录与日志归档方式 [文档5]。
- 实验前必须确认网卡型号、驱动版本、固件版本、内核版本及 OFED/rdma-core 版本已记录 [文档1]。
- 必须明确记录节点拓扑，包括 CPU socket、NUMA node、NIC 所在 PCIe 根及是否开启 SR-IOV 等配置 [文档1]。
- 每次实验至少记录实验日期、负责人、参与节点列表、CPU 型号、编译选项、代码 commit id 及数据集或请求模式 [文档1]。
- 对于高性能计算、RDMA 等方向，必须额外记录 CPU 绑定、NUMA 绑定、网卡绑定、hugepage 配置及交换机链路状态 [文档2]。
- 若线程与 NIC 不在同一 NUMA node，必须单独标注，因为这会显著影响测得的延迟和带宽 [文档1]。
- 没有 commit id 的结果不能视为可复现实验 [文档6]。
- 推荐按 `experiments/年份/实验名/config.md, env.txt, commit.txt` 的结构组织输出目录 [文档6]。
- 所有长时间运行任务必须提前登记，不允许在共享环境中随意修改系统级配置 [文档2]。
- 实验结论依赖环境强，若不记录参数、版本和平台信息，后续几乎无法复现 [文档4]。

3. 关键事实
- **硬件与驱动层**：必须记录网卡型号、驱动版本、固件版本、内核版本及 OFED/rdma-core 版本 [文档1]。
- **拓扑与资源层**：必须明确 CPU socket、NUMA node、NIC 所在 PCIe 根位置，以及是否开启 SR-IOV、IOMMU、HugePages [文档1]。
- **绑定策略层**：必须记录发送/接收线程绑定的核心/NUMA node，以及内存 buffer 分配的 NUMA node；若存在跨 NUMA 情况需特别标注 [文档1]。
- **软件与代码层**：必须记录代码 commit id、编译选项、使用的数据集或请求模式 [文档1][文档6]。
- **环境与配置层**：必须记录 CPU 绑定、NUMA 绑定、网卡绑定、hugepage 配置及交换机与链路配置 [文档2][文档7]。
- **流程合规层**：长任务需提前登记起止时间与用途，确保独占或共享状态明确 [文档3]。

4. 冲突/不确定项
- 未发现明确的证据冲突。
- 现有资料未提供具体的脚本自动化生成工具列表，仅建议用脚本记录参数 [文档2]。
- 未说明不同课题方向下实验记录的差异化要求，仅给出通用规范 [文档1][文档2]。
- 未包含组会汇报的具体模板细节，仅涉及实验记录规范 [文档9]。

5. 推断
- **推断**：由于 NUMA 和 RDMA 组合下绑定策略直接决定实验结论，新成员的证据包中必须显式包含“线程与 NIC 的 NUMA 绑定位置”这一字段，否则数据不可信 [文档1][文档6]。
- **推断**：代码 commit id 是区分实验版本的关键，若无此标识，即使环境一致也无法追溯具体代码逻辑，因此必须作为证据包的强制项 [文档6]。
- **推断**：考虑到共享节点的动态性，新成员在实验前必须确认当前节点未被他人占用且配置未被修改，这属于“环境一致性”的必要前置条件 [文档2][文档3]。

6. 下一步研究建议
- **建议**：新成员在首次实验前，应参照推荐结构建立独立的实验输出目录（如 `experiments/202X-MM-DD/实验名/`），并在其中预置 `config.md`（记录拓扑与绑定）、`env.txt`（记录软硬件版本）和 `commit.txt`（记录代码哈希）[文档6]。
- **建议**：在提交长任务预约时，务必同步更新实验记录中的“使用目的”与“是否独占”状态，避免与其他成员实验冲突 [文档3]。
- **建议**：实验结束后，应立即清理僵尸进程、无用 checkpoint 及临时缓存文件，保持共享环境整洁 [文档2]。
- **建议**：若实验结果出现异常，应优先检查代码版本、驱动版本及 NUMA 绑定策略是否与记录一致，而非盲目重跑 [文档4]。

## H02 · multi_evidence

问题：结合课题组会模板、投稿流程和实验记录制度，整理一次阶段性成果从内部汇报走向对外投稿还缺哪些可审计材料

预设关键点：区分内部进展与投稿证据；图表来源和实验条件；脚本参数与 commit；未解决风险/局限

参考资料范围：分布式NUMA课题组会模板；论文投稿与对外汇报流程；论文阅读与实验记录要求

### 候选甲

**前提核验**：当前证据支持该前提成立。

1. 研究问题
本次分析旨在梳理分布式系统课题从“内部组会阶段性汇报”过渡到“对外论文投稿”过程中，缺失的关键可审计材料。重点识别组会汇报中未强制要求、但投稿流程及实验规范中明确规定的证据链环节，以确保成果的可复现性、合规性及学术严谨性。

2. 已有证据
- 组会汇报要求准备当前代码版本、实验参数、图表出处及与上周的变化点，作为内部可审计基础材料 [文档1]。
- 论文投稿前必须确认论文结构完整、图表有来源说明、实验结果可复现（含脚本/参数/commit id）且所有作者已确认版本 [文档2]。
- RDMA类实验规范强制要求记录网卡驱动固件版本、内核参数、节点拓扑（CPU/NUMA/NIC位置）及线程绑定策略 [文档6]。
- 课题组会模板要求明确回答核心问题背景、相关工作瓶颈、系统设计接口/数据/控制路径及具体实验设计要素 [文档4]。
- 实验记录制度要求每次实验独立记录目标、环境、代码版本、参数配置、结果摘要、异常现象及下一步计划 [文档3]。
- 对外汇报与论文投稿版本不一致时，应明确说明当前版本状态 [文档2]。

3. 关键事实
- **作者确认记录**：组会汇报仅需关注技术内容，而投稿阶段必须提供所有作者对最终版本的确认记录，这是组会未强制要求的行政审计材料 [文档2]。
- **匿名化检查清单**：投稿前需进行严格的匿名化处理检查，确保文中无泄露作者身份的信息，此步骤在常规组会汇报中通常不涉及 [文档2]。
- **补充材料与Artifact完整性**：投稿阶段要求准备完整的补充材料（Supplementary Material）和代码库（Artifact），包括详细的复现脚本和特定环境配置，而组会仅侧重展示初步结论 [文档2]。
- **基线对比的完整性报告**：虽然组会需提及Baseline，但投稿阶段的“实验核查”要求提供充分的Baseline对比测试报告及不同负载下的扩展性测试数据，以证明实验的公平性和充分性 [文档2][文档4]。
- **详细的环境拓扑记录**：RDMA实验规范要求记录具体的NUMA绑定策略、NIC型号、驱动版本及内核参数等底层细节，这些是判断结果差异来源的关键，组会汇报往往只展示宏观结论而非全量环境日志 [文档6]。
- **选择性展示结果的排查记录**：投稿流程明确要求检查是否存在选择性展示结果的问题，这需要保留原始数据与筛选逻辑的审计痕迹，组会汇报通常直接呈现优化后的结果 [文档2]。

4. 冲突/不确定项
- 未发现明确的证据冲突。现有资料均指向“组会重进度与沟通，投稿重合规与复现”的差异。
- 关于非RDMA类实验的具体环境记录规范细节，现有文档主要聚焦于RDMA与高性能网络场景，对于通用实验的环境记录深度可能存在局限，但基本框架（如代码版本、参数）是一致的 [文档6][文档3]。
- 成员分工文档仅说明职责，未定义具体的审计材料清单，因此无法确定特定角色（如管理员或高年级骨干）在材料审核中的具体签字权限 [文档8]。

5. 推断
推断：从组会到投稿，缺失的关键可审计材料主要包括经导师审核的版本确认记录、匿名化检查清单以及完整的底层硬件拓扑与环境配置日志。组会汇报侧重于“做了什么”和“遇到什么问题”，而投稿阶段则必须证明“为什么这样做是科学的”以及“结果是否完全可复现”。特别是对于分布式系统，缺乏详细的NUMA绑定、驱动版本及内核参数记录，将导致外部评审无法验证实验结论的可靠性。此外，投稿阶段特有的“作者确认”和“匿名化”流程是组会内部讨论所不具备的行政审计环节。

6. 下一步研究建议
建议：在准备对外投稿前，立即对照投稿流程执行以下补充工作：
- 整理并归档所有实验的底层环境日志，特别是网卡驱动、固件版本、NUMA拓扑及线程绑定策略，确保满足复现要求 [文档6]。
- 生成一份详细的Baseline对比测试报告，涵盖不同负载强度下的延迟与吞吐数据，以应对“实验核查”阶段的质询 [文档4]。
- 执行匿名化检查清单，移除所有可能暴露作者身份的信息，并获取所有合作作者的书面或邮件版本确认 [文档2]。
- 整理完整的补充材料（Artifact），包括复现脚本、数据集版本及Commit ID，确保第三方能够一键复现实验结果 [文档2]。
- 若组会汇报中未包含某些关键阻塞点的详细排查记录，需补充书面说明，解释为何排除某些异常数据或选择特定实验路线 [文档3]。

6.  **局限性分析与边界说明**
    *   **内容**：明确界定工作边界、现有系统的不足及本工作的局限性分析。
    *   **依据**：内部汇报侧重解决问题，投稿需客观陈述局限性与相关工作边界 [文档1][文档3]。

## H03 · multi_evidence

问题：综合成员分工、安全值班和共享资源制度，分析共享计算节点故障时谁负责记录、升级、协调和交接

预设关键点：值班人员记录与交接；管理员协调公共资源；项目负责人处理项目阻塞；预约冲突升级路径

参考资料范围：实验室成员与分工说明；实验室安全与值班制度；设备预约与共享资源使用流程

### 候选甲

### 1. 研究问题
分析在实验室共享计算节点发生故障时，依据现有制度，故障记录、升级汇报、协调决策及值班交接的具体责任主体与流程机制。

### 2. 已有证据
- 故障发生时，使用人应立即停止进一步破坏性操作并在组内同步异常情况 [文档1]。
- 值班人员负责检查服务器运行状态和异常告警，并汇总本周公共环境问题 [文档3]。
- 若资源出现异常，需联系平台维护负责人 [文档1]。

## H07 · recommendation

问题：基于分布式 NUMA 计划、GAM 代码说明和 RDMA 实验规范，提出一个最小实验来区分数据放置与线程放置造成的远端访问代价

预设关键点：明确可证伪假设；控制线程/数据放置变量；记录拓扑与绑定；定义延迟/吞吐指标

参考资料范围：分布式NUMA研究计划；全局变量实现2；RDMA与高性能网络实验规范

### 候选甲

基于现有资料，建议设计如下最小实验以区分数据放置（Data Placement）与线程放置（Thread Placement）对远端访问代价的影响：

**1. 实验设计核心**
采用“控制变量法”，在固定节点拓扑下，分别测试以下两组场景的读写延迟：
*   **场景 A（数据远端，线程本地）**：将全局变量 `sa` 分配在 Worker B，执行线程绑定在 Worker A。此时访问为典型的“远程内存访问”。
*   **场景 B（数据本地，线程远端）**：将全局变量 `sa` 分配在 Worker A，执行线程绑定在 Worker B。此时若系统支持透明访问，需观察是否因缓存一致性或目录查找产生额外开销；若仅依赖显式接口，则需对比显式调用路径。

**2. 关键约束与记录要求**
*   **NUMA 绑定**：必须明确记录线程绑定的 CPU Core 与 NUMA Node，以及内存 Buffer 分配的 NUMA Node。若线程与 NIC 不在同一 NUMA Node，需单独标注，因其会显著影响测得的延迟 [文档 4]。
*   **环境一致性**：实验前需确认网卡型号、驱动版本及内核参数一致，确保差异仅源于逻辑放置策略而非底层硬件配置 [文档 4]。
*   **代码语义**：利用 GAM 现有的 `GAlloc` 和显式读写接口，先构建基础模型，再逐步引入全局虚拟地址层进行对比 [文档 2]。

**3. 预期分析**
通过对比两组场景的延迟曲线，可量化：
*   若场景 A 延迟显著高于场景 B，说明当前瓶颈主要在**数据跨节点传输**（物理距离/带宽）。
*   若两者差异不大但均高于本地访问，可能受限于**目录一致性协议**或**地址转换开销**。
*   若场景 B 出现异常高延迟，可能暴露了当前系统缺乏“位置无关”抽象导致的额外路由成本 [文档 3]。

**局限性说明**
现有 GAM 代码主要基于全局物理地址和显式接口，尚未完全实现变量级透明访问和逻辑进程抽象，因此该实验目前只能验证底层机制，无法直接反映未来分布式 NUMA 运行时的高级优化效果 [文档 1][文档 3]。

2. 已有证据
*   现有 GAM 系统已具备分布式共享内存底座，提供全局物理地址（GAddr）及显式读写接口，Worker 内部维护 Directory 与 Cache 状态结构 [文档1]。

*   **GAM 现状**：当前 GAM 本质上是一个基于全局物理地址的分布式共享内存运行时，而非位置无关的全局虚拟地址系统 [文档1]。其分配接口直接返回带有物理归属信息的全局物理地址 [文档1]。
