# 系统架构与请求链路详解

本文解释系统从浏览器发出请求，到鉴权、路由、检索、生成、流式返回和持久化的完整过程。本文以当前实际编译的生产图为准，不以文件中保留的旧类名或注释为准。

## 1. 架构结论

当前系统不是“多个 Agent 自由讨论”的自治系统，而是一套边界清晰的受控工作流：

```text
Vue 浏览器
  │ JWT + SSE
  ▼
FastAPI 控制器
  │ 输入检查、限流、用户上下文
  ▼
ChatService
  │ 创建 AgentState、驱动事件流
  ▼
maybe_summarize
  ▼
retrieve_mem0_memories
  ▼
planner（唯一入口路由器）
  ├─ knowledge_agent ─► retrieval_agent ─► generation_agent ─┐
  ├─ 错误前提核验 ─► Researcher ─► Analyst ─► Reviewer ─────┤
  │                                  └► 最多一次受限修订       │
  ├─ operation_agent ────────────────────────────────────────┤
  └─ general_agent ──────────────────────────────────────────┤
                                                            ▼
                                                   finalize_response
                                                            │
                                                            ▼
                                      SSE、会话数据库、后台 Mem0
```

这套设计有三个刻意的约束：

1. 知识问答必须经过 ACL 感知的 RAG，不能让工具 Agent 绕过权限检索。
2. 每轮只允许一个业务分支产出回答，统一终态只保留一个用户可见答案。
3. 一般对比、跨项目、多证据、冲突/演化和研究建议仍由查询扩展处理；仅复杂错误/绝对化前提核验进入固定三角色团队。

这正是项目“不过度设计”的核心：Agent 是职责分工，不是数量目标。

## 2. 代码入口与组装位置

| 层次 | 关键文件 | 职责 |
|---|---|---|
| 应用入口 | `src/api/main.py` | 创建 FastAPI、注册路由和中间件、管理生命周期、托管前端静态资源 |
| 对话控制器 | `src/api/controllers/chat_controller.py` | 接收 HTTP/SSE 请求、解析认证用户、绑定 ChatService |
| 对话编排 | `src/api/services/chat_service.py` | 输入预处理、驱动 LangGraph、过滤事件、保存会话、生成来源卡片 |
| 工作流图 | `src/agent/graph.py` | 定义 AgentState、节点、边和统一终态 |
| 入口路由 | `src/agent/agents/planner.py` | 规则优先地判断知识、工具或通用对话 |
| 知识分支 | `src/agent/agents/knowledge.py` | CRAG 检索、上下文组装、带引用生成 |
| 工具分支 | `src/agent/agents/operation.py` | 调用时间、计算等工具 |
| 通用分支 | `src/agent/agents/general.py` | 处理问候和不依赖实验室知识的对话 |
| 记忆 | `src/agent/memory.py` | 封装可选的 Mem0 长期记忆 |
| Checkpoint | `src/agent/checkpointer.py` | 同步测试用内存保存，异步服务用 SQLite 保存 |

阅读代码时应先看 `create_multi_agent_graph()` 的 `add_node`、`add_edge` 和 `add_conditional_edges`。`planner.py` 内仍保留 `execute_plan_node()` 等旧实现，`agents/supervisor.py` 和 `parallel_executor.py` 也仍存在，但它们没有被当前生产图注册，不能据此判断线上架构。

## 3. AgentState：节点之间的协议

`AgentState` 定义在 `src/agent/graph.py`，继承 LangGraph 的 `MessagesState`。它不是任意共享字典，而是各阶段之间的显式协议。

### 3.1 会话与身份字段

| 字段 | 含义 |
|---|---|
| `messages` | 当前保留的 HumanMessage、AIMessage 和内部消息 |
| `session_id` | LangGraph checkpoint 与业务会话关联键 |
| `user_id` | Mem0 与业务用户关联键 |
| `user_context` | 用户名、角色、项目成员关系等 ACL 上下文 |
| `summary` | 被压缩的旧对话语义摘要 |
| `mem0_memories` | 本轮检索到的跨会话偏好或历史信息 |

### 3.2 路由字段

| 字段 | 含义 |
|---|---|
| `_quick_agent` | Planner 最终选择的单一路由 |
| `is_complex` | 是否命中复杂知识问题特征 |
| `needs_expansion` | 是否让 RAG 执行查询扩展或分解 |
| `plan_reasoning` | 路由原因，主要用于诊断 |
| `plan_steps` 等 | 旧计划执行兼容字段，当前生产图不执行多步骤 fan-out |
| `use_research_team` | 是否进入固定复杂科研团队；普通复杂查询仍为 false |

### 3.3 RAG 字段

| 字段 | 写入者 | 消费者 |
|---|---|---|
| `retrieved_docs` | Retrieval Agent | Generation Agent、来源卡片、冲突检测 |
| `retrieval_context` | Retrieval Agent | Generation Agent |
| `retrieval_decision` | CRAG | Generation Agent、可观测逻辑 |
| `retrieval_avg_score` | CRAG | 诊断与评测 |
| `retrieval_rewrite_history` | CRAG | 诊断查询改写过程 |
| `conflict_warnings` | 版本冲突检测 | Generation Agent |
| `version_source` | 版本管理器 | SSE 与前端展示 |

固定团队另共享 `evidence_package`、`analysis_report`、`review_report`、`research_revision_count` 和 `research_team_metrics`。这些是结构化协议，不是 Agent 自由聊天记录。

### 3.4 输出字段

`final_answer` 是最终文本，`used_agent` 标识实际业务分支。所有分支都经过 `finalize_response_node()`，以避免重复 AIMessage、内部草稿泄露或前端收到多个最终答案。

## 4. 一次流式请求的完整生命周期

### 4.1 浏览器发起请求

前端 `frontend/src/App.vue` 使用 `fetch` 调用 `POST /api/v1/chat/stream`，请求中包含：

- `Authorization: Bearer <JWT>`；
- 当前会话 ID；
- 用户消息；
- 可选图片或视觉理解结果。

前端使用 `AbortController` 支持停止生成，并逐条消费 SSE 数据，增量更新当前助手消息。

### 4.2 中间件与认证

请求进入 `src/api/main.py` 后依次受到统一异常处理、限流、输入安全和 CORS 配置约束。控制器通过 JWT 取得用户身份，再从用户数据库刷新当前角色，而不是永久信任 token 里可能过时的角色。

控制器将身份转换为 `UserContext`。后续检索和科研工作区服务都使用这一上下文做服务端权限判断；前端隐藏按钮只改善体验，不构成安全边界。

### 4.3 ChatService 建立执行上下文

`ChatService.stream_chat()` 负责业务边界：

1. 清理和检查输入；
2. 处理可选视觉内容；
3. 对新手引导等确定性场景采用快速响应；
4. 组装初始 `AgentState`；
5. 使用 `session_id` 作为 LangGraph thread 配置；
6. 订阅 `graph.astream_events()`；
7. 将内部事件转换成稳定的前端 SSE 协议。

它不会把所有 LangChain 事件原样发给浏览器。仅用户可见的生成 token、允许展示的工具状态、检索阶段状态和最终元数据会被转发。这避免把内部提示词、评分链或中间草稿暴露给用户。

### 4.4 对话摘要节点

`maybe_summarize_node()` 每轮首先运行：

- 只统计 Human/AI 可见消息，工具消息不触发摘要；
- 消息数未超过 `summary_threshold` 时零调用透传；
- 超限时保留最近 `summary_keep_recent` 条可见消息；
- 使用 LLM 把更早对话压缩到约 300 字；
- 通过 LangGraph `RemoveMessage` 删除旧消息；
- 新摘要滚动吸收已有摘要。

这解决的是上下文窗口与长期会话成本，不是精确审计。完整业务聊天记录仍由 SessionService 存储，语义摘要只是推理上下文。

### 4.5 Mem0 节点

`retrieve_mem0_memories_node()` 仅在配置启用时工作。它提取当前问题，以 `user_id` 做一次用户级语义搜索，最多格式化有限长度的相关记忆。问候语直接跳过，以减少无意义调用。

Mem0 失败不会中止主请求，而是记录警告并降级为空记忆。回答结束后，ChatService 再以后台任务保存本轮用户/助手可见内容。因此：

- SQLite checkpoint 负责工作流短期状态；
- Session 数据库负责产品会话历史；
- `summary` 负责窗口压缩；
- Mem0 负责可选的跨会话语义偏好。

四者用途不同，不应混为一个“记忆库”。

### 4.6 Planner 唯一路由

`planner_node()` 采用“规则优先，必要时才调用模型”的方式：

- 问候、致谢、短回复 → `general_agent`；
- 时间、日期、计算等明确工具意图 → `operation_agent`；
- 与实验室制度、论文、项目、会议等相关的问题 → `knowledge_agent`；
- 无明确通用或工具信号时，默认进入知识分支，降低凭空回答内部事实的风险；
- 对比、区别、列举、多个文档、先后步骤等 → 仍进入知识分支，并设置 `needs_expansion=True`。
- 同时满足复杂多证据任务且明确要求验证错误/绝对化前提 → 设置 `use_research_team=True`，路由到 `research_agent`；其他跨项目、时间/冲突分析或研究建议继续走查询扩展单 Agent。

短问题通常完全不调用 Planner LLM。只有较长且规则无法判定的输入才进行模型辅助判断。`route_from_planner()` 返回三个生产分支之一。

### 4.7 知识分支

知识分支严格串行：

```text
retrieval_agent_node
  ├─ ACL 混合召回
  ├─ Qwen Rerank
  ├─ CRAG 相关性分级
  ├─ 必要时改写/分解后重试一次
  ├─ 版本与冲突检查
  └─ 构造带编号的可信上下文
        ▼
generation_agent_node
  ├─ NO_RESULTS 时确定性拒答
  ├─ 提示模型将检索文本视为不可信数据
  ├─ 强制用 [文档N] 引用
  ├─ 合并冲突提示
  └─ 只标记一个 user_visible_answer
```

将 Retrieval 与 Generation 拆开，主要是为了让检索质量、ACL、拒答和版本信息可单独测试，并不是为了增加 Agent 数量。

### 4.7.1 固定复杂科研团队

复杂错误前提核验分支固定执行 Researcher → Analyst → Reviewer。Researcher 最多拆 4 个检索子问题、保留 12 条证据并复用现有 ACL-aware CRAG；Analyst 只读 EvidencePackage，区分事实、比较、推断和建议；Reviewer 只输出 PASS/REVISE/NEED_MORE_EVIDENCE。非 PASS 最多经过一次 `research_revision`，随后强制进入团队终态，不存在图回边。36 条全量评测未证明团队适合全部复杂科研任务，因此生产门 `should_use_research_team()` 只覆盖复杂错误/绝对化前提核验。完整协议和评测见《复杂科研多智能体团队实现与评测》。

### 4.8 工具与通用分支

Operation Agent 和 General Agent 都通过 SkillLoader 构建受限 ReAct Agent。前者加载允许的工具，后者处理通用语言交互。节点只取子 Agent 的最终 AI 消息写回主状态，不把完整内部轨迹或嵌套 checkpoint 混入主对话。

### 4.9 统一终态

三个分支全部进入 `finalize_response_node()`。终态节点保证：

- `final_answer` 一定存在；
- 最终回答在主消息序列中只出现一次；
- `used_agent` 可供前端展示；
- 不把工具或评分中间消息当成最终答案。

测试 `tests/test_architecture_contract.py` 对这些结构约束做了静态和运行时保护。

### 4.10 SSE 收尾与持久化

图完成后，ChatService 从 checkpoint 读取最终状态，然后：

1. 保存用户与助手消息；
2. 首轮对话生成确定性标题；
3. 从 `retrieved_docs` 生成有限数量来源卡片；
4. 发送 `sources`、`version_source`、`used_agent`；
5. 发送 `done`；
6. 异步调度 Mem0 保存，避免拉长主响应。

## 5. 非流式、WebSocket 与 A2A

- 普通聊天接口适合脚本和简单调用；生产前端的主路径是 SSE。
- `/ws/chat` 是兼容性通道，目前认证能力弱于 HTTP JWT 主链，不应作为高权限生产入口。
- A2A 暴露 Agent Card、发送任务、查询任务和技能列表，适合机器调用；卡片中的描述可能滞后，真实行为仍以生产图为准。
- MCP 文件系统只暴露 `data/knowledge` 范围，不能访问任意服务器目录。

## 6. 失败与降级策略

| 故障 | 当前行为 | 设计目的 |
|---|---|---|
| Mem0 不可用 | 空记忆继续 | 长期记忆不能阻塞问答 |
| Redis 不可用 | 使用进程内评分缓存 | Redis 是优化项，不是必需依赖 |
| Rerank 不可用 | 记录错误并按检索结果降级 | 保持基本知识可用性 |
| 找不到证据 | 确定性拒答 | 防止模型凭空补内部事实 |
| 相关性低 | 改写或分解后最多重试一次 | 控制延迟与调用成本 |
| 子 Agent 异常 | 统一异常处理并结束流 | 避免半开连接 |
| 客户端取消 | AbortController 终止读取 | 用户可控 |

## 7. 为什么没有继续扩大多 Agent

旧代码曾尝试 Supervisor、Send 并行步骤和计划结果汇总。这类架构在当前规模下会带来：

- 复杂知识查询绕过统一 ACL/RAG 的风险；
- 多次 LLM 调用导致延迟和费用显著增加；
- 并行结果难以保持统一引用、版本与拒答语义；
- 中间 AIMessage 容易被 SSE 误认为最终答案；
- 评测难以把问题定位到召回、评分、生成还是汇总。

当前架构仍把“复杂”主要放在证据质量上。固定 Research Team 是唯一例外，而且只覆盖可独立评测的错误前提科研核验；它不是 Supervisor 或动态 fan-out 的回归。全量实测显示引用质量提高但总体正确性下降、延迟约翻倍以上，因此已经缩窄生产门，而不是继续增加角色。

## 8. 扩展架构的准入条件

新增 Agent 或节点前，应同时满足：

1. 现有三个分支无法清晰承载该职责；
2. 有独立输入、输出和失败语义；
3. ACL、安全和引用边界不会被绕过；
4. 能加入独立评测样本与回归测试；
5. 带来的质量收益高于新增延迟和维护成本。

否则优先新增一条路由规则、一个 RAG 元数据字段、一个受限工具或一项评测，而不是新增 Agent。
