# 检索与工具组合执行

> 2026-09-28。已实现知识生成阶段复用工具 Harness。无需新框架、服务或 TypeSafe；现有后端未重启，需正常重启后加载新代码。

## 1. 为什么之前做不到

主图将知识问题路由到 `retrieval_agent → generation_agent`，生成节点只调用一次未绑定工具的模型；独立工具任务才进入 `operation_agent`。因此“根据实验记录计算平均延迟”虽然可以检索，却没有工具完成计算。单独扩大 operation 的路由范围也不能解决，因为它没有本轮经过权限过滤的资料。

这里要区分**检索组件**与**知识任务**：检索组件负责获取证据，不必自己成为 ReAct Agent；知识任务可以先检索，再调用计算或写作工具。

## 2. 最小实现：流程与工具能力分开选择

复用已有 `RouteDecision.handler` 和 `skills`，允许二者组合：

| 请求 | handler | skills / 后续执行 |
|---|---|---|
| 实验室组会多久一次 | knowledge_agent | 无工具，沿用单次生成 |
| 计算 12/3 | operation_agent | calculator，直接处理输入 |
| 根据实验记录计算平均延迟 | knowledge_agent | statistics，检索后调用工具 |
| 检索论文里的实验结果，计算提升率 | knowledge_agent | statistics，检索后调用工具 |
| 根据项目资料生成论文摘要 | knowledge_agent | paper_writing、text_analysis、citation_check |
| 从论文中提取 DOI | knowledge_agent | citation_check |
| 根据下面内容生成论文摘要 | operation_agent | 使用用户给出的材料，无需额外检索 |
| 论文里写了 2*3=6，这个结论有证据吗 | knowledge_agent | 查证，算式本身不触发工具 |

```text
Planner：是否需要证据 + 需要哪些能力
  ├─ 纯工具任务 → 现有 operation Harness → Finalizer
  └─ 知识任务 → 现有权限检索 → generation_agent
                         ├─ 没有工具需求 → 单次模型生成
                         └─ 有工具需求 → 共享 Harness：模型 → 工具 → 模型 → 答案
```

主图节点和边保持不变。`generation_agent_node` 按路由决策调用 `knowledge_tool_agent_node`，后者和 `operation_agent_node` 共享 `_execute_tools` 与 `BoundedToolAgent`。这里是执行器复用，不是 operation 再调用 knowledge、knowledge 再调用 operation 的相互委派。

工具结果直接用于这一轮答案，不再另加一次普通生成调用。对外 `used_agent` 仍为 `knowledge_agent`，同时保留来源卡片和 Harness 报告。

## 3. 证据如何交给工具

1. 只有当前用户请求选出的 skill 才能装载，检索正文不能决定工具集合。
2. 进入工具循环前，对当前 `retrieved_docs` 再检查用户 ACL 和 `ingestion_state`；无当前身份、无可用证据、检索错误或低质量结果时不调用模型和工具。
3. 重新编号 `[文档1]…[文档N]`，把通过复核的完整 chunk 正文、显示标题、版本、页码组成 JSON 证据包。标题去掉服务器路径；证据作为资料消息提供，不提升为系统指令。
4. 使用完整的已检索 chunk，而不是普通生成提示中截断到 800 字符的摘录，避免位于片段末尾的数据丢失。完整 chunk 不等于完整文档或完整数据集。
5. 模型从证据中选择工具参数，真实工具执行；最终答案区分原文数据、计算方法、派生结果和限制，并引用原始输入来源。
6. 引用编号越界会拒绝最终答案；发生工具调用却没有任何 `[文档N]` 引用，也会标记失败。这个检查只保证基本引用格式，不能证明数字抽取或证据支持关系正确。

例如，两段授权实验记录包含同口径延迟 10 ms 和 20 ms，统计工具返回均值 15 ms；答案应标明原始输入的文档引用，而不是把 15 ms 当成论文中的原始测量。

执行预算直接沿用 operation 配置：默认最多 4 次模型调用、6 次工具调用、工具阶段总时限 90 秒、单工具 15 秒。证据过长会明确停止，不静默截断再统计。此预算只覆盖工具执行阶段，不代表检索和整个请求都受同一个 90 秒时限控制。

## 4. 多轮、引用与失败边界

Planner 在每轮开始清空上轮的检索正文、来源、检索决策、版本说明和生成指标，保留正常会话历史。这样“先查询实验记录，下一轮计算 1+1”不会给纯计算答案附上旧来源。

组合任务后的“继续”保留知识分支和允许能力，但重新检索、重新鉴权，不把旧 checkpoint 中的证据包直接交给工具。是否正确恢复省略语义仍取决于已有查询改写和历史上下文。

本轮来源仍按主图最终校验和 API 现有来源卡片链路返回。只有所有本轮原始文档都通过复核时才保留原版本说明；过滤掉部分来源后清空这段说明，避免包含被排除资料的信息。工具中间的模型输出不标记为可见流式答案，复用现有聊天结束后的最终答案发送机制。

仍然存在的限制：

- 路由依赖规则覆盖，不能保证识别所有自然语言混合意图；新增失败例后再扩规则。
- 数值抽取、单位选择、跨文档实验条件对齐仍由模型判断。白名单和 schema 保证执行结构，不保证语义正确。
- 提示要求缺失输入时请求补充，但没有普适的自动缺失字段判定器。
- 统计基于检索返回的片段，不能冒充全库统计。数据不全时应改走明确的数据查询任务，而不是把 top-k 调大就声称完整。
- 这是一次检索后使用工具，不支持工具执行中反复检索。显式 deep 模式维持既有流程，本轮未向它追加工具循环。
- 没有新增文件读取、网络、数据库写入或稿件自动发布权限。原有同步工具超时无法强制终止线程的限制仍存在。

## 6. 面试怎么讲

> 我发现互斥 Agent 路由不能处理“查资料后计算”的任务。于是把流程选择和工具能力选择分开：知识任务先经过权限检索，生成阶段按需绑定统计或写作工具，并复用同一套有界 Harness。整个改动没有增加调度 Agent，也没有把全库搜索或文件访问权限开放给工具循环。
>
> 我特别测试了权限复核、完整片段传递、工具协议、引用范围和跨轮状态清理。这里的工程保证是工具执行有边界、数据来源可追踪；模型有没有选对数值和统计口径，还需要真实任务评测来证明。
