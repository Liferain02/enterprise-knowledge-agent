# 知识库入库、检索与权限实现

本文覆盖知识从文件进入系统，到被切分、向量化、召回、重排、纠错、权限过滤、引用和版本展示的完整实现。

## 1. 总体数据流

```text
上传文件/文本
  ▼
元数据规范化与文件安全检查
  ▼
SQLite 入库任务队列
  ▼
解析器 ─► 分块器 ─► 版本处理 ─► Embedding
                                    ▼
                                Chroma
                                    │
用户问题 ─► ACL ─► 向量召回 + BM25 召回 ─► RRF 融合
                                    ▼
                              Qwen Rerank
                                    ▼
                           CRAG 相关性分级
                         ┌──────────┴─────────┐
                    足够相关             不足/无结果
                         │             改写/分解，最多一次
                         └──────────┬─────────┘
                                    ▼
                      版本冲突检查、编号上下文
                                    ▼
                        带 [文档N] 引用的回答
```

## 2. 知识来源与元数据

仓库内置知识位于 `data/knowledge`，目前覆盖实验室概览、制度与运维、组会、科研项目和论文 PDF。向量库中的“逻辑文档数”和“切片数”不同：一个源文件可产生多个 Chroma chunk。

核心元数据包括：

| 字段 | 用途 |
|---|---|
| `source` | 原始文件路径或业务来源，是更新和删除的主定位字段 |
| `title` | 前端列表、来源卡片和引用展示 |
| `doc_type` | 制度、论文、项目、会议等分类 |
| `author` | 作者筛选和溯源 |
| `project_name` / `project_id` | 项目筛选与项目级 ACL |
| `research_direction` | 研究方向筛选 |
| `visibility` | `public`、`project`、`restricted` |
| `tags` | 搜索与管理标签 |
| `version`、生效时间等 | 版本选择、过期和冲突判断 |
| `file_hash` / `chunk_index` | 去重和稳定定位 |

元数据在 `KnowledgeService._normalize_metadata()` 统一规范化，不能依赖前端自行填对。

## 3. 入库链路

### 3.1 API 层

知识接口位于 `/api/v1/knowledge`。文本可直接添加，文件通过上传接口进入。控制器负责认证与角色检查，Service 负责文件名清理、元数据规范化和任务创建。

`KnowledgeService._safe_filename()` 防止路径穿越。上传文件不会使用用户提供的任意路径写入服务器。

### 3.2 异步任务队列

`src/rag/ingestion/job_queue.py` 使用 `data/ingestion_queue.db` 保存任务。状态包括：

- `pending`：等待处理；
- `running`：已被 worker 领取；
- `completed`：入库成功；
- `failed`：达到重试上限；
- `retrying`：失败后等待再次领取。

队列按文件 SHA-256 查重，避免相同文件被反复提交。`recover_stale_jobs()` 会将长时间占用但未完成的任务恢复，防止进程异常后任务永远卡在 running。

SQLite 队列适合当前单机规模：部署简单、可恢复、无需额外基础设施。只有在多机 worker、极高上传吞吐或严格消息投递需求出现时，才有必要换成 Redis/Celery 一类系统。

### 3.3 Worker

`src/rag/ingestion/worker.py` 的处理顺序为：

1. 读取任务与文件；
2. 调用加载器解析；
3. 分块并合并元数据；
4. 处理文档版本；
5. 计算 embedding；
6. 先写入新 chunk；
7. 成功后删除同 source 的旧 chunk；
8. 标记任务完成或失败重试。

“先新后旧”降低更新期间完全没有可检索版本的窗口。chunk ID 综合文件 hash、序号与内容 hash，兼顾幂等与内容变化识别。

### 3.4 文件解析

加载器位于 `src/rag/ingestion/loaders.py`，支持 PDF、DOCX、TXT、Markdown、HTML、CSV、JSON。不同格式最终统一转换为 LangChain `Document`，正文放在 `page_content`，业务字段放在 `metadata`。

扫描版 PDF 若没有文本层，不会自动获得高质量 OCR；这是当前能力边界。此类资料应先 OCR，或未来明确增加 OCR 处理器与对应评测。

### 3.5 分块策略

`src/rag/ingestion/chunker.py` 支持递归字符、Markdown、语义和混合分块。默认目标约 500 token、重叠约 100 token，实际值由配置决定。

分块需要平衡：

- 太小：语义不完整、引用碎片化；
- 太大：向量主题混杂、重排和生成成本增加；
- 无重叠：跨边界定义可能丢失；
- 重叠过大：结果重复，评测指标虚高。

Markdown 标题会尽量与正文共同保留，使“某制度下的某一条”仍带上章节语境。

## 4. 向量存储与 Embedding

`src/rag/storage/vectorstore.py` 封装 Chroma，持久化目录默认是 `chroma_db`，集合默认是 `lab_knowledge`。它提供添加、相似度搜索、按 source 删除、列出逻辑文档和集合统计等操作。

Embedding 与对话模型是独立配置。当前设计使用 Qwen embedding 接口；切换聊天模型不应顺带改变向量维度。若必须更换 embedding 模型，应新建集合或完整重建索引，不能把不同维度或不同语义空间的向量混在同一集合。

## 5. 混合检索

### 5.1 为什么同时用向量和 BM25

向量检索擅长语义相似，例如“报销流程”与“费用报销规定”；BM25 擅长精确术语、项目名、缩写、编号和人名。实验室资料同时包含自然语言和大量专有名词，单一路径都容易漏召回。

`src/rag/retrieval/hybrid_retriever.py` 同时执行：

- Chroma 向量召回；
- 基于 `bm25s` 的关键词召回，必要时兼容 `rank_bm25`；
- 中文使用 jieba 分词；
- 使用 RRF 合并两个排名。

RRF 不强行比较两种检索器分数的数值尺度，而使用名次：

```text
RRF(document) = Σ 1 / (K + rank_i)
```

当前 `K=60`。候选数量通常是最终 top-k 的倍数，为重排留出空间。

### 5.2 固定融合权重

当前使用配置中的固定权重，默认 Vector/BM25 为 0.5/0.5。原先按 4/8 个字符切换权重的
启发式没有独立实验依据，中文字符数也不能稳定代表精确或语义意图，因此已删除。相同 26 条
消融中固定权重的 Hybrid indexed recall 为 0.841，高于旧启发式的 0.826。

### 5.3 ACL 的两道检查

检索前先用 `build_acl_filter()` 构造尽可能下推到向量库的过滤条件；取回后再调用 `check_doc_access()` 逐条检查。这是“性能过滤 + 安全复核”的组合。

双重检查很重要，因为不同存储后端对复杂过滤表达式的支持可能不同，元数据也可能存在旧格式。任何一个召回分支都不能绕过第二道检查。

## 6. Qwen Rerank

`src/rag/retrieval/reranker.py` 通过 DashScope `TextReRank` 接入 Qwen/GTE 重排模型。它接收原始问题和候选正文，输出更适合当前问题的排序与相关分。

运行模型名以环境配置为准。代码默认值与模板可能因历史更新出现差异，因此排查时应看：

1. 实际加载的 Settings；
2. 启动日志中的模型名；
3. 健康检查；
4. 一次真实搜索的 rerank 输出。

不能仅凭 `env.template` 判断实际模型。默认主链在 Hybrid 后执行重排；CRAG 只在显式实验开关启用时对重排候选评分。

重排失败时系统保留原召回顺序继续运行，并记录告警。这样会损失排序质量，但不会让整个知识库不可用。

## 7. Corrective RAG 实验路径

核心实现在 `src/rag/evaluation/retrieval_grader.py` 的 `CorrectiveRAGPipeline`。当前
`CRAG_ENABLED=false`，它不在默认 Normal/Deep 主链中；保留用于五路消融和有新证据时复测。

### 7.1 初次召回与评分

流程先获取扩大后的候选集，再进行 rerank，然后并发调用 RetrievalGrader 评估每个文档与问题的相关程度。评分按阈值归入 HIGH、MEDIUM 或 LOW，并形成整体决策。

当前默认配置的大意是：高相关阈值约 0.25、中相关阈值约 0.15、高相关占比下限约 0.2。准确值以 Settings 为准。

### 7.2 纠错策略

当证据不足时，管线不会无限自我改写：

- 普通问题可执行一次查询改写；
- `needs_expansion=True` 的复杂知识问题进行规则或模型辅助分解；
- 子查询结果再次通过 RRF 合并；
- 最多重试一次；
- 仍不充分则返回低相关或无结果决策。

限制重试次数是延迟、费用与收益之间的明确取舍。无限反思通常只会让简单系统变慢，并不保证找到不存在的资料。

### 7.3 无答案策略

纯标点、超长重复字符等无意义输入先由查询有效性检查拒绝。有效问题若最终没有足够证据，Generation Agent 走确定性拒答，不调用模型编造答案。

这仍是知识助手的重要目标，但当前三条 no-answer 样本上 CRAG 拒绝率在 0.333～0.667 波动，
不能把它宣传成已解决的稳定能力。默认生成提示仍要求资料不足时拒答，后续应由独立样本验证。

### 7.4 评分缓存

`src/rag/evaluation/grade_cache.py` 可使用 Redis 缓存“查询 + 文档”的评分；未配置 Redis、服务器无网或 Redis 异常时，自动使用进程内缓存。

因此 Redis 可以引入，但不是项目启动条件。当前单机环境使用内存降级已经足够；多实例共享缓存或评分调用量成为瓶颈时再部署 Redis，避免为了一个可选优化增加运维负担。

## 8. 查询扩展

`src/rag/retrieval/query_expander.py` 支持规则、LLM、混合和 HyDE 等策略，最大子查询数受配置限制。当前默认主链使用规则/混合分解解决：

- A 与 B 的对比；
- “有哪些”类广覆盖问题；
- 多项目、多制度汇总；
- 包含多个子问题的长查询。

扩展结果仍回到同一个 ACL 检索与融合管线，不会为每个子问题启动不受控 Agent。

## 9. 权限模型

`src/rag/retrieval/acl_filter.py` 定义 `UserContext` 和文档访问判断。概念规则如下：

| 可见性 | 典型允许者 |
|---|---|
| `public` | 所有已允许访问知识功能的用户 |
| `project` | 项目成员、项目角色或具有管理权限的角色 |
| `restricted` | 管理员、PI 或明确授权者 |

最终规则以 `check_doc_access()` 为准。管理接口同样在服务端校验 editor/admin 等角色。项目工作区则在 `ResearchService` 内再次实施项目成员和角色 ACL。

重要原则：

- JWT 证明“你是谁”，当前数据库角色决定“你现在能做什么”；
- 检索权限必须应用到向量和 BM25 两条路径；
- 来源卡片只能从已授权的最终结果生成；
- 不允许模型自行决定某文档是否可见。

## 10. 版本、时效和冲突

`src/rag/storage/version_manager.py` 使用 `data/document_versions.db` 记录版本，支持当前版本、归档替换、生效期和过期检查。

检索后会检查来自同一主题的材料是否存在版本或结论冲突，并生成：

- `conflict_warnings`：注入回答提示；
- `version_source`：通过 SSE 发给前端；
- 更友好的标题和来源，而不是只显示内部路径。

版本管理不能替代内容治理。上传者仍应填写可靠的 title、version 和有效期；缺失元数据时系统只能做有限推断。

## 11. 生成与引用约束

Generation Agent 将检索内容放入明确的“不可信资料区”：资料里的命令、角色要求或提示词不得改变系统行为，只能作为事实证据。这是针对知识库提示注入的基本隔离。

提示词要求事实结论使用 `[文档1]`、`[文档2]` 引用。编号与传入上下文一致，ChatService 再生成结构化来源卡片。冲突存在时回答应显式说明不同版本，而不是静默选择一个。

当前引用是 chunk/document 级溯源，不是逐句形式化证明。高风险科研结论仍应打开原文核验。

## 12. 更新、删除与一致性

- 更新同一 source：新内容成功写入后再清理旧 chunk；
- 删除文档：按 source 查找并删除所有相关 chunk；
- 清空知识库：属于高风险管理操作，应只在明确环境中使用；
- 文档目录列表：按 source 聚合，避免把每个 chunk 当作独立文档；
- BM25 索引：应与 Chroma 内容更新保持同步，入库后通过真实搜索验证。

## 13. 当前边界和合理改进顺序

当前边界包括：扫描 PDF 无完整 OCR、元数据质量依赖上传者、最终回答缺少逐声明忠实度评分、单机 SQLite 队列不适合大规模分布式 worker。

建议按以下顺序优化，而不是先换数据库或增加 Agent：

1. 扩充真实问题与相关文档标注；
2. 分析漏召回是分块、BM25、embedding 还是 rerank 问题；
3. 调整少量阈值并做 A/B 离线评测；
4. 增加回答级引用覆盖与事实一致性评测；
5. 只有吞吐证据明确时再引入 Redis 队列或外部检索服务。
