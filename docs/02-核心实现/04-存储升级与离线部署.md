# 存储升级、语料扩容与代理部署

更新：2026-09-23。本文记录当前改造；早期文档中的 SQLite / Chroma 冻结方案是历史基线。

## 方案与边界

部署采用 **MySQL 8.4 + Qdrant + Redis**。MySQL 保存业务记录和 Agent 状态，Qdrant 保存知识与记忆向量，Redis 保存可重建的模型计算结果。默认配置仍支持 SQLite / Chroma，便于隔离测试和回滚；服务器配置通过部署步骤显式切换。

几百份文档并没有达到 Chroma 的容量极限。原系统更直接的问题是语料覆盖不足、逐条远程 embedding、重建前清库、目录只读前 1,000 个分块，以及缓存没有接入默认检索路径。换数据库必须同时解决这些问题，不能把更换产品等同于检索质量提升。

| 选项 | 当前项目的判断 |
| --- | --- |
| Qdrant | 独立服务、payload 索引与过滤、稳定 point ID、快照及后续扩容能力；本次采用 |
| Chroma | 可继续承担本地原型；保留原库和兼容实现供回滚 |
| Milvus | 值得在更大规模或分布式需求出现后重新评估，当前引入更多运维组件收益有限 |
| pgvector | 已有 PostgreSQL 团队可优先考虑；本项目明确采用 MySQL，因此不再增加 PostgreSQL |

参考做法：Dify 将 embedding 的重复计算从 RAG 中抽离；本项目采用完整内容摘要、模型版本和用途作为 Redis key。Haystack 的 CacheChecker 体现“检查已有文档再写入”的增量思路；本项目按稳定来源、内容与元数据生成 chunk ID。Qdrant 官方建议为过滤字段建立 payload 索引，本项目为来源、文档 ID、可见性、密级、类别和项目建立索引。

## 真实语料扩容

当前准备的语料是 **338 份原文、1,545 个分块**：25 份已有实验室资料与论文，加 313 份 rdma-core 官方手册。313 份是不同上游手册文件，不是把分块数量称作文档数量，也没有生成虚构论文或实验结论。

上游固定为 `linux-rdma/rdma-core@00357df3a344b3515a9a4d345cf0b8c8efb7f116`。下载脚本保留原文、许可、源 URL、上游路径、提交号、原文与渲染文本 SHA-256；roff 文件通过 `groff -S -man -Tutf8` 转为可检索文本。别名、过短占位页和内容完全相同的文件不计入新增手册。

语料清单位于 `data/knowledge/public/rdma-core/manifest.json`，原文不提交 Git，可通过脚本复现。新增内容覆盖 RDMA verbs、连接管理、驱动 API 与诊断工具，主要是英文技术参考。它增强 RDMA API 问答覆盖，但不能替代 NUMA、远程内存论文和实验记录。后续扩容应继续按真实任务补齐 Linux 内存管理、UCX、性能实验与论文，不以数量作为唯一指标。

新导入流程先解析和校验全部文件，再按文档执行：稳定 ID 检查 → 仅计算缺失向量 → upsert → 回读确认 → 删除同来源旧 chunk → 登记 MySQL 元数据。不会自动删除清单之外的来源，失败不会先清空旧集合；它不是 MySQL 与 Qdrant 之间的分布式事务，中断后应重跑同步脚本修复。

## 缓存与检索

- Redis embedding key 包含模型/修订号、query 或 document 用途、完整文本的 SHA-256。批处理只计算未命中内容，保持原输入顺序。
- Qwen embedding 支持批量输入、批内去重及限流/临时错误重试。2026-09-23 已恢复百炼余额并切换到 `text-embedding-v2`；百炼向量单独写入 `lab_knowledge_qwen_v1`，避免与旧 BGE-M3 向量混用。
- 本地 BGE-M3 固定修订 `5617a9f61b028005a4858fdac845db406aefb181`，使用 1,024 维归一化稠密向量。运行时只读本地模型，不自动联网下载。
- 重排缓存保存候选位置和分数，不保存历史 Document 对象。命中后映射到本次候选文档及其当前元数据；key 包含完整候选内容、顺序、query、模型、阈值和 top-N。
- Redis 异常有 300 ms 网络超时和 10 秒短暂熔断；故障时重新计算，不阻止查询。AOF 用于降低重启后的冷缓存开销，缓存丢失不影响业务记录。
- 本次不缓存最终回答、会话状态或带权限的完整检索结果，避免把不同用户或不同权限版本的答案混用。
- 保留 BM25 + dense 的 RRF 融合。Qdrant 写入更新集合 revision，其他进程下次查询可重建 BM25 snapshot；未知过滤操作符直接报错。
- 普通检索和多查询检索中的同步 I/O 放入线程，避免阻塞 FastAPI 事件循环。

## MySQL 数据迁移

`src/storage/relational.py` 是统一连接入口。业务 SQL 保持绑定参数，MySQL DDL 单独定义在 `config/mysql_schema.json`，不通过替换连接字符串假装兼容所有 SQLite SQL。保留命名与位置两种行访问方式；MySQL 采用 InnoDB、utf8mb4_bin、事务和外键。

| Schema | 数据 |
| --- | --- |
| `eka_identity` | 旧认证账号、角色、权限 |
| `eka_catalog` | 业务账号、部门、文档注册表、审计 |
| `eka_sessions` | 会话、消息、反馈 |
| `eka_research` | 项目、成员、实验、任务、研究运行与知识记录 |
| `eka_versions` | 文档版本 |
| `eka_ingestion` | 入库任务 |
| `eka_checkpoints` | LangGraph checkpoint、blob、pending writes |
| `eka_mem0` | 本项目长期记忆的变更历史 |

认证与业务库原本存在同名、不同结构的 users/roles 表，使用独立 schema 避免错误合并账号。应用账号仅获这些 schema 的权限，应用不使用 root。

业务迁移先用 SQLite backup API 做一致性快照，再插入保留原 ID 的记录，逐表比较记录数和完整内容摘要，并检查外键。已验证原有 **22 张业务表、325 条记录**。目标非空且与源不一致时中止，不覆盖较新的数据。

历史 LangGraph 状态通过 saver API 转换，已验证 **772 个检查点、2,906 条 pending writes**。MySQL JSON 浮点序列化存在末位舍入，迁移校验仅对浮点使用极小容差；其余状态保持相等。

Mem0 另有隐藏的 SQLite 历史库和 Chroma 记忆集合。本次迁移本项目的 **13 条有效记忆及 13 条关联历史**，保留原 memory ID 和 user_id；共享历史库中不属于当前有效记忆的记录不擅自导入。运行态使用 Qdrant 与 MySQL 历史适配器。上游 Mem0 初始化时仍构造瞬时内存 SQLite 对象，立即关闭并替换，不再把业务历史写入 SQLite 文件。

任务领取使用 `FOR UPDATE SKIP LOCKED`，可防止两个独立 Worker 重复领取同一任务。修正了嵌套审计事务，以及 `lead` 保留字和 session ID 修改时的外键级联问题。

## 代理与容器部署

`set_proxy` 配置当前 shell 的代理，不会自动传递给独立运行的 Docker daemon。之前 `docker pull` 在 registry DNS 阶段失败，但同服务器通过 `127.0.0.1:7897` 能访问镜像 manifest 和 blob。

本次采用用户态经代理下载官方镜像，核验 manifest/config/layer SHA-256、解压后 diff_id，制作 Docker archive，再 `docker load`。因此不用修改系统 daemon 配置，也不用 sudo。脚本固定 linux/amd64 manifest digest；Compose `pull_policy: never` 使用校验后的本地标签。

三个服务只映射本机端口：MySQL 3306、Qdrant 6333、Redis 6379。凭据自动生成并写入 Git 忽略的 `.run/infrastructure.env`（0600）。Qdrant 和 MySQL 使用 Docker 本地命名卷，不把运行中的数据库直接放在 `/share` 的 GPFS 上。容器卷属于当前 Docker 主机，换服务器需恢复备份；镜像 tar 与 SQLite 原始备份保留在共享工作区。

```bash
# 下列 python 均指 agent-demo 环境
python scripts/download_container_images.py
python scripts/start_infrastructure.py

# 停止应用写入后迁移；原 SQLite 文件保留
python scripts/migrate_sqlite_to_mysql.py --apply
python scripts/migrate_checkpoints_to_mysql.py

python scripts/fetch_public_corpus.py
python scripts/download_embedding_model.py
HF_HUB_OFFLINE=1 python scripts/migrate_mem0_to_services.py

EMBEDDING_PROVIDER=local EMBEDDING_MODEL=BAAI/bge-m3 \
  python scripts/sync_knowledge_corpus.py --infrastructure --apply \
    --collection lab_knowledge_qwen_v1

# 检查服务与入库结果、备份原配置后切换本机 config/.env；默认沿用当前配置
python scripts/activate_storage.py
python scripts/benchmark_storage.py
```

日常导入仍可运行 `scripts/reingest_lab_knowledge.py --include-pdf`，但其行为已改为安全增量同步。不要再依赖旧版“先 reset 再重建”语义。

模型约需 2.2 GB embedding 权重，另有本地 reranker 权重；首次下载需要代理，后续推理无需外网。模型计算默认 CPU、8 个线程。对话模型、外部 MCP 等其他外部能力仍取决于其各自网络与账户状态，不能据此称整个 Agent 已完全离线。

## 验证与运维

运行 `RUN_MYSQL_TESTS=1 python -m pytest -q` 前，先用 `python scripts/start_infrastructure.py --database-prefix eka_verify` 创建隔离测试 schema。普通测试不依赖生产 MySQL。新增覆盖包含 SQL 特殊字符、中文、回滚、外键、并发领取、Qdrant ACL/filter/pagination/delete、embedding 批量顺序、Redis 故障熔断、重排缓存元数据及导入失败不删旧数据。

```bash
docker compose --env-file .run/infrastructure.env -f compose.infrastructure.yaml ps
docker compose --env-file .run/infrastructure.env -f compose.infrastructure.yaml logs --tail 50
```

数据库备份与业务文件应同时保存：MySQL dump、Qdrant collection snapshot、原始文档及来源清单、运行配置和固定模型版本。Redis 可以重建。不要执行 `docker compose down -v`，它会删除命名卷。

回滚可以恢复原 `.env` 并选择 `DATABASE_PROVIDER=sqlite`、`VECTOR_STORE_PROVIDER=chroma`；一旦新系统接受了新增写入，不能直接切回旧库而忽略增量数据，必须先停写并做反向迁移。模型更换必须重建新集合，不能将不同模型的同维向量混在原集合中。

当前仍是单机部署，不提供跨主机高可用。新增语料的问答质量需要独立任务集评估；真实入库数量、自动化测试通过、缓存命中和语义检索示例都不能替代 Recall@k、引用准确性与权限隔离回归。
