## 1. Redis 在系统里负责什么

| 功能 | 是否接入主链 | 缓存内容 / key 身份 | 当前有效期 |
|---|---|---|---|
| 百炼 embedding 缓存 | 是，当前开启 | 向量；provider、model、用途 query/document、完整文本的 SHA-256 身份 | 604800 秒，7 天 |
| embedding 批次缓存 | 当前工作区已接入 | 整批向量；模型、用途、按顺序排列的批次输入 | 同为 7 天 |
| 重排缓存 | 是，当前开启 | 文档位置和分数；模型/本地 revision、阈值、top_n、query、候选全文及顺序 | 600 秒，10 分钟 |
| CRAG 评分缓存 | 有实现；当前 CRAG 关闭 | 相关度分数和理由 | 300 秒，5 分钟 |
| API 限流 | 已注册中间件，配置开启 | 用户/IP + 端点类别的请求计数 | 默认 60 秒窗口 |
| LLM 最终答案缓存 | 有遗留模块，主业务链未调用 | 不应当作已启用能力介绍 | 不适用 |

当前配置为 `embedding_provider=qwen`、`text-embedding-v2`；重排为本地 `BAAI/bge-reranker-v2-m3`。因此 embedding 命中减少百炼 embedding 调用，重排命中减少本地推理；它们不会自动省掉最终回答的 LLM 调用。

MySQL 仍保存业务数据、聊天记录、入库队列和异步 LangGraph checkpoint；Qdrant 保存向量和文档 payload。Redis 没有取代它们，也不是本项目的持久任务队列或 Agent 长期记忆库。同步测试图仍可使用 MemorySaver。

## 2. 一次检索如何使用 Redis

```text
问题 → embedding key
      ├─ Redis 命中 → 使用向量
      └─ 未命中 → 百炼 embedding → 写回缓存
            ↓
      Qdrant + BM25 + 权限过滤 → 当前候选
            ↓
      rerank key（问题 + 候选内容/顺序 + 模型配置）
      ├─ 命中 → 缓存位置/分数映射到本轮候选
      └─ 未命中 → 本地 reranker → 缓存位置/分数
            ↓
      知识生成 / 有界工具执行 → 最终回答
```

重排缓存不保存旧 `Document` 或旧权限元数据；命中后使用本次候选对象。这是目前缓存设计值得在面试中说明的点：**缓存昂贵的计算结果，权限仍由当前请求重新判断。**

embedding 和 rerank 使用完整内容和模型身份构造 key，输入或模型身份变化会产生新 key。旧 key 留到 TTL 或内存淘汰，不意味着必须对整个 Redis 执行清空。远程模型同名但内部版本变化仍无法靠当前 key 自动识别，不能声称已覆盖一切模型漂移。

## 4. 故障与并发的真实边界

### 4.1 RAG 计算缓存

`src/rag/cache.py` 的 Redis 连接和读取超时各为 0.3 秒；异常后开启 10 秒进程内冷却，期间绕过 Redis。失效时走正常 embedding/rerank 计算，没有通用的本地长期缓存兜底。CRAG 评分缓存和 API 限流则有各自的内存降级，不能把三种实现混为一谈。

`get_or_set()` 的 single-flight 使用 `threading.Event`，同进程、相同批次 key 的正常并发冷请求由一个 producer 计算。其他线程等待最多 30 秒，再读 Redis；Redis 故障、producer 失败或等待超时后可能各自计算。因此“同批次只计算一次”是正常路径的去重效果，不是跨实例 exactly-once 保证。

当前该方法由 embedding 调用，rerank 仍为普通 get/compute/set。单文本 key 与批次 key 可能重复保存向量；可以在有内存/计算证据后简化，但没有必要现在增加分布式锁。

### 4.2 限流

主程序 `main.py` 注册 `src/api/middleware/__init__.py` 中的限流中间件，实际使用 `src/api/rate_limiter.py`。虽然后者注释称“滑动窗口”，实现是首次请求起算的**固定窗口计数**：`INCR`、查询 TTL，缺失有效期时再发 `EXPIRE`。

当前配置：普通登录请求 60/min，聊天 20/min，入库参数 10/min。**配置值不等于所有入口已正确应用**，本次代码核对发现：

- 中间件按 `/api/v1/knowledge/ingest` 前缀识别入库，但真实上传是 `/api/v1/knowledge/add/file`，未进入这条分支。
- 该前缀反而会匹配 `/api/v1/knowledge/ingestion/jobs`，任务轮询可能被当成入库限流。
- Redis 计数与首次设置 TTL 不在同一条原子操作里，中途进程退出存在短暂留下无 TTL key 的窗口。
- `_init_redis()` 在 `threading.Lock` 内执行 `await ping()`；同事件循环并发首次初始化存在阻塞风险，应改异步锁或启动时初始化。
- 一次初始化/运行故障后 `_initialized` 保持为真，没有与 RAG 缓存等价的自动重连冷却逻辑。

这些是**待修复项**，本次没有改动限流代码。先改这些小问题，比引入新的限流框架更有价值。

此外缓存和限流共用 DB/实例，当前 `allkeys-lru` 在内存压力下也可能淘汰计数 key。当前观察到淘汰为 0，不必立即拆分；如果未来依赖严格跨副本限流，再单独评估资源隔离。单纯换 Redis DB 编号并不隔离实例的内存淘汰。

## 5. 本次顺手修复的检索遗漏

在离线 BM25 固定分数探针中，原代码返回了 `staging`、`retired`、`active` 三类片段。原因是发布状态过滤只进入向量查询，BM25 路径仅应用调用方 `base_filter`。此前文档笼统声称“所有检索都排除未发布块”不够准确。

现在把发布状态与调用方过滤在 Hybrid 公共入口合并，两路都在候选排序和 top-k 前执行；向量返回结果也做复核。保持旧文档未带状态字段时可见，不增加新状态机或服务。

新增 [发布态回归测试](../../tests/test_retrieval_publication.py) 覆盖 BM25 普通/带分数入口、错误后端返回、调用方不能通过 base_filter 开放 staging。测试使用内存文档和固定分数，无外部服务调用。 本次全量回归 **531 passed、5 skipped**；跳过项为未显式开启的 MySQL 集成测试。已有后端未重启，修复需正常重启后生效。

## 6. 后续优先级：只做值得证明的改动

1. **限流正确性**：先修上传/轮询路径匹配、异步初始化锁、计数+TTL 原子性和故障后恢复，补并发与失败测试。这是代码已定位的缺口，不需要新组件。
2. **缓存收益度量**：沿用现有 smoke 脚本，分 embedding/rerank 统计实际模型调用次数、命中、Redis 错误、冷/热请求耗时；测量不能拿全实例累计 hits/misses 替代。当前脚本会实际调用模型，不应为本次只读核对自动运行。
3. **组合任务验收**：给“检索 → 工具”补真实样例，重点验证取数、单位、基线方向、引用支持；这比继续增加工具数量更有面试价值。
4. **条件性清理**：CRAG 以后重新启用前，将评分 key 从 `query + 前500字符` 改为完整评分输入、模型和提示版本；目前不为一个关闭功能扩大开发范围。

暂不建议直接开启最终答案缓存。当前问答依赖权限、证据版本、上下文和工具执行，简单按问题字符串复用最终答案可能造成错误来源或过期结论。保留计算缓存已经能提供明确收益。

## 7. 面试回答

> Redis 在我的系统里承担计算缓存和请求限流。Embedding 缓存按模型、用途和文本内容隔离；rerank 只缓存候选位置和分数，命中时映射回当前已鉴权候选。业务记录和 checkpoint 在 MySQL，语料向量在 Qdrant。Redis 不可用时计算仍能执行，限流退化为单进程计数。并发 embedding 目前只做进程内 single-flight；我没有把它说成分布式锁或严格一次执行。后续先用分项指标证明节省了多少计算，再决定是否需要更复杂的部署。
