# 项目定位与总体方案

## 1. 项目定位

本项目是面向计算机专业研究生实验室的内部科研知识与协作助手。它把分散在论文、项目资料、组会纪要、实验记录、环境配置和制度说明中的信息，转换为可检索、可引用、受权限控制的知识服务，并提供轻量科研项目空间和反馈闭环。

项目的重点不是“做一个万能聊天机器人”，也不是“展示尽可能多的 Agent”。核心价值按优先级排列为：

1. 资料能够稳定进入知识库，并保留可用元数据。
2. 用户问题能够检索到正确、允许访问、未过期的资料。
3. 回答必须能展示来源，并在资料不足时拒答。
4. 不准确或缺少资料能形成可处理的问题清单。
5. 项目、实验和组会待办能形成轻量、可追踪的科研记录。

登录、MCP、记忆、A2A、多模态和 Agent 编排都是支撑能力。除非它们阻断上述主路径、造成越权或数据丢失，否则不应抢占核心知识质量的投入。

## 2. 用户与典型任务

### 2.1 新生和普通成员

- 查询入组第一周应该完成什么。
- 查找服务器账号、环境配置、组会和考勤要求。
- 检索论文笔记、实验规范和常见问题。
- 查看自己有权限访问的公共或项目资料。

### 2.2 高年级成员、教师、PI 和资料维护者

- 上传制度、论文笔记、项目文档和组会纪要。
- 标注作者、项目、研究方向、可见范围和标签。
- 处理“不准确”和“缺少资料”反馈。
- 创建项目、实验记录和行动项。

### 2.3 平台维护者

- 管理模型、代理、嵌入、Reranker 和端口配置。
- 观察健康状态、日志、入库任务和评测指标。
- 备份 SQLite、Chroma 和知识原文件。
- 在模型或检索参数变化后重跑回归与评测。

## 3. 核心用户旅程

### 3.1 知识问答

```text
登录
  → 新建或选择会话
  → 输入实验室问题
  → 系统按用户身份检索
  → 页面流式展示回答
  → 展示最多 5 张来源卡和版本溯源
  → 用户提交有帮助/不准确/缺少资料反馈
```

验收标准不是“模型输出了文字”，而是：回答与资料相符、引用能核对、无权限资料不出现、无答案时不编造。

### 3.2 资料入库

```text
维护者选择文件和元数据
  → API 校验角色、文件类型、大小和内容哈希
  → 写入持久化文件并创建 SQLite 入库任务
  → Worker 解析、切块、补充元数据
  → 生成 Embedding 并写入 Chroma
  → 新数据成功后删除同来源旧 chunk
  → 页面轮询并显示任务状态
```

该顺序特意采用“先写新数据，再清理旧数据”，避免更新失败导致原知识直接消失。

### 3.3 科研工作区

```text
创建项目
  → 配置负责人、成员、方向和可见范围
  → 记录实验假设、环境、代码版本、数据集版本、指标、结论
  → 从组会纪要提取待办
  → 更新待办状态
```

科研空间是轻量结构化记录，不试图替代完整项目管理、代码托管或实验追踪平台。

### 3.4 反馈闭环

```text
回答完成
  → 有帮助 / 不准确 / 缺少资料
  → 反馈写入 SQLite
  → 普通用户只看自己的反馈统计
  → 审核角色查看全部 open 问题
  → 填写解决说明并标记 resolved
```

这条链路把“模型偶尔答错”转换为可见、可处理的知识维护任务。

## 4. 总体设计原则

### 4.1 核心链路确定性优先

知识问题不允许 LLM 自主决定是否检索。Planner 只负责选择分支；默认 `normal` 的知识、复杂科研和前提核验仍执行 Retrieval → Generation。只有调用者显式设置 `research_mode=deep` 时，才进入固定 Researcher → Analyst → Reviewer → 最多一次修订，并复用同一 ACL、Rerank、CRAG 与 Generation Agent。

### 4.2 单一路由优于路由叠加

旧架构先 Planner、再 Supervisor、再多 Agent fan-out，增加模型调用、状态分叉和失败点。当前以 Planner 为唯一入口；normal 交给 Query Expansion，显式 deep 才进入固定三角色串行分支。没有 Supervisor、动态 fan-out 或 Reviewer 回环。

### 4.3 检索前权限控制，返回前再次验证

ACL 不是生成后删词。向量检索阶段使用 Chroma filter，BM25/融合结果再用 `check_doc_access` 做二次验证。这样即使某个检索分支未完整支持过滤，也不会将无权限文档送入生成上下文。

### 4.4 模型职责分离

对话模型、Embedding 和 Reranker 分开配置。原因是某些 OpenAI-compatible 对话服务并不提供 Embedding；将三者绑在同一 provider 会让主聊天可用但知识检索失败。

当前推荐组合：

- 对话：Qwen `qwen3.5-flash`
- Embedding：Qwen `text-embedding-v2`
- Reranker：Qwen 百炼 `gte-rerank-v2` 或部署配置指定的 Qwen rerank 模型

### 4.5 可选依赖不能污染核心健康状态

Redis 只用于评估缓存的跨进程持久化。未配置时自动使用内存缓存，健康接口报告 `disabled/fallback=memory`，总体仍为 healthy。项目不为了一个可选缓存引入额外部署负担。

### 4.6 用户响应与后台工作分离

Mem0 记忆提取可能触发额外 LLM 和 Embedding 调用，因此写入被移出 LangGraph 响应关键路径。SSE 完成、来源和会话保存不等待长期记忆写入。

### 4.7 诚实评测

文档级命中、排序质量、无答案拒答和上下文关键词覆盖分别计算。关键词重叠不命名为 Faithfulness；检索指标不冒充最终回答正确性。当前缺少的最终答案支持度评测会被明确列为限制。

## 5. 总体方案

### 5.1 分层结构

| 层 | 主要职责 | 关键实现 |
|---|---|---|
| 表现层 | 登录、对话、资料中心、科研空间、反馈 | `frontend/src/App.vue`、`style.css` |
| 接口层 | HTTP/SSE、参数校验、认证依赖、错误转换 | `src/api/controllers/`、`schemas/` |
| 服务层 | 会话、聊天编排、知识目录、入库、科研、反馈 | `src/api/services/` |
| Agent 层 | 摘要、记忆检索、路由、知识/工具/通用分支、终态 | `src/agent/graph.py`、`agents/` |
| RAG 层 | 解析、切块、Hybrid、Rerank、CRAG、ACL、版本与冲突 | `src/rag/` |
| 模型与工具层 | LLM、Embedding、Vision、Mem0、MCP | `src/models/`、`src/agent/memory/` |
| 存储层 | 原文件、Chroma、多个 SQLite 数据库、日志 | `data/`、`chroma_db/`、`logs/` |

### 5.2 为什么采用本地 Chroma 和 SQLite

当前规模是实验室内部部署，资料和并发量有限。Chroma 和 SQLite 提供：

- 无额外服务依赖，适合无外网服务器。
- 数据文件容易备份和迁移。
- 足以支撑当前文档、会话、任务和实验记录规模。
- 便于测试中创建临时数据库。

代价是多实例写入、横向扩展和集中事务能力有限。如果未来出现多后端实例、高并发写或跨机器部署，再评估独立数据库和集中向量服务；当前不提前引入。

### 5.3 为什么保留多 Agent，但收敛生产主链

不同任务确实需要不同工具和提示：

- Knowledge：必须检索并引用资料。
- Operation：必须调用计算、时间或文件工具。
- General：处理问候和无需知识库的一般对话。

因此生产保留知识、工具和通用三类默认职责，不需要 Supervisor + Planner + N 个 Worker 的层层嵌套。固定 Deep 团队只作为第四条显式模式分支：18 条冻结盲测证明它仅在时间/冲突类有稳定净收益，全集与 normal 几乎持平且成本约高 3.6 倍，所以不自动路由、不替换默认链，也不继续扩展角色。

## 6. 关键数据对象

### 6.1 知识文档元数据

核心字段包括：

- `source`：来源文件标识。
- `title` / `document_title`：人类可读标题。
- `doc_type`：制度、项目资料、论文笔记、环境配置、组会、FAQ、实验记录、新人导览等。
- `author`：作者。
- `project_name`：所属项目。
- `research_direction`：研究方向。
- `visibility`：`public/project/restricted`。
- `tags`：标签。
- `version/effective_date/expiry_date`：版本和时效。
- `chunk_index/chunk_hash/file_hash`：片段和幂等写入标识。

### 6.2 用户上下文

JWT 解码后每次请求从数据库刷新当前角色，构造 `UserContext`：

- `username`
- `role`
- `department`
- `department_name`
- `department_path`
- 项目成员等可选字段

JWT 中的 role 只是兼容快照，不作为最终授权依据；用户删除或角色变化后，旧令牌不会继续保留旧权限。

### 6.3 Agent 状态

`AgentState` 同时保存：

- `messages`、`summary`、`mem0_memories`
- `session_id`、`user_id`、`user_context`
- 路由结果和复杂度标记
- `retrieval_context`、`retrieved_docs`、CRAG 决策、重写历史
- 冲突警告和版本溯源
- `final_answer`、`used_agent`

状态的详细读写者见架构分册。

## 7. 主要非功能要求

### 7.1 安全

- 鉴权开启时拒绝公开默认管理员口令和短 JWT 密钥启动。
- 密码使用 Argon2；旧 SHA-256 哈希首次成功登录后原位升级。
- 会话 ID 按用户名构造隔离键。
- 文档在进入生成上下文前执行 ACL 二次检查。
- 检索资料在生成 Prompt 中明确标为不可信数据，不能覆盖系统指令。
- 输入中间件处理零宽字符、XSS、SQL 注入特征和 Prompt 注入特征。

### 7.2 可用性

- `/health/live` 只判断进程存活。
- `/health/ready` 判断向量库可用。
- `/health` 展示向量库、Redis、MCP、LLM 组件状态。
- 入库任务支持重试和异常退出后的 stale job 恢复。
- 启停脚本检查端口、等待就绪并保存日志/PID。

### 7.3 可观察性

- 后端标准日志写到 `logs/agent.log` 和 `.run/后端.log`。
- RAG 日志记录 Query Expansion、Reranker、CRAG 决策和延迟。
- 前端来源卡、版本说明和 Agent badge 是用户侧可观察结果。
- 入库任务记录状态、重试次数、错误、耗时和存储片段数。

### 7.4 性能

- 规则路由避免不必要的 Planner LLM。
- Hybrid 候选先 Rerank，再做有限数量 CRAG LLM 评估。
- CRAG 评估并发受信号量控制。
- Mem0 写入后台化。
- 会话标题使用确定性截取，不增加模型调用。
- BM25 索引预构建并复用。

## 8. 明确不做或暂不做的事情

- 不把登录页面当作项目核心功能持续迭代。
- 不为当前规模强制引入 Redis、消息队列、Kubernetes 或分布式数据库。
- 不为“多 Agent 数量”增加无业务价值的路由层。
- 不把科研空间扩展成完整 Jira、GitLab 或 MLflow 替代品。
- 不在没有评测基线时盲调检索权重和阈值。
- 不宣称当前已经具备完整最终答案 Faithfulness 自动评测。

## 9. 已知边界

1. 最终回答支持度仍主要依赖引用要求、真实浏览器测试和人工反馈，尚无成熟 LLM Judge/声明级蕴含评测。
2. 启用 Mem0 后，普通问题也可能触发后台记忆判定，虽不阻塞响应但会增加 API 消耗。
3. WebSocket 端点是简化实现，认证处理不如主 HTTP/SSE 路径完整；前端生产交互使用 SSE。
4. A2A Agent Card 中仍有少量旧“多步骤并行规划”描述，真实生产主链以 LangGraph 编译结果为准。
5. 删除会话尚未统一清理 Session SQLite、LangGraph checkpoint 和 Mem0 的全部生命周期数据。
6. MCP stdio 关闭时可能出现 AnyIO cancel-scope 上游警告，运行期问答不受影响。

## 10. 成功标准

项目成功不以代码量、Agent 数量或模型调用次数衡量。更重要的指标是：

- 高频实验室问题能在前 5 个来源内命中正确资料。
- 无资料的问题稳定拒答。
- 页面引用与答案中的 `[文档N]` 能一一核对。
- 角色变化后权限立即按数据库最新状态生效。
- 上传失败不破坏旧资料。
- 反馈问题能被处理并留下解决说明。
- 新成员可以按文档在一个工作日内完成部署、调试和基础扩展。
