# 02 检索与答案指标实现

本文给出指标含义、计算方式和局限。指标名称必须和真实测量对象一致，不能把关键词重叠叫作 Faithfulness。

## 02.1 Hit@K

只要 Top K 至少包含一个 relevant document：

```text
Hit@K = 1，否则 0
```

适合单证据问答，但多证据题只命中一个也会得满分，因此必须配合 Recall。

## 02.2 Recall@K / Expected Document Coverage

```text
Recall@K = |TopK ∩ Relevant| / |Relevant|
```

当前 retrieval benchmark 中 relevant 是 expected doc IDs，title 使用 case-insensitive substring 匹配。

多证据题的 Recall 能看出“是否找齐”，但 relevant 标注本身可能不完整，且文档命中不代表目标 chunk 命中。

## 02.3 MRR

```text
RR = 1 / 第一个 relevant document 的 rank
MRR = mean(RR)
```

MRR 强调第一个正确结果是否靠前，对需要三份材料的问题不关心其余两份是否找到，所以同样要配合 Recall。

## 02.4 NDCG@K

有分级相关性时：

```text
DCG@K = Σ_i (2^rel_i - 1) / log2(i+1)
NDCG@K = DCG@K / IDCG@K
```

它同时关注相关性等级和排序位置。快速真实检索基线曾记录 NDCG@5=0.9167，但这属于特定小数据快照。

## 02.5 MAP

对每个 relevant 命中位置计算 Precision@i，再对 relevant 数取平均，最后跨 query 求均值。

MAP 适合多个相关结果，但如果 relevant set 只标文档标题而不标 chunk，会把文档内重复 chunks 的处理复杂化，因此评测先按文档去重。

## 02.6 文档级去重

检索返回 chunk，gold 是 document。评测从 metadata title/source 得到显示文档，按首次出现去重后再算 rank。

否则同一文档的三个 chunks 会占据 Top 3，虚高或压低多文档覆盖。

## 02.7 Keypoint Coverage

每题定义 expected key points，自动程序检查回答是否覆盖对应关键词/表达：

```text
coverage = matched key points / total key points
```

它衡量内容覆盖 proxy，不理解否定。例如回答“没有记录驱动版本”也包含“驱动/版本”，可能被算匹配。

## 02.8 Citation Coverage

衡量需要证据的重要内容是否附带 `[文档N]` 或 `[Sx]`。它关心引用形式覆盖，不证明引用片段支持该句。

Deep 的 Claim 自带 source IDs，Normal 的引用由最终文字解析，因此两者协议不同，比较时应保持评分口径一致。

## 02.9 Citation Support Proxy

自动比较被引用 Claim/句子和对应 excerpt 的词汇重叠或关键实体，输出 0–1。

它可能把“支持”与“不支持”判得很像，也不能理解条件范围。因此报告明确写 proxy，最终需要人工检查 entailment。

## 02.10 Relevant Document Recall

从最终 sources 或 EvidencePackage 提取标题，与每题 relevant docs 比较。这是答案链路实际带到最终阶段的召回，不等同 retrieval-only raw recall。

Deep 的 Researcher expected evidence coverage 就是这一层的核心指标。

## 02.11 Conflict Accuracy

对标记 `should_handle_conflict` 的题检查回答是否区分时间、成熟度、观察与结论等预期冲突关系。

关键词检测只表明回答出现相关区分词；是否真正正确仍需人工评分。

## 02.12 Premise Accuracy

每个 premise case 的 gold 是 false 或 supported。回答/trace 的 assessment 与 gold 一致才正确。

V2 特意同时放入支持和反驳题，避免“总是反驳绝对命题”获得高分。普通非 premise 题还检查不应被强行加 premise 前缀。

## 02.13 ACL Violation

如果结果、EvidencePackage、Claim source IDs、最终 sources 或回答中出现当前用户无权访问的污染标识，则 violation。

```text
ACL violations = count(cases with any forbidden evidence exposure)
```

目标必须为 0，不用平均分稀释安全失败。

## 02.14 成功率

成功表示请求完成并得到可解析结果，不等于回答正确。26/26 成功只证明运行稳定性，必须与质量和安全指标同时看。

## 02.15 延迟

- P50：典型用户体验。
- P95：尾延迟。
- Mean：易受少量极慢请求影响。

当前 percentile 实现按排序后索引取值，样本只有 26 条时 P95 估计较粗，不能外推高并发 SLA。

## 02.16 成本

记录每题 logical LLM calls、input/output tokens，并按 variant 求均值。usage metadata 缺失时为 0，字符估算只作为辅助，不和真实 token 混用。

Deep 的多阶段调用必须完整计入，不能只统计最终 Generation。

## 02.17 Analyst Claim Coverage

```text
referenced evidence count / total evidence count
```

它检查 Analyst 是否利用 Researcher 证据。覆盖过高也不一定好：把无关证据硬绑 Claim 会虚高，所以 Reviewer 和人工相关性仍重要。

## 02.18 Reviewer Drop Rate

被 Reviewer/最终校验删除的 Claims 占初始 Claims 比例。高 drop 说明 Analyst 不稳定或证据不足；低 drop 也可能是 Reviewer 放水，需要结合 invalid citation 和人工质量。

## 02.19 Final Validated-Claim Coverage Proxy

比较最终答案和 validated Claim 的关键词：

```text
covered validated claims / all validated claims
```

它检测生成是否漏写已经审核的 Claim。无法证明答案没有新增不受支持内容，也无法判断语义反转。

## 02.20 无答案正确拒答率

对明确知识库不存在的题，回答应拒绝而不是编造：

```text
correct refusal / no-answer cases
```

过高拒答率可能来自检索器过于保守，因此还要看有答案题 Recall。

## 02.21 指标组合

一个合理的质量视图：

```text
可用性：success + P50/P95
证据获取：Hit/Recall/MRR/NDCG
回答覆盖：keypoint + citation coverage
证据安全：ACL violations + premise
生成利用：claim coverage + final coverage proxy
成本：calls + tokens
人工质量：correctness + faithfulness + usefulness
```

任何单一平均分都不能替代这个分层视图。

## 02.22 小样本置信边界

26 条可发现系统性回退，但不足以给出精确统计置信区间或覆盖真实分布。按类别只有 6–8 条，一题就会让 accuracy 变化 0.125–0.167。

因此报告更适合做工程 gate，不应包装成学术显著性结论。
