# 02 状态、摘要、路由与图编排

本文解释生产图为什么长成现在这样，以及状态字段、消息 reducer、摘要、Planner 和 Finalizer 如何共同维持稳定协议。

## 02.1 真实生产图

```text
maybe_summarize
→ retrieve_mem0_memories
→ planner
   ├─ retrieval_agent → generation_agent ┐
   ├─ operation_agent                    ├→ finalize_response → END
   ├─ general_agent                      ┤
   └─ research_agent → analyst → reviewer
        ├─ revision once ────────────────┤
        └─ deep_generation ──────────────┘
```

源码判断标准是 `create_multi_agent_graph()` 中的 `add_node/add_edge/add_conditional_edges`。Supervisor、Parallel Executor 等文件未注册，不能算生产架构。

## 02.2 AgentState 是跨节点协议

`AgentState` 继承 `MessagesState`，消息字段由 LangGraph 的 `add_messages` reducer 管理。其余字段按职责分组：

| 分组 | 字段举例 | 写入方 | 消费方 |
|---|---|---|---|
| 终态 | final_answer、used_agent、sources | Worker | Finalizer/ChatService |
| 会话 | session_id、user_id、user_context | ChatService | 全节点 |
| 记忆 | summary、mem0_memories | 记忆节点 | Planner/Worker |
| Planner | is_complex、needs_expansion、_quick_agent | Planner | 条件边/Retrieval |
| Retrieval | context、docs、decision、rewrite history | Retrieval | Generation/Trace |
| Deep | evidence、claims、review、revision count | Research Team | 后续 Deep 节点 |
| 可观测 | team metrics、trace、generation metrics | 各阶段 | 评测/诊断 |

状态字段的价值是消除隐藏耦合。例如 Generation 不需要重新从全局变量找检索文档，只读取 `retrieval_context`。

## 02.3 MessagesState 与业务字段的区别

messages 用 reducer 追加或删除，适合对话历史；`retrieved_docs`、`review_report` 等是本轮快照，不应当用消息方式累计。

把所有中间结果都塞进 messages 会造成：

- 摘要把 tool/JSON 当成用户对话；
- Mem0 错把 Reviewer 结论保存成助手记忆；
- 上下文 token 快速膨胀；
- SSE 难以区分正文。

所以子 Agent 的内部 messages 只在本轮工具循环内使用，主图通常只接收最终 AIMessage。

## 02.4 摘要触发算法

伪代码：

```python
visible = indices(message.type in {human, ai})
if len(visible) <= threshold:
    return {}
first_kept = visible[-keep_recent]
old_messages = messages[:first_kept]
summary_input = only human/ai content, each <= 300 chars
new_summary = LLM(existing_summary + summary_input), <= 300 chars
return {"summary": new_summary,
        "messages": [RemoveMessage(id=...) for old message]}
```

注意 `first_kept` 是原 messages 数组的索引，因此即使 human/ai 之间夹杂 ToolMessage，也能把整个旧片段一起移除。

## 02.5 摘要失败与一致性

当前摘要模型调用异常会沿图抛出，由上层处理；不像 Mem0 那样完全可选降级。这是因为摘要发生在主图入口。未来若真实观察到摘要服务频繁影响可用性，可增加“失败保留原消息”的降级，但不能在无故障证据时继续复杂化。

滚动摘要是有损压缩，可能遗漏精确数字。因此检索问题仍重新查知识库，不能用摘要作为来源引用。

## 02.6 用户身份、摘要和记忆的注入顺序

共享工具 `inject_user_identity_to_messages()` 构建：

```text
System: 当前用户身份
System: Mem0 记忆（若有）
System: 历史对话摘要（若有）
原始近期 messages
```

身份放在最前面，确保 Agent 知道提问者；但真正 ACL 在检索程序中执行，不能依赖 LLM 读到身份后“自觉保密”。

## 02.7 Planner 的规则优先

Planner 先使用规则识别：

- 问候与普通闲聊；
- 计算、时间、文件操作等工具意图；
- 知识库问题；
- 对比、列举、多个实体等复杂形式。

复杂 pattern 与 Query Expansion pattern 需要同步，避免 Planner 认为 simple 而检索器又拆查询，导致监控语义不一致。

LLM structured output 使用 `TaskPlan` TypedDict，包含 is_complex、reasoning、steps、final_agent。TypedDict 与 LangGraph/structured output 的兼容更直接，也避免不必要的 Pydantic 序列化警告。

## 02.8 快速路由与 LLM Planner 的关系

简单且规则明确的问题可直接写 `_quick_agent`，减少一次模型调用。复杂问题需要 LLM 解释步骤时，plan steps 只用于规划与可观测，不会启动旧的动态 `Send` fan-out。

也就是说当前 Planner 有“理解复杂度”的能力，但生产执行拓扑仍固定。这保留了诊断信息，同时避免动态图带来的不可控成本。

## 02.9 Deep 路由的硬条件

Deep 路由不能只看 `is_complex`，还必须检查 `research_mode == "deep"`。Normal 下的复杂问题设置 `needs_expansion=True`，走 Query Expansion RAG。

这条产品约束写在图路由逻辑而不是只写在前端，因此即使其他 API 调用方没有 UI，也不能意外自动进入 Deep。

## 02.10 条件边与终止性

Planner 条件边只有四个目标。Reviewer 条件边只有 revision 或 generation。Revision count 初始为 0，最多增至 1；超过上限必进 generation。

图中不存在返回 Reviewer 的无界边，因此终止性可以从拓扑和计数器共同证明，而不是依赖 Prompt 说“不要循环”。

## 02.11 Finalizer 的契约

每个 Worker 都可能以不同方式生成 final answer。`finalize_response_node()`：

1. 去除首尾空白。
2. 空回答变成稳定兜底文本。
3. 若最后一条已经是相同 AIMessage，不重复追加。
4. 否则只追加一个最终 AIMessage。

这避免同一回答在历史里出现两次，也让 ChatService、摘要和 Mem0 始终消费统一终态。

## 02.12 Checkpointer 的 event loop 问题

同步测试使用 `MemorySaver`。FastAPI 异步路径可配置 `AsyncSqliteSaver`，但必须在实际使用它的同一个 event loop 中创建连接。

若在模块 import 或另一个 loop 中创建 aiosqlite 连接，再在 FastAPI loop 中调用，可能出现跨循环阻塞。因此异步图通过 `get_agent_graph_async()` 延迟初始化。

## 02.13 图实例缓存

图和 checkpointer 不应每次请求重新编译。异步实例在服务器事件循环中初始化后复用；测试同步图使用独立内存 saver。缓存需要与 event loop 生命周期绑定，不能简单做跨 loop 的全局单例。

## 02.14 Operation 与 General 的状态约束

Operation 使用 `create_react_agent` 动态调用 calculator/datetime/general/MCP tools，超时 180 秒。General 由 SkillLoader 创建，超时 120 秒。

它们会把身份、摘要、Mem0 注入本轮消息，但不使用自己的 checkpointer，也不把工具循环的完整消息回写主图。主图只收到 final answer 和一个 AIMessage。

## 02.15 旧字段为什么仍存在

AgentState 仍有 `next_agent`、`supervisor_reasoning` 等兼容字段，是为了旧 checkpoint 或测试导入不立即破坏。它们不代表 Supervisor 仍在线。

删除兼容字段应当独立进行：先搜索所有外部导入和历史 checkpoint，再迁移测试。不能为了让 state 看起来干净而冒险破坏已有数据。

## 02.16 可观测性应该记录什么

建议每轮关联：

```text
request/session/thread ID
research mode
planner route + expansion flag
retrieval decision + rewrite count
used agent
per-stage latency/tokens
failure attribution
```

不记录密码、API Key、完整 restricted 文档或模型内部 chain-of-thought。Planner 的短 reasoning 是业务决策说明，不等同于要求模型暴露隐式思维链。

## 02.17 常见设计错误

- 看到 `is_complex=True` 就自动进入 Deep。
- 在每个子 Agent 上再挂一个 checkpointer。
- 把 Analyst/Reviewer 的 JSON 全部追加到 messages。
- 让多个路由器顺序判断同一请求。
- 用 Prompt 控制循环次数而没有图级上限。
- 只根据仓库文件名画架构，不看实际注册边。

当前实现的核心原则是：固定控制流、显式状态、最小可观察协议和确定性终止。
