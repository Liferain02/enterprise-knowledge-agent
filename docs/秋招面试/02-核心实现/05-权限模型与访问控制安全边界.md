# 05 权限模型与访问控制安全边界

本文区分身份认证、管理动作 RBAC、知识文档 ACL 和科研项目 ACL，并解释为什么权限必须从请求进入一直保持到最终引用。

## 05.1 四层权限概念

| 层 | 问题 | 实现 |
|---|---|---|
| Authentication | 你是谁？ | JWT + 数据库用户/配置管理员 |
| API RBAC | 能否上传、删除、审阅？ | 路由角色集合/role permissions |
| Knowledge ACL | 能看到哪些 chunks？ | UserContext + metadata filter + Python check |
| Research ACL | 能看/写哪些项目？ | 项目 visibility、负责人、成员关系 |

它们不能混用。管理员能上传资料，不自动意味着某个普通用户能检索该资料。

## 05.2 UserContext

```python
UserContext(
  user_id,
  username,
  role,
  department,
  department_name,
  department_path,
  is_active,
)
```

它由当前授权数据构建，通过 ChatService 写入 AgentState，传给 Normal、Query Expansion 和 Deep 每次检索。

`anonymous()` 返回 student/public-safe 上下文。没有 user context 时 Deep 不应全库检索；安全降级是最小权限。

## 05.3 Confidentiality 等级

```text
public < internal < confidential < secret
```

角色最大等级举例：

- student/assistant/employee：internal。
- senior_student/teacher/lab_admin：confidential。
- pi/admin：secret。

`can_access()` 比较等级 rank，而不是依赖字符串大小。未知角色默认 internal，未知文档等级默认 public/internal 的行为需结合入库规范审查。

## 05.4 Visibility

业务可见性是另一维：

```text
public | project | restricted
```

student/viewer/employee 只有 public；teacher/lab_admin/senior_student/editor 等可 public+project；pi/admin 可三类。

Confidentiality 与 visibility 同时满足才允许。例如某文档 confidentiality=internal 但 visibility=restricted，student 仍不能看。

## 05.5 部门与角色限制

metadata 还可以声明：

```text
department_restrict = [project-A, project-B]
role_restrict = [pi, senior_student]
```

字段缺失、空字符串或空数组表示无限制。若文档有部门限制而用户部门为空，默认拒绝；若用户部门或角色不在列表，也拒绝。

这体现 deny-by-default：无法证明满足限制时不放行。

## 05.6 第一层：Chroma 候选过滤

`build_acl_filter()` 当前能稳定表达：

```json
{
  "$and": [
    {"confidentiality": {"$in": ["public", "internal"]}},
    {"visibility": {"$in": ["public"]}}
  ]
}
```

它在向量 similarity search 时传入，受限向量候选不会先被召回再裁剪。

## 05.7 为什么第一层不够

Chroma where 对数组 contains、空值和 ISO 日期比较有限，难以可靠表达 department、role 和有效期。BM25 又是内存索引，不走 Chroma where。

因此若只依赖存储 filter：

- BM25 可能带回受限内容；
- 历史 metadata 类型差异可能绕过条件；
- 无法完整做时效判断。

## 05.8 第二层：check_doc_access

Python 逐候选检查顺序：

1. 用户是否 active。
2. confidentiality 等级。
3. visibility 角色集合。
4. department restriction。
5. role restriction。

任一失败立即返回 false，并记录 source/doc ID 和原因。日志避免输出受限正文。

它目前没有校验 `effective_date` 和 `expiry_date`。也就是说，部门、角色、密级和可见性具备检索后复核，而文档有效期尚未形成同等级别的主链路兜底。`VersionManager` 中存在日期相关能力，不等于混合检索路径已经调用；这是需要如实保留的已知缺口。

## 05.9 为什么过滤必须在 Rerank 前

Reranker 是外部 DashScope API。如果先把所有候选传去 Rerank，再删除无权结果，受限文本已经离开安全边界。

正确顺序：

```text
Vector ACL candidate filter
→ merge BM25
→ Python ACL check
→ Rerank/Grader/LLM
```

权限不仅控制用户看到什么，也控制哪些数据能发送给外部模型。

## 05.10 Deep 的重复校验

Researcher 每个子查询都传 user context；结果返回后再次 `check_doc_access()`。EvidencePackage 只从 allowed results 构造，metadata 还经过 `_safe_metadata()` 白名单，只保留展示和分析所需字段。

后续 Analyst 不能检索，只能看 EvidencePackage；Reviewer 也只审这些 Claims 和证据。Revision 的 targeted retrieval 仍复用相同 ACL pipeline。

这形成不变量：任何进入 Claim 的 source ID 都来自当前用户可访问 EvidenceItem。

## 05.11 引用阶段校验

即使模型 structured output 生成 `S99` 或空引用，确定性校验也会拒绝：

- source ID 不在 EvidencePackage → invalid_source。
- Claim 无 source IDs → citation_gap。
- 修订后仍非法 → 从 final claims 删除并写入 limitation。

模型不能通过“编造一个引用编号”让受限或不存在证据进入答案。

## 05.12 Prompt injection 与 ACL 的关系

ACL 防止未经授权的文档进入上下文；Prompt 安全边界防止已授权文档中的恶意指令改变系统行为。这是两种不同威胁：

- Unauthorized content：靠程序权限过滤。
- Authorized but malicious content：标记为不可信数据，模型不得执行指令。

只做其中一个都不完整。

## 05.13 科研空间 ACL

结构化项目使用独立规则：

- admin/pi 看全部；
- public 项目可访问；
- created_by/lead/member 可访问所属项目；
- 写实验和待办要求特权角色或项目成员。

`list_projects()` 服务端过滤，`get_project()` 再校验；创建实验、任务和更新状态也重新检查写权限。前端隐藏按钮只是体验，不能作为授权。

## 05.14 角色变化

JWT role 不是授权来源。每次 API 请求查数据库后构造 UserContext，所以撤销角色会影响下一次检索。

已在运行中的单次 Deep 请求使用本轮开始时的 context；若要求长任务中途实时撤权，需要每个外部阶段重新取授权，目前没有这一复杂机制。当前 Deep 只有几十秒且检索有界，这一边界应如实说明。

## 05.15 ACL 测试矩阵

至少覆盖：

| 用户 | 公共 | 项目 | restricted | 部门不符 | role 不符 | inactive |
|---|---:|---:|---:|---:|---:|---:|
| student | allow | deny | deny | deny | deny | deny |
| senior | allow | allow | deny | deny | 按规则 | deny |
| pi/admin | allow | allow | allow | 按显式限制 | 按显式限制 | deny |

此外用“高关键词密度的受限污染文档”做对抗测试：即使它比公共资料更相关，也不能出现在 raw candidate、EvidencePackage、Claim 引用和最终 sources。

## 05.16 `ACL violation=0` 的正确解释

只能说：在冻结角色矩阵和污染样本中没有观察到越权。不能推出：

- 所有 metadata 组合都安全；
- Chroma/第三方 SDK 永远无漏洞；
- 日志、备份、运维接口没有其他泄漏；
- 系统达到某项正式合规认证。

自动测试是已覆盖场景的证据，不是绝对安全证明。

## 05.17 已知实现限制

- 日期过滤既未完整下推 Chroma，也未在当前 `check_doc_access()` 中完整兜底。
- 部门字段在当前实验室账号中较轻量，尚无复杂组织树继承测试。
- API 角色集合和通用 role_permissions 存在兼容角色，需长期统一。
- A2A 入口使用固定身份，未实现细粒度跨 Agent 委托，不应直接公网开放。
- 没有集中审计、OIDC、MFA 和密钥轮换。

## 05.18 安全评审清单

新增任何检索入口时必须检查：

1. 是否从可信当前用户构造 UserContext？
2. 候选生成是否先过滤？
3. BM25/缓存/重排是否可能绕过过滤？
4. 外部模型调用前是否已删除受限正文？
5. source cards 是否只来自 allowed docs？
6. trace/log 是否保存了受限 excerpt？
7. anonymous/failure 是否最小权限？
8. 是否有角色矩阵和污染回归测试？

ACL 必须是端到端不变量，而不是某一个函数的功能标签。
