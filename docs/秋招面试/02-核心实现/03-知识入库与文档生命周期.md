# 03 知识入库与文档生命周期

RAG 的上限首先由知识库决定。本文详细说明文件如何从 HTTP 上传变成 Chroma chunk、如何去重和安全替换，以及为什么“磁盘有 PDF”不等于“模型能检索到”。

## 03.1 两种入库入口

- `POST /api/v1/knowledge/add`：直接提交文本和 metadata，适合脚本或小段资料。
- `POST /api/v1/knowledge/add/file`：上传 PDF、DOCX、Markdown、TXT，进入异步队列。

文件路径是主产品入口。只有编辑角色可以上传；清空整个知识库需要更高管理员角色。

## 03.2 上传阶段校验

`KnowledgeService.enqueue_document_from_file()` 在入队前完成：

1. 文件名存在且扩展名在白名单。
2. 大小不超过 50 MB。
3. metadata 归一化。
4. 计算 SHA-256 内容哈希。
5. 查询相同哈希最近任务，避免重复 embedding。
6. 将文件安全写入知识目录。
7. 创建 pending job。

校验发生在队列前，避免 worker 消费明显不合法的数据。HTTP 层把 ValueError 映射成 400，而不是统一变成 500。

## 03.3 Metadata 为什么重要

chunk 继承的典型字段：

```text
source / title / doc_type / category
author / project_name / research_direction
visibility / confidentiality
department_restrict / role_restrict
version / effective_date / expiry_date
uploaded_by / file_hash
chunk_index / chunk_hash
```

内容回答“文档说了什么”，metadata 回答“文档是谁、属于哪里、谁能看、何时有效”。ACL、目录筛选、来源卡片和版本溯源都依赖 metadata。如果只把正文嵌入，后续很难可靠补齐权限。

Chroma metadata 要求标量，因此 list/tuple/set 会被转成逗号分隔字符串。读取 ACL 字段时必须兼容字符串和列表两种历史格式。

## 03.4 SHA-256 文件去重

文件级哈希基于原始 bytes，而不是文件名。两个文件名不同但内容完全相同，哈希一致，可以识别重复；同名文件内容变化则产生新哈希，允许更新。

任务表保存 `file_hash` 和 `original_filename`。去重查询看最近同哈希任务的状态，不能只看文件是否存在，因为同名文件可能正在失败或重试。

文件哈希解决整文件重复，不解决同一文件内部重复段落；后者由处理器的 chunk 内容 hash 去重。

## 03.5 SQLite 任务状态机

```text
pending ──dequeue──> running ──success──> completed
   ^                    |
   |                    └─failure below limit─> retrying
   |                                              |
   └──────────────────── dequeue ─────────────────┘

running/retrying ──failure at limit──> failed
stale running ──server restart recovery──> retrying
```

`IngestionJob` 保存 job ID、路径、category、metadata、retry count、错误、时间戳、hash 和 result。completed result 包括 stored chunks、耗时和 source。

## 03.6 原子 dequeue 的实际边界

队列在进程内用 `threading.Lock` 包裹“选择最早 pending/retrying + 更新 running”。这能防止同一进程多个 worker 线程重复领取。

它不是跨多进程、跨机器的严格租约队列：SELECT 和 UPDATE 没有使用数据库级 `UPDATE ... RETURNING` 竞争协议。因此当前准确定位是单进程轻量 worker。多实例部署前需要重新设计领取锁和可见性超时。

## 03.7 Worker 生命周期

Worker 启动时先调用 `recover_stale_jobs()`，把超过 900 秒的 running 任务改为 retrying。之后默认每 2 秒轮询：

```text
dequeue
→ load and chunk
→ optional version check
→ embed and store
→ complete
```

失败时重试延迟为 `min(30, 2^retry_count × 2)` 秒，最大默认 3 次。`stop()` 设置 Event，处理完当前任务后退出，实现有限的优雅关闭。

## 03.8 文档解析

DocumentLoaderManager 按扩展名选择 loader：

- PDF：提取页面文本并保留页码 metadata。
- DOCX：提取段落内容。
- Markdown/TXT：按文本读取。

解析器输出 LangChain `Document(page_content, metadata)`。解析为空必须视为入库失败或零 chunk 结果，不能用“任务 completed”掩盖空知识。

扫描 PDF、复杂表格和公式可能提取质量差。Vision `/describe` 是图片理解辅助，目前没有完整 OCR/版面评测流水线，因此不能声称所有 PDF 都能高质量结构化。

## 03.9 语义切块

`SemanticChunker` 的核心步骤：

1. 保护 Markdown 列表项，避免把一条完整操作拆散。
2. 用中英文标点、章节编号等切句。
3. 过滤极短或符号占比过高的 PDF 噪声块。
4. 对相邻句 embedding，计算余弦变化 `1-cosine`。
5. 在语义变化较大的位置寻找边界。
6. 同时满足最小/最大字符和 token 约束。
7. 可将父 Markdown 标题前置到 chunk。
8. 使用相邻句而非固定字符做语义 overlap。

默认构造参数包括 `min_tokens=150`、`max_tokens=800`、最大字符 2000。token 编码器不可用时，用中文字符和其他字符比例估算。

## 03.10 为什么标题要进入 chunk

某个 chunk 正文可能只有“执行 `ib_write_bw` 并记录结果”，离开章节标题“RDMA 带宽基线”后语义不完整。前置父标题能改善 embedding 和 BM25，也让来源片段更易理解。

代价是标题在多个 chunk 重复，会消耗少量 token；对当前短文档规模，召回收益更重要。

## 03.11 Chunk 去重与稳定 ID

DocumentProcessor 用正文 MD5 前 12 位去除单次处理中的完全重复 chunk。Worker 写入时使用：

```text
chunk_hash = MD5(page_content + file_hash + index)[:12]
chunk_id = file_hash[:20] + "-" + index + "-" + chunk_hash
```

文件内容、位置和正文共同决定 ID。同一内容重新提交能得到稳定 ID，部分变化只替换变化的 chunks。

MD5 在这里用于非安全的内容标识，不用于密码或防篡改；文件级去重使用 SHA-256。

## 03.12 Embedding 与 Chroma 写入

Embedding provider 与 Chat 模型独立，当前为 Qwen `text-embedding-v2`。VectorStoreManager 延迟创建 Chroma collection `lab_knowledge`，支持 add、similarity search、按 source/ID 删除和列表读取。

写入前将所有 metadata 转成 Chroma 可接受标量。Embedding API 失败会让任务进入 retrying，而不是把未生成向量的空记录标成成功。

## 03.13 安全替换顺序

更新同 source 文档时：

```python
old_ids = get_document_ids_by_source(source)
new_ids = add_documents(new_chunks)
obsolete = old_ids - new_ids
delete_documents_by_ids(obsolete)
```

“先写新，再删旧”的原因：如果 embedding 或 add 失败，旧资料仍可检索。若先删旧再写新，任何外部 API 波动都会造成知识窗口。

这个顺序不是完整跨系统事务：Chroma 写入成功但任务状态更新失败时可能需要幂等恢复。稳定 chunk ID 和 source 查询降低了重复写入风险。

## 03.14 版本管理

有 `doc_id/version` 时，VersionManager 维护 SQLite 版本记录：

- 新版本更高：warning，并将旧 active 标为 superseded。
- 新版本更低：reject。
- 同版本但生效日期不同：warning，提示灰度冲突。

检索来源可以显示版本、生效日期和来源系统。需要注意：Chroma 对 ISO 日期字符串范围比较存在兼容问题，所以代码没有把完整时效条件放进 Chroma `where`。`VersionManager` 提供了日期相关能力，但当前主检索链的 `check_doc_access()` 并未执行完整的 `effective_date`、`expiry_date` 判断。这是现状缺口，不能表述成“已经在 Python 层完整兜底”，更不能说所有时效规则都在向量库原生执行。

## 03.15 删除文档

资料目录按 source 聚合 chunks。删除接口接收 source，先验证编辑权限，再按 source 找出所有 chunk IDs 删除。

删除是物理移除 Chroma chunks，不是软删除。执行前需要精确 source，不能允许路径通配或模糊匹配。生产化还应增加审计和可恢复回收站，但当前没有过度扩张。

## 03.16 为什么“磁盘有文件”仍检索不到

一个文件要可检索必须同时满足：

```text
文件存在
∧ loader 成功
∧ chunk 非空
∧ embedding 成功
∧ Chroma 已写入
∧ metadata/ACL 允许当前用户
∧ query 能召回候选
```

H08/H16 的论文在磁盘，但冻结 Chroma title/source 集合没有对应条目，所以失败应标成 `missing_document`，不能继续调 RRF 或 Reranker。

## 03.17 入库诊断清单

1. API 是否返回 job ID？
2. job 是 pending、running、retrying、failed 还是 completed？
3. error 是否为 loader、embedding、metadata 或版本冲突？
4. completed result 的 stored chunks 是否大于 0？
5. Chroma 中是否能按 source 查到 IDs？
6. metadata 的 visibility/confidentiality 是否正确？
7. BM25 文档快照是否已包含新 chunks？
8. 用管理员和普通角色分别做检索验证。

## 03.18 已知边界

- SQLite queue 适合单机低频上传，不是分布式消息系统。
- 扫描 PDF、表格、公式没有完整专项质量保障。
- source 级替换假设同一逻辑文档 source 稳定。
- 版本 SQLite 与 Chroma 不是一个 ACID 事务。
- 入库成功只说明可检索，不说明答案质量；仍需 retrieval benchmark。
