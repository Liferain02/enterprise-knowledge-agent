# 04 混合检索、重排与纠错检索

本文拆解候选生成、融合、精排、相关性评估和纠错。面试时必须区分“没召回”“召回但排后”“精排过滤”“评估拒绝”和“生成没使用”五类失败。

## 04.1 完整检索管线

```text
Query
→ meaningful query guard
→ optional decomposition
→ Vector Top-2K + ACL where
→ BM25 Top-2K
→ weighted RRF
→ Python ACL verification
→ candidate Top-K×multiplier
→ Qwen gte-rerank-v2 Top-N
→ CRAG per-document grade
→ HIGH/MEDIUM selection
→ bounded rewrite/decomposition when LOW
→ NO_RESULTS or usable documents
```

## 04.2 无意义查询防护

`is_meaningful_retrieval_query()` 拒绝：

- 空白和纯符号；
- 没有中英文或数字的内容；
- 很长但只有一两个重复字符的填充。

这是确定性快速防护。否则向量检索即使对乱码也会返回“最近”的文档，后续模型可能把随机候选组织成看似合理的答案。

## 04.3 向量检索

查询通过 Embedding 转成向量，在 Chroma 做 similarity search。向量路擅长：

- 同义改写；
- 口语问题与正式文档表达差异；
- 长句整体语义。

弱点是专有名词和短查询可能被稀释，而且距离分数与 BM25 不同量纲。

向量检索在候选生成时传入 confidentiality/visibility filter，减少不允许文档进入后续链路。

## 04.4 BM25 检索

BM25 根据词频、逆文档频率和文档长度归一评分。直观形式：

```text
score(D,Q)=Σ IDF(q) × f(q,D)(k1+1)
                    / [f(q,D)+k1(1-b+b|D|/avgdl)]
```

项目用 Jieba 分词，优先 `bm25s`，不可用时 `rank_bm25`。如果引擎返回全 0，还会用 token 是否出现在正文的简单比例做降级，保持词法路径不完全失效。

BM25 强项是论文名、命令、配置项和缩写；弱点是不能自然理解同义改写。

## 04.5 BM25 文档集合

BM25 不像 Chroma 自动持久化检索器对象，它需要从当前文档构建 tokenized corpus 和索引。索引应在资料变化后刷新，否则 Chroma 已有新文档但 BM25 仍用旧快照，会造成两路数据不一致。

面试中如果问动态更新，应承认当前规模可重建内存 BM25；大规模增量索引需要专门搜索引擎或增量结构。

## 04.6 查询长度自适应权重

```text
len <= 4：vector=0.3, BM25=0.7
len <= 8：vector=0.4, BM25=0.6
len > 8：使用配置权重，当前通常 0.5/0.5
```

这是低成本启发式：短查询常由关键词组成，BM25 更可靠；长查询语义更完整，提高向量贡献。

它不是学习得到的最优策略。若未来有足够 query 级训练数据，可以用分类器或 learning-to-rank 替代；当前固定规则更可解释。

## 04.7 RRF 融合

对于每个文档：

```text
RRF(d)=w_vector/(60+rank_vector)
      +w_bm25/(60+rank_bm25)
```

若某文档只在一路出现，另一路贡献为 0。之后按融合分降序取 Top K。

示例，权重各 0.5：

```text
文档A：vector rank 1, BM25 rank 4
scoreA=0.5/61+0.5/64≈0.01601

文档B：vector rank 2, BM25 未命中
scoreB=0.5/62≈0.00806
```

A 在两路都靠前，因此稳定胜过只在一路排名稍高的 B。

## 04.8 去重键

Hybrid 当前用 `hash(doc.page_content)` 作为同轮融合键，多查询 RRF 则结合文档对象/来源。它适合当前进程内临时去重，但 Python hash 跨进程不稳定，不能作为持久化 ID。

持久化使用 ingestion 生成的 chunk ID。未来可以在检索融合中直接优先用 metadata chunk ID，降低相同正文不同来源被误合并的风险。

## 04.9 Python ACL 二次过滤

融合后的候选必须再调用 `check_doc_access()`。原因是 BM25 路本身不支持 Chroma where，且部门、角色和日期条件难以完整表达为 Chroma filter。

未经二次过滤的 BM25 候选不能进入 Rerank；否则即使最后删除，也已经把受限正文发送给外部 Rerank API。

## 04.10 Rerank 的职责

Bi-encoder 向量先独立编码 query/doc，速度快但交互有限。Cross-encoder 风格 Reranker 联合看 query-document，更适合精排少量候选。

项目用 DashScope `TextReRank.call`：

```text
model=gte-rerank-v2
query=query
documents=[page_content...]
top_n=min(config_top_n, candidate_count)
return_documents=true
```

只保留 relevance score 不低于阈值的结果，默认 top N 和阈值由配置控制。

## 04.11 Reranker 降级

Qwen API 非 200、SDK 缺失或异常时，不让整个检索失败，而是保留原始候选顺序并赋均匀分。这样系统退化为 Hybrid 排序，而非完全不可用。

但均匀分不是“重排成功”。监控和评测应记录 provider 失败，不能把降级结果当成真实 Qwen score。

代理环境下，Qwen Reranker读取 HTTP_PROXY，并设置 DashScope SDK 代理变量。Chat 可用不代表 Rerank 一定可用，因为它们可能走不同 SDK 和端点。

## 04.12 为什么不能先 CRAG 再 Rerank

CRAG Grader 每篇候选需要模型判断。如果对 15 个原始候选全部评分，成本高；先 Rerank 到 3–5 篇，可以显著减少 grader 调用。

代价是 Reranker 错删的文档无法被 Grader 恢复。因此评测要同时保存 raw、reranked、final candidates，才能定位损失发生在哪一层。

## 04.13 DocumentGrade

每篇文档评分结果：

```text
doc
raw_score: 1..5
relevance_score: normalized 0..1
reasoning: 简短评估理由
grade: HIGH | MEDIUM | LOW
```

多个 DocumentGrade 聚合成 GradeResult，统计 high/medium/low 数量、平均分、延迟和总 decision。

## 04.14 CRAG 决策

默认逻辑大意：

- 没有文档 → NO_RESULTS。
- 没有 HIGH/MEDIUM 且低分比例足够高 → NO_RESULTS。
- HIGH 比例和平均分达到阈值 → HIGH。
- 有 HIGH/MEDIUM 且平均分达到 medium threshold → MEDIUM。
- 其他 → LOW，触发纠错。

阈值来自配置，当前 `crag_grade_threshold`、`crag_medium_threshold` 等不是通用真理，必须由固定数据集验证。

## 04.15 Grader 缓存与重试

缓存键基于 query 和文档内容。Redis 可用时持久缓存，不可用时内存降级。模型遇到 429 或 5xx 时最多重试 3 次，等待采用指数退避加随机 jitter。

非限流异常直接将该文档标 LOW；所有重试失败也返回 LOW 而不是抛垮整个请求。这提高可用性，但可能在服务故障时产生保守拒答，所以需用日志区分“真实低相关”和“评分失败”。

## 04.16 Query Expansion

复杂对比、列举或多实体问题可以先拆子查询。每个子查询分别检索，再用多列表 RRF 合并。

Normal Expansion 与 Deep Research 的区别：

| Normal Expansion | Deep Researcher |
|---|---|
| 是检索预处理 | 是显式团队阶段 |
| 输出仍是普通文档上下文 | 输出 EvidencePackage |
| 不生成 Claim/ReviewReport | 继续 Analyst/Reviewer |
| 成本较低 | 多次模型和检索调用 |

## 04.17 纠错路径

若首轮 LOW：

1. 尝试 query rewrite。
2. 重新 Hybrid + Rerank + Grade。
3. 必要时使用 Query Expander 拆分并行检索。
4. 合并后选择当前最好的一组。

纠错有明确次数边界，避免一个知识库不存在的问题消耗无限调用。

## 04.18 NO_RESULTS

Retrieval 节点将状态写为 no_results，Generation 走确定性快速路径，提示更换关键词或联系管理员补资料。

这不是“模型不会回答”，而是产品选择：内部知识问题在无证据时拒答，比用通用常识补齐更可信。

## 04.19 冲突检测

通过多个文档的版本、时间和文本模式检测潜在不一致，输出 `conflict_warnings`。Generation 被要求客观呈现冲突，不擅自选择某一条。

冲突检测是启发式，不等于形式化事实验证。它能提醒用户和评测 conflict case，但仍需要人工判断实际政策或实验结论。

## 04.20 五层失败归因

| 现象 | 归因 |
|---|---|
| Chroma/BM25 都没有目标文档 | missing document 或 candidate generation |
| raw 有、RRF 后掉出 | fusion failure |
| fused 有、rerank 后消失 | rerank failure |
| reranked 有、grader 判低 | grading failure 或文档确实不相关 |
| final docs 有、答案未引用 | generation/coverage failure |

只有保存每层候选才能做这种归因。只看最终答案会错误地把所有问题都归给 LLM。

## 04.21 复杂度

设向量候选 V、BM25 文档总量 N、最终 grader 候选 G：

- 向量 ANN 由 Chroma 索引决定。
- BM25 查询约遍历/评分索引中的 N 文档。
- RRF 合并 O(V+B)。
- Rerank 通常 O(C) 次 query-document 评分。
- Grader 是 G 次外部 LLM 调用，但并发受 semaphore 限制。

当前 N 很小，主要延迟来自外部 Rerank/LLM，不来自 RRF 本身。

## 04.22 调优原则

一次只改一类变量：

1. 固定知识库 snapshot。
2. 保存 raw/reranked/final candidates。
3. 预声明 Recall/MRR/NDCG 或类别 gate。
4. 改权重、top K、阈值或 query strategy 中的一项。
5. 在同一数据集重跑。
6. 失败则回滚，不为个别 case 写 ID 补丁。

这比凭主观观察“回答好像更顺”可靠。
