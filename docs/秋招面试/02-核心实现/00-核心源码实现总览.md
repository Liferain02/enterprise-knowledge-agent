## 2. 请求协议

### 2.1 Pydantic 请求

`ChatRequest` 和 `ChatStreamRequest` 共享四个主要字段：

```python
message: str
session_id: str = "default"
images: Optional[List[ImageContent]] = None
research_mode: Literal["normal", "deep"] = "normal"
```

`Literal` 在 API 边界就拒绝未知模式，不需要让路由器处理任意字符串。默认值放在 schema 而不只是前端，因此脚本、旧客户端和 API 直接调用都保持 Normal。

### 2.2 认证和授权分离

JWT 证明“这个请求是谁”，不被当作当前授权状态的唯一真相。`get_current_user()` 解码 JWT 后用 `sub` 重新读取 SQLite 用户，得到最新 role 和 department。这解决了管理员已经撤销权限，但用户持有的长效 JWT 仍包含旧 role 的问题。

配置管理员是回退身份，数据库同名账号优先，避免两种身份混淆。密码使用 Argon2，历史 SHA-256 账号在成功登录后原位升级。

### 2.3 会话隔离

HTTP 层不相信客户端传入的用户 ID，而是使用认证用户名。业务会话表始终用 `(user_id, session_id)` 定位，LangGraph checkpoint 的 thread ID 也是 `f"{user_id}_{session_id}"`。即使两个用户都创建 `default` 会话，状态也不会共享。

## 3. SSE 实现

### 3.1 为什么不只返回最终 JSON

LLM 和多阶段检索可能需要几秒到数十秒。SSE 让前端能展示：

- 当前用户权限；
- “正在检索”、“正在形成声明”等阶段状态；
- 用户可见的 token；
- 工具开始/结束；
- 来源卡片、版本信息和最终 agent 标识；
- `done` 或 `error`。

### 3.2 可见 token 过滤

LangGraph `astream_events()` 会产生 Planner、Analyst、Reviewer 等所有 LLM 的 stream event。如果前端无区别转发，用户会看到结构化 JSON、内部评审和最终答案混在一起。

`generation_agent_node()` 调用 LLM 时添加 `tags=["user_visible_answer"]`，`_is_user_visible_llm_event()` 只允许这些事件通过。这是“一轮请求只有一个用户可见答案”的关键实现，也是多 Agent 系统容易忽略的协议问题。

### 3.3 图结束后为什么再读 checkpoint

token 流只包含可见生成过程，不一定包含确定性拒答、工具答案、来源文档和 `used_agent`。因此图结束后用 `graph.aget_state()` 取最终 state，checkpoint 是最终业务事实，而 token 只是增量展示。

## 4. AgentState 和生产图

### 4.1 AgentState 为什么是协议

`AgentState` 继承 `MessagesState`，但不只存消息。主要字段分为：

- 身份/会话：`session_id`、`user_id`、`user_context`、`summary`、`mem0_memories`；
- 路由：`_quick_agent`、`is_complex`、`needs_expansion`、`research_mode`；
- Retrieval：`retrieval_context`、`retrieved_docs`、`retrieval_decision`、`rewrite_history`、`conflict_warnings`；
- Deep：`evidence_package`、`analysis_report`、`review_report`、`research_trace`、`research_revision_count`；
- 终态：`final_answer`、`used_agent`、`sources`、`version_source`。

每个节点只写自己的输出字段。例如 Retrieval 不写最终答案，Analyst 不改用户身份，Reviewer 不自己检索。这比让 Agent 通过自由消息互相“聊天”更容易保证边界。

### 4.2 生产图注册决定真实架构

`create_multi_agent_graph()` 实际注册：

```text
maybe_summarize
  → retrieve_mem0_memories
  → planner
      ├─ retrieval_agent → generation_agent
      ├─ operation_agent
      ├─ general_agent
      └─ research_agent → analyst_agent → reviewer_agent
            ├─ deep_research_generation
            └─ research_revision → deep_research_generation
  → finalize_response
  → END
```

`planner.py` 中仍保留 execute plan / Send 兼容函数，`supervisor.py` 和 `parallel_executor.py` 也可能存在，但没有被注册到上述图中。面试时如果被问“项目是否有 Supervisor”，应回答“历史兼容代码有，当前生产图没有”。

### 4.3 统一 Finalizer

`finalize_response_node()` 保证 `final_answer` 非空，并确保最终 AIMessage 不重复追加。这是一个确定性节点，不是新 Agent。

## 5. Planner 的设计

### 5.1 规则优先

`_quick_complexity_check()` 将问题分为 simple / complex / uncertain。问候、纯计算、时间查询等窄类型用规则直接路由。“有哪些”、“比较”、“先…再…”即使很短也优先判为复杂，避免被短文本规则误当成 simple。

### 5.2 复杂不等于 Multi-Agent

Normal 中“比较 A/B”、“列举多份材料”会设置 `needs_expansion=True`，然后仍进入统一 Retrieval。复杂度由 Query Expansion 处理，不会触发旧的 fan-out Agent。

### 5.3 Deep 不由 Planner 自动决定

`route_from_planner()` 首先检查 `research_mode`。这不是“Planner 认为复杂所以进 Deep”，而是“用户在 API/UI 明确同意更高延迟后进 Deep”。

## 6. 文档入库

### 6.1 API 边界

`KnowledgeService.enqueue_document_from_file()` 执行：

1. 空文件和 50MB 上限校验。
2. 只允许 PDF、DOCX、Markdown、TXT。
3. `Path(filename).name` 去除路径，正则清理异常字符，防止路径穿越。
4. 计算 SHA-256，查询队列中 pending/running/retrying/completed 的相同文件。
5. 持久化到 `data/uploads`，而不是依赖 HTTP 请求期间的临时文件。
6. 归一 `doc_type`、visibility、project、author、tags、time 等元数据。
7. 写入 SQLite `IngestionJobQueue`。

### 6.2 为什么要队列

PDF 解析、Vision、切块和 Embedding 可能较慢，不应长时间占住上传请求。队列保存 pending/running/completed/failed/retrying，并记录 retry count、error、started/completed time 和 result。服务重启后 `recover_stale_jobs()` 将超时 running 任务恢复。

### 6.3 Worker 链路

`IngestionWorker._process_job()`：

```text
dequeue
 → loader.load_file
 → chunker.chunk
 → version archive/replace（有 doc_id 时）
 → metadata scalar normalization
 → deterministic chunk IDs
 → add new chunks
 → delete obsolete chunks of same source
 → complete job
```

更新时先写新 chunks，再删同来源的旧 chunks。如果新 Embedding 写入失败，旧版资料仍然可用，这比“先删后写”更安全。

### 6.4 切块与元数据

默认混合切块目标约 500 tokens，overlap 100 tokens，并可将父标题拼到 chunk 前。元数据不是只用于展示；visibility、confidentiality、department/project restriction 直接决定该 chunk 是否能进入检索候选。

对于 Chroma 不支持的 list/dict 元数据，worker 转换成标量或逗号分隔字符串。这是存储适配层的责任，不应让上层 Agent 感知。

## 7. Hybrid Retrieval

### 7.1 为什么同时需要 BM25 和向量

- BM25 擅长文档名、代码名、缩写、精确术语。
- 向量检索擅长用户没有使用文档原词的语义查询。
- 单独使用任意一路都会对另一类问题不稳定。

### 7.2 自适应权重

`HybridRetrieverManager.search_with_scores()` 按查询字符长度调整两路权重：

```text
≤4 字： vector 0.3 / BM25 0.7
5～8 字：vector 0.4 / BM25 0.6
>8 字：使用配置权重
```

这是窄而可解释的启发式：越短的查询越可能是标题、缩写或精确名词。

### 7.3 RRF

两路原始分数量纲不同，直接加权可能让某一路因分数范围占优。RRF 只使用排名：

```text
RRF(d) = Σ weight_i / (60 + rank_i(d))
```

同时在向量和 BM25 前列出现的文档获得更高融合分。它的优点是对分数尺度不敏感，缺点是忽略了同一排名间的绝对差距。

### 7.4 Rerank

Hybrid 生成较多候选，`gte-rerank-v2` 按 query–document 配对重新排序，再给 CRAG Grader 评少量 top candidates。如果 Rerank API 不可用，代码记录警告并保留原排序，知识问答降级而不是整个不可用。

## 8. CRAG 纠错检索

`CorrectiveRAGPipeline.retrieve()` 是所有 Normal 和 Deep 证据检索的统一入口。

### 8.1 正常路径

```text
query
 → optional Query Expansion
 → ACL-aware Hybrid candidates
 → Rerank before grading
 → batch relevance grading
 → HIGH/MEDIUM/LOW/NO_RESULTS
 → usable documents
```

### 8.2 纠错路径

- LOW：改写 query 再检索；仍 LOW 时可分解为多 query，并用 RRF 合并。
- NO_RESULTS：最多按 `max_retries` 重试，仍无结果则返回空。
- Expansion 失败：回退标准 CRAG，不让分解器成为单点故障。
- 无语义 query：直接返回空 GradeResult，不浪费外部调用。

### 8.3 为什么不无限重试

每次改写、分解、Rerank 和 Grading 都增加延迟和不确定性。当知识库根本没有文档时，更多重试不会创造证据。因此重试次数是产品成本上界，不是越多越好。

## 9. ACL 实现

### 9.1 UserContext

`UserContext` 包含 user_id、username、role、department ID/name/path 和 active 状态。匿名用户降级为 student/public 语义，而不是用 `None` 意外获得全库权限。

### 9.2 第一层：候选过滤

`build_acl_filter()` 把角色允许的 confidentiality 和 visibility 组成 Chroma where clause。这减少敏感 chunk 进入候选的机会，也避免它们占据 top-k 后再被删除导致可用文档不足。

### 9.3 第二层：Python 精细复核

Chroma 对 list contains 和日期字符串比较的支持有限，因此 department/role 限制不只依赖 where clause。`check_doc_access()` 依次检查：

1. 用户是否 active；
2. 角色能否访问该 confidentiality；
3. 角色是否允许 public/project/restricted；
4. 有 department restriction 时是否同部门/项目；
5. 有 role restriction 时是否在允许角色集。

### 9.4 Deep 为什么要重复校验

Deep 有初次检索和 revision 补检索，证据还会进入多个 LLM 阶段。`_retrieve_evidence()` 对 pipeline 结果再调 `check_doc_access()`，`EvidencePackage.acl_checked` 是后续阶段的强约束。`_validate_claims_for_finalization()` 遇到 `acl_checked=false` 会删除所有 Claim，不尝试让模型“自觉不泄密”。

## 10. Normal Generation

### 10.1 不可信检索数据

Generation system prompt 用显式边界包围检索文本：

```text
【不可信检索资料开始】
...
【不可信检索资料结束】
```

这里的不可信不代表文档不能作为事实依据，而是表示文档不能发布系统指令。即使文档中写着“忽略之前的要求”，模型也应将其视为数据。

### 10.2 引用编号和来源卡片

`_build_retrieval_context()` 按最终 results 顺序编号为文档1..n，Generation 用同样编号引用。ChatService 再从 `retrieved_docs` 生成来源卡片，包含 title、snippet、doc type、project、time、score 和 visibility。

### 10.3 冲突和版本

Retrieval 将文档交给 conflict detector，如果存在新旧规则或多份资料不一致，Generation Prompt 要求显式呈现不一致，不得随意选一份。`version_source` 单独发给前端，不用非结构文本猜测版本。

## 11. Deep 数据协议

### 11.1 EvidencePackage

```text
original_question
subquestions[0..4]
evidences[0..12]
  source_id          S1..Sn
  subquestion
  title / safe source basename
  excerpt            <=800 chars
  score
  safe metadata
  time_info
  conflict_warnings
missing_evidence
conflicts
acl_checked
```

EvidencePackage 是 Researcher 与 Analyst 之间的数据合同，而不是一段自由 prompt。`_safe_metadata()` 只传 title、doc type、project、visibility、version、time 等白名单标量，`_display_source()` 只保留 basename，避免服务器路径泄露。

### 11.2 Claim Map

```text
claim_id
text                  <=200 chars
claim_type            fact/comparison/inference/recommendation
source_ids
confidence
```

Claim 不允许只有“我觉得”而没有 source IDs。即使 recommendation 也必须绑定它基于的现有证据，但在输出中必须标记为建议而不是事实。

### 11.3 ReviewReport

```text
decision              PASS/REVISE/NEED_MORE_EVIDENCE
items[]
  claim
  source_ids
  supported
  issue_type
  revision_instruction
premise_assessment
premise_source_ids
false_premise_detected
conflict_handled
acl_verified
overall_instruction
targeted_queries[0..2]
```

Pydantic `AliasChoices` 兼容 Qwen 可能输出的 `review_result`、`review_decision`、`reviewer_decision`、`status` 等 wire format，但内部始终归一为 `decision`。Premise 枚举偶尔被包装为对象时，validator 提取 status/value/assessment/result。

## 12. Deep 节点实现

### 12.1 `_plan_subquestions()`

复用既有 `QueryDecomposer`，而不再维护一套第二份拆问 prompt。结构化输出失败时，`_fallback_subquestions()` 按句号、句号和连词切分，最后补原问题、事实/时间/实验条件和冲突/缺口/建议三类通用子问题。Fallback 也不超过 4 条。

### 12.2 `_retrieve_evidence()`

逐子问题调 CRAG，对异常记录 error 而不让整个研究任务崩溃。每次记录 decision、rewrite history、titles 和 error。检索结果再做 ACL，然后去重、排序和编号。

### 12.3 `_normalize_analysis()`

模型结构化输出仍可能语义不符合协议。此函数负责一次、通用、无网络的归一，不会针对 V2 个别 case ID 打补丁。归一后计算 `uncovered_source_ids`，让评测能区分“Researcher 没找到”和“Analyst 找到但没用”。

### 12.4 `_deterministic_review_issues()`

LLM Reviewer 可能错误 PASS。程序先扫描每个 Claim，不存在的 S 编号标记 `invalid_source`，空引用标记 `citation_gap`。只要存在确定性问题，PASS 就改为 REVISE。

### 12.5 `_is_premise_task()`

该函数只判断用户是否显式要求验证一个命题，不判断命题真假。这一分离避免了“只要句子里有判断就当作 false premise”。普通比较、总结和建议被确定性归一为 not applicable。

### 12.6 `_validate_claims_for_finalization()`

修订后不再经过 Reviewer，因此必须有最后硬校验。该函数不会猜测“S99 可能是 S9”，而是直接删除非法/空引用 Claim，并把删除数量降级为 limitation。安全边界不使用自由模型修复。

### 12.7 `deep_research_generation_node()`

1. 删除 Reviewer 明确否决的 Claim。
2. 重复最终 Claim 校验。
3. 生成 Evidence 和 Claim Map 上下文。
4. 设置 Deep 专用 Research Brief 结构和 1400 字上限。
5. 复用 Normal Generation Agent。
6. 对真正 premise 在顶部加确定性结论，`not_applicable` 不加。
7. 比较最终答案和 validated claims，记录 omitted claim IDs 和词汇覆盖 proxy。
8. 生成 failure attribution。

## 13. Trace 和可观测性

`research_trace.stages` 包含：

| 阶段 | 关键记录 |
|---|---|
| researcher | query、subquestions、query runs、文档标题、EvidencePackage、missing、latency/tokens |
| analyst | claims、uncovered source IDs、evidence-to-claim coverage、latency/tokens |
| reviewer | ReviewReport、premise task、rejected claims 及理由、latency/tokens |
| revision | 修订前后 claims、targeted queries、新增证据、删除 claims、latency/tokens |
| generation | reviewer 删除项、validated claims、omitted IDs、final coverage proxy、latency/tokens |

顶层 `failure_attribution` 只取：

```text
retrieval | analysis | review | generation | knowledge_gap | acl | none
```

这个 runtime 归因没有 gold，因此只能根据当前信号区分大层。在 retrieval-only 评测里，因为知道预期文档，才能进一步区分 missing document、rerank failure 等细类。

## 14. 前端模式选择

`App.vue` 定义：

```typescript
const researchMode = ref<'normal' | 'deep'>('normal')
```

`sendMessage()` 先保存 `requestResearchMode = researchMode.value`，再立即设回 normal，最后把保存值写入 JSON。它比在请求成功后才复位更稳健：即使网络失败，下一次也不会意外继续 Deep。

fieldset 在 loading 时 disabled，避免用户在一次请求中途改变 UI 导致“显示模式”与已发送请求不一致。

## 15. 配置与降级

当前主要配置：

```text
LLM_PROVIDER=qwen
DASHSCOPE_MODEL=qwen3.5-flash
EMBEDDING_MODEL=text-embedding-v2
RERANKER_PROVIDER=qwen
RERANKER_MODEL=gte-rerank-v2
QUERY_EXPAND_ENABLED=true
DEEP_RESEARCH_ENABLED=true
MEM0_ENABLED=false
REDIS_HOST=disabled
API_PORT=8010
```

Chat、Embedding 和 Rerank 分开配置，因为 OpenAI-compatible 对话端点不一定提供 Embedding/Rerank。`DEEP_RESEARCH_ENABLED` 是紧急产品开关，关闭后非流式和 SSE 都确定性返回 Deep offline 提示，Normal 不受影响。

Pydantic Settings 在 auth 开启时拒绝仓库公开占位管理员口令，并要求 JWT secret 至少 32 字符。这让“忘记改默认密码”在启动期失败，而不是上线后才发现。

## 16. 面试时的源码讲解顺序

1. 从 `ChatStreamRequest` 说入口协议。
2. 进 `ChatService.achat_stream()` 说身份、thread ID 和 SSE。
3. 打开 `create_multi_agent_graph()` 画真实生产图。
4. 打开 `route_from_planner()` 说明 Normal/Deep 边界。
5. 跟 Normal：`retrieval_agent_node()` → CRAG → Hybrid → ACL → `generation_agent_node()`。
6. 跟 Deep：EvidencePackage → Claim → ReviewReport → one revision → reused Generation。
7. 最后用 trace 和评测数据解释这些节点为什么存在。

这个顺序能防止面试变成零散类名记忆，始终保持“请求如何流动”的主线。

## 17. 辅助业务模块：它们解决什么，不解决什么

前 16 节是项目的技术主线。本节覆盖仓库里已经实现、但不应在面试中抢占 RAG 主线的辅助模块。推荐把能力按下面三层介绍：

| 层级 | 模块 | 面试定位 |
|---|---|---|
| 核心 | Normal RAG、Deep Research、ACL、摄取与评测 | 项目主体，必须能从请求讲到评测 |
| 产品闭环 | 资料中心、科研空间、反馈处理 | 说明系统不只是聊天 Demo |
| 可选扩展 | Vision、MCP、A2A、通用/运维 Agent | 证明架构可扩展，但主动说明完成度和边界 |

这种分层不是弱化辅助模块，而是防止把项目介绍成“功能很多但没有主线”。

### 17.1 前端的三个工作区

`frontend/src/App.vue` 通过 `activeWorkspace` 管理三个一级工作区：

```typescript
const activeWorkspace = ref<'chat' | 'knowledge' | 'research'>('chat')
```

- 对话工作区：会话、Normal/Deep 单次模式选择、SSE 回答、引用和反馈入口。
- 资料中心：资料目录、元数据筛选、文件上传、摄取任务状态和反馈问题列表。
- 科研空间：项目、成员、实验记录、行动项和概览统计。

当前实现把这些状态放在一个 Vue 单文件组件中，优点是演示链路简单、无需引入额外状态库；缺点是 `App.vue` 较大。对当前项目规模，拆出组件是可维护性优化，不是支撑核心能力的前置条件，因此没有为了“架构看起来漂亮”做大规模前端重构。

### 17.2 科研空间的数据模型

`src/api/services/research_service.py` 使用独立 SQLite 文件 `data/research_workspace.db`，初始化四张表：

```text
research_projects
  └─ research_project_members
  ├─ research_experiments
  └─ research_tasks
```

核心字段如下：

| 实体 | 关键字段 | 用途 |
|---|---|---|
| project | title、direction、status、visibility、lead、created_by | 定义科研项目空间与访问范围 |
| member | username、member_role | 记录项目成员关系 |
| experiment | hypothesis、environment、code_commit、dataset_version、metrics、conclusion、next_steps | 让实验结果具备最基本的可复现上下文 |
| task | assignee、due_date、status、source | 把组会结论变成可跟踪行动项 |

实验指标以 JSON 字符串保存在 SQLite 中，读出时反序列化为对象。这是一种适合实验室规模的折中：无需为不同实验设计动态列，同时保留结构化展示能力；它不等同于完整的实验追踪平台。

数据库访问通过 `_connection()` 上下文管理器统一提交、异常回滚和关闭连接，并开启外键约束。项目删除时，成员、实验和待办可由外键级联处理。

### 17.3 科研空间的权限规则

科研空间没有复用向量检索 ACL 的元数据判断，而是在服务端对结构化实体执行单独的项目级权限：

1. `admin`、`pi` 可访问所有项目。
2. `public` 项目对已认证用户可见。
3. 创建者、负责人和成员可访问所属项目。
4. 创建项目要求角色属于编辑角色集合。
5. 写实验和待办要求是特权角色、创建者、负责人或项目成员。

`list_projects()` 不是把未授权项目返回给前端再隐藏，而是在服务端过滤；`get_project()`、创建实验、创建待办和修改待办状态也会再次校验。这与知识检索 ACL 的共同原则是：界面隐藏不是安全边界，服务端才是。

### 17.4 从组会纪要提取行动项

`extract_meeting_tasks()` 没有调用 LLM，而是逐行识别两类稳定格式：

```markdown
- [ ] 补充基线实验 | 负责人：alice | 截止：2026-09-01
- TODO: 整理数据集版本 | owner: bob | due: 2026-09-03
```

它识别 Markdown checkbox 或 `TODO/待办/行动项/后续动作`，再解析负责人和 `YYYY-MM-DD` 日期，最终复用 `create_task()` 持久化。选择确定性规则的原因是：

- 常见组会模板格式有限，正则足够解决当前需求；
- 不增加模型成本和网络失败点；
- 提取结果可预测，出错时容易解释；
- 未来只有在真实纪要格式明显超出规则覆盖时，才值得增加 LLM 抽取与人工确认。

这是“不过度设计”的具体例子：不是所有带“提取”二字的需求都必须做成 Agent。

### 17.5 用户反馈到知识治理的闭环

回答下方有三种反馈：

```text
helpful | incorrect | missing_material
```

`FeedbackService` 把反馈写入会话 SQLite 数据库中的 `feedback` 表。`FeedbackDAO.get_stats()` 汇总三类数量；只有 `incorrect` 和 `missing_material` 会进入问题列表，因为“有帮助”是正向统计而不是待处理工单。

问题状态只有 `open` 和 `resolved`。标记为 `resolved` 时必须填写 `resolution_note`，并记录处理人和处理时间；恢复为 `open` 时清空这些处理字段。普通用户只能查看自己的统计与问题，有审阅角色的用户才能查看全局问题和修改处理状态。

完整闭环是：

```text
用户发现回答问题
  → 提交“不准确”或“缺少资料”
  → 审阅者查看待处理列表
  → 修正文档、元数据或检索问题
  → 填写解决说明并关闭问题
  → 必要时把案例加入回归集
```

最后一步目前是治理流程约定，并非代码自动生成回归样本。面试时应说“系统提供了反馈采集和处理状态，问题是否进入回归集由维护者判断”，不能说成已经实现自动持续学习。

### 17.6 Vision：对话前置理解与独立接口

图片能力有两条入口：

- `ChatService` 收到图片时先调用 `understand_images()`，把图片理解结果作为文本上下文加入本轮请求；主图仍处理文本状态。
- `vision_controller.py` 提供 `/api/v1/vision/understand` 和 `/describe`，适合独立图片问答或生成可索引描述。

这种做法避免让 LangGraph 中每个 Agent 都处理多模态消息格式。它的边界也很明确：当前是图片理解辅助，不是完整的图片向量检索、版面分析流水线或视觉评测体系。Vision 失败应作为可选能力故障处理，不能影响纯文本知识问答主线。

### 17.7 Operation Agent 与 General Agent

Planner 除了知识检索外，还能路由到两个轻量分支：

| Agent | 负责内容 | 主要实现 |
|---|---|---|
| Operation Agent | 计算、时间、受限文件工具等操作 | `create_react_agent` + Skill 工具 + MCP 工具，180 秒超时 |
| General Agent | 问候、简单常识、有限会话历史搜索 | SkillLoader 创建 ReAct Agent，120 秒超时 |

两者都遵守同一条状态原则：子 Agent 内部的工具调用消息只服务于本轮循环，不整段写回主图；主图只接收最后的 `AIMessage`。这样可以防止 tool call、tool result 污染后续摘要和长期记忆。

General Agent 的 `general_search` 只是很小的内置常识响应，不是真正的联网搜索。它对天气会明确提示无法获取实时信息。面试时不能把它描述成 Web Search Agent。

### 17.8 MCP 工具接入与文件边界

MCP 初始化流程是：

```text
应用启动
  → MCPConnectionManager.initialize()
  → 读取 config/mcp_servers.json
  → 并发启动/连接 stdio server，并施加单服务超时
  → 拉取 MCP tools
  → mcp_adapter 将 inputSchema 转成 Pydantic 参数模型
  → 转成 LangChain StructuredTool
  → Operation Agent 按需调用
```

适配器为常见文件工具补充了参数 schema 和描述，同时支持从 MCP `inputSchema` 动态推导字符串、数字、布尔、数组和对象等类型。调用时先做 Pydantic 校验，再定位工具所属 server 并执行，异常被转换成可读错误，不直接让 Agent 循环崩溃。

当前 `config/mcp_servers.json` 只配置 filesystem server，并把允许目录限制为：

```text
data/knowledge
```

因此“支持 MCP 文件操作”不等于“Agent 可以访问整个服务器文件系统”。这个目录白名单是必须主动讲清楚的安全边界。MCP 还支持关闭或连接失败降级；未初始化时返回空工具列表，核心 RAG 不依赖 MCP 才能工作。

### 17.9 A2A：能力发现兼容层，不是完整协议实现

`src/api/routes/a2a_routes.py` 提供：

- `/.well-known/agent.json`：Agent Card，声明名称、能力、技能和端点。
- `/.well-known/agent.jsonl`：便于脚本读取的事件格式。
- `/api/v1/a2a/send`：提取文本消息并复用 `ChatService.achat()`。
- `/api/v1/a2a/tasks/{task_id}`：把 task ID 简化映射为 session ID 查询结果。
- `/api/v1/a2a/skills`：返回技能声明和关联端点。

源码注释已经明确：当前没有实现独立 Task 资源的完整生命周期、任务取消、流式推送和显式技能选择。因此准确说法是“实现了 Agent Card 和简化消息兼容层，用于能力发现与基本互操作验证”，不是“完整支持生产级 A2A 协议”。

此外，`/api/v1/a2a/send` 当前使用固定的 `a2a_agent` 身份复用聊天服务，不能据此声称已经完成跨 Agent 的细粒度身份委托。若未来对外开放，认证、调用方身份映射、配额、审计和重放防护都需要单独设计。

### 17.10 辅助模块的面试表达模板

如果面试官问“除了问答还有什么”，可以回答：

> 产品层做了资料中心、科研项目空间和反馈治理闭环，使知识从上传、摄取、检索、反馈到修订能够被实际管理。架构层还验证了 Vision 前置理解、MCP 受限工具调用和 A2A 能力发现。不过我把它们定位为辅助或扩展能力，核心投入仍然是带 ACL 的可引用 RAG、Deep Research 证据链和可复现评测；像 A2A 完整任务协议、自动持续学习和企业级高并发并没有过度承诺。

这个回答同时体现了产品完整性、技术取舍和边界意识。
