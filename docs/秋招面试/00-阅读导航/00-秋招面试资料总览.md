# 00 秋招面试资料总览

本文是整套秋招资料的唯一入口。资料按“先建立主线，再读实现，再看评测和复盘，最后练表达”的顺序组织，所有目录和文件均使用两位序号。

文档事实基线：2026-09-04；源码基线：Git `96b6500`。历史数字保留时必须注明对应快照，不代表当前运行结果。

## 00.1 项目最核心的定位

这是一个面向计算机实验室的可信知识与科研协作助手。重点不是登录页、Agent 数量或聊天界面，而是下面四件事：

1. 实验室资料能够可靠入库、检索、引用和更新。
2. 不同成员只能检索自己有权访问的证据。
3. 普通问题走低成本 Normal RAG，显式复杂研究才进入有界 Deep Research。
4. 所有架构改动都尽量由固定评测和失败归因驱动。

## 00.3 各分区解决什么问题

| 分区 | 目标 | 读完后应能做到 |

| 00 阅读导航 | 建立代码与资料地图 | 知道问题应该去哪里查 |

## 00.5 推荐阅读顺序

### 00.5.1 一天速读

1. 读 `01-项目全景与架构讲解`，掌握一句话、两分钟和五分钟版本。
2. 读 `02-请求全链路与时序`，手画 Normal 和 Deep 两条时序。
3. 读核心实现的 04、05、07，分别掌握 RAG、ACL、Deep Research。
4. 读 `04-实验结果解读与停止决策`，记住最重要的数字和负结果。
5. 从故障复盘中挑 3 个 STAR 故事，再用高频问答自测。

### 00.5.2 三天准备

- 第一天：00、01 分区，脱稿讲产品与架构。
- 第二天：02 分区，对着源码跟踪 Normal、Deep、入库与 ACL。
- 第三天：03、04、05 分区，练指标、复盘、简历和演示。

### 00.5.3 一周深度准备

1. 前两天逐函数跟踪 API → ChatService → LangGraph → RAG → SSE。
2. 第三天手写 Hybrid、RRF、CRAG、ACL 的伪代码和边界。
3. 第四天手画 EvidencePackage → Claim → ReviewReport 生命周期。
4. 第五天重新理解 Recall@K、MRR、NDCG、Citation Coverage 等指标。
5. 第六天完成两轮模拟面试和一次断网 Demo。
6. 第七天只修正说不清的地方，不再堆新功能。

## 00.6 必须记住的事实

1. 冻结知识库只有 18 份文档、40 个 chunks，是实验室规模原型。
2. Normal 是默认路径；Deep 必须由用户显式选择，发送后前端立即复位。
3. Planner 是唯一入口路由器；生产图不经过 Supervisor 或动态 Worker。
4. Normal 是 Retrieval → Generation，不再使用旧 Knowledge ReAct 循环。
5. Deep 是 Researcher → Analyst → Reviewer → 最多一次 Revision → 复用 Generation。
6. ACL 覆盖候选生成、结果二次校验、Deep 证据构建和最终引用，不是回答后的字符串删除。
7. Hybrid 使用向量与 BM25，默认 RRF `K=60`，短查询提高 BM25 权重。
8. 当前 Reranker 是 Qwen `gte-rerank-v2`，与 Chat/Embedding 分开配置。
9. 入库使用 SHA-256 去重、SQLite 任务队列、失败重试、陈旧任务恢复和安全替换。
10. V2 中 Deep 召回 0.811 高于 Normal 0.679，但 premise 0.167 低于 0.667。
11. Deep P50/P95 是 27.5/33.0 秒，Normal 是 6.6/9.1 秒。
12. 独立真人 Calibration 仍是可选后续工作；不能把 Codex 模拟评分写成真人结果。

## 00.7 证据等级

| 等级 | 合理表达 | 不合理表达 |
|---|---|---|
| 代码事实 | “实现了两层 ACL 和有界 Deep 图” | “因此绝不会泄漏” |
| 自动测试 | “固定角色矩阵和污染样本中 violation=0” | “已经达到绝对安全” |
| 自动评测 | “固定数据集 proxy 上召回提高” | “最终答案一定更好” |
| 历史人工结果 | “V1 曾观察到正向信号，现作为 Regression” | “盲测永久证明有效” |
| 待验证假设 | “独立人工评分尚待完成” | 把未完成结果写进简历 |

## 00.8 最终自测

面试前应能不看材料回答：

- 为什么不用自动路由把复杂问题全部送入 Deep？
- `thread_id` 为什么包含用户和会话两个维度？
- SSE 如何只转发最终用户可见模型 token？
- 对话摘要为何只统计 user/assistant 消息？
- RRF 为什么比直接相加向量分数和 BM25 分数更稳健？
- Rerank 失败、Redis 不可用、MCP 连接失败分别如何降级？
- ACL 为什么需要存储过滤和 Python 二次检查？
- 未入索引文档为何不能归因成模型召回失败？
- structured output 为什么仍然需要确定性归一和最终校验？
- 为什么没有继续增加 Agent 或换 GraphRAG？

能回答“是什么”还不够，还要能指出源码、说明替代方案并承认验证边界。
