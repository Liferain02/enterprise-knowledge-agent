# 01 代码阅读地图

本文解决两个问题：项目文件很多时从哪里开始，以及某个面试问题应该落到哪段真实代码。不要按目录从头到尾阅读，应该沿生产调用链阅读。

## 01.1 第一条主线：流式 Normal RAG

```text
frontend/src/App.vue::sendMessage
→ POST /api/v1/chat/stream
→ src/api/controllers/chat_controller.py::chat_stream
→ src/api/services/chat_service.py::achat_stream
→ src/agent/graph.py::get_agent_graph_async
→ maybe_summarize_node
→ retrieve_mem0_memories_node
→ src/agent/agents/planner.py::planner_node
→ retrieval_agent_node
→ CorrectiveRAGPipeline.retrieve
→ generation_agent_node
→ finalize_response_node
→ ChatService SSE 过滤、持久化和 sources/done
```

首次阅读只跟这条链。先理解一个用户问题如何完整返回，再读扩展模块。

## 01.2 第二条主线：显式 Deep Research

```text
ChatStreamRequest.research_mode = deep
→ ChatService 把 research_mode 放入初始 state
→ Planner 保留 research_agent 路由
→ research_agent_node
→ analyst_agent_node
→ reviewer_agent_node
→ route_after_reviewer
   ├─ research_revision_node（最多一次）
   └─ deep_research_generation_node
→ generation_agent_node
→ finalize_response_node
```

重点不是背 Agent 名称，而是理解三种结构化协议：

- `EvidencePackage`：检索到了什么、缺什么、来自哪里。
- `Claim`：准备说什么、由哪些证据支持、置信度和类型是什么。
- `ReviewReport`：哪些 Claim 可用、哪些需修订、前提状态如何。

## 01.3 第三条主线：文档入库

```text
knowledge_controller.add_document_from_file
→ KnowledgeService.enqueue_document_from_file
→ 文件大小/类型/元数据校验
→ SHA-256 去重
→ 文件落盘
→ IngestionJobQueue.enqueue
→ IngestionWorker
→ document_loader
→ chunker
→ DocumentProcessor
→ Chroma 新 chunks 写入成功
→ 删除同 source 的旧 chunks
→ 标记 job completed
```

阅读时重点检查失败发生在写新版本之前还是之后。安全替换的关键是先写新 chunks，成功后再删除旧版本，而不是先清空旧数据。

## 01.4 第四条主线：身份到 ACL

```text
Authorization Bearer JWT
→ get_current_user
→ 每次请求刷新数据库角色/部门
→ UserContext.from_jwt_payload
→ build_acl_filter
→ Chroma metadata filter
→ check_doc_access Python 二次校验
→ 只允许可访问文档进入 Rerank/CRAG/Deep evidence
```

JWT 证明“谁登录了”，数据库决定“他现在有什么权限”。二者不能混成一个概念。

## 01.6 状态与存储地图

| 数据 | 存储 | 生命周期 |
|---|---|---|
| 原始知识文件 | `data/knowledge/` | 管理员上传到删除 |
| 检索 chunks/metadata | Chroma `lab_knowledge` | 入库、替换、清理 |
| 入库任务 | `data/ingestion_queue.db` | pending 到 completed/failed |
| 用户、会话、消息、反馈 | SQLite | 账号/会话生命周期 |
| 科研项目、成员、实验、待办 | `data/research_workspace.db` | 项目生命周期 |
| LangGraph state | MemorySaver 或 AsyncSqliteSaver | thread 生命周期 |
| Mem0 长期记忆 | 可选外部/本地实现 | 用户级跨会话 |
| 检索评分缓存 | Redis 可选、内存降级 | TTL/进程生命周期 |

SQLite 并不是一个数据库保存所有事情，而是按职责分离多个轻量库；Chroma 只承担向量检索与 chunk metadata，不承担用户和任务事务。

## 01.7 生产代码与兼容代码

存在文件不等于生产链路正在调用。以下是常见误读：

- `supervisor.py`：保留兼容，不在编译后的生产图。
- `parallel_executor.py`：保留历史并行执行代码，不在当前主链。
- `knowledge_agent_node()`：旧 ReAct 实现，生产走 `retrieval_agent_node()` 和 `generation_agent_node()`。
- Planner 的旧 Execute Plan / `Send` 辅助函数：保留导入兼容，生产图不注册。

判断真实架构的最终依据是 `create_multi_agent_graph()` 注册了哪些 node 和 edge，而不是仓库里有哪些类名。

## 01.8 推荐断点与日志点

排查一次回答时，优先观察：

1. `ChatService` 构建的 `thread_id`、`research_mode` 和 `user_context`。
2. Planner 输出 `_quick_agent`、`is_complex`、`needs_expansion`。
3. Retrieval 输出 `retrieval_decision`、平均分、rewrite history、doc source。
4. ACL 前后候选数量以及被拒绝的元数据原因。
5. Deep trace 中每阶段输入输出数量、延迟和 token。
6. SSE 中事件类型是否只包含 progress、answer、sources、done/error。

日志不能记录 API Key、原始密码或未脱敏的受限全文。需要诊断 ACL 时记录 source ID 和拒绝原因即可。

## 01.9 阅读源码的检验标准

读完一个模块后，至少能回答五件事：

1. 输入是什么，谁构造？
2. 输出是什么，下游谁消费？
3. 正常路径如何走？
4. 外部依赖失败如何降级？
5. 哪些测试或评测证明当前实现可用？

如果只能描述类名和框架名，还没有真正掌握实现。
