# 04 系统化排障方法

本项目最可迁移的能力是把复杂 AI 系统拆成可证伪层级。本文给出通用排障流程、观测字段和面试表达模板。

## 04.1 先定义现象

不要说“AI 不好用”，要写：

```text
输入：用户、角色、session、mode、query
期望：文档/结论/事件
实际：缺失、错误、超时或泄漏
频率：必现/偶发，哪类题
环境：commit、模型、知识库 snapshot
```

可复现描述是后续所有推理的前提。

## 04.2 请求分层

```text
L0 浏览器交互
L1 HTTP/认证
L2 ChatService/会话
L3 LangGraph 路由与状态
L4 Retrieval candidates
L5 Rerank/CRAG
L6 Generation/引用
L7 Persistence/SSE presentation
```

先确定最早出现错误的层，后层现象通常只是传播结果。

## 04.3 检索漏文档决策树

```text
目标在 corpus？
├─ 否 → missing_document / ingestion
└─ 是，当前用户允许？
   ├─ 否 → expected ACL filtering
   └─ 是，raw candidate 有？
      ├─ 否 → lexical/semantic candidate failure
      └─ 是，reranked 有？
         ├─ 否 → rerank failure
         └─ 是，final 有？
            ├─ 否 → grading failure
            └─ 是，答案引用？
               ├─ 否 → generation failure
               └─ 是 → 检索链正常
```

## 04.4 慢请求决策树

记录每阶段 elapsed：

```text
Vision
Summary/Mem0
Planner
Vector/BM25
Rerank
Grader/rewrite
Researcher/Analyst/Reviewer
Generation
SSE/persistence
```

如果 Deep calls 为 7.77、输入 token 约 12.6k，优化 RRF 的毫秒级代码不会改变 27 秒 P50。先优化占比最大的外部调用。

## 04.5 权限问题决策树

1. 当前数据库 role 是什么？
2. UserContext 是否正确传入？
3. Chroma filter 是什么？
4. BM25 合并后 Python check 是否执行？
5. Rerank request 中是否已有 forbidden content？
6. EvidencePackage/Claims/sources 哪个阶段首次出现泄漏？
7. 缓存是否跨用户复用了未过滤结果？

权限 bug 必须定位首次暴露点，不能只修最后显示。

## 04.6 SSE 问题决策树

```text
后端有 token event？
→ tag 是否 user_visible？
→ SSE frame 是否完整 JSON？
→ 网络是否拆帧？
→ 前端 placeholder index 是否有效？
→ sources 是否在 done 前缓存？
→ finally 是否误清理过早？
```

同时保存浏览器 Network 原始响应和服务器 event 日志，避免只看 DOM。

## 04.7 假设清单

面对问题先写 3–5 个互斥假设，并为每个设计最低成本检查。例如“检索不到”：

- H1 未入库 → 列 corpus titles。
- H2 ACL 拒绝 → admin/student 对照。
- H3 candidate failure → raw titles。
- H4 rerank failure → reranked titles。
- H5 grader failure → grade details。

按信息增益排序检查，不按自己最熟悉的代码排序。

## 04.8 一次只改一个变量

固定 commit、corpus、provider 和 dataset，只改 top K、权重、Prompt 或阈值之一。否则即使结果变好，也不知道原因。

AI 输出有随机性时保留 raw result 和运行时间，必要时多次重复，但正式 Holdout 不为了挑好结果反复跑。

## 04.9 负结果记录

每次实验记录：

```text
假设
改动
预声明指标
结果
为什么未合入
未来重新考虑条件
```

Named Anchor、Redis、GraphRAG 和第四 Agent 都可以作为“有条件不做”的设计记录，而不是被遗忘后重复尝试。

## 04.10 日志最小字段

```text
request/thread/session hash
user role（不记录 token）
mode / route
query 摘要
candidate source IDs
ACL reject reason
decision / rewrite count
stage latency / calls / tokens
error type
```

restricted 正文、密码、API key 和完整 JWT 不进日志。

## 04.11 修复验证

至少四步：

1. 为原问题写最小 regression。
2. 运行邻近类别，检查没有回退。
3. 运行安全/ACL gate。
4. 更新相关文档和已知边界。

仅手工重试一次成功不是验证。

## 04.12 何时停止

- 已定位为外部数据/权限预期，不需代码改动。
- 改动没有通过预声明指标。
- 修复成本远高于真实影响。
- 需要新用户选择或外部授权。
- 继续工作只是在同一 Holdout 上过拟合。

停止时写清证据、剩余风险和重新开启条件。

## 04.13 STAR 通用模板

```text
Situation：用数据规模、用户影响描述问题。
Task：说明约束，如不能增加基础设施/不能泄漏/要保持 Normal。
Action：重点讲假设、观测、最小实验、取舍，而非流水账。
Result：同时给质量、安全、延迟或减少复杂度的结果。
Reflection：说明边界和下一次会怎么验证。
```

## 04.14 白板排障表达

面试官给模糊问题时，可以先说：

> 我不会先换模型。我会先确定错误最早发生在数据、候选生成、重排、评估还是生成，并保存各层候选；如果涉及权限，还会检查数据在首次发送给外部模型前是否已经过滤。定位后只改一个变量，用回归集和安全 gate 验证。

这比背某个框架 API 更能体现系统能力。
