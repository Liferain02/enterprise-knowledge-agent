总览保留 12 个完整案例，分册进一步补充源码位置、决策树、失败边界和 STAR 表达。

面试官通常不满足于“项目用了哪些技术”，而会追问：出过什么问题，你如何证明根因，为什么选这个修复，备选方案是什么，结果怎么样，哪些问题仍未解决。本文按这个口径复盘。

## 1. 难点一：从“检索不到”定位到未入库

### 现象

Historical Blind V1 的 H08/H16 中，问题明确提到 Nu、Quicksand、Argo、AIFM，Researcher 没有返回目标论文。直觉上很容得出“命名文档检索弱”。

### 错误的第一反应

对标题词优先、增加 Named Evidence Anchor、为四篇论文加别名 query。这些做法在没有证据前都只是围绕已看失败样本调参。

### 定位方法

1. 建立 26 条 retrieval-only Development Benchmark，不跑 Analyst、Reviewer 和 Generation。
2. 分为 exact named、alias、multi evidence、temporal/version、semantic 五类。
3. 记录 raw candidates、reranked candidates、final docs、rank、Hit/Recall/MRR、rewrite history。
4. 从 Chroma snapshot 直接查 title/source 集合，与文件系统对照。

### 证据

磁盘上存在四个 PDF，但冻结的 Chroma 只有 40 chunks / 18 documents，标题和 source 集合中没有 Nu、Quicksand、Argo、AIFM。检索器不可能返回没有入索引的内容。

### 决策

归因为 `missing_document`，而不是 semantic retrieval failure。不修 Retrieval，不改 V1 数据，不将磁盘文件临时塞进 Blind 知识库。

### 结果

避免了一个针对已知案例的检索补丁。更重要的结果是建立了“文件存在 ≠ 已入库 ≠ 能召回 ≠ 进入答案”的分层故障模型。

### 面试简答

> 我没有立即改 query prompt，而是先把答案级失败降维成 retrieval-only benchmark。最后发现目标 PDF 在磁盘但不在 Chroma，根因是 ingestion/index coverage，所以保留 Retrieval，把问题归因为 missing document。

## 2. 难点二：证明“不应该做 Named Anchor”

### 问题

否定一个功能同样需要证据。只说“感觉会过度设计”不足以做工程决策。

### 对照结果

Retrieval AFTER 类别 Recall：

| 类别 | Normal | Deep Researcher |
|---|---:|---:|
| exact named | 0.500 | 0.500 |
| named alias | 0.600 | 0.600 |
| multi evidence | 0.733 | 0.867 |
| temporal/version | 0.833 | 0.933 |
| semantic | 0.800 | 0.500 |

Deep 在命名类没有提升，语义类反而更低。唯一已入库别名失败 `GAM` 在单独查询时也没能保住目标文档进最终 top-k，失败更接近候选缩减/Rerank，不是 Researcher 删了命名词。

### 决策

触发停止条件 A：开发基准没有证明这是系统性命名检索缺陷。因此不实施 Anchor。

### 反思

负结果不是“什么都没做”。它节省了后续 query 数量、token、延迟和专有规则的维护成本，并保持 Normal 对照公平。

## 3. 难点三：复杂架构很容越做越大

### 历史状况

仓库曾尝试 Supervisor、计划步骤、Send fan-out、并行 Worker 和 ReAct 知识 Agent；这些不可达兼容代码现已删除。

### 实际问题

- 普通复杂问题可能绕过统一 ACL-aware RAG。
- 每个步骤都可能产生 AIMessage，SSE 难以识别哪个是最终答案。
- 自由循环的最大调用次数和延迟难以给出硬上界。
- 错误可能来自任何 Worker、汇总或工具，归因困难。
- 小规模知识库上的质量收益没有证明值得这些成本。

### 收敛过程

1. Planner 改为唯一入口路由。
2. 普通复杂知识问题进 Query Expansion，不进 Agent fan-out。
3. 知识 Agent 拆成确定的 Retrieval → Generation。
4. Deep 只保留 Researcher、Analyst、Reviewer 三个职责，不加 Writer。
5. Reviewer 最多一次 revision，修订后进硬校验和 Generation。
6. 只有用户显式选择 Deep 才进入，默认 Normal。

### 结果

生产图比历史设计更小，但边界更强：每一阶段可单测，ACL 和引用可保护，SSE 只有一个用户可见生成源，最大 revision 可计算。

### 面试简答

> 我不把 Agent 数量当作架构成熟度。现在的生产图只有一个 Planner，Normal 走 Retrieval–Generation，Deep 才走固定三角色。我保留有独立输入输出和可评测职责的节点，删掉无法证明收益的动态协商。

## 4. 难点四：Multi-Agent 的中间输出会污染 SSE

### 问题

LangGraph 会向外发出所有 Chat Model 的 stream events。Analyst 的 JSON、Reviewer 的判定和 Final Generation 都是 LLM 输出。如果只根据 `on_chat_model_stream` 转发，前端会收到多个不同语义的答案。

### 解决

- 只给最终 Generation 调用加 `user_visible_answer` tag。
- ChatService 的 `_is_user_visible_llm_event()` 只允许该 tag 通过。
- 所有分支最后经过 deterministic Finalizer。
- 图结束后从 checkpoint 读取权威 `final_answer`，不只依赖 token 拼接。
- 对无 LLM 的确定性拒答，如果没有 collected tokens，在收尾时一次性补发。

### 为什么这是架构问题

它不是前端把字符串过滤一下就能可靠解决的问题。可见性应由生成节点的语义 tag 和统一终态协议决定，否则添加一个 Agent 就可能再次泄漏中间结果。

## 5. 难点五：ACL 不能只在回答后裁剪

### 风险

如果 restricted 文档已进入 prompt，即使最后来源卡片不显示它，模型仍可能在答案中概括其事实；trace 也可能泄露标题或摘要。因此“回答后删 sources”不是权限控制。

### 难点

Chroma where clause 擅长标量比较，但对部门/角色列表的 contains、空值语义和日期字符串比较支持有限。只用一层 filter 很容在元数据编码和回退分支中出现绕过。

### 解决

1. Chroma 候选阶段按 confidentiality 和 visibility 过滤。
2. Python `check_doc_access()` 再检查 active、密级、visibility、department/project 和 role restriction。
3. Hybrid 融合后再检查，避免 BM25 路径绕过向量 where clause。
4. Deep 初检索和 revision 补检索都再校验。
5. EvidencePackage 以 `acl_checked` 传递不可变式约束。
6. 最终 Claim validation 发现 ACL 未验证时删除全部 Claim。

### 如何测试

不只测“正常检索不返回 secret”。专项测试故意让 denied document 出现在初检索和 revision 的 pipeline 返回值中，然后扫描 EvidencePackage、Claim、Review、retrieval context、trace、sources 和 Final Answer。这是对攻击路径的测试，而不是对理想路径的测试。

### 结果与边界

anonymous、ordinary、project member、lead/authorized、non-member 与 public/project/restricted、same/other/no project 矩阵测试通过，污染标记没有出现在后续阶段。但“ACL violation=0”只能说固定矩阵与对抗样本通过，不代表经过安全认证或绝对无漏洞。

## 6. 难点六：结构化 LLM 输出并不等于稳定协议

### 现象

Qwen 在 structured output 中可能返回：

- `claim_text`、`claim_content`、`content` 而不是 `text`；
- `category` 而不是 `claim_type`；
- `reviewer_decision`、`review_result`、`status` 而不是 `decision`；
- `{status: "supported"}` 而不是字符串枚举；
- 只填 `draft_answer`，没有完整 claims。

### 解决

- Pydantic `AliasChoices` 兼容 wire field；
- field validator 拆解被对象包装的枚举；
- `_normalize_analysis()` 统一 claim IDs、source IDs 和语义类型；
- `draft_answer` 降级时只提取真实 `[Sx]` 引用的句子；
- 解析失败时返回保守报告，不让未验证文本直接进 Final。

### 原则

兼容应该针对“模型通用 wire format 波动”，不应针对某个评测 case 内容写关键词补丁。前者修复协议，后者污染评测。

## 7. 难点七：Reviewer 把普通问题强行前提化

### 现象

普通“比较 A 和 B”、“给出建议”、“判断两份材料是冲突还是互补”偶尔被 Reviewer 解释成“问题前提不成立”，Generation 就在答案顶部加上多余的前提核验。

### 为什么不能靠 Prompt 一句话完全解决

LLM 对“判断”、“冲突”、“是否”的理解不稳定。如果把产品协议完全交给模型，同一类问题可能随采样波动。

### 解决

1. 协议从三态扩为四态，加 `not_applicable`。
2. `_is_premise_task()` 只识别明确验证可判真命题的任务形式。
3. 对非 premise 任务，程序强制清空 premise sources、false flag 和 false-premise items。
4. Generation context 只在 premise 不是 not applicable 时写入前提结论。
5. 增加普通比较/总结/建议的边界测试。

### 重要限制

这个修复只解决“什么时候不该做 premise assessment”，没有解决“真正 premise task 能否判对”。Blind V2 中 Deep premise 只有 0.167，这是必须主动承认的能力缺口。

## 8. 难点八：评测器本身也可能错

### 现象

前提指标曾经通过搜索整个答案中的“证据不足”等表达判定结论。但一个答案可能顶部明确说“前提成立”，后文只是说某个局部细节证据不足。全文关键词会把它判错。

### 修复

Evaluator 只读取显式的“前提核验”结论行，不让正文局部表达覆盖主判断。然后重算 Development Eval。

### 结果

修正 metric 后 Deep premise 仍落后。所以结论从“可能是 evaluator bug”更新为“评测器曾有问题，但能力限制也真实存在”。

### 面试价值

评测不是裁判项目的绝对真理，也是代码，同样需要单测、反例和 scope audit。当指标异常时，既不应立刻否认模型，也不应立刻否认指标；应先构造最小反例审计 evaluator。

## 9. 难点九：评测污染与冻结顺序

### 问题

V1 的 H06/H07/H08/H16 已被实现者查看。任何针对这些失败的修复再回到同一数据集上测，都不能叫新的 blind generalization。

### 方法

1. 将 V1 六个核心文件永久冻结为 Historical Blind V1 / Regression after inspection。
2. 所有修复只在 retrieval Development 和 41 条 Development Eval 上迭代。
3. 在看到 V2 数据和结果前写生产 gate。
4. 跑 272 条测试和前端 build。
5. 生成源码、配置、知识库 snapshot 的 SHA-256 冻结清单。
6. 冻结后才创建 26 条 Blind V2。
7. 只运行一次 B/C，产物存在时 runner 拒绝覆盖。
8. 生成候选甲/乙的 label-blind packet 和独立密封映射。
9. Codex 不打开映射，不担任最终人工评分者。

### 边界

因原始 Deep 答案有明显 Research Brief 风格，即使去掉固定标题，评分者仍可能通过文风猜到系统。因此这只能称 `label-blind but potentially style-identifiable`，不能称 double blind。

## 10. 难点十：质量收益与成本取舍

### 数据

Blind V2：

| 指标 | Normal | Deep |
|---|---:|---:|
| 文档召回 | 0.679 | 0.811 |
| 引用覆盖 | 0.507 | 0.727 |
| conflict | 0.923 | 1.000 |
| premise | 0.667 | 0.167 |
| P50/P95 | 6.6s/9.1s | 27.5s/33.0s |
| calls | 2.00 | 7.77 |
| input/output tokens | 2071/367 | 12590/2304 |

### 决策

- 不用平均召回提升掩盖 premise safety gate 失败。
- 不将 Deep 默认开启，不自动路由。
- 前端显示“多阶段证据分析，耗时更长”，让用户明确选择成本。
- 在独立人工 V2 评分完成前不扩大产品声明。

### 如果人工评分仍不支持呢

关闭 `DEEP_RESEARCH_ENABLED`，Normal 继续服务，Deep 作为可复现实验保留。已经投入很多代码不是继续上线的理由，这是避免 sunk cost fallacy。

## 11. 难点十一：服务器无直接网络与可选 Redis

### 环境约束

服务器对外网访问需要 `set_proxy` 或端口转发。前端/后端还需与其他项目避免端口冲突，因此本项目使用 3000/8010，而不是默认 5173/8000。

### 决策

- 对话、Embedding 和 Rerank 均通过可配置提供商调用，当前选 Qwen。
- Rerank 不可用时降级原检索排序。
- Redis 不作为核心依赖；配置为 disabled 时使用进程内缓存。
- 一键启动脚本固定端口、检查环境和日志，SSH 访问文档区分 `-L` 和 `-R`。

### 反思

基础设施应根据规模和故障模型引入。当前没有多实例共享缓存、分布式锁或高 QPS 证据，为简历加 Redis 只会增加启动故障和运维面。

## 12. 难点十二：长对话与记忆不能侵入主路径

### 问题

长对话不断将全部消息发给 LLM 会增加 token、延迟和无关干扰；但强制依赖长期记忆服务会增加新的可用性问题。

### 解决

- `maybe_summarize_node()` 只在可见 user/assistant 消息超阈值时触发。
- 只保留最近 N 条，旧对话滚动压缩到 300 字左右。
- 工具和内部 Agent 消息不进用户语义摘要。
- Mem0 默认开启，搜索或保存失败返回空并继续，不阻塞主链。
- Mem0 保存由 ChatService 在回答后异步调度，不延长用户主响应。

## 13. 可复用的故障定位框架

遇到任意 RAG/Agent 错误时，可以按以下顺序：

```text
1. 产品输入是否明确？
2. 目标文档是否真的入库？
3. ACL 是否允许当前用户看？
4. 目标 chunk 是否进 raw candidates？
5. 是否在 RRF/Rerank/Grade 中被丢弃？
6. Researcher 是否得到 Evidence？
7. Analyst 是否将 Evidence 转成 Claim？
8. Reviewer 是否错误删除？
9. Generation 是否漏写 validated Claim？
10. Evaluator 是否在测真正需要的内容？
```

这个顺序将“调 Prompt”放在事实证据之后，避免用模型语言去掩盖入库、ACL 和候选管道问题。

## 14. STAR 故事模板

### 14.1 H08/H16 归因

- S：明确命名论文在 Blind 问题中漏召回。
- T：判断是 query planning、semantic retrieval、rerank 还是知识缺口。
- A：构建 26 条 retrieval-only 基准，检查 Chroma snapshot 和全候选链。
- R：证明四个 PDF 未入索引，放弃 Named Anchor，避免污染 Blind 和增加无效复杂度。

### 14.2 ACL 全生命周期

- S：多 Agent 中即使 Retriever 过滤正常，补检索、trace 或 Claim 仍可能泄漏。
- T：建立不依赖某一节点的权限 invariant。
- A：Chroma + Python 双层 ACL，初检索/revision 复检，最终 Claim 校验，对抗注入 denied document 并扫描所有阶段。
- R：固定矩阵 7 项测试通过，ACL violation=0，并把权限从 filter 提升为 Evidence Lifecycle Invariant。

### 14.3 停止默认 Multi-Agent

- S：Deep 提高召回和引用，但延迟和 premise 异常。
- T：不用单一平均分决定上线，给出可审计产品决策。
- A：预声明 gate，冻结实现后新建 Blind V2，报告 Recall、Premise、P50/P95、calls/tokens，不自己做最终人工 Judge。
- R：保持 Normal default、Deep explicit，不自动路由，并把独立盲评列为外部收尾而不是继续调参。
