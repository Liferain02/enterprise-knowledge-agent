# 01 项目全景与架构讲解

本分区建议按顺序阅读：本文建立项目主线；[02 请求全链路与时序](02-请求全链路与时序.md)跟踪真实执行顺序；[03 技术选型与架构决策](03-技术选型与架构决策.md)解释替代方案与停止条件。

本文的目标是让候选人能用不同时长讲清项目，并能在面试官追问时从产品定位自然下钻到源码、数据、评测和取舍。

## 1. 一句话定位

> 这是一个面向计算机专业研究生实验室的可信知识与科研协作助手：用 ACL-aware Hybrid RAG 回答制度、项目、论文、实验和组会问题，强制证据引用和权限隔离；另提供一个用户显式选择的有界 Deep Research 模式，通过冻结评测验证收益和成本，而不是盲目追求更多 Agent。

## 2. 三种介绍版本

### 2.1 30 秒版

“我做了一个实验室内部知识助手。它把文档入库、Hybrid Retrieval、Qwen Rerank、ACL、引用、SSE 和评测连成完整链路，并实验了 Researcher–Analyst–Reviewer 的显式 Deep 模式。评测后我删除了无依据的自适应权重和不可达 Agent，默认关闭收益不稳定的 CRAG；Deep 仍因成本高保持显式入口。”

### 2.2 2 分钟版

“项目解决三个真实问题。第一，实验室资料分散在制度、论文笔记、实验记录和组会纪要里，普通关键词搜索难以综合。第二，内部资料有 public、project、restricted 权限，不能在生成后才裁剪。第三，RAG 和 Multi-Agent 很容易只看 Demo，不知道错在入库、检索、重排、分析还是生成。

我用 FastAPI + LangGraph + Vue 做了完整链路。文档异步入库后按 token 切块，写入 Chroma；检索同时跑向量和 BM25，用 RRF 融合，再用 Qwen `gte-rerank-v2` 精排。ACL 在候选、Python 结果、Graph 终态和 API 来源卡多层检查，Deep 里还验证被拒文档不能进入 EvidencePackage、Claim、Review、Trace 和答案。CRAG 作为第五路消融保留，但因收益不稳定默认关闭。

Normal 是默认链路。Deep 只有用户显式点选才会进入 Researcher、Analyst、Reviewer，且 Reviewer 最多只能促发一次修订。我建了 retrieval-only Development Benchmark、41 条答案级 Development Eval，冻结代码后再创建 26 条 Blind V2。结果显示 Deep 召回 0.811 高于 Normal 0.679，但 premise 只有 0.167，且 P50 约 27.5 秒，所以没有自动上线替换 Normal。”

### 2.3 5 分钟版结构

1. 30 秒：场景与问题。
2. 60 秒：文档入库和 Hybrid RAG。
3. 45 秒：权限与证据引用。
4. 60 秒：Normal 与显式 Deep 架构。
5. 60 秒：评测体系与两个关键反例。
6. 45 秒：成本、不足和为什么停止。

五分钟版不应穷举 API。主线是：“可信证据链 → 复杂架构假设 → 分层评测 → 用反证限制产品”。

## 3. 场景、用户和问题

### 3.1 目标用户

- 新入组研究生：查环境、规范、方向和 FAQ。
- 项目成员：查本项目实验、会议、阶段结论和待办。
- 高年级成员/教师：跨时间对比多份材料，排查冲突和证据缺口。
- 资料管理者：上传、去重、追踪入库任务、管理可见范围。

### 3.2 典型问题

| 问题 | 风险 | 对应设计 |
|---|---|---|
| “集群环境如何配置？” | 凭通用经验回答错内部细节 | 无证据则拒答，有证据强制 `[\u6587\u6863N]` |
| “比较两个项目的实验进展” | 单 query 只召回一侧 | Query Expansion 和 RRF |
| “最新计划与旧纪要是否冲突？” | 时间和版本语义丢失 | 时间元数据、冲突提示、Deep 多证据综合 |
| “某受限项目的未发布结果是什么？” | 越权证据进入 prompt 或答案 | JWT 授权刷新 + ACL 双层过滤 + 全阶段 invariant |
| “是否可以认为所有成员都无需预约？” | 问题带有可能错误的前提 | premise 四态协议，并用评测监测真实局限 |

## 4. 项目边界

项目做的：

- PDF、DOCX、Markdown、TXT 资料入库；
- 元数据、切块、Embedding、Chroma 持久化；
- BM25 + 向量混合检索、RRF、Rerank、CRAG；
- JWT、RBAC、文档密级/可见性/项目限制；
- Normal 问答、显式 Deep Research、SSE 流式输出；
- 会话、来源卡片、资料目录、反馈和科研项目样例；
- 分层自动评测、冻结和 label-blind 人工评分包。

项目没有证明的：

- 大规模企业租户和高并发；
- 百万/亿级向量运维；
- 真实公司的安全合规认证；
- Deep 在最终答案质量上全局优于 Normal；
- 不依赖领域数据的普适 Agent 框架。

## 5. 总体架构

```text
Vue 3 / TypeScript
  │  JWT + fetch SSE
  ▼
FastAPI Controller
  │  Pydantic 校验 + 当前用户授权刷新
  ▼
ChatService
  │  session 隔离 + AgentState + SSE 事件过滤
  ▼
maybe_summarize → optional Mem0 retrieval → Planner
  │
  ├─ General Agent
  ├─ Operation Agent
  ├─ Normal: ACL-aware CRAG Retrieval → Generation
  └─ explicit Deep: Researcher → Analyst → Reviewer
                    └─ at most one Revision
                    → existing Generation
  ▼
deterministic Finalizer
  │
  ├─ SSE token/thinking/sources/used_agent/version/done
  ├─ SQLite session persistence
  └─ background optional Mem0 save
```

### 5.1 数据平面

```text
上传文件
 → 格式/大小/文件名检查
 → SHA-256 内容去重
 → SQLite IngestionJobQueue
 → Worker 解析和切块
 → metadata 归一
 → Qwen text-embedding-v2
 → Chroma lab_knowledge
```

### 5.2 控制平面

- FastAPI 管理请求和身份。
- LangGraph 管理节点顺序和有界分支。
- `AgentState` 作为节点之间的显式协议。
- SQLite checkpointer 保存图状态，业务会话另存 SQLite。
- 配置由 Pydantic Settings 统一解析和安全校验。

## 6. Normal 请求的完整链路

### 6.1 前端发起

`frontend/src/App.vue` 在 `sendMessage()` 中捕获当前 `researchMode`，立即将 UI 复位为 `normal`，然后请求 `/api/v1/chat/stream`。这实现了“只对当前一次请求生效”，不会在后续简单问题中意外继续 Deep。

### 6.2 认证与请求模型

`ChatStreamRequest` 将 `research_mode` 限定为 `normal | deep`，默认 `normal`。`get_current_user()` 验证 JWT 后不盲信 token 中的旧角色，而是从用户数据库刷新 role 和 department，减少角色已变更但旧 token 仍继续授权的问题。

### 6.3 ChatService 进入图

`ChatService.achat_stream()`：

1. 使用 `user_id + session_id` 生成 LangGraph `thread_id`，隔离不同用户的同名会话。
2. 先输出 `user_profile`，让界面展示当前权限。
3. 构建只包含当前 HumanMessage、会话、用户和 research mode 的初始 state。
4. 订阅 `graph.astream_events(version="v2")`。
5. 只把标记为 `user_visible_answer` 的 LLM token 发给用户，避免 Planner、Analyst、Reviewer 中间输出混入最终答案。
6. 图结束后从 checkpoint 读取 `final_answer`、`retrieved_docs`、`used_agent` 和 `version_source`。
7. 保存会话，首轮生成确定性标题，最后发送 `sources`、`used_agent`、`version_source`、`done`。

### 6.4 摘要与可选长期记忆

`maybe_summarize_node()` 只在可见对话超过阈值时压缩旧消息，忽略工具和内部消息。`retrieve_mem0_memories_node()` 受配置控制，当前 Mem0 默认开启；即使 Mem0 故障也返回空记忆继续，不得阻塞知识问答。

### 6.5 Planner 单一路由

`planner_node()` 用窄规则判断问候、时间、计算、列举、比较等类型，完全不调用 LLM。普通复杂知识问题仍进 Normal Retrieval，只设置 `needs_expansion=True`。

`route_from_planner()` 是唯一路由函数。它仅在请求已显式带 `research_mode=deep` 时进 Researcher，不实现第二套“自动判断复杂问题后升级”逻辑。

### 6.6 Retrieval 与 Generation 分离

`retrieval_agent_node()` 默认调用 ACL Hybrid + Rerank，只写入文档、检索历史、冲突和版本信息；显式 CRAG 实验才附带评级。`generation_agent_node()` 只消费已检索上下文。这比让 ReAct Agent 自由决定是否检索更容易测试、归因和保证 ACL。

`NO_RESULTS` 不调用模型编造答案，而是确定性返回“知识库没有相关文档”。有证据时，Generation Prompt 把检索文本声明为不可信数据，防止文档内容覆盖系统指令，并要求 `[\u6587\u6863N]` 就近引用。

## 7. Deep 请求的完整链路

### 7.1 Researcher

- 最多 4 个 subquestions。
- 每个子问题复用同一个 ACL-aware Hybrid + Rerank 入口，不建第二套检索器。
- 最多保留 12 条 Evidence，每条摘录最多 800 字符。
- 用 `source + 正文前缀` 去重，按分数排序。
- 每条文档在进 EvidencePackage 前再执行 `check_doc_access()`。
- 保留 missing subquestions、conflicts、query decision、rewrite history 和 returned titles。

### 7.2 Analyst

Analyst 只读 EvidencePackage，不能检索。它输出 fact、comparison、inference、recommendation 四种 Claim，每条必须绑定实际 S 编号。确定性归一会：

- 移除不存在的 source ID；
- 将模型误放入 Claim 的 limitation 移到 limitations；
- 按通用语义把“建议”、“推断”从 fact 修正为对应类型；
- 记录哪些 Evidence 没有进入任何 Claim。

### 7.3 Reviewer

Reviewer 输出 `PASS | REVISE | NEED_MORE_EVIDENCE`，检查 Claim–Evidence 对齐、冲突、ACL 和 premise。LLM 审查外还有确定性校验：不存在的 S 编号和无引用 Claim 不能被 PASS 放行。

Premise 使用四态：

```text
not_applicable  普通比较/总结/建议
supported       证据直接支持可判真前提
unsupported     证据直接反驳
insufficient    既不支持也不反驳
```

`_is_premise_task()` 判断任务形式，不判断真假。对非 premise 任务，即使模型误报 unsupported，程序也会强制归一为 `not_applicable`。

### 7.4 一次 Revision

Reviewer 要求 `REVISE` 时只重写 Analysis；`NEED_MORE_EVIDENCE` 时最多再检索 2 条 targeted query。修订后不再回 Reviewer，而是执行确定性 `_validate_claims_for_finalization()`，删除无合法引用的 Claim。

这个取舍不是认为一次修订一定最优，而是在当前数据和延迟下给成本设定硬上界。

### 7.5 复用 Generation

Deep 没有 Writer Agent。`deep_research_generation_node()` 先应用 Reviewer 否决，将 S1..Sn 稳定映射为文档1..n，构建已验证 Claim Map，然后复用 `generation_agent_node()`。这样 SSE、引用和来源卡片无需第二套代码。

## 8. 技术栈与选型理由

| 层 | 当前实现 | 选型理由 |
|---|---|---|
| 前端 | Vue 3 + TypeScript + Vite | 快速实现 SSE、来源卡片和管理页，生产构建有类型校验 |
| API | FastAPI + Pydantic | async 适合 LLM/SSE I/O，请求协议可显式限定 |
| 编排 | LangGraph | 将阶段、分支、checkpoint 和一次 revision 显式化 |
| 主 LLM | Qwen `qwen3.5-flash` | 当前可用网络/配置下的稳定选择 |
| Embedding | Qwen `text-embedding-v2` | 与 Chat 模型独立配置，避免 OpenAI-compatible 端点不提供 Embedding |
| Rerank | Qwen `gte-rerank-v2` | 语义精排，失败时保留原排序降级 |
| 向量库 | Chroma PersistentClient | 适合当前单机实验室规模，运维简单 |
| 关键词 | bm25s，rank_bm25 备用 | 补充专有名词、配置名和缩写召回 |
| 业务存储 | 职责分离的 SQLite | 规模较小，不为展示分布式能力引入维护成本 |
| 缓存 | 进程内，Redis 可选 | 服务器网络和产品规模不支持强制增加 Redis |

## 9. 产品决策

```text
Normal             默认
Deep               显式 opt-in
Automatic routing  false
Fourth Agent       no
```

这个决策来自评测而不是个人偏好。Blind V2 自动结果中，Deep 提高了文档召回和引用覆盖，但 premise 从 0.667 降到 0.167，P50 从 6.6 秒增到 27.5 秒。因此不能用一个平均指标隐藏安全子项和成本。

## 10. 项目亮点

### 10.1 证据生命周期

很多 RAG 项目只展示“检索出了几段文本”。本项目把证据从候选、ACL、Rerank、Grade、EvidencePackage、Claim、Review 到 Final Citation 串成可追踪生命周期。

### 10.2 评测驱动的架构删减

项目曾存在 Supervisor、Send fan-out 和自由 ReAct 的历史代码，但当评测显示成本高、ACL 边界难保证时，生产图收敛为 Planner 单路由和固定三角色。亮点不是“会搭复杂图”，而是“会根据证据删图”。

### 10.3 Failure Attribution

最终答案不好时，系统不再统一归因为“大模型不行”。Runtime 有 retrieval / analysis / review / generation / knowledge_gap / acl / none，retrieval-only 评测还细分 query planning、semantic、rerank、missing document 等类型。

### 10.4 负结果也作为产出

Named Evidence Anchor 没有实现，因为开发基准不支持它。Deep 没有设为默认，因为 premise 和成本不达标。能够展示“为什么没做”是比功能数量更重要的工程判断。

## 11. 项目不足

1. 知识库规模小，不足以验证横向扩展、分片和高并发。
2. Blind V2 独立人工评分未完成。
3. Deep premise 能力不稳定，已违反预声明 safety gate。
4. 自动 citation support 是词汇覆盖 proxy，不是语义蕴含或事实正确率。
5. 文件在磁盘上不等于已入索引，H08/H16 证明入库完整性仍需运维关注。
6. SQLite 和单机 Chroma 符合当前规模，但不是多实例生产方案。
7. 项目保留一些历史兼容模块，阅读代码时必须以 `create_multi_agent_graph()` 的实际注册为准。

## 12. 面试收尾

介绍项目时可以用这句话收尾：

> 这个项目对我最大的价值，不是证明 Multi-Agent 一定更好，而是学会把检索、权限、证据、评审、生成和评测拆成可验证的协议，再用失败数据决定哪些复杂度应该保留，哪些应该停止。
