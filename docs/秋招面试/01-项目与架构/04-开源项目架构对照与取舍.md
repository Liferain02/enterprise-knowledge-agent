# 04 开源项目架构对照与取舍

## 04.1 对照目的

本项目是实验室科研智能助手，不是通用 Agent Harness，也不是面向互联网全域搜索的自动研究
产品。参考开源项目的目的，是检查当前请求链、证据链和评测边界是否合理，而不是复制其代码量、
插件数量或 Agent 数量。

当前最值得保留的主线是：

```text
实验室问题
  → 显式 Normal / Deep 选择
  → ACL 感知检索
  → 稳定证据身份与来源
  → 有界分析或直接生成
  → 最终引用重新鉴权
  → 可复现评测与失败归因
```

## 04.2 DeepSeek Harness：借边界，不借规模

DeepSeek Harness 是通用 Agent 运行时，官方架构强调 everything is a plugin，并把 session、
system prompt、tools、agent 和 agent loop 分成明确能力接口。它将 append-only typed session
event log 作为单一事实源，模型可见内容必须能从日志重建；工具注册也通过显式 schema allowlist
控制模型能够看到的字段。

参考源码：

- [DeepSeek Harness Architecture](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.md)
- [Core 与 Agent Loop](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/core.md)
- [Session 单一事实源](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/session.md)
- [Tool 执行边界](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/tools.md)
- [Subagent 是可选能力而非主循环](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/subagent.md)
- [SessionEventMap 源码](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/core/session/src/types.ts)
- [Tool Registry 与单调拒绝 Guard 源码](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/core/tools/src/index.ts)

适合本项目借鉴的只有三点：

1. **事实只有一个权威来源。** 当前用 LangGraph `AgentState` 承载请求状态，Deep 用
   `EvidencePackage → Claim → Review → Final` 传递研究证据，不再并行维护另一套 Planner 计划或
   Supervisor 私有状态。
2. **能力边界必须显式。** Normal、Deep、CRAG 实验、MCP 和记忆均由显式入口或配置决定；模型
   不能自行获得未声明能力。ACL 也不是提示词约定，而是候选、终态和 API 输出的代码约束。
   Harness 的 `ToolGuard` 只允许返回拒绝原因、不能由后续监听器重新放行，这与本项目最终引用
   再鉴权的 fail-closed 思路一致。
3. **评测状态必须有类型。** `independent_human_review_complete` 与
   `model_simulated_blind_review_complete` 已分开，防止模型评分被误报成人工证据。

不借鉴的部分：插件总线、动态加载、通用 shell/filesystem 沙箱、多种 subagent provider、后台
job engine 和 event-sourced 持久化。当前系统已有 LangGraph、SQLite 与固定业务边界，再建设一套
Harness 会形成重复基础设施。

## 04.3 Open Deep Research：借有界研究过程

LangChain Open Deep Research 将研究过程设计为可配置的 scope/research/write 路径，并提供
Deep Research Bench 评测；仓库也保留了旧 workflow 和 supervisor-researcher 多 Agent 实现，
说明不同拓扑需要通过评测比较，而不是默认“Agent 更多更强”。

参考源码：

- [Open Deep Research](https://github.com/langchain-ai/open_deep_research)
- [Deep Research from Scratch](https://github.com/langchain-ai/deep_research_from_scratch)

本项目已经采用更适合内部资料的收缩版：Researcher 只拆问题并检索实验室证据，Analyst 形成
带 source_id 的 claim，Reviewer 做三分前提判断和最多一次修订，最终复用同一个 Generation。
当前没有理由恢复 Supervisor、无限反思或自动并行研究。

## 04.4 STORM：借先组织证据、后写报告

STORM 把长报告拆成研究/提纲与写作两个阶段，并用多视角提问提高问题覆盖，最终生成带引用的
文章。它的关键价值不是模拟多少角色，而是先建立问题结构和参考资料，再进行长文写作。

参考源码：

- [Stanford STORM](https://github.com/stanford-oval/storm)

对本项目的对应关系是：Researcher 的子问题相当于轻量提纲，EvidencePackage 相当于参考资料集，
Analyst 的 claims 相当于写作前论点结构。当前 26 条模拟盲评表明 C 在多证据问题上更好，证明这层
组织有价值；但 premise 类 B 更高，也证明增加研究步骤不能替代明确的前提裁决规则。

不引入 STORM 的多视角人物模拟、长对话 mind map 或互联网搜索流水线。实验室资料规模小、ACL
严格，先把内部证据判断做对比扩大检索范围更重要。

## 04.5 RAGChecker、RAGAS 与 DeepResearchBench：借评测协议

RAGChecker 最接近本项目的下一步：它将 response 和 ground-truth answer 拆成原子 claim，再做四组
比较——回答对标准答案看正确性、标准答案对回答看完整性、回答对检索上下文看忠实度、标准答案
对检索上下文看召回归因。RAGAS 的 Faithfulness 也采用“拆 claim → 判断 context 是否蕴含 →
supported/total”的口径。DeepResearchBench 则用 RACE 评价长报告质量、FACT 评价引文正确性和
完整性；Open Deep Research 直接按该 benchmark 输出结果。

参考实现：

- [RAGChecker](https://github.com/amazon-science/RAGChecker)
- [RAGChecker claim-level 教程](https://github.com/amazon-science/RAGChecker/blob/main/tutorial/ragchecker_tutorial_en.md)
- [RAGAS Faithfulness](https://github.com/vibrantlabsai/ragas/blob/main/docs/concepts/metrics/available_metrics/faithfulness.md)
- [DeepResearchBench](https://deepresearch-bench.github.io/)
- [Open Deep Research 评测入口](https://github.com/langchain-ai/open_deep_research#-evaluation)

当前不直接安装整套包，原因不是“自己重写更厉害”，而是输入契约尚不满足：RAGChecker 需要人工
`gt_answer` 和逐题 `retrieved_context`；冻结 V2 只有 expected key points，且 Normal 没有冻结完整
context。运行环境也没有 `ragchecker`、`ragas`、`litellm`，RAGChecker 默认还要求英文 spaCy 模型，
官方只说明强多语模型“可能”支持非英文。此时强行接入会得到不可公平复现的中文分数。

最小复用路线是：V3 同时保存 Normal/Deep 的已鉴权 context；在运行前为 20～30 条核心题写标准
答案并拆 atomic claims；先按 RAGChecker 的 JSON 输入契约导出，再用现有 Qwen-compatible Judge
做 claim extraction/entailment；拿 20% 独立人工标签校准。只有输入和中文一致性达标，再决定安装
原包或保留轻量 adapter。DeepResearchBench 的 web 长报告和 URL 引文抓取与内部知识库不匹配，
只借 rubric/FACT 思路，不直接搬 benchmark。

## 04.6 对当前架构的具体结论

| 开源做法 | 当前项目对应 | 决策 |
|---|---|---|
| DeepSeek typed session / single source of truth | LangGraph AgentState + research trace | 保留单一状态链，不另建事件总线 |
| DeepSeek capability seam | 显式 Normal/Deep、CRAG 开关、ACL finalizer | 借边界，不做插件化重构 |
| DeepSeek optional subagent | 固定 Researcher–Analyst–Reviewer | 不恢复动态 subagent |
| Open Deep Research scope/research/write | 问题拆分、证据包、最终生成 | 保留有界三阶段 |
| STORM outline before writing | sub_questions + claims + citations | 保留证据组织，不增加人物模拟 |
| LLM-as-judge / 自动评测 | 模型模拟盲评 | 单独标记，不能冒充人工评审 |
| RAGChecker claim entailment | 下一版声明级正确性/完整性/忠实度 | 复用输入与指标协议，先补 gold/context |
| RAGAS Faithfulness | claim 对 context 的 supported/total | 可作实现参考，不把词汇重叠冒充该指标 |
| DeepResearchBench RACE/FACT | Research Brief rubric 与引用检查 | 借评分维度，不搬 web benchmark |

## 04.7 下一步只改失败类别

模型模拟盲评和阶段 trace 给出的优先级不是增加 Agent，而是：

1. **补声明级评测输入。** 新 V3 同时冻结两组 context 和人工 gold claims，避免继续依赖关键词
   与词汇重叠 proxy。
2. **跳过不可执行的空修订。** 冻结 V2 的 21 个 `REVISE` 中，16 个没有 rejected claim、未处理
   冲突或具体 instruction，却仍触发 Analyst。当前已加 actionability gate：没有结构化问题就归一
   为 `PASS`，不新增 Agent；下一步只在新 Development/V3 验证质量与成本。
3. **前提判断一致性。** 避免答案先写“证据不足”，后文又列出足够证据；继续用明确的
   supported/refuted/insufficient 三态契约。
4. **最小实验设计。** V221、V222 的两组候选都没有完整给出可证伪假设、单变量处理和复测判据，
   后续 Development 样本应专门覆盖实验设计质量。
5. **证据检索完整性。** 某些候选因漏掉指定文档而无法完成多证据任务，应优先归因检索覆盖，
   不用更长生成提示掩盖缺文档。
6. **回答压缩。** Deep 常有重复的事实、推断和建议。应在不损失 source_id 的前提下减少重复，
   但只能在新 Development/V3 Holdout 上验证，不能继续使用已解盲 V2 调参后声称盲测提升。

到这里应停止架构扩张。开源项目提供的是设计检查表，不是待复制的功能清单。
