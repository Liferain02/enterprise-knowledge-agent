# 02 请求全链路与时序

本文按真实运行顺序解释四条链：Normal 流式问答、Deep Research、文档入库和反馈治理。架构图只表达模块关系，时序则强调“谁先做什么、失败时谁负责收口”。

## 02.1 Normal 流式请求总时序

```text
Browser         FastAPI       ChatService       LangGraph       RAG/LLM       SQLite
  |                |               |                |               |             |
  | POST stream    |               |                |               |             |
  |--------------->| auth/schema   |                |               |             |
  |                |-------------->| prepare image  |               |             |
  |                |               | ainvoke/astream_events         |             |
  |                |               |--------------->| summarize     |             |
  |                |               |                | memory lookup |             |
  |                |               |                | planner       |             |
  |<-- thinking SSE|<--------------|<---------------|               |             |
  |                |               |                | retrieval ----------------->|
  |                |               |                | generation ---> LLM         |
  |<-- llm_token --|<--------------|<---------------| token events  |             |
  |                |               | read checkpoint|               |             |
  |                |               | save user + final answer ------------------->|
  |<-- sources SSE-|<--------------|                |               |             |
  |<-- done SSE ---|<--------------| schedule Mem0  |               |             |
```

这里有三个重要的顺序约束：

1. 流式 token 只来自带 `user_visible_answer` tag 的生成调用。
2. 图结束后读取 checkpoint，拿到最终 state。
3. 当前实现随后一次保存原始问题和最终回答，再发送 sources/done；进程在图执行中中断时，本轮问题也可能未持久化，这是简化写入的一致性取舍。

## 02.2 浏览器如何发起请求

前端 `sendMessage()` 会快照本次模式：

```typescript
const requestResearchMode = researchMode.value
researchMode.value = 'normal'
```

然后将 `requestResearchMode` 写入本次 JSON 请求。立即复位而不是响应后复位，解决两类边缘情况：

- 网络失败时，下一轮不会意外继续 Deep。
- 用户在请求进行中操作控件，也不会改变已经提交的请求语义。

请求期间 radio fieldset 被禁用，避免 UI 展示状态与后端已接收状态不一致。

## 02.3 API 入口做什么

`ChatStreamRequest` 约束：

```python
message: str
session_id: str = "default"
images: Optional[List[ImageContent]]
research_mode: Literal["normal", "deep"] = "normal"
```

FastAPI 依次完成：

1. Pydantic 类型和枚举校验。
2. OAuth2 Bearer token 解析。
3. 数据库重新加载当前 role/department。
4. Controller 将消息、会话、图片、模式和用户交给 ChatService。

Controller 不负责路由 Agent，也不拼 Prompt。它保持薄层，HTTP 错误映射和业务编排由不同层承担。

## 02.4 ChatService 构造执行上下文

如果有图片，`_prepare_message()` 先调用 Vision，将图片描述与原问题组合成文本；Vision 异常时记录 warning 并返回原文本，因此纯文本主链继续。

用户身份转换成 `UserContext` 后进入 state。线程标识使用：

```text
thread_id = user_id + "_" + session_id
```

只用 session ID 会导致两个用户碰巧使用相同会话 ID 时共享 checkpoint；只用 user ID 又会混合该用户的所有会话。复合键同时提供用户隔离与会话隔离。

初始 state 还包括：

- `messages=[HumanMessage(...)]`
- `session_id`、`user_id`、`user_context`
- `research_mode`
- Deep/检索输出的空初值

## 02.5 摘要节点

`maybe_summarize_node()` 只统计 HumanMessage 和 AIMessage，不统计 ToolMessage 或内部步骤。默认超过 20 条可见消息时触发，保留最近 6 条。

处理逻辑：

1. 找到需要保留的第一条可见消息位置。
2. 将此前 user/assistant 内容每条最多截取 300 字。
3. 将已有摘要一起交给 LLM 滚动总结，目标 300 字。
4. 返回新摘要与 `RemoveMessage` 操作。
5. LangGraph 的 message reducer 删除旧消息，保留近因上下文。

摘要不是最终事实库。它只帮助理解对话指代，知识事实仍应来自本轮 ACL 检索。

## 02.6 可选 Mem0 节点

Mem0 默认开启。每次只做一次 user-level search，最多取 5 条，再限制注入字符数。问候语跳过检索，失败返回空状态。

响应结束后的记忆写入通过后台 task 调度，只保存最近 4 条用户可见 user/assistant 消息。这样 Mem0 网络或模型延迟不会阻塞 sources 和 done 事件。

## 02.7 Planner 路由

Planner 是唯一入口路由器，结果映射为：

```text
knowledge → retrieval_agent
operation → operation_agent
general   → general_agent
explicit deep → research_agent
```

确定性规则识别问候、操作和知识问题；复杂模式只决定 Normal 中是否开启 Query Expansion，不自动切换 Deep。只有用户显式选择 Deep 才进入固定团队。

这一区分非常重要：

- `is_complex`：问题是否可能需要拆查询。
- `needs_expansion`：Normal 检索是否做多查询扩展。
- `research_mode=deep`：用户是否接受固定研究团队的成本和延迟。

## 02.8 Normal Retrieval 时序

```text
query
→ meaningful query check
→ optional Query Expansion
→ Vector candidate generation with ACL filter
→ BM25 candidate generation
→ weighted RRF merge
→ Python check_doc_access
→ Qwen Rerank
→ per-document grading
→ HIGH/MEDIUM: select usable docs
→ LOW: rewrite/decompose once and retrieve again
→ NO_RESULTS: deterministic refusal context
→ conflict detection
→ retrieval_context + source/version metadata
```

检索节点不生成答案，只写状态；生成节点不重新决定是否检索，只消费已经评估的上下文。这使检索评测、错误归因和生成提示能够独立观察。

## 02.9 Normal Generation 时序

生成 Prompt 分成：身份、摘要、可选记忆、安全边界、不可信检索内容、冲突警告、回答规则和用户问题。

检索内容被明确包在“不可信资料”边界内，文档中的指令不得覆盖系统规则。生成调用带 `user_visible_answer` tag，温度 0.3，普通回答默认上限 500 字，并要求 `[文档N]` 引用。

`retrieval_decision=no_results` 时不调用生成模型，直接返回知识库无资料提示，避免 LLM 用常识补齐内部事实。

## 02.10 SSE 事件时序

前端可能收到：

| 事件 | 内容 | 前端用途 |
|---|---|---|
| `user_profile` | 当前用户角色与权限提示 | 展示身份上下文 |
| `thinking` | 当前节点的用户友好阶段描述 | 展示进度，不当作正文 |
| `used_agent` | 最终使用的分支 | 状态标签 |
| `llm_token` | 用户可见 token/文本片段 | 增量拼接回答 |
| `tool_start/tool_end` | Operation 分支的工具状态 | 显示受限工具进度 |
| `sources` | 结构化来源卡片 | 独立展示证据 |
| `version_source` | 文档版本溯源 Markdown | 展示来源版本 |
| `error` | 可公开错误信息 | 失败提示 |
| `done` | 结束信号 | 关闭 loading |

内部 Analyst、Reviewer 或 tool call 的模型 token 没有用户可见 tag，因此不会被当成最终正文发送。

## 02.11 Deep Research 时序

```text
explicit deep
→ Researcher: 规划子问题、运行受 ACL 约束的检索、生成 EvidencePackage
→ Analyst: 只基于 EvidencePackage 生成 Claims
→ deterministic normalization: 修正枚举、引用与 coverage 字段
→ Reviewer: 检查证据充分性、冲突、前提和引用
→ deterministic review checks: 拒绝空/非法引用
→ if revise and count < 1:
     targeted revision retrieval + update evidence/claims
→ final claim validation
→ build Research Brief prompt
→ reuse generation_agent_node
→ generation coverage proxy + failure attribution
```

Reviewer 没有无限循环权限。最多修订一次；修订后直接进入最终确定性校验和生成。这个上限同时控制延迟、费用和图的终止性。

## 02.12 文档入库时序

```text
UploadFile
→ 编辑角色检查
→ 读取 bytes，限制最大 50 MB
→ 扩展名白名单 PDF/DOCX/MD/TXT
→ 规范化 metadata，记录 uploaded_by
→ SHA-256 内容哈希
→ 检查相同哈希的最近任务
→ 保存到知识目录
→ enqueue pending job
→ worker 原子取队列并标记 running
→ loader 提取正文
→ chunker 切分并继承 metadata
→ 为新 chunks 生成 embedding 并写 Chroma
→ 新版本成功后删除旧 source chunks
→ completed + result
```

如果 worker 异常退出，超过阈值的 running job 会被恢复为 retrying。失败在最大重试次数内继续重试，否则进入 failed 并保留错误，便于前端显示和排查。

## 02.13 反馈治理时序

```text
assistant answer
→ 用户选择 helpful / incorrect / missing_material
→ POST feedback
→ SQLite 保存问题、答案、agent、评论
→ incorrect/missing_material 进入 open issue 列表
→ reviewer 修正文档或配置
→ PATCH resolved + resolution_note + resolved_by + resolved_at
→ 必要时人工加入 regression dataset
```

系统没有自动用用户反馈微调模型，也没有自动把反馈写成评测样本。这是刻意的安全边界：低质量或恶意反馈不能未经审阅进入训练和回归资产。

## 02.14 四类失败的责任边界

| 失败 | 负责层 | 典型行为 |
|---|---|---|
| JWT 无效/用户已删除 | Security/API | 401，不进入图 |
| 没有可访问资料 | Retrieval/ACL | NO_RESULTS，不让生成猜测 |
| Reranker/Redis/Mem0/MCP 不可用 | 对应适配层 | 降级或跳过，保核心链 |
| LLM 生成失败 | Agent/ChatService | error 或稳定错误回答，SSE 最终结束 |

清晰的责任边界能防止所有异常都在最外层变成模糊的 HTTP 500。
