# 03 源码追问与白板讲解

本文提供源码面试和系统设计白板的讲解顺序。目标不是背函数，而是能从一个请求推导状态、失败和取舍。

## 03.1 十分钟源码导览

### 第 0–1 分钟：定位

> 这是实验室内部可信知识与科研协作助手，核心是带 ACL 的 Hybrid/CRAG RAG、显式有界 Deep Research 和可复现评测，不是追求 Agent 数量。

### 第 1–3 分钟：入口

打开 `ChatStreamRequest` 和 `ChatService.achat_stream()`：

- normal/deep 枚举；
- current user 转 UserContext；
- thread ID=user+session；
- initial state；
- `astream_events` 与 visible tag；
- 图结束读取 checkpoint。

### 第 3–5 分钟：生产图

打开 `create_multi_agent_graph()`，指出唯一 Planner、Normal 两节点、Deep 三角色+一次修订和统一 Finalizer。明确 Supervisor 兼容文件不在图中。

### 第 5–7 分钟：RAG

打开 `retrieval_agent_node()` 和 `CorrectiveRAGPipeline.retrieve()`：Vector/BM25、RRF、ACL before Rerank、Qwen Rerank、Grade/rewrite/no-results，以及 Retrieval 与 Generation 分离。

### 第 7–9 分钟：Deep

展示 EvidencePackage、Claim、ReviewReport 和 final claim validator，强调 structured output 后仍有确定性校验。

### 第 9–10 分钟：评测决策

给出 V2 召回、premise、P50 和 token 对照，说明为何 Normal 默认、Deep opt-in、没有第四 Agent。

## 03.2 白板一：系统总架构

```text
控制平面：Browser → FastAPI/Auth → ChatService → LangGraph → SSE
数据平面：Files → Queue/Loader/Chunker → Embedding/Chroma/BM25
                                   ↑ ACL/metadata/version
```

再补 SQLite：users/sessions/feedback/research/jobs，以及可选外部 Qwen/Mem0/MCP。不要一上来画十几个 Agent，会丢失数据和安全主线。

## 03.3 白板二：Normal 状态流

```text
HumanMessage
→ summary/memory
→ route
→ docs + decision + conflicts
→ retrieval_context
→ final_answer + sources
→ Finalizer/checkpoint
→ SSE + session DB
```

在箭头旁写主要 state key，体现你理解 LangGraph 是状态协议而不只是流程图。

## 03.4 白板三：ACL 生命周期

```text
JWT identity
→ DB refresh role
→ UserContext
→ Chroma confidentiality/visibility filter
→ BM25 merge
→ Python active/confidentiality/visibility/dept/role check
→ Rerank/Grader
→ EvidencePackage acl_checked
→ Claim source ID validation
→ final sources
```

强调过滤必须在外部 Rerank/LLM 前完成。

## 03.5 白板四：Deep 证据生命周期

```text
Q
→ up to 4 subquestions
→ up to 12 EvidenceItems (S IDs)
→ up to 12 typed Claims (C IDs)
→ ReviewReport
→ 0/1 targeted revision
→ deterministic validated Claims
→ Research Brief
```

在旁边写预算 4/2/12/800/1，体现终止和成本控制。

## 03.6 白板五：评测设计

```text
Development retrieval-only
→ Development answer-level
→ freeze code/config/corpus/gates
→ Blind V2 auto proxies
→ label-blind human packet
→ human review pending
→ V2 becomes regression after inspection
```

再画指标四象限：质量、证据、安全、成本。

## 03.7 为何图结束后读 state？

流事件只提供 token 和生命周期，业务 state 的 docs、agent、version、trace 不一定出现在 token 中。`aget_state().values` 才是完整终态，也可能包含确定性修正后的 final answer。

## 03.8 为何不把 docs 原样发给前端？

ChatService 构建白名单 source cards，只暴露需要的 title/snippet/metadata，限制数量和片段长度；避免泄漏任意内部 metadata 或服务器路径。

## 03.9 为什么 BM25 后还检查 ACL？

BM25 是内存索引，不使用 Chroma where。它与向量结果融合后如果不再检查，会把 restricted 内容发送给 Rerank/Grader，即使最终答案删除也已经泄漏。

## 03.10 为什么 RRF 的 K 是 60？

60 是经典且稳定的平滑常数，使排名差一位的贡献变化不过度剧烈。它不是通过当前 26 题过拟合得到；项目重点是跨分数量纲稳健，而不是声称 60 全局最优。

## 03.11 Rerank 与 Grader 有何区别？

Rerank 对候选做相对排序；Grader 对每篇给相关等级并决定使用、纠错或拒答。前者回答“谁更相关”，后者回答“是否足够相关”。先 Rerank 可减少 Grader 成本。

## 03.12 为什么不用模型自动判断权限？

权限是确定性安全规则，模型输出不稳定，也会先看到敏感正文。ACL 必须由程序在检索和外部调用前执行，LLM 只得到已授权内容。

## 03.13 为什么 structured output 之后还校验？

JSON schema 能保证字段形状，不能保证 source ID 存在、Claim 有证据、类型语义正确。程序可以确定检查的规则不应交给概率模型。

## 03.14 为什么 Revision 后不再 Reviewer？

为了固定上限。第二次 Reviewer 可能再次要求修订形成循环；当前用 final deterministic validator 保证引用不变量。代价是修订后的语义质量没有第二次独立模型审查，这是已知限制。

## 03.15 为什么不并行四个子查询？

并行可降延迟，但会增加瞬时请求、触发限流，并让 trace/费用控制复杂。当前 V2 延迟说明值得研究，但应先用 Development 对照有限并发，而不是直接修改正式路径。

## 03.16 如何优化 27 秒 Deep 延迟？

1. 减少或有限并行 Researcher queries。
2. 缓存重复 retrieval/grading。
3. 限制 evidence/Prompt 字符。
4. 对简单类别跳过不必要阶段，但仍需用户显式 Deep。
5. 不通过删除安全校验换速度。

先采 per-stage latency，再决定，不优化 RRF 的微秒代码。

## 03.17 如果知识库变成百万文档？

当前方案需要演进：BM25 内存全量索引迁移搜索服务；Chroma 评估分片/多租户；SQLite 换 PostgreSQL/队列；缓存与 worker 分布式；ACL filter 数据建模；负载和恢复演练。

但这属于扩展方案，当前没有做过百万级验证，不能包装成已具备。

## 03.18 如果面试官要求 GraphRAG

先建立多跳关系 benchmark。如果当前失败能归因于实体关系连接，再做实体/关系抽取和图检索 A/B；当前 40 chunks 的主要失败是 missing document、rerank 和 premise，直接上 GraphRAG 会改变太多变量。

## 03.19 如果问 Redis

核心不依赖 Redis。入库用 SQLite 队列，grade cache Redis 可选且内存降级。多实例共享缓存或高吞吐任务成为真实需求时再引入，服务器受限网络下不把它设为启动前置条件。

## 03.20 如果问项目最大不足

建议主动答三个：

1. 数据规模小，缺大规模并发和长期运行证据。
2. V2 人工盲评未完成，Deep premise 自动 gate 失败。
3. 前端 SSE 解析缺跨 chunk buffer，取消也未传播后端 task。

随后说明下一步优先级，而不是用“时间有限”含糊带过。

## 03.21 如果问个人贡献

只说自己真实完成的：架构收敛、RAG/ACL/Deep 协议、入库、评测或文档。不要把框架/开源库能力全部说成自己实现。

可以区分“基于 LangGraph 编排”与“我设计 state/edge/budget”，“基于 Qwen API”与“我实现降级、ACL 和评测”。

## 03.22 一分钟白板收尾

> 这个项目的关键不是把所有问题都做成 Multi-Agent，而是将低成本 Normal 与显式 Deep 分开；证据在进入外部模型前经过 ACL，Deep 用 Evidence—Claim—Review 协议限制自由发挥；最后用冻结数据同时看质量、安全和成本。评测发现 Deep 搜证更强但 premise 和延迟退化，所以系统选择不默认上线，这个停止决策本身也是架构结果。
