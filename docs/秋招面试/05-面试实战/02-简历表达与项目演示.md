# 02 简历表达与项目演示

本文将项目转换成简历、作品集、自我介绍、现场 Demo 和行为面故事。表达原则是“技术动作 + 解决的问题 + 可验证结果 + 证据边界”，不堆砌名词。

## 1. 项目名称建议

简历中可使用：

> 实验室可信知识与科研协作助手

英文副标题可写：

> Evidence-Grounded RAG and Bounded Deep Research System

不建议只写“企业级 Multi-Agent 知识库”。“企业级”容易引出多租户、HA、高并发、分布式存储、安全合规和审计等当前没有验证的追问。

## 2. 一页简历的项目描述

### 2.1 四条版

- 设计并实现 FastAPI + LangGraph + Vue 的实验室可信知识助手，打通 PDF/DOCX/Markdown/TXT 异步入库、Chroma 持久化、SSE 问答、会话与来源溯源。
- 构建 BM25 + 向量检索、RRF 融合、Qwen `gte-rerank-v2` 精排和 CRAG 有界改写/分解链路，将 Retrieval 与 Generation 分离以支持拒答、冲突检测和失败归因。
- 将 ACL 建模为证据全生命周期 invariant：JWT 身份与实时授权分离，Chroma 候选过滤 + Python 二次校验，对抗注入验证 denied document 未进入 Evidence/Claim/Trace/Final，固定 ACL 矩阵 7 项测试通过。
- 实现 Researcher–Analyst–Reviewer 有界 Deep Research 和分层评测；冻结后 26 条 Blind V2 中 Deep 文档召回 0.811 对 Normal 0.679，但 premise 0.167 对 0.667、P50 27.5s 对 6.6s，因此保持 Normal 默认、Deep 显式 opt-in，不自动路由。

### 2.2 三条精简版

- 搭建实验室可信 RAG 系统，实现异步文档入库、BM25/向量 RRF 融合、Qwen Rerank、CRAG 纠错、引用/版本溯源与 SSE 交互。
- 设计 JWT/RBAC 与文档 public/project/restricted 双层 ACL，以对抗污染测试验证被拒证据不进入 Claim、Trace、Sources 和 Final Answer。
- 建立 retrieval-only、Development、Blind V2 和 Regression 分层评测，根据前提判断退化与 4× 延迟拒绝默认 Multi-Agent，用预声明 gate 决定产品边界。

### 2.3 只允许两条时

- 实现 FastAPI/LangGraph/Vue 的实验室可信 RAG 助手，集成异步入库、BM25+向量 RRF、Qwen Rerank、CRAG、引用溯源、SSE 和全链路 ACL。
- 实现有界 Researcher–Analyst–Reviewer 模式并建立冻结 Blind A/B；根据召回收益、premise 退化和成本数据，保持 Normal 默认且不自动路由 Deep。

## 3. 不要这样写

| 不建议 | 问题 | 更准确的表达 |
|---|---|---|
| “搭建企业级知识库” | 无大规模多租户证据 | “实验室内部可信知识助手/企业知识场景原型” |
| “多 Agent 显著提升准确率” | 无全局人工结论，premise 退化 | “自动评测提高召回/引用，但安全子项和成本未达门槛” |
| “ACL 零泄漏” | 容易被理解为绝对安全 | “固定角色矩阵和对抗污染样本中 ACL violation=0” |
| “实现高性能检索” | 没有 QPS/大数据压测 | “在冻结小规模知识库上完成延迟与质量对照” |
| “完全解决幻觉” | RAG 和引用不能完全消除幻觉 | “无证据确定性拒答，Claim/引用校验降低无依据输出” |
| “独立双盲评测” | 文风可能被猜测，人工尚未评 | “已生成 label-blind packet，独立人工评分待完成” |

## 4. 自我介绍中的项目片段

### 4.1 45 秒版

“我在大模型应用方向的一个主要项目是实验室可信知识助手。我负责从文档入库、Hybrid RAG、权限、SSE 到 Agent 评测的完整链路。我比较关注不只是把功能做出来，还要知道错在哪一层。例如我曾通过 retrieval-only benchmark 证明几个漏召回案例其实是文档未入索引，因此拒绝了针对 case 的检索补丁。我也实验了固定三角色 Deep Research，但评测发现 premise 和延迟不达标，所以没有将它设为默认。”

### 4.2 与 JobMatchTune 联动版

“我的两个项目有一条共同主线。JobMatchTune 中我在训练效果不错后发现数据和评测问题，所以停止盲目继续训练；知识库项目中我发现 Multi-Agent 召回更好，但前提判断和成本不稳定，所以不自动上线。我的主要特点是会用评测证明一个技术假设，也愿意在证据不支持时限制或停止复杂度。”

## 5. 八分钟现场 Demo

### 5.1 Demo 目标

现场不要展示所有页面。八分钟只要证明：

1. 它是可运行产品，不是 Notebook；
2. Normal 能做有来源的知识问答；
3. ACL 会改变用户可见证据；
4. Deep 是用户显式选择的有界模式；
5. 你有真实评测和负结果。

### 5.2 演示前准备

```bash
./scripts/start.sh
curl http://127.0.0.1:8010/health
```

检查：

- 前端 3000、后端 8010 未被其他项目占用；
- Qwen API 可访问，必要时已 `set_proxy`；
- 不在录屏/现场显示 `config/.env`、API Key 或管理员口令；
- 准备一个 Normal 知识问题、一个无答案问题和一个 Deep temporal/multi-evidence 问题；
- 不在现场依赖上传超大 PDF 或运行全量 Blind Eval。

### 5.3 时间线

#### 0:00～0:45：场景和边界

打开首页，用 30 秒说一句话定位，再说冻结规模只是 18 份文档/40 chunks，主动防止面试官把它误解为大规模平台。

#### 0:45～2:15：Normal 问答

- 保持“普通”。
- 输入一个明确内部知识问题。
- 说明 SSE 的 thinking 和 token 是两类事件。
- 展开来源卡片，对照正文 `[\u6587\u6863N]`。
- 说明 Normal 走 Hybrid → Rerank → CRAG → Generation。

#### 2:15～3:00：无证据拒答

- 输入一个知识库明确没有的内部事实。
- 展示系统不用常识编造实验室信息。
- 说明 NO_RESULTS 是 deterministic path。

#### 3:00～4:15：ACL

有两个测试账号时，展示普通用户与授权项目成员的资料目录/检索差异。如果现场账号不便准备，不冒险做伪实时 Demo，而是展示 ACL 矩阵报告和对抗注入测试代码。

#### 4:15～6:15：Deep

- 点“深度研究”，指出耗时提示。
- 输入时间冲突或多证据问题。
- 在等待期间画出 Researcher → Analyst → Reviewer → one Revision → Generation。
- 展示 Research Brief 和多来源引用。
- 立即指出 UI 已复位 Normal。

#### 6:15～7:30：评测

展示 Blind V2 表格，只讲四组数字：

```text
Recall        0.679 → 0.811
Citation      0.507 → 0.727
Premise       0.667 → 0.167
P50 latency   6.6s  → 27.5s
```

然后说产品决策：Normal default、Deep explicit、no automatic routing。

#### 7:30～8:00：收尾

“我最终不是证明多 Agent 更好，而是做出了可追踪的证据系统，并用评测证明了多 Agent 的价值边界。”

## 6. Demo 失败降级脚本

### 6.1 外部 LLM 突然不可用

- 先展示 health 中的组件状态和日志，说明是外部依赖而不是隐藏失败。
- 使用预先录制的 2～3 分钟无剪辑演示视频。
- 展示冻结的 JSON/自动报告和测试代码。
- 不将预设文本伪装成当场实时结果。

### 6.2 Deep 超时

- 不重复点击，避免并发两个高成本请求。
- 利用等待时间解释阶段和 Blind P95 33s，反而用它说明为什么 Deep 不默认。
- 超过预期后切换到冻结报告，不为现场演示临时改配置。

### 6.3 网页打不开

- 先在服务器本机 `curl 127.0.0.1:3000/8010`。
- 本机正常则检查 SSH `-L` 而不是 `-R`。
- 检查端口是 3000/8010，不是被 JobMatchTune 占用的 5173/5174/8000。
- 使用 `scripts/start.sh` 和日志，不现场手工拼多条命令。

## 7. 五个 STAR 故事

### 7.1 未入库被误当检索弱

- Situation：Blind 中明确命名论文漏召回。
- Task：找到可证明的失败阶段。
- Action：建 retrieval-only 基准，记录全候选链，对照磁盘和 Chroma snapshot。
- Result：证明四个 PDF 未入索引，放弃无证据的 Named Anchor。
- Reflection：先验证数据存在性，再调检索。

### 7.2 ACL 从 filter 变成 invariant

- Situation：Deep 多了补检索、Claim、Review 和 trace，任一层都可能泄漏。
- Task：建立证据全生命周期权限契约。
- Action：Chroma/Python 双层校验，初次/revision 复检，最终 Claim 校验，注入 denied document 对抗测试。
- Result：角色×visibility×project 矩阵通过，标记未进任何后续阶段。
- Reflection：安全属性需要故意污染路径，不能只测 happy path。

### 7.3 SSE 中间输出污染

- Situation：多 Agent 的所有 LLM stream 都可能被前端当成答案。
- Task：保证一次请求只有一个用户可见回答。
- Action：Generation tag、事件白名单、统一 Finalizer、checkpoint 权威收尾。
- Result：Normal/Deep SSE 均完整 done，中间 structured JSON 不会流向前端。
- Reflection：多 Agent 不只是 prompt 编排，还需要用户可见性协议。

### 7.4 评测器反过来欺骗实现

- Situation：premise metric 可能被正文局部“证据不足”覆盖主结论。
- Task：确认低分是 metric bug 还是真实能力问题。
- Action：将 scope 改为只读显式 premise line，增加反例并重算 Development。
- Result：指标更准确，但 Deep 仍退化，因此承认真实能力限制。
- Reflection：Evaluator 也是需要审计的代码。

### 7.5 拒绝 sunk cost

- Situation：Deep 已经有较多实现，部分指标也比 Normal 高。
- Task：决定是否默认上线。
- Action：在结果前固化安全/质量/成本 gate，完整报告负指标和调用成本。
- Result：premise gate 失败，保持 explicit only，人工无收益时允许关闭。
- Reflection：工程成功包括证明不应扩大某项技术。

## 8. 作品集页建议

一个作品集页只需要：

1. 一句话定位和真实边界。
2. 一张 Normal/Deep 架构图。
3. 一张 Evidence Lifecycle/ACL 图。
4. 一张 Blind V2 召回、premise、延迟对照图。
5. 两个失败案例：missing document 和 premise regression。
6. 一段 2～3 分钟录屏。
7. 代码、测试、评测和文档入口。

不应上传真实 API Key、口令、JWT secret、实验室敏感文档、受限回答或 sealed mapping。

## 9. 针对岗位调整重点

### RAG / 大模型应用工程师

突出 Hybrid Retrieval、CRAG、Rerank、Citation、Failure Attribution、A/B 和 Agent boundary。

### AI 平台 / 评测工程师

突出 Development/Blind/Regression、冻结 hash、gate、proxy 限制、checkpoint、trace 和负结果。

### Python 后端 / AI 应用后端

突出 FastAPI async、SSE、JWT 授权刷新、SQLite 事务、异步入库 worker、降级、会话隔离和一键启停。

### 算法工程岗

可以强调 RRF、Recall/MRR、分层归因和实验设计，但不要将项目包装成自主训练 Embedding/Reranker/LLM，因为当前使用的是现成 Qwen 模型服务。
