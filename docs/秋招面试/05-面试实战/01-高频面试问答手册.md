# 01 高频面试问答手册

同分区还包括[02 简历表达与项目演示](02-简历表达与项目演示.md)和[03 源码追问与白板讲解](03-源码追问与白板讲解.md)。建议先口答本手册，再做八分钟 Demo 和十分钟源码导览。

本文不建议逐字背诵。每题先用“简答”在 20～40 秒内直接回答，面试官继续追问时再展开“深入”。所有数字都是 2026-08-13 冻结快照，不应当作 SLA 或大规模企业结论。

## 一、项目与架构

### 1. 请用一分钟介绍项目

**简答：**这是一个面向研究生实验室的可信知识与科研协作助手。核心主链是 ACL-aware Hybrid RAG：文档入库后通过 BM25 + 向量、RRF、Qwen Rerank 和 CRAG 得到证据，然后强制引用回答。对用户显式选择的复杂问题，有 Researcher–Analyst–Reviewer 固定 Deep 模式。我用冻结评测发现 Deep 的召回和引用覆盖更高，但 premise 和延迟不达标，所以保持 Normal 默认，没有自动升级 Multi-Agent。

### 2. 这不就是一个普通的 RAG Demo 吗？

**简答：**如果只看向量检索加 Chat UI，确实是 Demo。该项目的工程重点在完整证据生命周期：持久化入库队列、混合检索和纠错、JWT 授权刷新、ACL 双层过滤、引用与版本溯源、SSE 可见性契约、阶段 trace、Failure Attribution、Development/Blind/Regression 分离和生产 gate。

**深入：**应主动承认它仍是小规模单机原型，冻结知识库只有 18 份文档和 40 chunks。它的价值是信任边界和方法论，不是虚构大规模性能。

### 3. 为什么用 LangGraph？

**简答：**因为项目需要显式的阶段、分支、checkpoint 和有界 revision，不是只串行调几个函数。LangGraph 让 `AgentState` 成为节点协议，并且可用结构图保证 Reviewer 最多修订一次。

**反问准备：**如果只有 Normal Retrieval → Generation，普通 async Python 就足够。在当前项目里 LangGraph 的主要价值来自 Deep 分支、checkpoint 和 SSE event integration，而不是为了使用流行框架。

### 4. 生产图有多少个 Agent？

**简答：**Normal 分支是 Retrieval 和 Generation 两个职责节点；Deep 有 Researcher、Analyst、Reviewer 三个角色，最终复用既有 Generation Agent。没有第四个 Deep Agent，Finalizer 是确定性节点。

### 5. 仓库里明明有 Supervisor，为什么说没有？

**简答：**架构以 `create_multi_agent_graph()` 实际注册的节点和边为准，不以文件名为准。Supervisor、Parallel Executor 和 Send 执行是历史兼容代码，没有接回生产图。

### 6. 为什么 Planner 只保留一个？

**简答：**多层路由会出现决策冲突、重复 LLM 调用和 ACL 绕过。当前 Planner 用规则优先将请求分到 knowledge/operation/general，Deep 只根据 API 显式 mode 进入。

### 7. 为什么不自动识别复杂问题进 Deep？

**简答：**因为“复杂”不等于“Deep 有稳定净收益”。Blind V2 中 Deep P50 27.5s，Normal 6.6s，Deep premise 还明显退化。用户应明确同意更高成本，系统不应悄悄升级。

### 8. 为什么 Reviewer 最多修订一次？

**简答：**无限 Reviewer–Analyst 回环会让延迟、token、Prompt drift 和最大调用数不可控。一次 revision 是当前产品成本上界。修订后不靠第二轮 LLM Review，而靠 deterministic Claim validation 守住引用和 ACL 硬边界。

### 9. 为什么没有 Writer Agent？

**简答：**既有 Generation Agent 已经处理 SSE tag、引用、用户身份和冲突信息。Deep 只需要把已验证 Claim Map 适配为它的 retrieval context。再造 Writer 会重复生成逻辑，也容易导致 Normal/Deep 引用语义不一致。

## 二、RAG 与检索

### 10. 一次 Normal Retrieval 经过哪些步骤？

**简答：**Query Expansion（条件触发）→ ACL-aware BM25/向量候选 → RRF 融合 → Qwen Rerank → CRAG batch grading → 低质量时有界改写/分解 → Python 二次 ACL → context、conflict 和 version source → Generation。

### 11. 为什么不只用向量检索？

**简答：**文档名、项目缩写、配置项和代码名对词面匹配很敏感，BM25 更稳定；用户的自然语言改写和语义问题则更适合向量。两路用 RRF 融合，避免直接比较不同分数尺度。

### 12. RRF 是什么？

**简答：**Reciprocal Rank Fusion 根据每条检索路的排名累加 `weight/(k+rank)`。当前 `k=60`。一份文档同时在 BM25 和 vector 前列出现时得分更高。优点是不依赖分数校准，缺点是只看排名而不看绝对差距。

### 13. 为什么 RRF 后还需要 Rerank？

**简答：**RRF 是候选融合，只知道两路排名，不会细粒度判断 query 与文档的语义配对。Reranker 对联合候选做更精细的 cross-encoding 排序，再让 CRAG 评少量文档，同时降低 grading 调用量。

### 14. CRAG 在项目里是什么？

**简答：**它是 Corrective RAG，不是一个新 Agent。Retrieval Grader 将文档评为高/中/低/无结果，低质量时改写 query，仍不好时可分解多 query 并融合，每条路都有最大重试上限。

### 15. Query Expansion 与 Deep Researcher 拆问有什么不同？

**简答：**Normal Query Expansion 是 Retrieval 内部技术，用多个 query 改善候选召回，最后仍由一个 Generation 直接答。Deep Researcher 也拆子问题，但它还建立 EvidencePackage，后续有 Claim Map 和 Review。Deep 的复杂度主要在证据分析和复核，不是只多发几个 query。

### 16. 知识库没结果怎么办？

**简答：**CRAG 有界改写/分解后仍 `NO_RESULTS`，Generation 不调模型自由补内部事实，而是确定性拒答并建议换关键词或联系管理员补文档。Deep 无 Evidence 或无合法 Claim 时也返回证据不足，不生成 Research Brief。

### 17. H08/H16 是怎么定位的？

**简答：**我先建 26 条 retrieval-only Development Benchmark，保存 raw/reranked/final candidates。再检查冻结 Chroma 的 title/source 集合，发现 Nu、Quicksand、Argo、AIFM 只在磁盘，不在 18 份已索引文档里。所以归因是 missing document，不是 semantic retrieval。

### 18. 为什么没有做 Named Evidence Anchor？

**简答：**因为基准没证明通用收益。exact named 和 alias 中 Deep 与 Normal 持平，semantic 反而回落。主要已知失败又是未入库。如果此时加 Anchor，只是针对已看 case 过拟合。

### 19. Reranker 不可用怎么办？

**简答：**记录警告，保留 Hybrid 原排序的 top candidates 继续 Grading/Generation。Reranker 是质量优化，不是核心可用性的单点故障。

### 20. 为什么没有换向量库或上 GraphRAG？

**简答：**当前只有 18 份文档、40 chunks，失败也没有被定位为 Chroma 规模或图关系表达问题。换基础设施会同时改变多个变量，降低评测可解释性。如果未来有大量跨文档关系问题和独立基准，才有证据重新评估。

## 三、ACL 与安全

### 21. ACL 是如何传递的？

**简答：**JWT 识别用户，每次请求从数据库刷新 role/department，构造 UserContext 进 AgentState。Retrieval 候选先按 confidentiality/visibility 做 Chroma filter，再用 Python 检查 department/project 和 role restriction。Deep 初检索和补检索都复检，后续用 `acl_checked` 和 final Claim validation 守边界。

### 22. 为什么不只用 Chroma filter？

**简答：**Chroma 适合标量 `$in` 等过滤，但部门/角色列表、空值语义和日期字符串比较不适合全部放在 where clause。而 BM25 还是一条独立候选路。所以候选前过滤用于减少暴露，Python 二次检查用于统一所有路径语义。

### 23. 为什么不在答案后删敏感字段？

**简答：**如果文档已进 prompt，敏感事实已经被模型消费，删来源卡片或关键词无法证明答案没有改写泄露。ACL 必须在证据进入 prompt 前完成。

### 24. 你如何证明 Deep 没泄密？

**简答：**我不只跑正常查询，而是在测试里故意把 denied restricted document 注入初检索和 revision 的 pipeline 结果，再扫描 EvidencePackage、Claim、Review、retrieval context、trace、source cards 和 Final Answer。固定矩阵 7 项测试通过，未发现标记泄漏。

### 25. ACL violation=0 是不是代表绝对安全？

**简答：**不代表。它只表示预定义的角色×visibility×project 矩阵和对抗污染样本中没有违规。没有经过安全认证、代码外部审计或大规模攻击面测试。

### 26. JWT 里已经有 role，为什么每次查数据库？

**简答：**JWT role 是签发时快照。如果管理员之后降权，旧 token 在过期前仍会携带旧 role。项目用 JWT 证明身份，用数据库当前值决定授权。

## 四、Deep Research

### 27. Researcher 做什么？

**简答：**把原问题最多拆为 4 个子问题，逐个复用 ACL-aware CRAG，最多形成 12 条去重证据。它输出 EvidencePackage，同时记录 missing subquestions、conflicts、query decision 和 rewrite history。

### 28. Analyst 为什么不能自己检索？

**简答：**否则“证据是什么”会在分析阶段悄悄改变，ACL、证据编号和失败归因都会失去边界。Analyst 只把 EvidencePackage 转成带 source IDs 的 Claim Map，让“找到了但没用”可单独测量。

### 29. Claim 为什么要分类？

**简答：**fact/comparison 是证据性陈述，inference/recommendation 是模型对证据的解释或后续行动。如果不区分，研究建议很容被写成知识库已确认的事实。

### 30. Reviewer 的 LLM 判断可信吗？

**简答：**不完全可信。Reviewer 适合评估语义支持、冲突和前提，但非法 source ID、空引用、ACL flag 等硬约束由程序检查。Blind V2 也证明 Reviewer 的 premise 判断仍有真实能力限制。

### 31. premise 四态是什么？

**简答：**supported 表示证据直接支持，unsupported 表示直接反驳，insufficient 表示既不支持也不反驳，not_applicable 表示用户本来就没在验证可判真命题。第四态避免普通比较/建议被强行转成前提审判。

### 32. 普通问题的多余 premise 提示解决了吗？

**简答：**解决了任务边界：非 premise 问题被程序强制归一为 not applicable，清空 false flag 和 premise sources，Generation 不加前提结论。但真正 premise task 中判 supported/unsupported/insufficient 的准确性没解决，Blind V2 只有 0.167。

### 33. 为什么 structured output 还需要归一？

**简答：**JSON schema 只降低格式波动，不能消除字段 alias、枚举包装、语义错分类和缺字段。项目用 Pydantic AliasChoices、validator 和确定性 normalization 稳定 wire protocol，再用 final validation 保护硬边界。

### 34. Deep 如何得到最终答案？

**简答：**先应用 Reviewer 明确否决，再删除无合法 source ID 的 Claim，将 S1..Sn 稳定映射为文档1..n，把已验证 Claim Map 编辑为 retrieval context，复用 Normal Generation 生成 Research Brief。

### 35. 为什么 final validated-claim coverage 只叫 proxy？

**简答：**它先看是否引用了 Claim 绑定文档，再用词和中文 bigram 重叠判断 Claim 是否被写入。这不能判断否定、因果或语义改写是否正确，所以只能做回归和归因信号。

## 五、SSE、存储与工程

### 36. SSE 如何避免中间 Agent 输出泄露？

**简答：**只有 Generation LLM 调用带 `user_visible_answer` tag，ChatService 只转发该 tag 的 token。Analyst/Reviewer 的 structured output 只写 state/trace。图结束后还用 checkpoint 的 `final_answer` 校正最终文本。

### 37. 为什么用 SSE 而不是 WebSocket？

**简答：**主链是客户端发一次 HTTP 请求、服务器单向推送 token 和状态，SSE 足够且更简单，可复用 HTTP/JWT/代理设施。项目有 WebSocket 兼容通道，但其认证边界弱于 HTTP 主链，不作高权限生产入口。

### 38. 文档入库为什么异步？

**简答：**文档解析、切块、Vision 和 Embedding 耗时不确定。上传请求只校验、持久化文件和写 SQLite job，worker 后台处理，支持 retrying、stale recovery 和任务查询。

### 39. 如何处理重复上传？

**简答：**上传时对内容计算 SHA-256，如果队列中相同 hash 已处于 pending/running/retrying/completed，直接返回已存在任务。chunk ID 也结合 file hash、index 和 content hash 稳定生成。

### 40. 更新文档怎么避免入库失败后旧文档也丢失？

**简答：**worker 先 add 新 chunks，成功后再删同 source 的 obsolete IDs。不采用先删旧版再计算 Embedding 的顺序。

### 41. 为什么用 SQLite，不用 PostgreSQL/Redis？

**简答：**当前是单机实验室原型，没有多实例写冲突或高 QPS 证据。SQLite 对用户、会话、队列、版本和项目样例足够，运维简单。Redis 是可选缓存，当服务器网络受限且不需要跨实例共享时，强制引入只会增加故障面。

### 42. 什么时候你会把 SQLite 换掉？

**简答：**当出现多实例共享业务状态、较高并发写、严格 HA/备份恢复、复杂事务或运维平台统一要求时，会将业务库迁到 PostgreSQL；当出现多实例缓存、限流、锁或任务协调需求时再引 Redis。

### 43. 长对话如何处理？

**简答：**超过阈值后将旧的用户可见对话压缩为滚动摘要，保留最近消息。工具和中间 Agent 消息不进语义摘要。Mem0 是可选能力，默认关闭，失败时不阻塞主链。

## 六、评测与结果

### 44. 为什么不只看最终答案？

**简答：**因为答案失败可以来自未入库、query planning、retrieval、rerank、ACL、analysis、review 或 generation。只看答案会导致用 Prompt 修复入库问题。我将 retrieval-only、stage trace 和 answer-level 评测分开。

### 45. Development、Blind 和 Regression 有什么区别？

**简答：**Development 可看 gold 和失败，用于调试；Blind 必须在实现和 gate 冻结后创建/运行，用于新数据证据；一旦 Blind 失败被查看并用于修复，它就变成 Regression，只能检查旧能力是否回退。

### 46. 为什么 V1 不能继续当 Blind？

**简答：**H06/H07/H08/H16 等失败已被查看。针对它们的任何修复都使开发者获得了 holdout 信息，所以再跑只是 regression after inspection。

### 47. V2 如何避免污染？

**简答：**先在 Development 上完成实现，写预声明 gate，跑全量测试/前端 build，生成源码和知识库 hash 冻结清单，再创建 26 条 V2。Runner 只允许一次正式产物，已存在时拒绝覆盖。人工包候选随机标为甲/乙，映射另存并未打开。

### 48. 最新结果是什么？

**简答：**Blind V2 中 Normal/Deep 均 26/26 成功，ACL 均0。Deep 文档召回 0.811 对 Normal 0.679，引用覆盖 0.727 对 0.507，但 premise 0.167 对 0.667。Deep P50/P95 27.5/33.0s，Normal 6.6/9.1s；调用 7.77 对 2.00，输入/输出 token 12590/2304 对 2071/367。

### 49. 这些结果证明 Deep 更好吗？

**简答：**不证明全局更好。自动评测只能证明固定数据集上的文档召回、引用形式和关键点等 proxy。Premise safety gate 已经失败，独立人工答案评分仍待完成。

### 50. 为什么不用 LLM Judge？

**简答：**本轮要验证产品最终收益，且样本只有 26×2。额外 LLM 可能偏好 Deep 的长结构化文风，与被评模型共享偏差。因此自动 proxy 用于回归，最终质量交给独立人工 label-blind 评分。

### 51. citation support 为什么只是 proxy？

**简答：**它主要检查答案句和引用文档的词汇重叠，不能理解否定、时间、因果和条件范围。这个指标可以发现明显引用不相关，但不能叫 faithfulness 或事实正确率。

### 52. premise 0.167 会让你怎么决策？

**简答：**它已低于预声明的“不得比 Normal 低超过 0.10”门槛，所以不宣布 V2 通过、不自动路由、不扩大使用范围。等独立人工评分；如果人工也确认无稳定收益，就关闭 Deep flag，保留为实验。

## 七、取舍与反思

### 53. 项目里最大的技术挑战是什么？

**参考回答：**不是某个 API 难调，而是让一条证据在经过检索、重排、ACL、分析、审查和生成后仍能保持来源、权限和语义边界，并在失败时知道是哪一层丢了它。H08/H16 和 ACL 污染测试是这个挑战的两个代表。

### 54. 如果重做一次，你会怎么改？

**参考回答：**我会更早建立文档 registry/index coverage 检查和 retrieval-only benchmark，避免从最终答案反推检索问题；更早定义 AgentState 协议和用户可见 event tag，少走 Supervisor/ReAct 的弯路；从第一天就分开 Development/Blind/Regression。但在当前规模下我仍不会加 Redis、Kafka 或 GraphRAG。

### 55. 项目最失败的尝试是什么？

**参考回答：**早期将“复杂问题”等同于多 Agent 执行，导致架构延迟、状态和输出协议复杂，而评测没证明稳定收益。后来我把生产图收敛为单 Planner，普通复杂问题用 Query Expansion，Deep 改为显式有界实验。这比继续调 prompt 维护一个过大架构更重要。

### 56. 你如何避免过度设计？

**简答：**每个新组件必须有独立职责、输入输出、失败语义和专项评测。先用 Development Benchmark 证明系统性问题，再实施；无净收益或伤害整体时回退。Named Anchor、第四 Agent、Redis 和自动 Deep 都因没有证据而没做。

### 57. 这个项目最强的亮点是什么？

**参考回答：**我认为是“证据生命周期 + 评测驱动的停止决策”。前者让权限和引用贯穿 Retrieval、Claim、Review 和 Final，后者让我不会因为已经写了 Multi-Agent 就强行宣布它更好。

### 58. 项目最大的限制是什么？

**简答：**数据和部署规模小，Blind V2 人工评分未完成，Deep premise 安全指标失败，自动 support 仍是 proxy，SQLite/Chroma 没有验证多实例扩展。所以它适合表达 RAG/Agent/评测的系统设计，不应包装成大规模企业平台。

### 59. 项目现在还要继续开发吗？

**简答：**不继续开发核心 Agent 功能。当前只需要独立人工 Blind V2 评分和秋招交付收尾。只有真实 ACL/入库故障、新用户反馈或新盲评证据才重新开启。

### 60. 如果面试官要你明天上线，你会做什么？

**参考回答：**我不会把当前原型直接当大型企业系统上线。对小范围实验室内测，我会先关闭或严格限制 Deep，备份 SQLite/Chroma，检查知识库 registry 与磁盘一致性，更换所有密钥，运行 ACL matrix、全量测试、build 和真实 smoke，定义回滚和数据恢复方案。如果是多租户企业生产，还需要重做存储、密钥、审计、容灾、压测和安全边界，不会虚构“可立即上线”。

## 八、模拟面试使用方法

1. 随机选 10 题，每题限时 40 秒回答。
2. 每题再补一个“备选方案为什么没选”。
3. 对涉及数字的问题，先说数据集身份，再说数字，最后说限制。
4. 对源码问题，必须能说出至少一个文件和函数名。
5. 对难点问题，使用“现象—假设—证据—决策—结果—限制”顺序。
6. 如果回答中出现“完全解决”、“绝对安全”、“企业级高并发”或“Multi-Agent 显著更好”，立即检查是否超出证据。
