# 02 项目最终评估与秋招定位分析

更新时间：2026-09-04
说明：本文保留评估过程和面试定位，数字来自历史冻结快照；当前入口和最新检索、知识演化结果见 `docs/03-评测与验证/02-秋招版评测收口说明.md`。

## 一、最终结论

实验室科研智能助手项目目前已经达到：

> **Implementation / Auto-Eval Freeze**

同时保留：

> **独立真人盲评不是当前代码缺口；模拟评分只能用于失败分析。**

这意味着核心实现、自动评测、Failure Attribution、ACL、Deep Research 产品入口和 V2 冻结流程已经完成，不建议继续修改 Researcher / Analyst / Reviewer 架构，也不建议再通过增加 Agent、模型或检索框架追求更漂亮的指标。

Blind V2 的独立人工答案评分未形成新的产品结论。这不是代码实现缺口，也不应阻塞项目收口；Codex 模拟评分只用于失败分析，不能冒充真人评分。

## 二、当前项目定位

项目核心仍然是：

> **面向计算机专业研究生实验室的可信科研 RAG + 权限隔离 + 证据引用 + 可评测 Deep Research 系统。**

Deep Research 是一个显式、有限、实验验证驱动的扩展模式，而不是项目主体。

当前默认结构：

```text
Normal（默认）

maybe_summarize
→ retrieve_mem0_memories
→ planner
→ ACL-aware Retrieval
→ Query Expansion / CRAG
→ Generation Agent
→ Finalizer
```

显式 Deep：

```text
research_mode=deep
→ Researcher
→ Analyst
→ Reviewer
   ├─ PASS
   └─ REVISE / NEED_MORE_EVIDENCE
       → 最多返工一次
→ 复用原 Generation Agent
→ Research Brief
```

没有增加 Supervisor、第四个 Agent、动态 Worker、Agent 自由协商、Blackboard、GraphRAG、Knowledge Graph、Redis/Kafka、新向量库、新 Embedding、新 Reranker、新主 LLM 或 LLM Judge。

## 三、为什么 Multi-Agent 现在值得保留，但不能成为默认

最初 Multi-Agent 实验的核心假设是：

> 多 Agent 可以通过更多检索、更好的证据分析和相互审查，在复杂科研问题上显著优于 Single Agent。

经过多轮评测后，最终结论不是“Multi-Agent 全局更好”，而是：

> **Deep 在部分复杂任务上有价值，但没有稳定全局优势，而且成本显著更高。**

Blind V2 当前自动指标：

| 指标 | Normal | Deep |
|---|---:|---:|
| 成功 | 26/26 | 26/26 |
| 关键点覆盖 | 0.865 | 0.913 |
| 引用覆盖 | 0.507 | 0.727 |
| 引用支持 proxy | 0.995 | 0.979 |
| 文档召回 | 0.679 | 0.811 |
| Conflict | 0.923 | 1.000 |
| Premise | 0.667 | 0.167 |
| ACL leak | 0 | 0 |
| P50 | 6.6s | 27.5s |
| P95 | 9.1s | 33.0s |
| 平均逻辑调用 | 2.00 | 7.77 |

因此 Deep 的真实产品结论必须保持：

```text
Normal = default
Deep = explicit opt-in
Automatic routing = false
```

而不是自动把“复杂问题”全部升级为多 Agent。

## 四、当前最大风险不是 Recall，而是 Premise

Blind V2 最值得关注的数字不是 Deep 文档召回 0.811，而是：

```text
Normal premise accuracy = 0.667
Deep premise accuracy   = 0.167
```

这已经违反预先声明的 safety gate。

因此当前不能宣布：

> “Deep V2 全局优于 Normal。”

也不能因为 Recall、Citation Coverage、Conflict 提升就忽略 Premise 明显退化。

## 五、Premise 问题已经从“评测 bug”区分为真实能力限制

前一阶段曾经存在一个合理怀疑：

> Premise 低分会不会只是自动 evaluator 口径问题？

最新 V2 已经重新修正了 premise evaluator，使它只读取回答中的明确前提结论，不再让正文中局部“证据不足”覆盖答案顶部的主判断。

修正后 Development Eval 中 Deep premise 仍然出现明显退化。

因此当前更可靠的结论是：

> **Premise weakness 不只是 metric bug，而是 Reviewer / Deep 整体链路的真实能力边界。**

这是一次很好的 Failure Analysis：

```text
发现异常指标
↓
怀疑 evaluator
↓
审计 metric
↓
修正 metric scope
↓
重新评估
↓
问题仍存在
↓
承认能力限制
```

## 六、普通问题被错误前提化的问题已经解决

此前 Reviewer 可能把普通比较、总结和建议任务错误解释成“前提真假核验”。

现在已经明确引入：

```text
supported
unsupported
insufficient
not_applicable
```

四态协议。

对于非 premise：

```text
premise_assessment = not_applicable
premise_source_ids = []
false_premise_detected = false
```

并且最终 Generation 不会再自动注入“前提核验”。

因此“普通任务被强行前提化”已经解决，但“真正 premise task 判断是否准确”仍然是当前未解决的能力边界。

## 七、H08 / H16 Failure Attribution 已经真正做清楚

之前 Deep 的一些失败被怀疑是：

> Researcher 没有把明确命名论文检索出来。

V2 专门建立了 Retrieval-only Development Benchmark，把“检索错误”和“Agent 综合错误”拆开。

最终发现：

```text
Nu
Quicksand
Argo
AIFM
```

虽然文件存在于磁盘，但没有进入冻结的：

```text
Chroma snapshot
40 chunks / 18 documents
```

因此这些失败首先属于：

> **missing_document**

而不是 semantic retrieval failure。

这说明系统现在已经具备更成熟的 RAG Failure Attribution：

```text
ingestion
index
query planning
retrieval
rerank
ACL
analysis
review
generation
knowledge gap
```

## 八、为什么最终没有实现 Named Evidence Anchor

Retrieval Development Benchmark 结果显示：

```text
exact named:
Normal = 0.500
Deep   = 0.500

named alias:
Normal = 0.600
Deep   = 0.600

multi evidence:
Normal = 0.733
Deep   = 0.867

temporal/version:
Normal = 0.833
Deep   = 0.933

semantic:
Normal = 0.800
Deep   = 0.500
```

所以 Deep 的优势更偏 multi-evidence 和 temporal/version，并没有证明“Named Evidence Retrieval 是通用缺陷”。

如果此时为了 H08/H16 增加专门的 Named Evidence Anchor，只会变成基于已看案例的局部优化。

因此最终选择：

> **不实现 Anchor。**

## 九、ACL 已经成为这个项目最强的技术点之一

最开始 ACL 可能只被描述成：

> 检索时做权限过滤。

现在已经升级成：

> **Evidence Lifecycle Invariant。**

V2 已覆盖完整角色矩阵：

```text
anonymous
ordinary user
project member
project lead / authorized user
non-member
```

×

```text
public
project
restricted
```

×

```text
same project
other project
no project
```

并且不是只验证 Final Sources，而是故意让一个 denied secret document 混进 pipeline，然后验证它不会进入：

```text
EvidencePackage
AnalysisReport / Claim
ReviewReport
research_trace
retrieval_context
source cards
Final Answer
```

Revision 补检索同样重新执行 ACL。

最终 ACL violation = 0。

因此面试时可以说：

> **权限控制不是 Retriever 的一个 filter，而是证据从检索到最终生成全过程都必须满足的 invariant。**

## 十、Researcher / Analyst / Reviewer 的分工是合理的

### Researcher

```text
问题拆解
→ 最多 4 个 subquestions
→ 复用现有 Corrective RAG
→ 最多 12 条 Evidence
→ EvidencePackage
```

### Analyst

```text
EvidencePackage
→ Structured Claim Map
```

Claim 类型：

```text
fact
comparison
inference
recommendation
```

每条 Claim 必须绑定真实 Evidence ID。

### Reviewer

职责包括 Claim-Evidence 对齐、Premise、Conflict 和 ACL，只允许：

```text
PASS
REVISE
NEED_MORE_EVIDENCE
```

并且最多只允许一次 Revision。

### Final Generation

没有新增 Writer Agent，而是复用原本已经比较稳定的 Generation Agent。

这使得 Multi-Agent 系统保持固定、有限、可观测和有明确成本上界。

## 十一、为什么只允许一次 Revision

如果 Reviewer 可以无限回环：

```text
Reviewer
→ Analyst
→ Reviewer
→ Analyst
→ ...
```

系统会出现延迟、Token、Prompt drift 和输出稳定性不可控的问题。

当前：

```text
REVISE / NEED_MORE_EVIDENCE
→ 最多修订一次
→ 直接 Generation
```

因此 Deep 的最大调用次数和 latency 有明确上界。

## 十二、Trace 与 Failure Attribution 已经足够完整

当前 `research_trace` 可以回答：

- Researcher 找到了哪些文档；
- 哪些预期证据没找到；
- 哪些 Evidence 没进入 Claim；
- Reviewer 删除了什么；
- 为什么删除；
- Revision 增加或删除了什么；
- Final Generation 漏掉哪些 validated claim；
- 各阶段耗时多少；
- 最终错误发生在哪一层。

顶层 failure attribution：

```text
retrieval
analysis
review
generation
knowledge_gap
acl
none
```

这使项目从“Agent 跑完得到答案”升级成“Agent 每一层都能定位失败”。

## 十三、Blind V2 的方法论价值

新的 Blind V2 有 26 条：

```text
temporal_conflict              8
named_multi_evidence           6
premise                        6
recommendation/research brief  6
```

并且是在实现冻结后创建。

当前候选甲/乙映射未形成新的独立人工结论；该状态不阻塞代码收口。

这一点很重要：

> Codex 不再同时担任开发者和最终人工 Judge。

因此“未形成独立人工结论”不是代码 Goal 没做完，而是评价独立性时保留的外部证据边界。

## 十四、Blind V1 与 V2 的关系

Blind V1 已经被冻结为：

```text
Historical Blind Holdout V1
+
Regression after inspection
```

不再作为新的 blind evidence。

Blind V2 才是当前冻结实现之后的新评测集。

但由于 V2 还没有完成独立人工评分，所以目前不能对最终答案质量给出新的正式产品结论。

特别是：

> Temporal Conflict 的自动指标虽然继续显示正向信号，但还不能宣称“已经在人类评价中稳定优于 Normal”。

## 十五、前端显式 Deep 产品入口是合理的

前端已经新增：

```text
回答模式

○ 普通
○ 深度研究
```

Deep 明确提示“多阶段证据分析，耗时更长”。

而且：

- 默认 normal；
- 只影响当前请求；
- 请求发送后自动回 normal；
- 刷新后回 normal；
- 新会话回 normal。

这比自动复杂路由更合理。

## 十六、当前不能怎么宣传这个项目

不应该写：

- Multi-Agent 全局优于 Single Agent；
- Deep 显著提高所有科研问答质量；
- Deep 已通过 V2 Safety Gate；
- Deep 能解决所有复杂科研问题；
- ACL=0 代表绝对安全；
- Citation Support proxy 等于事实准确率。

更准确的说法是：

> **构建 Researcher–Analyst–Reviewer 固定多 Agent Deep Research 模式，并通过 Development Eval、实现冻结和新的 26 条 Blind V2 对照验证；Deep 提升文档召回和引用覆盖，但 premise 判断明显退化且延迟、调用成本显著增加，因此最终仅保留为用户显式触发模式，不替换默认 Single-Agent RAG，也不自动路由。**

## 十七、当前项目最适合的秋招定位

这个项目最适合体现：

> **RAG + Agent System + Evidence / ACL + Evaluation-driven Architecture**

核心关键词包括：

- Hybrid RAG；
- Query Expansion；
- CRAG；
- Rerank；
- ACL；
- Citation；
- EvidencePackage；
- Claim Map；
- Researcher / Analyst / Reviewer；
- Failure Attribution；
- Blind A/B；
- Latency / Cost Trade-off；
- SSE；
- FastAPI + Vue。

和 JobMatchTune 的后训练 / 数据治理方向形成明显互补。

## 十八、与 JobMatchTune 的共同工程主线

JobMatchTune：

```text
训练效果不错
↓
发现数据和评测问题
↓
停止继续训练
```

实验室项目：

```text
Multi-Agent 很有吸引力
↓
发现收益不稳定且成本高
↓
不自动上线
```

共同思想是：

> **先提出技术假设，再设计评测；如果评测不能证明稳定净收益，就限制、停止或拒绝复杂化。**

这是两个项目共同最强的秋招工程标签。

## 二十、重新开启核心开发的条件

只有出现以下情况才建议重新打开：

1. 独立人工 Blind V2 评分得到新的可靠结论；
2. 真实用户反馈暴露明确产品故障；
3. 新知识库数据暴露稳定可复现的 Retrieval Failure；
4. ACL 出现实际权限问题；
5. 新任务类别证明 Deep 存在稳定净收益。

否则继续改 Agent 架构的价值已经很低。

## 二十一、当前最优下一步

这个项目现在同样应该从“待开发”转成“待掌握”。

秋招需要真正能脱离文档回答：

- 为什么不自动使用 Multi-Agent？
- 为什么 Reviewer 最多只返工一次？
- 为什么 Deep Recall 提高仍不能说明答案更好？
- 为什么 premise 0.167 会直接阻止扩大上线？
- H08/H16 为什么是 missing_document，而不是 Retriever 错？
- 为什么没有实现 Named Evidence Anchor？
- ACL 为什么必须贯穿 EvidencePackage / Claim / Review / Generation？
- Citation Support 为什么只是 proxy？
- Blind V1 和 Blind V2 有什么区别？
- 为什么不用 LLM Judge？
- 为什么 Codex 不应该自己做 Blind V2 最终人工评分？
- 为什么 Deep 只能显式 opt-in？

当这些问题可以自然讲清，这个项目才真正成为自己的系统设计经验，而不只是一个多 Agent Demo。
