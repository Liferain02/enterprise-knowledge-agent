# 04 实验结果解读与停止决策

本文集中解释结果意味着什么、不能意味着什么，以及为什么当前正确动作是停止扩张 Deep 架构，而不是继续堆 Agent。

## 04.1 Retrieval-only Development 的作用

它比较：

- Normal：原问题 + 当前 Query Expansion/CRAG。
- Deep Researcher：最多四个规划查询 + 相同 CRAG。

因为下游完全关闭，差异可以归因到查询规划和证据检索，而不是 Analyst 文风。

## 04.2 Missing document 结论

H08/H16 涉及 Nu、Quicksand、Argo、AIFM。脚本先读取 Chroma 全部 title/source，确认目标不在 18 文档 snapshot，于是标记 `missing_document`。

正确动作是补齐入库流程或调整评测 corpus 声明，不是提高 top K、加 Named Anchor 或换模型。

## 04.3 Named Evidence Anchor 负结果

开发对照没有证明“额外根据标题强行搜索一次”具有稳定收益，可能增加重复候选、调用和特例规则。因此没有进入生产。

负结果的价值：避免为了几个名字题把检索器做成 case-specific patch。

## 04.4 Development A/B/C

答案级开发阶段通过相同题目比较 Normal、历史方案和固定团队，观察 keypoint、citation、document recall、premise、延迟和 token。

因为结果可见，它只用于修复 structured output、premise not-applicable、trace 和评测器错误。任何漂亮数字都不能作为最终泛化结论。

## 04.5 Blind V2 总体结果

| 指标 | B Normal | C Deep |
|---|---:|---:|
| 请求成功 | 26/26 | 26/26 |
| 关键点覆盖 | 0.865 | 0.913 |
| 引用覆盖 | 0.507 | 0.727 |
| 引用支持 proxy | 0.995 | 0.979 |
| 文档召回 | 0.679 | 0.811 |
| conflict | 0.923 | 1.000 |
| premise | 0.667 | 0.167 |
| ACL violation | 0 | 0 |
| P50/P95 | 6.6/9.1s | 27.5/33.0s |
| 平均 input/output token | 2071/367 | 12590/2304 |
| 平均 logical calls | 2.00 | 7.77 |

## 04.6 Deep 的确定收益信号

在该数据集自动 proxy 上：

- 文档召回提高 0.132。
- 引用覆盖提高 0.220。
- temporal conflict 提高到 1.0。
- named_multi_evidence recall 从 0.833 到 1.0。

这些支持“Deep 更擅长搜齐和组织多证据”的有限假设。

## 04.7 Deep 的严重回退

Premise 从 0.667 降到 0.167，违反预声明 safety gate。由于 6 条 premise 中一题会改变约 0.167，这相当于 Deep 只正确约 1 条。

安全子项不能被总体 keypoint 增益抵消。系统如果能搜更多资料却更容易误判制度前提，不适合默认替代 Normal。

## 04.8 成本倍率

粗略比值：

```text
P50 latency ≈ 4.2×
logical calls ≈ 3.9×
input tokens ≈ 6.1×
output tokens ≈ 6.3×
```

Deep 不是免费质量增强。即使人工评分未来证明某些类别更好，也应保持显式模式或只在明确场景使用。

## 04.9 按类别解读

### temporal_conflict

Deep keypoint 0.906 对 0.875，recall 1.0 对 0.833，自动 conflict 更好。仍需人工判断是否真正区分观察、计划和因果。

### named_multi_evidence

双方 keypoint 都 0.958，Deep recall 1.0。这说明多找文档未必继续提高关键词覆盖，可能已接近自动指标上限。

### premise

Deep keypoint 0.958 看似更高，但 premise accuracy 很差，证明“提到更多关键词”与“判断正确”可以完全相反。

### recommendation

双方 keypoint 均 0.833，Deep recall 0.569 对 0.389。更多证据是否让方案更可执行必须靠人工评分。

## 04.10 Deep 内部指标

```text
Researcher expected evidence coverage 0.811
Analyst claim coverage 0.815
Reviewer drop rate 0.074
Final validated-claim coverage proxy 0.996
Failure attribution: generation 1, none 24, retrieval 1
```

这些说明证据大多进入 Claims、校验后 Claims 大多进入最终答案。但它们无法发现 premise 语义判断错误，说明内部流程完整不等于结论正确。

## 04.11 为什么不宣布 Deep 全局更好

至少三个原因：

1. 预声明 safety gate 已失败。
2. 独立人工 label-blind review 未完成。
3. 自动指标主要是关键词和引用 proxy。

因此当前状态是“实现和自动评测完成、产品收益未定”。

## 04.12 为什么保持 Normal 默认

Normal 更快、更便宜，premise 更好；对多数单文档和简单问题已经足够。Deep 的主要优势集中在显式多证据研究，不应让所有用户为其付费。

产品决策：Normal 默认，Deep 单次 opt-in，关闭开关可立即下线。

## 04.13 为什么停止加第四个 Agent

现有失败不是“少一个角色”：

- premise 是 Reviewer/确定性判断质量问题；
- latency/token 已高；
- Writer 已由 Generation 覆盖；
- 人工评分尚未完成。

增加 Agent 会扩大变量空间和成本，不能直接修复已知 gate。

## 04.14 下一步真正有价值的工作

按优先级：

1. 完成独立人工 V2 评分并解盲。
2. 对 premise 错题做类别级分析，但只在 Development/新数据上修。
3. 修复前端 SSE 残帧解析并补测试。
4. 从真实反馈积累新的 regression 和未来 V3 holdout。
5. 有数据后再判断是否并行 Researcher 查询或减少调用。

## 04.15 停止条件

满足以下任一条件应停止当前优化方向：

- 主指标提高但安全 gate 下降。
- 增益只出现在已看过 Development 个例。
- 复杂度/成本增加且人工价值未证明。
- 失败归因指向数据或入库，不是算法。
- 真实用户没有该需求。

停止不是项目失败，而是防止 sunk cost。

## 04.16 可写进简历的结论

> 构建固定三角色 Deep Research 与分层评测，冻结后 26 条 V2 中 Deep 文档召回 0.811 对 Normal 0.679、引用覆盖 0.727 对 0.507；同时发现 premise 0.167 对 0.667、P50 约 4.2 倍，因此保持 Normal 默认、Deep 显式选择，并停止继续堆叠 Agent。

这段同时报告收益、退化和决策，比只写“提升 13.2%”更可信。

## 04.17 不能写的结论

- “Deep 全面优于 Normal”。
- “通过双盲证明”。
- “ACL=0 代表绝对安全”。
- “引用支持 0.979 就是 97.9% Faithfulness”。
- “26 条证明生产规模稳定”。
- “Multi-Agent 显著提高所有任务质量”。

## 04.18 最终评估观

项目最有价值的不是某个平均分，而是建立了：

```text
问题分层
→ 代码/数据冻结
→ 自动与人工职责分离
→ 安全 gate
→ 失败归因
→ 成本报告
→ 有证据的停止决策
```

这套方法可以迁移到其他 RAG/Agent 项目，也是秋招最值得讲的能力。
