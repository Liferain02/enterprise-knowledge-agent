# 01 数据集身份、冻结与防污染

评测可信度首先取决于数据身份。本文解释开发集、历史 V1、盲测 V2 和回归测试的用途，以及如何防止看过答案后继续调参却仍声称盲测。

## 01.1 四种数据身份

| 身份 | 可以做什么 | 不可以做什么 |
|---|---|---|
| 开发集 | 看逐题结果、改实现、调阈值 | 用于最终泛化结论 |
| 历史盲测 V1 | 描述当时未看数据得到的历史信号 | 检查后继续称当前盲测 |
| 盲测 V2 | 冻结后一次正式运行 | 覆盖、调参、反复挑结果 |
| 回归测试 | 防止已知问题复发 | 证明对未知问题泛化 |

数据身份一旦从 blind 被打开分析，就永久变成 regression，不因换了一个模型或隔几天重跑而恢复。

## 01.2 仅检索开发集

26 条检索开发题分为：

```text
exact_named_document
named_entity_alias
multi_evidence
temporal_version
semantic_query
```

只运行普通模式 retrieval 和深度研究模式 retrieval，不调用分析员、审核员、回答生成。每题记录预期 doc IDs 和 minimum 预期 docs。

它回答“证据是否被找到”，不能回答“最终文字是否更好”。

## 01.3 为什么保存三层候选

每个查询运行记录保存：

- 原始 candidate 标题；
- 重排后标题；
- CRAG 最终标题；
- rewrite 历史；
- 决策和延迟。

这样目标文档丢失时可以定位 candidate generation、重排或 grading，而不是统一写“RAG 召回差”。

## 01.4 答案级开发集

41 条复杂科研开发集评测用于迭代深度研究模式协议、前提判断和 trace。它可比较普通模式、旧方案和深度研究模式，但因为开发者可以查看问题和结果，只能用于工程调试。

开发集上的明显提升是“值得进入新留出集”的信号，不是简历最终数据。

## 01.5 历史 V1

18 条 V1 最初按 holdout 运行，但后来结果和映射已被检查，并据此改了系统。因此它现在的身份是历史盲测留出集 / 回归测试 after inspection。

可以说“V1 曾观察到 temporal conflict 正向信号并推动 V2 设计”；不能把它与 V2 合并后声称有 44 条新盲测。

## 01.6 盲测 V2 的构成

冻结后新建 26 条：

```text
temporal_conflict            8
named_multi_evidence         6
premise                      6
recommendation_research_brief 6
```

前提判断又分 3 条 false 与 3 条 supported，防止系统只学会“看到绝对词就反驳”。每题包含相关 docs、预期 keywords、key points、min 来源和类别特定期望。

## 01.7 预声明门槛

`深度研究V2生产门槛定义.json` 在正式结果前冻结，核心规则：

- 普通模式/深度研究模式请求全部成功。
- ACL violation 为 0，角色矩阵和全阶段传播测试通过。
- 深度研究模式前提判断准确率不能比普通模式低 0.10 以上。
- temporal、named、recommendation 各自有最低样本数和人工胜出门槛。
- P50/P95、调用数和词元必须完整报告。
- 没有新的独立真人评分结论前，不得作最终产品收益结论；模型模拟评分只用于失败分析。

先写门槛能防止看到结果后临时选择对自己有利的指标。

## 01.8 代码冻结

实现冻结清单至少记录：

- Git commit；
- 核心源码 SHA-256；
- 模型和检索配置；
- 测试结果；
- Chroma 快照信息。

若正式运行后改代码，下一轮必须新建版本和留出集。不能覆盖旧结果文件。

## 01.9 数据冻结

评测产物清单记录 dataset、正式 JSON、自动报告、人工表和密封映射的 SHA-256。规则明确禁止覆盖或用于调参。

知识库也属于评测条件：18 文档 / 40 文档片段。若重新入库、修改元数据或换向量表示，即使代码不变也必须重跑基线。

## 01.10 方案标签盲测表

人工评分表隐藏 B/C 对应普通模式/深度研究模式，密封映射独立保存并在评分完成前不打开。这样评分者至少不知道方案标签。

但回答文风可能暴露方案，且没有形成新的独立真人产品结论，因此准确名称是方案标签盲测 packet，不应称严格双盲。

## 01.11 为什么 Codex/开发者不做最终评分器

开发者知道系统设计和预期，很难提供独立评价；同类 LLM 评分器还可能偏好更长、更结构化的深度研究模式回答。

V2 明确 `No LLM-as-a-Judge`，自动指标只作代理指标；当前没有新的独立真人产品结论。

## 01.12 防止题目泄漏

需要遵守：

1. 不把盲测样本文本写进提示词或规则。
2. 不根据样本 ID 分支。
3. 不把预期 keywords 加入查询 expansion 词典。
4. 不在看到逐题失败后重跑同一正式版本。
5. 新改动只用开发集/回归测试，最终再建 V3 留出集。

通用归一规则可以开发，但必须证明不依赖个别题目内容。

## 01.13 Manifest 能证明什么

SHA-256 能证明文件之后没有变化，不能证明：

- 最初数据没有主观偏置；
- 人工评分真的独立；
- 运行时外部模型完全相同；
- 结果具有统计显著性。

冻结提高可追溯性，不替代实验设计。

## 01.14 可复现运行信息

每个结果至少保存：

```text
generated_at / duration
git commit
provider + model
embedding + reranker
top K / thresholds
corpus chunk/document count
per-case raw outputs
aggregate and category metrics
```

只保存汇总平均值无法复盘失败，也无法验证指标代码。

## 01.15 下一轮评测流程

```text
从用户反馈与新场景收集候选
→ 去标识和审阅
→ 划分 Development 与未见 Holdout
→ 预声明 gates
→ 冻结代码/配置/知识库
→ 一次正式自动运行
→ 生成 label-blind packet
→ 独立人工评分
→ 解盲与按类别决策
→ Holdout 转 Regression
```

这个流程比继续在 V2 上反复优化更重要。
