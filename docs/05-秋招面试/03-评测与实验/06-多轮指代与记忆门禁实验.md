# 06 多轮指代与记忆门禁实验

## 06.1 为什么做这项改进

当前项目是实验室科研助手，不是通用聊天机器人。真实使用中常出现“它呢”“那第四天呢”“与之前方案相比呢”这类追问。如果只检索当前句，语义主体会丢失；但无条件用 LLM 重写所有问题，又会增加延迟、漂移和不可解释性。

因此本阶段只实现一个窄能力：当追问包含明确的指代、省略或上下文比较信号时，同时检索原追问和一条 Standalone 查询。原查询永远保留，最多增加一条查询，不改变 Planner、Normal 默认路径或 Deep 的固定拓扑。

## 06.2 冻结数据集

数据集代码位于 `tests/eval/multi_turn_coreference_dataset.py`，身份为：

```text
lab-multi-turn-coreference-v1
version = 2026-09-03
```

共 24 条，全部围绕当前真实知识库主题独立编写：

| 类别 | 数量 | 例子 |
|---|---:|---|
| 指代追问 | 6 | “它结束后要清理什么？” |
| 省略追问 | 6 | “那大额支出呢？” |
| 上下文比较 | 3 | “跟一般远程内存问题相比呢？” |
| 不应改写的完整问题 | 9 | “设备预约冲突如何处理？” |

每条记录包含前一轮用户问题、当前追问、是否应触发、必须保留的语义词和 gold source。评测集先于主链路接入冻结；失败样本不会通过知识库插入 GOLD 标记解决。

## 06.3 最小实现

`StandaloneQueryRewriter` 是确定性规则，不调用 LLM：

```text
输入：最近用户问题 + 当前追问
触发：明确代词 / 追问前缀 / 缺少一侧主体的上下文比较
输出：
  1. original，权重 1.0，永远保留
  2. standalone，权重 0.95，最多一条
```

Standalone 形式为：

```text
关于“上一轮用户问题”的追问：当前追问
```

它不尝试通用共指解析，也不生成领域关键词。最近用户问题最多取 120 字；原查询、Standalone 和复杂问题分解查询合计最多 4 条。

## 06.4 预声明准入门槛

脚本 `tests/eval/run_multi_turn_standalone_ablation.py` 在看到结果前固定以下门槛：

1. 触发 F1 必须为 1.0。
2. 正例 Hit@5 不得下降。
3. 正例 MRR@5 至少提升 0.03。
4. 已命中的正例不得退化为未命中。
5. 负例结果变化率必须为 0。
6. ACL 违规结果必须为 0。
7. 单请求查询变体不得超过 2。

Baseline 只检索当前追问；实验组用当前真实 Hybrid + Qwen Rerank 分别检索 original 与 standalone，再用 RRF 合并。两组都使用同一个匿名用户 ACL。

## 06.5 实验结果

运行产物在 gitignore 的 `data/多轮指代改写消融结果.json` 和 `data/多轮指代改写消融报告.md`。

| 15 条正例指标 | Baseline | Standalone | 变化 |
|---|---:|---:|---:|
| Hit@1 | 0.867 | 0.867 | 0.000 |
| Hit@5 | 0.867 | 1.000 | +0.133 |
| MRR@5 | 0.867 | 0.933 | +0.067 |
| NDCG@5 | 0.867 | 0.951 | +0.084 |
| 平均检索延迟 | 647 ms | 1173 ms | +526 ms |

安全与稳定性结果：

- Trigger Precision / Recall / F1 均为 1.000。
- 正例 Hit@5 回退率为 0。
- 9 条负例结果变化率为 0。
- ACL violation 为 0。
- 最大查询数为 2。

结论是“在当前 24 条开发集和 40 chunks 知识库上通过准入”，不是宣称通用共指能力已经解决。约 0.53 秒的正例额外延迟是明确代价，所以只有检测到上下文信号时才触发。

## 06.6 为什么没有继续做 Step-back

Standalone 已把需要上下文的正例 Hit@5 提升到 1.0，当前没有证据表明再增加 Step-back 能解决新的主要失败。继续叠加会同时改变查询数、延迟和召回来源，使收益无法归因。因此本阶段停止在 Standalone；只有新的独立多轮数据暴露抽象层级不足时，才单独评测 Step-back。

## 06.7 三层记忆边界

```text
会话摘要：短期上下文，帮助延续对话，不是事实来源
Research Run：情景记忆，保存过程；同题时只复用历史子问题计划
Mem0：长期用户记忆；科研事实必须经过受控提升
```

Research Run 只在问题文本和项目 ID 都相同时复用历史 `subquestions`；未绑定项目的请求只能匹配未绑定项目的 Run。它不把旧答案、旧 Claim 或旧证据直接放进新 Prompt，新运行仍执行当前知识库检索和当前 ACL 检查。这样可以省掉重复规划调用，同时避免跨项目、过期资料或撤权资料借历史记录回流。

## 06.8 科研事实进入 Mem0 的五道门

前端“确认并记住”按钮和接口
`POST /api/v1/research/runs/{run_id}/claims/{claim_id}/confirm-memory` 共同执行：

1. Research Run 状态必须是 completed。
2. Claim 必须是 `fact`，推断和建议不能进入事实记忆。
3. Claim 必须至少绑定一个当前仍可访问的 EvidenceItem。
4. ReviewReport 必须为 PASS、ACL verified，且该 Claim 未被 Reviewer 否决。
5. 用户必须显式点击确认。

成功后才向 Mem0 写入，并在 `research_memory_confirmations` 记录 run、claim、user 和时间。已验证 Claim 使用 `infer=False` 精确存储，避免 Mem0 再调用 LLM 改写事实；真实接口耗时由约 83 秒下降到 1.23 秒。重复确认根据审计记录直接返回成功，不重复写入。Mem0 不可用或处于降级模式时接口明确失败，不伪装“已经记住”。普通问答仍保持 Mem0 失败不阻断回答。

## 06.10 面试表达

可以用一句话概括：

> 我没有增加新 Agent，而是在真实多轮集上先做检索消融；确定性 Standalone 让上下文追问 Hit@5 从 86.7% 到 100%，无负例漂移后才默认接入。记忆则分为摘要、Research Run 情景记忆和 Mem0 长期记忆，历史运行只复用检索计划，科研事实必须经过证据、Reviewer、ACL 和用户确认才能提升。

必须同时说明限制：数据规模小、属于开发集、正例多一次检索增加约半秒，后续需要独立 holdout 才能证明泛化。
