# 05 核心可信度收口与消融评估

## 05.1 本轮目标

本轮不考虑生产部署，不新增智能体，不引入 Redis、PostgreSQL、Celery、Kubernetes、
GraphRAG 或新模型。目标只有三个：权限边界正确、真实链路足够简单、每个保留组件有实验依据。

完成条件是：ACL 全链路泄漏为 0；最终引用重新鉴权；稳定文档片段身份不依赖 Python 进程哈希；
不可达架构被删除；普通 RAG、深度研究模式和检索消融有统一可复现入口；冻结盲测 V2
保持不覆盖，人工盲评状态如实保留。

## 05.2 权限正确性修复

### 05.2.1 时间有效性

`acl_filter.py` 现在同时检查 `effective_date` 与 `expiry_date`。合法区间是：

```text
effective_date <= 当前日期 <= expiry_date
```

旧文档缺少日期时仍可访问；字段存在但无法解析时关闭访问，避免错误元数据意外放行。
角色/部门 restriction 兼容字符串、JSON 数组和原生列表；未知密级不再默认公开。

### 05.2.2 先鉴权再截断

旧混合检索可能先取 top-k 再过滤 ACL：如果高分结果都无权访问，低一位但有权访问的结果会
永远丢失。现在 Vector 先扩大候选，BM25 对完整候选集过滤，然后才融合、重排和截断；
纯 Vector 分支也执行同一 ACL 复核。

这既是安全问题，也是召回正确性问题。正确顺序为：

```text
召回候选 → ACL → 融合/重排 → top-k → 最终防御性 ACL
```

### 05.2.3 最终来源重新鉴权

LangGraph `finalize_response_node()` 在把 `retrieved_docs` 写入终态前重新鉴权；ChatService
生成普通响应和 SSE 来源 card 时再次检查当前用户。即使上游节点以后发生回归，未经授权的
来源也不能通过最终 API 返回。

## 05.3 检索身份与真实混合检索

文档去重不再使用 `hash(page_content)`。Python hash 会随进程变化，不适合 checkpoint、评测和
跨重启追踪。当前优先使用来源/doc_id、version、chunk_id/chunk_hash 计算 SHA-256；缺少
结构化身份时才使用来源 + 内容摘要。

同时修复了一个更关键的问题：混合检索 Manager 原先没有调用方为 BM25 自动装载语料，名义
混合检索实际可能只有 Vector。现在第一次检索时从当前 Chroma 快照懒加载 BM25，知识库新增、
删除或 reset 后使索引失效，下次检索重建。

## 05.4 架构减法

以下代码因未进入主链、无法由评测证明价值，或会扩大权限与维护面而删除：

- Supervisor；
- Parallel Executor；
- 路由规划器的 Execute Plan、Send 和计划汇总；
- 旧 Knowledge ReAct 包装；
- `_schemas.py` 的历史协议；
- 未接入请求链且缺少 ACL/版本失效设计的查询 Cache；
- 未接入主链、无评测样本的 Table QA；
- 只互相引用的通用答案/检索缓存与批推理优化器；
- AgentState 中相应历史字段。

路由规划器收敛为约百行的确定性路由器。问候走 General，明确时间/计算走 Operation，其余安全
默认走 Knowledge；普通模式的复杂形式只启用查询扩展，深度研究模式仍必须由用户显式选择。

## 05.5 五路检索消融

统一入口：

```bash
python -m tests.eval.run_core_evaluation ablation
```

同一组 26 条检索开发样本、同一知识库快照的结果如下。`indexed recall` 只统计当前快照确实
存在且匿名用户有权访问的目标文档，避免把未入库资料错误归因给检索算法。

| 方案 | 全部召回 | 已入库召回 | Hit Rate | MRR | P50/P95(ms) | 无答案拒绝 |
|---|---:|---:|---:|---:|---:|---:|
| Vector | 0.660 | 0.780 | 0.769 | 0.712 | 209/245 | 0.000 |
| BM25 | 0.660 | 0.780 | 0.808 | 0.543 | 0/1 | 0.000 |
| 混合检索 | 0.712 | 0.841 | 0.808 | 0.696 | 213/255 | 0.000 |
| 混合检索 + Qwen 重排 | 0.705 | 0.833 | 0.808 | 0.808 | 600/673 | 0.000 |
| 混合检索 + 重排 + CRAG | 0.679 | 0.803 | 0.808 | 0.769 | 2156/3955 | 0.333 |

结论必须保持克制：固定 0.5/0.5 的混合检索整体有效；无依据的字符长度自适应权重已删除。
Qwen 重排没有提升总体召回（0.841 降到 0.833），但把 MRR 从 0.696 提升到 0.808，
同时 multi-证据类别由 0.800 降到 0.667；CRAG 两次复测的无答案拒绝在 0.333～0.667
之间波动，最新召回降到 0.803、P50 为 2156 ms。它没有证明足以抵消成本的稳定默认收益，
因此默认关闭，只保留显式消融能力。不能把重排或 CRAG 描述为所有维度上的通用增益。

### 05.5.1 默认主链快速回归

在默认关闭 CRAG 后，11 条 quick eval 中 6 条正常问题的 Hit@5 为 1.000、MRR 为 0.889，
平均检索耗时约 1.66 秒；4 条无答案问题正确拒答 3 条，拒答率为 0.750。纯标点、超长重复字符
和随机不存在内容会在检索前或检索后拒绝，但“食堂周末几点开门”这类自然语言越界问题仍可能
召回语义相近资料。因此只能说轻量输入门控有效，不能把 no-答案宣传成已经解决。

## 05.6 深度研究模式结论与前提回归

历史冻结盲测 V2 中，普通模式/深度研究模式的关键点覆盖为 0.865/0.914，引用覆盖为 0.507/0.727，
文档召回为 0.680/0.811；但深度研究模式的 P50 为 27.5 秒，平均输入/输出 Token 约为
12590/2304，逻辑调用约 7.77 次。它有质量收益，但成本远高于普通模式，所以继续显式启用。

历史深度研究模式前提判断只有 0.167。逐条 trace 证明主要问题不在检索，而在审核员把明文支持
或反驳判成 insufficient，以及“是否可以确认”没有进入前提判断 task。修复方式没有新增智能体
或模型调用：分析员也输出带来源编号的三分判断；审核员有直接证据时优先，审核员
不确定时才采用分析员的带来源判断；资料冲突时禁止回退。

已知缺陷定向回归入口：

```bash
python -m tests.eval.run_core_evaluation premise-regression
```

六条冻结前提样本在默认关闭 CRAG 后的回归结果：错误前提 3/3、成立前提 3/3、总体 6/6，
ACL 泄漏 0；P50/P95 为 27.1/34.4 秒，平均逻辑调用约 7.17。该结果只证明已知回归被修复，
不是新盲测，不能替代人工判断。

## 05.7 评测边界与停止条件

统一入口支持 inventory、ablation、rag、深度研究模式-retrieval、深度研究模式-答案-dev、前提判断-regression、
blind-template 和 blind-review。冻结盲测 V2 结果、盲评表与密封映射不允许覆盖；自动指标不
冒充人工质量结论。

当前唯一必须由项目作者或独立评审者完成的事项，是在不打开密封映射的前提下填写
`data/深度研究V2人工盲评评分.json`，再运行 blind-review 汇总。除此之外应停止功能扩张，
重点准备项目演示、失败案例、消融结论和源码讲解。本轮后端全量测试为 294 passed，前端
Vue TypeScript 检查与 Vite 构建通过。

模型模拟盲评另存为 `data/深度研究V2模型模拟盲评评分.json`，不覆盖人工模板。26 条评分在
解盲前锁定，解盲后 B/C 平均分分别为 5.077/5.423，胜场为 B=8、C=9、平局=9。C 在
multi-证据、temporal conflict 和研究简报上更高，B 在前提判断上更高。该结果只能
用作失败分析，不能把 `pending_independent_review` 改写成“人工评测完成”。
