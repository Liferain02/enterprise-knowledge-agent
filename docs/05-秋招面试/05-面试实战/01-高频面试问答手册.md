# 01 高频面试问答手册

同分区还包括[02 简历表达与项目演示](02-简历表达与项目演示.md)和[03 源码追问与白板讲解](03-源码追问与白板讲解.md)。建议先口答本手册，再做八分钟 Demo 和十分钟源码导览。

本文不建议逐字背诵。每题先用“简答”在 20～40 秒内直接回答，面试官继续追问时再展开“深入”。数字必须连同数据集、模型和日期一起说；本文保留的数字是对应评测快照，不是 SLA 或大规模企业结论。

## 一、项目与架构

### 1. 请用一分钟介绍项目

**简答：**这是一个面向研究生实验室的可信知识与科研协作助手。核心主链是带访问控制的混合检索增强生成：文档入库后通过关键词检索、向量检索、排名融合和 Qwen 重排得到证据，然后强制引用回答。对用户显式选择的复杂问题，有资料研究员–分析员–审核员固定深度研究模式。我用冻结评测和消融保留了混合检索与重排，同时因收益不稳定默认关闭纠错检索，没有自动升级多智能体。

### 2. 这不就是一个普通的 RAG Demo 吗？

**简答：**如果只看向量检索加 Chat UI，确实是 Demo。该项目的工程重点在完整证据生命周期：持久化入库队列、混合检索和纠错、JWT 授权刷新、ACL 双层过滤、引用与版本溯源、SSE 可见性契约、阶段 trace、失败归因、开发集/盲测/回归测试分离和产品门槛。

**深入：**应主动承认它仍是小规模单机原型，冻结知识库只有 18 份文档和 40 文档片段。它的价值是信任边界和方法论，不是虚构大规模性能。

### 3. 为什么用 LangGraph？

**简答：**因为项目需要显式的阶段、分支、checkpoint 和有界 revision，不是只串行调几个函数。LangGraph 让 `AgentState` 成为节点协议，并且可用结构图保证审核员最多修订一次。

**反问准备：**如果只有普通模式检索 → 回答生成，普通 async Python 就足够。在当前项目里 LangGraph 的主要价值来自深度研究模式分支、checkpoint 和 SSE event integration，而不是为了使用流行框架。

### 4. 生产图有多少个智能体？

**简答：**普通模式分支是检索和回答生成两个职责节点；深度研究模式有资料研究员、分析员、审核员三个角色，最终复用既有回答生成智能体。没有第四个深度研究模式智能体，终态整理器是确定性节点。

### 5. 为什么删除 Supervisor，而不是保留作展示？

**简答：**它没有进入实际编译图，却增加误读、维护面和潜在 ACL 绕路。项目以可达代码和评测证据为准，因此连同 Parallel Executor、Send 执行和旧 ReAct 知识路径一起删除。

### 6. 为什么路由规划器只保留一个？

**简答：**多层路由会出现决策冲突、重复 LLM 调用和 ACL 绕过。当前路由规划器用规则优先将请求分到 knowledge/operation/general，深度研究模式只根据 API 显式 mode 进入。

### 7. 为什么不自动识别复杂问题进深度研究模式？

**简答：**因为“复杂”不等于“深度研究模式有稳定净收益”。盲测 V2 中深度研究模式 P50 27.5s，普通模式 6.6s，深度研究模式前提判断还明显退化。用户应明确同意更高成本，系统不应悄悄升级。

### 8. 为什么审核员最多修订一次？

**简答：**无限审核员–分析员回环会让延迟、词元、提示词 drift 和最大调用数不可控。一次 revision 是当前产品成本上界。修订后不靠第二轮 LLM Review，而靠 deterministic 声明 validation 守住引用和 ACL 硬边界。

### 9. 为什么没有 Writer 智能体？

**简答：**既有回答生成智能体已经处理 SSE tag、引用、用户身份和冲突信息。深度研究模式只需要把已验证声明映射适配为它的 retrieval 上下文。再造 Writer 会重复生成逻辑，也容易导致普通模式/深度研究模式引用语义不一致。

## 二、RAG 与检索

### 10. 一次普通模式检索经过哪些步骤？

**简答：**查询扩展（条件触发）→ ACL-aware BM25/向量候选 → RRF 融合 → Qwen 重排 → Python 防御性 ACL → 上下文、conflict 和 version 来源 → 回答生成。CRAG 只在显式消融时增加 batch grading 与有界改写。

### 11. 为什么不只用向量检索？

**简答：**文档名、项目缩写、配置项和代码名对词面匹配很敏感，BM25 更稳定；用户的自然语言改写和语义问题则更适合向量。两路用 RRF 融合，避免直接比较不同分数尺度。

### 12. RRF 是什么？

**简答：**Reciprocal Rank Fusion 根据每条检索路的排名累加 `weight/(k+rank)`。当前 `k=60`。一份文档同时在 BM25 和 vector 前列出现时得分更高。优点是不依赖分数校准，缺点是只看排名而不看绝对差距。

### 13. 为什么 RRF 后还需要重排？

**简答：**RRF 是候选融合，只知道两路排名，不会细粒度判断查询与文档的语义配对。重排模型对联合候选做更精细的 cross-encoding 排序；消融中 MRR 从 0.696 提升到 0.808，但总体召回略降，所以应描述为排序收益而非全面收益。

### 14. CRAG 在项目里是什么？

**简答：**它是 Corrective RAG 实验，不是新智能体。两次复测显示召回与延迟退化，三条 no-答案拒绝率还在 0.333～0.667 波动，因此默认关闭；代码和运行脚本保留用于复现实验，而不是强行当主链亮点。

### 15. 查询扩展与深度研究模式拆问有什么不同？

**简答：**普通模式查询扩展是检索内部技术，用多个查询改善候选召回，最后仍由一个回答生成直接答。深度研究模式也拆子问题，但它还建立证据包，后续有声明映射和 Review。深度研究模式的复杂度主要在证据分析和复核，不是只多发几个查询。

### 16. 知识库没结果怎么办？

**简答：**无有效候选时确定性拒答；有低相关候选时由生成约束要求明确证据不足。当前自动检索层 no-答案能力仍不稳定，CRAG 也只做到 0.333～0.667，因此不宣称已经解决。深度研究模式无证据或无合法声明时同样返回证据不足。

### 17. H08/H16 是怎么定位的？

**简答：**我先建 26 条仅检索开发集基准测试，保存原始/重排后/最终 candidates。再检查冻结 Chroma 的 title/来源集合，发现 Nu、Quicksand、Argo、AIFM 只在磁盘，不在 18 份已索引文档里。所以归因是缺失文档，不是 semantic retrieval。

### 18. 为什么没有做命名证据锚点？

**简答：**因为基准没证明通用收益。exact named 和 alias 中深度研究模式与普通模式持平，semantic 反而回落。主要已知失败又是未入库。如果此时加 Anchor，只是针对已看样本过拟合。

### 19. 重排模型不可用怎么办？

**简答：**记录警告，保留混合检索原排序的 top candidates 继续 Grading/回答生成。重排模型是质量优化，不是核心可用性的单点故障。

### 20. 为什么没有换向量库或上 GraphRAG？

**简答：**当前只有 18 份文档、40 文档片段，失败也没有被定位为 Chroma 规模或图关系表达问题。换基础设施会同时改变多个变量，降低评测可解释性。如果未来有大量跨文档关系问题和独立基准，才有证据重新评估。

## 三、ACL 与安全

### 21. ACL 是如何传递的？

**简答：**JWT 识别用户，每次请求从数据库刷新角色/部门，构造 UserContext 进 AgentState。检索候选先按 confidentiality/可见范围做 Chroma 过滤条件，再用 Python 检查部门/project 和角色 restriction。深度研究模式初检索和补检索都复检，后续用 `acl_checked` 和最终声明 validation 守边界。

### 22. 为什么不只用 Chroma 过滤条件？

**简答：**Chroma 适合标量 `$in` 等过滤，但部门/角色列表、空值语义和日期字符串比较不适合全部放在 where clause。而 BM25 还是一条独立候选路。所以候选前过滤用于减少暴露，Python 二次检查用于统一所有路径语义。

### 23. 为什么不在答案后删敏感字段？

**简答：**如果文档已进提示词，敏感事实已经被模型消费，删来源卡片或关键词无法证明答案没有改写泄露。ACL 必须在证据进入提示词前完成。

### 24. 你如何证明深度研究模式没泄密？

**简答：**我不只跑正常查询，而是在测试里故意把 denied restricted 文档注入初检索和 revision 的处理链结果，再扫描证据包、声明、Review、retrieval 上下文、trace、来源 cards 和最终 Answer。固定矩阵 7 项测试通过，未发现标记泄漏。

### 25. ACL violation=0 是不是代表绝对安全？

**简答：**不代表。它只表示预定义的角色×可见范围×project 矩阵和对抗污染样本中没有违规。没有经过安全认证、代码外部审计或大规模攻击面测试。

### 26. JWT 里已经有角色，为什么每次查数据库？

**简答：**JWT 角色是签发时快照。如果管理员之后降权，旧词元在过期前仍会携带旧角色。项目用 JWT 证明身份，用数据库当前值决定授权。

## 四、深度研究模式

### 27. 资料研究员做什么？

**简答：**把原问题最多拆为 4 个子问题，逐个复用带访问控制的混合检索和重排，最多形成 12 条稳定身份去重证据。它输出证据包，同时记录未覆盖子问题、冲突、查询决策和检索过程。

### 28. 分析员为什么不能自己检索？

**简答：**否则“证据是什么”会在分析阶段悄悄改变，访问控制、证据编号和失败归因都会失去边界。分析员只把证据包转成带来源编号的声明映射，让“找到了但没用”可单独测量。

### 29. 声明为什么要分类？

**简答：**事实/比较是证据性陈述，推断/建议是模型对证据的解释或后续行动。如果不区分，研究建议很容易被写成知识库已确认的事实。

### 30. 审核员的 LLM 判断可信吗？

**简答：**不完全可信。审核员适合评估语义支持、冲突和前提，但非法来源编号、空引用、访问控制标记等硬约束由程序检查。盲测 V2 也证明审核员的前提判断仍有真实能力限制。

### 31. 前提判断四态是什么？

**简答：**supported 表示证据直接支持，unsupported 表示直接反驳，insufficient 表示既不支持也不反驳，not_applicable 表示用户本来就没在验证可判真命题。第四态避免普通比较/建议被强行转成前提审判。

### 32. 普通问题的多余前提判断提示解决了吗？

**简答：**解决了任务边界：非前提判断问题被程序强制归一为 not applicable，清空 false flag 和前提判断来源，回答生成不加前提结论。但真正前提判断 task 中判 supported/unsupported/insufficient 的准确性没解决，盲测 V2 只有 0.167。

### 33. 为什么结构化输出还需要归一？

**简答：**JSON 字段结构只降低格式波动，不能消除字段 alias、枚举包装、语义错分类和缺字段。项目用 Pydantic AliasChoices、validator 和确定性 normalization 稳定 wire protocol，再用最终校验保护硬边界。

### 34. 深度研究模式如何得到最终答案？

**简答：**先应用审核员明确否决，再删除无合法来源编号的声明，将 S1..Sn 稳定映射为文档1..n，把已验证声明映射整理为检索上下文，复用普通模式的回答生成规则输出研究简报。

### 35. 为什么“最终通过校验的声明覆盖率”只叫代理指标？

**简答：**它先看是否引用了声明绑定文档，再用词和中文 bigram 重叠判断声明是否被写入。这不能判断否定、因果或语义改写是否正确，所以只能做回归和归因信号。

## 五、SSE、存储与工程

### 36. SSE 如何避免中间智能体输出泄露？

**简答：**只有回答生成 LLM 调用带 `user_visible_answer` tag，ChatService 只转发该 tag 的词元。分析员/审核员的结构化输出只写状态/trace。图结束后还用 checkpoint 的 `final_answer` 校正最终文本。

### 37. 为什么用 SSE 而不是 WebSocket？

**简答：**主链是客户端发一次 HTTP 请求、服务器单向推送词元和状态，SSE 足够且更简单，可复用 HTTP/JWT/代理设施。项目有 WebSocket 兼容通道，但其认证边界弱于 HTTP 主链，不作高权限生产入口。

### 38. 文档入库为什么异步？

**简答：**文档解析、切块、Vision 和向量表示耗时不确定。上传请求只校验、持久化文件和写 SQLite job，工作进程后台处理，支持 retrying、stale recovery 和任务查询。

### 39. 如何处理重复上传？

**简答：**上传时对内容计算 SHA-256，如果队列中相同 hash 已处于 pending/running/retrying/completed，直接返回已存在任务。文档片段 ID 也结合 file hash、index 和 content hash 稳定生成。

### 40. 更新文档怎么避免入库失败后旧文档也丢失？

**简答：**工作进程先 add 新文档片段，成功后再删同来源的 obsolete IDs。不采用先删旧版再计算向量表示的顺序。

### 41. 为什么用 SQLite，不用 PostgreSQL/Redis？

**简答：**当前是单机实验室原型，没有多实例写冲突或高 QPS 证据。SQLite 对用户、会话、队列、版本和项目样例足够，运维简单。Redis 是可选缓存，当服务器网络受限且不需要跨实例共享时，强制引入只会增加故障面。

### 42. 什么时候你会把 SQLite 换掉？

**简答：**当出现多实例共享业务状态、较高并发写、严格 HA/备份恢复、复杂事务或运维平台统一要求时，会将业务库迁到 PostgreSQL；当出现多实例缓存、限流、锁或任务协调需求时再引 Redis。

### 43. 长对话如何处理？

**简答：**超过阈值后将旧的用户可见对话压缩为滚动摘要，保留最近消息。工具和中间智能体消息不进语义摘要。Mem0 默认开启，失败时不阻塞主链，结构化项目事实仍需证据提升门。

## 六、评测与结果

### 44. 为什么不只看最终答案？

**简答：**因为答案失败可以来自未入库、查询 planning、retrieval、重排、ACL、analysis、review 或 generation。只看答案会导致用提示词修复入库问题。我将仅检索、stage trace 和答案-level 评测分开。

### 45. 开发集、盲测和回归测试有什么区别？

**简答：**开发集可看标准答案和失败，用于调试；盲测必须在实现和门槛冻结后创建/运行，用于新数据证据；一旦盲测失败被查看并用于修复，它就变成回归测试，只能检查旧能力是否回退。

### 46. 为什么 V1 不能继续当盲测？

**简答：**H06/H07/H08/H16 等失败已被查看。针对它们的任何修复都使开发者获得了 holdout 信息，所以再跑只是 regression after inspection。

### 47. V2 如何避免污染？

**简答：**先在开发集上完成实现，写预声明门槛，跑全量测试/前端 build，生成源码和知识库 hash 冻结清单，再创建 26 条 V2。Runner 只允许一次正式产物，已存在时拒绝覆盖。人工包候选随机标为甲/乙，映射另存并未打开。

### 48. 最新结果是什么？

**简答：**盲测 V2 中普通模式/深度研究模式均 26/26 成功，ACL 均0。深度研究模式文档召回 0.811 对普通模式 0.679，引用覆盖 0.727 对 0.507，但前提判断 0.167 对 0.667。深度研究模式 P50/P95 27.5/33.0s，普通模式 6.6/9.1s；调用 7.77 对 2.00，输入/输出词元 12590/2304 对 2071/367。

### 49. 这些结果证明深度研究模式更好吗？

**简答：**不证明全局更好。自动评测只能证明固定数据集上的文档召回、引用形式和关键点等代理指标。前提判断安全门槛已经失败；当前没有形成新的独立真人产品结论，模拟评分只用于失败分析。

### 50. 为什么不用 LLM 评分器？

**简答：**本轮要区分回归信号和最终质量，且样本只有 26×2。额外 LLM 可能偏好深度研究模式的长结构化文风，还可能与被评模型共享偏差。因此自动代理指标用于回归，不能把模型模拟评分冒充真人结论；目前只报告这个限制。

### 51. 引用支持度为什么只是代理指标？

**简答：**它主要检查答案句和引用文档的词汇重叠，不能理解否定、时间、因果和条件范围。这个指标可以发现明显引用不相关，但不能叫 faithfulness 或事实正确率。

### 52. 前提判断 0.167 会让你怎么决策？

**简答：**它已低于预声明的“不得比普通模式低超过 0.10”门槛，所以不宣布 V2 通过、不自动路由、不扩大使用范围。深度研究模式保留为显式实验入口，后续只有新的可靠证据才重新评估。

## 七、取舍与反思

### 53. 项目里最大的技术挑战是什么？

**参考回答：**不是某个 API 难调，而是让一条证据在经过检索、重排、ACL、分析、审查和生成后仍能保持来源、权限和语义边界，并在失败时知道是哪一层丢了它。H08/H16 和 ACL 污染测试是这个挑战的两个代表。

### 54. 如果重做一次，你会怎么改？

**参考回答：**我会更早建立文档 registry/index 覆盖率检查和仅检索基准测试，避免从最终答案反推检索问题；更早定义 AgentState 协议和用户可见 event tag，少走 Supervisor/ReAct 的弯路；从第一天就分开开发集/盲测/回归测试。但在当前规模下我仍不会加 Redis、Kafka 或 GraphRAG。

### 55. 项目最失败的尝试是什么？

**参考回答：**早期将“复杂问题”等同于多智能体执行，导致架构延迟、状态和输出协议复杂，而评测没证明稳定收益。后来我把生产图收敛为单路由规划器，普通复杂问题用查询扩展，深度研究模式改为显式有界实验。这比继续调提示词维护一个过大架构更重要。

### 56. 你如何避免过度设计？

**简答：**每个新组件必须有独立职责、输入输出、失败语义和专项评测。先用开发集基准测试证明系统性问题，再实施；无净收益或伤害整体时回退。Named Anchor、第四智能体、Redis 和自动深度研究模式都因没有证据而没做。

### 57. 这个项目最强的亮点是什么？

**参考回答：**我认为是“证据生命周期 + 评测驱动的停止决策”。前者让权限和引用贯穿检索、声明、Review 和最终，后者让我不会因为已经写了多智能体就强行宣布它更好。

### 58. 项目最大的限制是什么？

**简答：**数据和部署规模小，盲测 V2 没有形成新的独立真人产品结论，深度研究模式前提判断安全指标失败，自动支持度仍是代理指标，SQLite/Chroma 没有验证多实例扩展。所以它适合表达 RAG/智能体/评测的系统设计，不应包装成大规模平台。

### 59. 项目现在还要继续开发吗？

**简答：**当前不继续扩张核心智能体功能，重点是面试材料、回归维护和真实故障修复。只有新的 ACL/入库故障、明确用户反馈或可靠评测证据，才重新打开架构优化。

### 60. 如果面试官要你明天上线，你会做什么？

**参考回答：**我不会把当前原型直接当大型企业系统上线。对小范围实验室内测，我会先关闭或严格限制深度研究模式，备份 SQLite/Chroma，检查知识库 registry 与磁盘一致性，更换所有密钥，运行 ACL matrix、全量测试、build 和真实 smoke，定义回滚和数据恢复方案。如果是多租户企业生产，还需要重做存储、密钥、审计、容灾、压测和安全边界，不会虚构“可立即上线”。

## 八、模拟面试使用方法

1. 随机选 10 题，每题限时 40 秒回答。
2. 每题再补一个“备选方案为什么没选”。
3. 对涉及数字的问题，先说数据集身份，再说数字，最后说限制。
4. 对源码问题，必须能说出至少一个文件和函数名。
5. 对难点问题，使用“现象—假设—证据—决策—结果—限制”顺序。
6. 如果回答中出现“完全解决”、“绝对安全”、“企业级高并发”或“多智能体显著更好”，立即检查是否超出证据。
