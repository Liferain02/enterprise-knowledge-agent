# 03 权限、评测与工程故障复盘

本文覆盖安全、评测器、代理网络、依赖和部署中最容易误判的问题。

## 03.1 只在回答后删敏感内容

### 错误方案

全库检索和重排/LLM 后，再从最终答案删除 restricted 片段。

### 风险

- 敏感正文已发送给外部 API。
- 模型可能融合事实，无法可靠按字符串删除。
- trace/cache/工具结果已经包含内容。
- 来源卡片可能仍泄漏标题。

### 修复

Chroma candidate 过滤条件 + 融合后 Python check + 深度研究模式每次检索复核 + 来源 ID 最终校验。

### 验证

高相关 restricted 污染文档在原始 allowed candidate、证据包、声明和最终来源全部为零。

## 03.2 Chroma 过滤条件表达不了完整 ACL

### 现象

日期字符串、空数组、部门/角色 contains 的 where 语义不稳定。

### 错误倾向

为了“检索前过滤”强行把所有逻辑塞进数据库过滤条件，造成合法文档误拒或规则绕过。

### 处理

存储层只下推稳定的 confidentiality/可见范围；部门、角色、active 等在 Python 复核。面试中准确说“两层过滤”，不夸大全部原生下推。

## 03.3 评测器把答案写好看但评分错

### 现象

实现肉眼改善，自动分反而异常；或关键词齐全的错误前提判断得高关键点覆盖。

### 定位

抽查原始答案、标准答案关键点覆盖、分词器/正则表达式和逐样本明细，不直接按总体平均值改模型。

### 修复原则

- 修评测器必须先写最小反例测试。
- 保留旧结果，不覆盖正式报告。
- 不能根据某个盲测样本 ID 特判。
- 区分关键点覆盖代理指标与语义正确性。

### 教训

评测代码也是生产级决策依赖，必须像业务代码一样测试。

## 03.4 盲测数据被看过后继续使用

### 风险

开发者查看 V1 逐题结果后据此修提示词，却继续称其 blind，形成数据污染。

### 修复

将 V1 永久标为历史/回归测试；新建 V2、先冻结门槛s 和代码、正式运行后锁定 SHA-256。

### 边界

V2 自动结果已经可见，也不能再作为新功能调参依据；下一次需 V3 留出集。

## 03.5 大模型评分器偏好长答案

深度研究模式回答更长、更结构化，LLM 评分器可能系统性偏好，且模型家族与被测模型相近。

V2 禁用 LLM-as-a-评分器，使用透明代理指标 + 方案标签盲测评分包。当前没有形成新的独立真人产品结论，因此不作最终收益结论；模型模拟评分只用于失败定位。

## 03.6 Redis 在无公网服务器不可稳定安装

### 场景

服务器只有通过 `set_proxy` 临时联网，Redis 服务和镜像不是可靠部署前提。

### 决策

- 入库队列使用 SQLite。
- CRAG 只保留查询-doc 相关性 grade cache，并有内存降级；不缓存答案或检索结果。
- REDIS_HOST=disabled 不视为故障。
- 核心 RAG 不依赖 Redis。

### 何时引入

多实例共享缓存/任务、真实高并发或跨进程一致性成为测量瓶颈时再引入。

## 03.7 代理只对部分 SDK 生效

### 现象

curl 或 Chat 可访问，DashScope TextReRank/向量表示仍超时。

### 原因

不同 SDK 读取 HTTP_PROXY、HTTPS_PROXY 或自有环境变量；启动脚本环境与交互 shell 也可能不同。

### 排查

1. 确认 SSH 是本地 `-R` 还是 `-L` 方向。
2. 服务器 `curl 127.0.0.1:7897`/代理测试。
3. 查看后端进程真实 env，不输出 key。
4. 分别做 Chat/向量表示/重排最小调用。
5. 检查 no_proxy 是否误绕过。

## 03.8 端口冲突和 SSH 转发方向

项目改用前端 3000、后端 8010，避开另一项目 5173/5174/8000。

访问远程服务通常需要本地转发：

```text
ssh -L 3000:127.0.0.1:3000 -L 8010:127.0.0.1:8010 user@server
```

`-R` 是把客户端端口暴露给服务器，用于代理回传等相反场景，不能用它替代网页本地转发。

## 03.9 启动脚本看似成功但页面打不开

分层检查：

1. `.run` PID 是否存在且进程对应当前项目。
2. 后端本机 `curl 127.0.0.1:8010/health`。
3. 前端本机 `curl 127.0.0.1:3000`。
4. `ss -ltnp` 看绑定地址和端口。
5. 日志检查 Vite/Uvicorn 错误。
6. 再排 SSH tunnel 和浏览器地址。

不要一开始就改 CORS、Nginx 或登录逻辑。

## 03.10 默认密码与 JWT 配置

Settings 在 auth 开启时拒绝仓库占位管理员密码，并要求 JWT secret 至少 32 字符。让配置错误在启动期失败，比运行后留下安全漏洞更好。

日志和文档只写变量名，不写真实值。测试用合成 secret。

## 03.11 SQLite 路径迁移

用户数据库历史路径与当前路径可能不同。直接修路径会让旧账号“消失”。`_merge_legacy_users()` attach 旧库并 INSERT OR IGNORE 合并用户和角色。

数据路径修复必须考虑迁移，不只是改一个常量。

## 03.12 文档漂移

仓库保留 Supervisor 等兼容文件，早期文档容易把它们当生产链。解决方式：文档以编译图和调用链为准，索引标注生产/可选/兼容/限制。

文档链接和术语应自动检查，架构变化必须同步更新总览和代码地图。

## 03.13 质量门槛与业务优先级

如果登录已经可用，继续迭代登录动画/复杂账号体系不会改善知识可信度。优先级应是：入库→检索/ACL→回答/来源→反馈治理→真实性能问题。

这也是对“不要过度设计”的工程落实。
