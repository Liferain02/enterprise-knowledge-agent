# 01 入库、检索与模型故障复盘

本文聚焦数据、检索和外部模型故障。每个案例按现象、错误假设、证据、根因、处理和防复发组织，可直接转成 STAR 故事。

## 01.1 磁盘有论文但检索不到

### 现象

Nu、Quicksand、Argo、AIFM 相关题无论 Normal 还是 Researcher 都失败，最初容易归因成中文英文混合检索弱。

### 错误假设

- top K 太小；
- Embedding 不懂论文名；
- 需要标题检索或 GraphRAG；
- Reranker 把结果删了。

### 证据链

1. 用评测脚本导出 Chroma 全部 title/source。
2. 当前 snapshot 为 40 chunks / 18 documents。
3. 目标四篇不在 title/source 集合。
4. raw candidates 也没有目标。
5. 原始 PDF 只存在磁盘目录。

### 根因

文件存在但没有完成 loader→chunk→embedding→Chroma 的入库链。检索器不可能返回索引外文档。

### 决策

将失败明确标为 `missing_document`，不修改检索算法。评测报告保留这些题，证明 failure attribution 能区分数据问题。

### 防复发

- 入库后检查 stored chunks > 0。
- 对知识目录与 Chroma source 做差集审计。
- 评测前冻结 corpus manifest。
- UI 显示 job status/error。

### 面试表达

> 我没有立即调模型，而是把检索拆成 corpus、raw、rerank、final 四层。最后证明目标根本未入索引，因此停止算法优化，修正失败归因和入库可观测性。

## 01.2 Named Anchor 没有通用收益

### 假设

对包含明确论文名的 query，额外提取标题并进行强锚定搜索，可能改善命名文档召回。

### 实验

在 retrieval-only Development 上保持知识库、模型、top K 不变，对照 baseline 与 anchor，观察 named 类 Recall/MRR、重复候选、延迟和其他类别回退。

### 结果

没有稳定通用提升；部分失败本来就是 missing document，anchor 无法解决，额外查询还会增加成本和标题特例。

### 决策

不合入生产。保留通用 Hybrid + Query Expansion，除非未来已有入库文档的命名题持续出现 lexical/title failure。

### 反思

“听起来合理”的检索技巧必须先定位其能作用的失败阶段。候选不存在时任何精排和 anchor 都无效。

## 01.3 Chat 可用但 Qwen Rerank 不可用

### 现象

对话模型请求成功，但重排仍使用旧 provider、报 SDK/端点错误或没有真正调用 Qwen。

### 根因

Chat、Embedding、Rerank 是不同 API。OpenAI-compatible Chat base URL 和 key 不能自动让 TextReRank 工作；Rerank 需要 DashScope SDK、独立 provider/model 和代理环境。

### 修复思路

- `RERANKER_PROVIDER=qwen`。
- `RERANKER_MODEL=gte-rerank-v2`。
- 每次调用设置正确 DashScope key。
- 将 HTTP proxy 传给 SDK 专用环境变量。
- 非 200/ImportError/异常时保持原候选顺序降级。

### 验证

不能只看接口 200；要记录 provider/model、返回 relevance score，并设计一个原始排序与语义精排明显不同的 case。

### 边界

降级均匀分保证可用性，不等于 Rerank 功能正常。监控必须区分 success 与 fallback。

## 01.4 CRAG 评分限流

### 现象

复杂问题要评估多个候选，出现 429 或 5xx，延迟抖动，部分文档被判 LOW。

### 处理

- Rerank 前置，将评分量从约 15 降到 3–5。
- grader 并发设上限。
- 429/5xx 最多重试 3 次。
- 指数退避叠加 jitter，避免同步重试风暴。
- Redis 可用时缓存，断网使用内存缓存。

### 降级风险

所有重试失败会保守标 LOW，可能导致 NO_RESULTS。因此结果中需要记录“评分失败”而不是把它当真实低相关。

## 01.5 查询拆分过度

### 现象

一个普通列举题被拆成多条相似 query，候选大量重复、延迟上升，但文档覆盖没有增加。

### 原因

复杂度 pattern 过宽，或 Planner 与 Query Expander 判断不一致。

### 处理

- 规则只覆盖明确对比、多实体和顺序任务。
- Normal Expansion 与 Deep 严格区分。
- 子查询去重并限制数量。
- 使用多列表 RRF 合并而不是简单拼接。
- benchmark 比较 avg query count 与 Recall 增益。

### 停止条件

如果 query count 增加而 Recall/MRR 不提高，就收紧规则，不继续优化 Prompt 文风。

## 01.6 切块导致标题语义丢失

### 现象

正文片段描述操作步骤，却没有章节主题，搜索论文名或实验名时匹配弱；来源卡片也难理解。

### 修复

语义 chunk 前追踪父 Markdown heading，并将标题前置；保护列表项，使用相邻句 overlap，过滤 PDF 噪声。

### 验证

不能只看 chunk 数，要用标题查询和正文改写 query 比较 Recall/NDCG，并人工抽查片段是否能独立理解。

## 01.7 文档更新失败导致旧资料丢失

### 风险

传统做法先按 source 删除旧 chunks，再生成新 embedding。外部 embedding 超时会让该资料整个消失。

### 修复

先查询 old IDs，写入稳定 ID 的新 chunks，成功后只删除 obsolete IDs。失败时旧版本仍可用，任务进入 retry。

### 边界

Version SQLite 与 Chroma 不是跨库事务。若版本记录先更新而向量写入失败，仍可能出现元数据状态不一致，需要幂等恢复和运维检查。

## 01.8 如何把案例讲成 STAR

```text
S：关键论文检索连续失败，团队倾向换模型。
T：在不扩大架构的前提下定位真正瓶颈。
A：建立 retrieval-only benchmark，保存 corpus/raw/rerank/final，检查 snapshot。
R：确认目标未入库，将失败归因为 missing_document，避免无效调参，并补充入库可观测与冻结规则。
```

面试重点是证据如何推翻直觉，不是列出用了哪些库。
