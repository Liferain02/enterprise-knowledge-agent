# 01 入库、检索与模型故障复盘

本文聚焦数据、检索和外部模型故障。每个案例按现象、错误假设、证据、根因、处理和防复发组织，可直接转成 STAR 故事。

## 01.1 磁盘有论文但检索不到

### 现象

Nu、Quicksand、Argo、AIFM 相关题无论普通模式还是资料研究员都失败，最初容易归因成中文英文混合检索弱。

### 错误假设

- top K 太小；
- 向量表示不懂论文名；
- 需要标题检索或 GraphRAG；
- 重排模型把结果删了。

### 证据链

1. 用评测脚本导出 Chroma 全部 title/来源。
2. 当前快照为 40 文档片段 / 18 文档。
3. 目标四篇不在 title/来源集合。
4. 原始 candidates 也没有目标。
5. 原始 PDF 只存在磁盘目录。

### 根因

文件存在但没有完成 loader→文档片段→向量表示→Chroma 的入库链。检索器不可能返回索引外文档。

### 决策

将失败明确标为 `missing_document`，不修改检索算法。评测报告保留这些题，证明失败归因能区分数据问题。

### 防复发

- 入库后检查 stored 文档片段 > 0。
- 对知识目录与 Chroma 来源做差集审计。
- 评测前冻结语料库 manifest。
- UI 显示 job 状态/error。

### 面试表达

> 我没有立即调模型，而是把检索拆成语料库、原始、重排、最终四层。最后证明目标根本未入索引，因此停止算法优化，修正失败归因和入库可观测性。

## 01.2 Named Anchor 没有通用收益

### 假设

对包含明确论文名的查询，额外提取标题并进行强锚定搜索，可能改善命名文档召回。

### 实验

在仅检索开发集上保持知识库、模型、top K 不变，对照基线与 anchor，观察 named 类召回率/MRR、重复候选、延迟和其他类别回退。

### 结果

没有稳定通用提升；部分失败本来就是缺失文档，anchor 无法解决，额外查询还会增加成本和标题特例。

### 决策

不合入生产。保留通用混合检索 + 查询扩展，除非未来已有入库文档的命名题持续出现 lexical/title 失败。

### 反思

“听起来合理”的检索技巧必须先定位其能作用的失败阶段。候选不存在时任何精排和 anchor 都无效。

## 01.3 Chat 可用但 Qwen 重排不可用

### 现象

对话模型请求成功，但重排仍使用旧服务提供方、报 SDK/端点错误或没有真正调用 Qwen。

### 根因

Chat、向量表示、重排是不同 API。OpenAI-compatible Chat base URL 和 key 不能自动让 TextReRank 工作；重排需要 DashScope SDK、独立服务提供方/model 和代理环境。

### 修复思路

- `RERANKER_PROVIDER=qwen`。
- `RERANKER_MODEL=gte-rerank-v2`。
- 每次调用设置正确 DashScope key。
- 将 HTTP 代理指标传给 SDK 专用环境变量。
- 非 200/ImportError/异常时保持原候选顺序降级。

### 验证

不能只看接口 200；要记录服务提供方/model、返回 relevance score，并设计一个原始排序与语义精排明显不同的样本。

### 边界

降级均匀分保证可用性，不等于重排功能正常。监控必须区分 success 与降级。

## 01.4 CRAG 评分限流

### 现象

复杂问题要评估多个候选，出现 429 或 5xx，延迟抖动，部分文档被判 LOW。

### 处理

- 重排前置，将评分量从约 15 降到 3–5。
- grader 并发设上限。
- 429/5xx 最多重试 3 次。
- 指数退避叠加 jitter，避免同步重试风暴。
- Redis 可用时缓存，断网使用内存缓存。

### 降级风险

所有重试失败会保守标 LOW，可能导致 NO_RESULTS。因此结果中需要记录“评分失败”而不是把它当真实低相关。

## 01.5 查询拆分过度

### 现象

一个普通列举题被拆成多条相似查询，候选大量重复、延迟上升，但文档覆盖没有增加。

### 原因

复杂度 pattern 过宽，或路由规划器与查询 Expander 判断不一致。

### 处理

- 规则只覆盖明确对比、多实体和顺序任务。
- 普通模式 Expansion 与深度研究模式严格区分。
- 子查询去重并限制数量。
- 使用多列表 RRF 合并而不是简单拼接。
- 基准测试比较 avg 查询 count 与召回率增益。

### 停止条件

如果查询 count 增加而召回率/MRR 不提高，就收紧规则，不继续优化提示词文风。

## 01.6 切块导致标题语义丢失

### 现象

正文片段描述操作步骤，却没有章节主题，搜索论文名或实验名时匹配弱；来源卡片也难理解。

### 修复

语义文档片段前追踪父 Markdown heading，并将标题前置；保护列表项，使用相邻句 overlap，过滤 PDF 噪声。

### 验证

不能只看文档片段数，要用标题查询和正文改写查询比较召回率/NDCG，并人工抽查片段是否能独立理解。

## 01.7 文档更新失败导致旧资料丢失

### 风险

传统做法先按来源删除旧文档片段，再生成新向量表示。外部向量表示超时会让该资料整个消失。

### 修复

先查询 old IDs，写入稳定 ID 的新文档片段，成功后只删除 obsolete IDs。失败时旧版本仍可用，任务进入 retry。

### 边界

Version SQLite 与 Chroma 不是跨库事务。若版本记录先更新而向量写入失败，仍可能出现元数据状态不一致，需要幂等恢复和运维检查。

## 01.8 如何把案例讲成 STAR

```text
S：关键论文检索连续失败，团队倾向换模型。
T：在不扩大架构的前提下定位真正瓶颈。
A：建立仅检索基准测试，保存语料库、原始候选、重排结果和最终结果，并检查快照。
R：确认目标未入库，将失败归因为 missing_document，避免无效调参，并补充入库可观测与冻结规则。
```

面试重点是证据如何推翻直觉，不是列出用了哪些库。
