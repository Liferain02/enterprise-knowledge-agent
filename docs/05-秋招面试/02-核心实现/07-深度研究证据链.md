# 07 深度研究证据链

深度研究模式的重点不是“三个智能体”，而是证据在阶段间如何被结构化、校验和有界修订。本文逐个数据结构和节点解释。

## 07.1 进入条件

只有 API 明确传入 `research_mode="deep"` 才进入固定团队。深度研究模式开关关闭时 ChatService 直接返回 offline 提示。

源码还有 `is_complex_research_task()` 的窄规则，用于分析和兼容，但产品入口不依赖自动复杂度偷偷升级。

## 07.2 固定资源上限

```text
MAX_SUBQUESTIONS = 4
MAX_TARGETED_QUERIES = 2
MAX_EVIDENCES = 12
MAX_EVIDENCE_CHARS = 800
revision_count <= 1
```

这些是图的预算，不是提示词建议。它们限制检索次数、上下文长度、费用和最坏延迟。

## 07.3 证据条目（EvidenceItem）

```python
source_id: S1, S2...
subquestion
title / source
excerpt
score
safe metadata
time_info
conflict_warnings
```

证据条目是可引用的最小证据单元。来源编号在证据包内稳定，分析员只能引用这些编号。

## 07.4 证据包

```python
original_question
subquestions <= 4
evidences <= 12
missing_evidence
conflicts
acl_checked = True
```

它是资料研究员 → 分析员的唯一主要协议。分析员不拿原始全库访问权，也不自己调用检索器。

`acl_checked` 不只是说明字段：最终声明 validator 在 false 时删除全部声明，防止未经校验的包继续生成。

## 07.5 资料研究员子问题规划

资料研究员复用现有 QueryDecomposer。结果经 `SubquestionPlan` 限制和去重；少于两条时用确定性降级：原问题、事实/时间/实验条件、冲突/缺失/建议依据。

结构化规划失败不会启动另一个智能体，而是降级为最多 4 条固定查询。

## 07.6 资料研究员检索

每个子问题依次调用现有 ACL-aware CRAG：

```python
pipeline.retrieve(
  query=subquestion,
  top_k=5,
  needs_expansion=False,
  user=user_context,
)
```

`needs_expansion=False` 防止深度研究模式子问题内部再次无限拆分。每次结果又做 `check_doc_access()`，记录决策、rewrite 历史、标题和错误。

## 07.7 证据去重与排序

去重 key 由来源/title 与正文前 300 字组合；同一证据多次命中时保留更高分。所有结果按分数排序，只取前 12 条。

excerpt 截断到 800 字，元数据经过白名单，只保留 title、项目、可见范围、版本、时间等字段，不把任意上传字段带给后续模型。

## 07.8 声明模型

```python
claim_id
text <= 200
claim_type: fact | comparison | inference | recommendation
source_ids
confidence: high | medium | low
```

事实、比较、推断和建议分开，能防止模型把建议写成已证实事实。`limitation` 仅作 wire 兼容，归一后移到 report limitations。

## 07.9 AnalysisReport

```text
claims <= 12
comparison <= 300 chars
uncovered_source_ids
limitations（归一后最多 4）
draft_answer（兼容字段，正式流程留空）
```

分析员被要求生成 6–10 条紧凑声明，每条绑定来源。最终文字不由分析员写，而由回答生成根据校验后的声明组织。

## 07.10 为什么结构化输出仍不可靠

Qwen 可能：

- 使用 `claim_text` 而非 `text`；
- 把 enum 包成对象；
- 把建议标成 fact；
- 只填 draft_答案；
- 引用不存在的 S 编号；
- limitations 超出产品上限。

Pydantic AliasChoices、field validator 和 `_normalize_analysis()` 共同兼容常见形态。结构化输出只是语法协议，不能保证语义正确。

## 07.11 Analysis 归一

归一过程：

1. 生成缺失声明 ID。
2. 删除不在证据包的来源 ID。
3. 用关键词把“建议/下一步”从 fact 改为 recommendation。
4. 把“推断/可能”改为 inference。
5. 若只有 draft_答案，从带 `[Sx]` 的句子恢复声明。
6. 重新计算 uncovered 来源 IDs。
7. limitations 去重并截断。

归一规则不根据评测样本 ID 写补丁，因此仍具有通用性。

## 07.12 ReviewItem 与 ReviewReport

ReviewItem 记录声明、来源 IDs、是否支持、问题类型和修订指令。问题类型包括 unsupported、invalid_来源、false_premise、conflict、acl、missing_证据、citation_gap。

ReviewReport 包括：

```text
decision: PASS | REVISE | NEED_MORE_EVIDENCE
items
premise_assessment
premise_source_ids
conflict_handled / acl_verified
overall_instruction
targeted_queries <= 2
```

审核员不生成最终答案，也不能自己检索。

## 07.13 确定性审核员前置检查

`_deterministic_review_issues()` 扫描所有声明：

- 非法 来源 ID → invalid_来源。
- 来源 IDs 为空 → citation_gap。

只要存在确定性问题，即使 LLM 审核员返回 PASS，也会改成 REVISE。这把不可妥协的引用规则从概率模型移到程序。

## 07.14 前提判断四态

```text
not_applicable：不是前提核验问题
supported：证据明确支持前提
unsupported：证据明确反驳前提
insufficient：现有证据既不能支持也不能反驳
```

`_is_premise_task()` 只识别用户是否明确要求验证一个命题，不判断真假。普通对比、总结、建议即使出现“判断”也会归一为 not_applicable。

## 07.15 为什么不能“绝对词=错误前提”

制度可能明确写“所有成员必须……”。看到“所有”就默认 unsupported 会反过来违背证据。因此审核员使用三分法：直接支持→supported；直接相反→unsupported；没有覆盖→insufficient。

supported/unsupported 必须绑定前提判断来源 IDs；insufficient 可以为空。

## 07.16 审核员结构化失败

调用失败时采取安全降级：有证据则 REVISE，没有证据则 NEED_MORE_EVIDENCE，并要求只保留明确引用声明。失败不会默认 PASS。

这体现默认拒绝，但会增加保守性。trace 应记录复核服务失败，避免误判成业务证据不足。

## 07.17 修订

当决策要求修订且修订次数为 0：

1. 最多取 2 条 targeted 查询。
2. 通过相同 ACL 处理链补充证据。
3. 合并包，去重并维持最多 12 条。
4. 分析员根据 ReviewReport 做一次针对性重写。
5. 修订次数设为 1。

修订后不再回审核员，直接执行最终确定性声明校验。这是延迟与复核强度的折中。

## 07.18 最终声明校验

`_validate_claims_for_finalization()`：

- package 未 ACL checked → 删除全部声明。
- 来源 ID 非法或为空 → 删除该声明。
- 来源 IDs 去重。
- 将删除数量写入 limitation。

它不会猜测“S99 可能是 S9”，因为安全协议不应靠模糊修复。

## 07.19 最终生成

深度研究模式生成上下文包含证据、声明映射、Review 结论、limitations 和指定研究简报结构，字符上限约 1400。随后复用普通模式 `generation_agent_node()`。

复用避免新增 Writer 智能体，也让引用安全提示、用户身份和生成指标保持一致。

## 07.20 前提判断前缀

对真正前提判断 task，程序确保最终答案顶部有确定性结论，例如支持、反驳或证据不足。not_applicable 不添加前提段，避免普通问题出现突兀“前提核验”。

## 07.21 最终覆盖率代理指标

生成后比较 validated 声明与最终答案的关键词覆盖，记录：

- omitted validated 声明 IDs；
- 最终通过校验的声明覆盖率代理指标；
- 最终声明引用覆盖率。

它只能发现“声明可能没写进答案”，不能证明表述真正忠实，因此必须保留代理指标名称。

## 07.22 失败归因

运行时归因为：

```text
retrieval | analysis | review | generation
knowledge_gap | acl | none
```

没有标准答案时只能区分大阶段。例如证据为空可能是 retrieval 或 knowledge gap，结合查询 runs 再判断。离线基准测试有预期文档，才能细分缺失文档/重排失败。

## 07.23 Research 执行轨迹

每个阶段保存可序列化摘要：

| 阶段 | 内容 |
|---|---|
| researcher | 子问题、查询 runs、证据标题、缺失项、耗时/词元 |
| analyst | 声明、未覆盖来源、覆盖率 |
| reviewer | 决策、前提判断、问题与修订要求 |
| revision | targeted 查询、新证据、前后声明 |
| generation | validated/dropped/omitted 声明、覆盖率、归因 |

trace 用于评测和诊断，不直接完整展示给普通用户，也不应持久化超出权限的全文。

## 07.24 结构化调用实现

`_invoke_structured()`：

1. 在提示词中显式要求 JSON，兼容 DashScope JSON mode。
2. `with_structured_output(schema, include_raw=True)`。
3. 抑制已知 Pydantic serializer 假阳性 warning。
4. parsed 为空时抛出明确错误。
5. 用 `model_validate()` 再校验。
6. 尽可能从原始 usage 元数据提取词元。

这套封装让三个角色不重复处理 SDK 差异。

## 07.25 为什么当前不能默认上线

盲测 V2 自动结果：深度研究模式召回率 0.811 对普通模式 0.679，Citation 覆盖率 0.727 对 0.507；但前提判断 0.167 对 0.667，P50 27.5 秒对 6.6 秒，调用和词元也显著增加。

因此深度研究模式只作为显式能力。架构完成不等于产品门槛通过。

## 07.26 已知边界

- 修订后没有第二次独立审核员，仅有确定性引用校验。
- 自动覆盖率无法替代人工 faithfulness。
- 12 条、800 字可能截断长证据。
- 子查询依次执行，延迟较高；盲目并行又可能触发限流。
- 前提判断分类规则仍可能遗漏自然语言表达。
- 没有形成新的独立真人 V2 产品结论；模型模拟评分仅用于失败定位。

这些限制比继续增加智能体更值得优先验证。
