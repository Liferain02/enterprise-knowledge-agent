# 08 前端状态管理与交互

前端不仅是聊天框，还承担登录恢复、三个工作区、流式消息、资料管理、入库轮询、反馈和科研协作。本文件说明当前单组件实现及其边界。

## 08.1 三个工作区

```typescript
activeWorkspace: 'chat' | 'knowledge' | 'research'
```

- chat：会话、Normal/Deep、回答、来源和反馈。
- knowledge：资料目录、筛选、上传、搜索、入库任务、反馈问题。
- research：项目列表、实验记录、行动项和概览。

使用一个 `App.vue` 降低演示和状态传递复杂度；文件已经较大，继续增长时应按 workspace 拆组件和 composable，但当前不引入 Pinia 只为“架构好看”。

## 08.2 登录状态

token 保存在 `localStorage.eka_token`，Axios 默认 Authorization header 随登录/登出更新。用户展示信息保存在 `eka_current_user`。

页面恢复时不会只相信 localStorage：会调用 sessions 接口验证 token，有效后再加载数据；401/异常时 logout 清空状态。

localStorage token 易受 XSS 影响。当前是内网原型；更高安全要求可改 HttpOnly/SameSite cookie、CSP 和 CSRF 防护。

## 08.3 服务端身份覆盖本地缓存

SSE 首先发送 `user_profile`，前端用其覆盖 currentUser 和缓存。这样角色变更后 UI 会使用服务端当前值，而不是继续显示登录时旧角色。

前端的 `canManageKnowledge` 只控制按钮显示；真正权限仍由后端 403 保证。

## 08.4 会话状态

关键 state：

```text
sessionId / sessions / messages
inputMessage / loading / currentAgent
partialAnswer / partialAnswerKey
pendingSources / pendingVersionSource
abortController
```

发送前把用户消息和空 assistant placeholder 加入数组，token 到达时原位替换 placeholder，避免每个 token 都新增一条消息。

## 08.5 Deep 模式是单次状态

发送时先快照再复位：

```typescript
const requestResearchMode = researchMode.value
researchMode.value = 'normal'
```

新会话、刷新和退出也不会继承 Deep。loading 时控件禁用，防止本轮请求中途改变。

## 08.6 fetch 流式读取

因为原生 EventSource 只方便 GET，当前 POST SSE 使用 `fetch`：

```text
fetch POST
→ response.body.getReader()
→ TextDecoder(stream=true)
→ 逐块读取
→ 解析 data: JSON
→ 按 event.type 更新状态
```

`llm_token` 增量拼接，sources/version 先缓存，流结束后挂到最终消息。

## 08.7 当前 SSE 解析限制

代码按每次网络 chunk 的换行拆分，并对无法解析的行静默忽略，但没有维护跨 chunk 的残余 buffer。TCP chunk 边界不保证与 SSE 行一致，因此一个 JSON 行被拆成两次 read 时可能丢事件。

当前真实测试未把它标为阻断问题，但这是明确的工程改进点。正确增强应维护 `buffer += decoder.decode(...)`，只处理完整 `\n\n` 帧，剩余半帧留到下一轮。它比继续扩展 UI 功能优先级更高，但应通过复现测试后修改。

## 08.8 取消请求

再次点击发送按钮时，如果 loading：

1. 调用 `AbortController.abort()`。
2. 清理 loading 和 partial state。
3. 显示“已手动取消回答”。

这只取消浏览器连接，不保证服务器端 LangGraph/LLM 已停止。要真正节省后端成本，需要将 client disconnect 传播成 task cancellation，当前尚未实现。

## 08.9 流结束处理

完成后：

- final assistant message 写入 agent 和 sources；
- version source 追加到正文；
- 刷新会话列表，获得标题和消息数；
- finally 清空所有 pending 状态和 AbortController；
- 滚动到底部。

finally 无论成功、错误还是取消都执行，避免 UI 卡在 loading。

## 08.10 Markdown 渲染

回答用 `marked.parse()` 渲染，并配合高亮库展示代码。任何 Markdown/HTML 渲染都需关注 XSS；如果未启用严格 sanitize，就不能把它描述成已完成内容安全。

正式对外部署应引入 DOMPurify 或禁用原始 HTML，并用测试覆盖脚本标签、事件属性和危险 URL。

## 08.11 资料中心

资料目录 state 包括 overview、documents、filters、upload form、search results、ingestion jobs。

上传使用 multipart FormData，字段与后端 metadata 对齐。任务每 4 秒轮询，但只在 knowledge workspace 激活时请求，减少无意义流量。新 completed job 出现时刷新目录。

轮询适合低频任务；任务量或客户端量上升时可以改 SSE/WebSocket 通知，但当前不需要额外基础设施。

## 08.12 搜索与目录的区别

- 目录 API：按 source 聚合，面向浏览和管理。
- search API：返回 chunk 级相关结果，面向验证检索。

前端分别维护列表，避免把 chunk 数误当文档数。

## 08.13 反馈交互

每条 assistant message 保存其 question 和 feedbackSubmitted。点击 helpful 直接提交；incorrect/missing material 提示补充评论。

提交成功后禁用本消息的反馈按钮，避免重复点击。这个限制只在当前前端消息状态，后端没有严格幂等键，因此脚本仍可重复提交；这是轻量产品边界。

审阅角色可在资料中心切换 open/resolved，并在解决时填写 resolution note。

## 08.14 科研空间交互

选择项目后并行/顺序加载 experiments 和 tasks。表单把 metrics 文本解析为 JSON，提交 hypothesis、environment、commit、dataset version、conclusion 和 next steps。

组会纪要输入提交给后端确定性提取，不在浏览器正则解析，使规则和权限集中在服务端。

## 08.15 健康检查

登录后每 30 秒调用 `/health` 更新连接状态；3 秒超时。health 成功只说明 API 可访问，不证明 LLM、Embedding、Rerank、Chroma 全部健康。

更完善的 readiness 可以分别报告依赖，但不要让外部模型短时波动导致进程存活探针重启服务。

## 08.16 响应式与无障碍

当前界面支持基本窄屏布局和表单 label/disabled 状态，但没有完整 WCAG 审计、键盘焦点管理和屏幕阅读器测试。面试可以说做了响应式产品验证，不能说达到无障碍标准。

## 08.17 为什么暂不引入全局状态库

状态主要属于单页面、没有深层组件传递；Pinia 会增加文件和概念，但当前收益有限。触发拆分的证据可以是：

- App.vue 多人频繁冲突；
- 多路由需要共享状态；
- 状态生命周期难以测试；
- workspace 组件需要重复请求逻辑。

## 08.18 前端测试重点

1. 登录失效后清空状态。
2. Normal/Deep 单次复位。
3. SSE JSON 跨 chunk 分帧。
4. sources 在 token 后正确挂载。
5. 取消和网络错误不留 loading。
6. 上传 completed 后目录刷新。
7. 非管理角色不能看到管理按钮，后端仍返回 403。
8. Markdown XSS 输入被安全处理。

当前构建通过不等于这些行为全部有自动化覆盖，真实浏览器巡检仍是必要补充。
