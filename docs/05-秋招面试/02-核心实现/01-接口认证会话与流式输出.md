# 01 接口、认证、会话与流式输出

本文从 HTTP 边界讲到流式完成，重点解释身份如何刷新、会话如何隔离、事件如何过滤，以及为何图结束后还要读取 checkpoint。

## 01.1 API 分层

```text
Controller：HTTP 路由、依赖注入、状态码
Service：业务编排、会话与 Agent 调用
Repository/DAO：SQLite 持久化
Agent/RAG：推理、检索与生成
```

以流式聊天为例：Controller 不直接调用 LangGraph 节点，而是把验证后的参数交给 `ChatService.achat_stream()`。这样非流式、流式、A2A 等入口可以复用 ChatService 语义。

## 01.2 请求与响应协议

核心请求：

```python
class ChatStreamRequest(BaseModel):
    message: str
    session_id: str = "default"
    images: Optional[List[ImageContent]] = None
    research_mode: Literal["normal", "deep"] = "normal"
```

使用 Literal 的意义是非法模式在进入业务代码前就返回 422，不需要在每个节点防御诸如 `research_mode="auto"` 的未知状态。

非流式 `/chat` 返回一个完整对象；流式 `/chat/stream` 返回 `text/event-stream`。两条路径共享模式开关、身份、Vision、图和持久化逻辑，但流式路径额外承担事件过滤。

## 01.3 登录与密码存储

数据库用户位于 `data/users.db`：

```text
users
roles
user_roles
role_permissions
```

新密码使用 Argon2 哈希。历史 SHA-256 账号不是一次性强制迁移，而是在首次成功登录后调用 `verify_password_and_upgrade()` 原位升级。这减少了升级时要求所有用户重置密码的影响。

注册约束包括用户名 3–32 字符、字母数字下划线，密码 6–128 字符。这里是最低产品约束，不应宣称满足所有企业密码策略。

配置管理员是数据库账号之外的回退身份，token 中用 `auth_source=config_admin` 区分。若数据库出现同名账号，数据库用户优先，避免两套身份混淆。

## 01.4 JWT 内容与信任边界

Token 使用 HS256，包含：

```json
{
  "sub": "alice",
  "role": "viewer",
  "department": "",
  "auth_source": "database",
  "iat": 0,
  "exp": 0
}
```

其中 `sub/iat/exp/auth_source` 用来确认身份和有效期；role/department 只作为历史兼容快照，不能作为当前授权依据。

`get_current_user()` 每次请求都会：

1. 解码并验证签名和过期时间。
2. 读取 `sub`。
3. 按 `auth_source` 区分数据库用户和配置管理员。
4. 对数据库用户重新查询账号和角色。
5. 用户被删除、来源非法或管理员身份冲突时返回 401。

因此管理员撤销某用户角色后，无需等待旧 JWT 过期，后续请求就使用新权限。这是“认证与授权分离”的具体实现。

## 01.5 API 角色检查与文档 ACL 的区别

上传、删除、清空知识库使用路由级角色集合：

```text
EDITOR_ROLES → 上传/删除单文档
ADMIN_ROLES  → 清空知识库
```

这回答“用户能否执行管理动作”。检索 ACL 则回答“这个用户能看到哪些文档”。前者不能替代后者：一个普通成员虽然可以调用搜索接口，也不能看到 restricted 资料。

## 01.6 会话复合主键

对外 session ID 由前端生成或使用默认值；内部持久化通过：

```text
internal_session_id = user_id + "_" + session_id
```

SessionService 的 create/get/list/save/delete 都先组合内部 ID。这样：

- Alice 的 `default` 与 Bob 的 `default` 不冲突；
- 列表查询可以只返回当前用户前缀下的会话；
- 删除会话不会误删其他用户同名会话。

LangGraph checkpointer 的 `thread_id` 使用相同复合规则，使业务消息和图状态具有一致隔离维度。

## 01.7 Session 与 Message 数据

`sessions` 记录标题、创建/更新时间和 message count；`messages` 记录 role、content、时间与 JSON metadata。助手消息 metadata 包括 used agent 与 source cards。

首次消息的标题生成必须发生在 message count 增加前，或显式保存 `is_first_message`。流式路径先读取 session 状态，再保存 user/assistant，最后更新标题。

历史兼容迁移函数负责处理旧的无用户前缀消息，避免修正隔离规则后原会话突然消失。它是数据迁移兼容，不应成为新请求的正常分支。

## 01.8 SSE 编码

`_sse_event()` 将事件编码为标准帧：

```text
event: llm_token
data: {"...": "..."}

```

数据必须 JSON 序列化，帧以两个换行结束。前端按事件类型分发，而不是从一段混合文本中猜测来源和状态。

## 01.9 用户可见 token 过滤

LangGraph 的 `astream_events(version="v2")` 会产生所有嵌套模型调用事件，包括：

- 摘要模型；
- Planner；
- CRAG Grader；
- Researcher/Analyst/Reviewer；
- 最终 Generation。

如果把所有 `on_chat_model_stream` 直接发给前端，用户会看到 JSON、审查理由和内部 Prompt 片段。项目只允许带 `user_visible_answer` tag 的生成调用通过 `_is_user_visible_llm_event()`。

Generation 调用显式设置：

```python
config={"tags": ["user_visible_answer"]}
```

这是输出协议，不只是界面过滤：内部推理与用户回答在事件源头被区分。

## 01.10 为什么仍监听 tool 事件

Operation Agent 的工具调用不产生回答 token，但用户需要知道正在执行什么。SSE 将 `on_tool_start/on_tool_end` 转成：

- `tool_start`：工具名；
- `thinking`：用户友好进度；
- `tool_end`：工具名和截断后的输入摘要。

输入摘要只取前 100 字，避免把大量内容或敏感参数原样推送。文件工具本身仍受 MCP 目录白名单约束。

## 01.11 为什么图结束后读取 checkpoint

流式 token 只能得到文本片段，拿不到完整业务 state 中的：

- `retrieved_docs`
- `used_agent`
- `version_source`
- `research_trace`
- 最终确定性修改后的 `final_answer`

因此事件流完成后调用 `graph.aget_state(config)`。要读取 `state_snapshot.values`，而不是把底层 checkpointer 对象当业务 dict。

若 checkpoint 的 final answer 与已收集 token 不同，以 checkpoint 为准；若某分支根本没有用户可见模型 token（例如确定性拒答或工具返回），则在图结束后一次性补发 `llm_token`。

## 01.12 流式持久化顺序

正常流式链：

1. 确保 session 存在。
2. 运行图并发送 token/progress。
3. 读取最终 checkpoint。
4. 保存原始用户问题，而不是图片展开后的内部文本。
5. 保存最终回答和来源 metadata。
6. 首条消息更新标题。
7. 发送 `sources`、`used_agent`、`version_source` 和 `done`。
8. 可选 Mem0 写入后台执行。

保存原始问题可避免用户历史出现大段图片描述或系统注入上下文。

## 01.13 特殊快速路径

Deep 开关关闭时，ChatService 确定性返回 offline 提示，不进入图。新生导览命中确定性产品逻辑时也直接组织已授权项目与起步资料。

这些路径仍必须发送完整的 SSE 结束序列，不能只返回一段文本后让前端永久 loading。

## 01.14 异常处理

流式异常需要满足：

- 服务端记录堆栈，但不泄漏 key 和敏感上下文；
- 前端收到可读 `error`；
- 连接能结束，loading 被清理；
- 已经发送的部分 token 不重复持久化成两条回答；
- 失败不会错误标记为 completed Deep trace。

非流式路径则通过 FastAPI HTTPException 返回状态码。两种协议的失败表现不同，但业务错误语义应一致。

## 01.15 面试追问

**为什么不用 JWT 里的 role？** 因为 token 有有效期，角色撤销后旧 token 仍会携带旧值；每次查数据库能让授权变化立即生效。

**SSE 断线能续传吗？** 当前没有事件 ID 和断点续传，属于已知边界。回答可能已生成但前端未完整接收，需要从会话历史重新加载。

**为什么不先保存空 assistant 消息再逐 token 更新？** 当前规模下结束后一次保存更简单，避免频繁 SQLite 更新；代价是进程中断时部分回答不会持久化。

**是否企业级认证？** 不是。实现了 JWT、Argon2、RBAC 和实时角色刷新，但未接 OIDC/SSO、MFA、集中审计和密钥轮换。
