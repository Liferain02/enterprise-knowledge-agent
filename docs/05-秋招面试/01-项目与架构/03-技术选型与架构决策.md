# 03 技术选型与架构决策

本文不罗列技术栈，而是说明每项选择解决了什么、替代方案是什么、为什么当前没有继续扩张。

## 03.1 FastAPI 与 Pydantic

选择原因：

- async endpoint 能自然承接模型调用和 SSE。
- Pydantic 统一校验 `research_mode`、资料 metadata、反馈状态等协议。
- Depends 把认证放到路由边界，业务服务无需自己解析 token。
- OpenAPI 便于前后端联调。

没有选择重型微服务框架，因为当前单机实验室规模不需要服务发现、分布式事务或多团队自治。FastAPI 单体内部按 controller/service/repository 分层已经足够。

## 03.2 Vue 3 + TypeScript + Vite

选择原因是开发反馈快、类型能约束 SSE/接口状态、部署简单。当前所有工作区仍集中在 `App.vue`，这是一个已知可维护性问题；但拆成 Pinia、复杂组件层级和微前端不能改善 RAG 正确性，因此只在前端继续增长时再拆。

## 03.3 LangGraph 而不是手写 if/else

项目需要：

- 多节点共享显式 state；
- 条件边；
- checkpoint/thread 隔离；
- 流式事件；
- 有界 Reviewer 修订。

这些需求使 LangGraph 比散落在 Service 中的 if/else 更容易观察和测试。但图没有被用来制造 Agent 数量：Normal 仍只有 Planner、Retrieval、Generation 等明确节点。

## 03.4 为什么移除生产 Supervisor

Planner 已经能区分 knowledge/operation/general。再放一个 Supervisor 会导致：

- 同一问题发生两次路由模型调用；
- 两层决策可能矛盾；
- 延迟和 token 增加；
- trace 更难归因。

因此当前图以确定性 Planner 作为唯一入口，Supervisor 及其兼容代码已删除。架构价值来自职责清晰，不来自路由层级数量。

## 03.5 为什么 Normal 不使用 ReAct 检索

知识问答的默认检索顺序是确定的：Hybrid → Rerank → Generate。CRAG 只保留显式实验。让 ReAct Agent 自主决定是否调用搜索工具会增加：

- tool selection 失败；
- 重复检索和不可控循环；
- 中间消息污染会话；
- 难以做 retrieval-only benchmark。

因此生产 Normal 直接调用 pipeline，检索与生成拆成两个节点。Operation Agent 才保留 ReAct，因为计算、时间、文件等任务确实需要动态工具选择。

## 03.6 ChromaDB

当前选择 Chroma 的原因：

- 本地持久化，部署和备份简单；
- 支持 metadata filter；
- 与 LangChain Document/Embedding 适配成熟；
- 18 文档、40 chunks 的规模没有显示基础设施瓶颈。

没有切 Milvus/Weaviate/Elasticsearch 向量集群，因为当前缺乏百万级数据、高并发、分片和多租户性能证据。更换存储会改变大量变量，却不能修复“文档根本没入库”这类实际失败。

## 03.7 BM25 + 向量而不是单一路径

向量擅长语义改写，BM25 擅长专有名词、命令、论文名和短查询。实验室资料中 RDMA、NUMA、AIFM、配置参数等词法信号重要，因此两路互补。

BM25 优先使用 `bm25s`，不可用时退回 `rank_bm25`；中文统一用 Jieba，且支持一次性加载项目词典。

## 03.8 为什么使用 RRF

Chroma 距离和 BM25 分数不在同一量纲，直接线性相加需要脆弱的归一化。RRF 只使用排名：

```text
score(d) = Σ_i weight_i / (K + rank_i(d)), K=60
```

它牺牲部分绝对分信息，换取跨检索器稳定性。项目仍保留 score fusion 作为兼容降级，但默认使用 RRF。

## 03.9 Qwen Rerank 独立于 Chat 模型

对话、Embedding、Rerank 是三类不同 API：

```text
Chat       → qwen3.5-flash
Embedding  → text-embedding-v2
Rerank     → gte-rerank-v2
```

OpenAI-compatible Chat endpoint 不代表能提供 Embedding 或 Rerank。独立 provider/model 配置可以避免因为切换对话模型而误用不存在的重排接口。

Reranker 的职责是对已召回候选做 query-document 相关性精排，它不能找回候选集中不存在的文档。因此召回失败与重排失败必须分开归因。

## 03.10 CRAG 的价值与代价

CRAG 在生成前逐文档评估相关性，根据 HIGH/MEDIUM/LOW/NO_RESULTS 决定直接使用、改写或拒答。它改善低质量上下文进入模型的问题，但也增加 LLM 调用和延迟。

项目通过以下方式控制成本：

- 先 Rerank，减少要评分的文档数；
- 评分并发上限；
- Redis 可用时缓存，断网用进程内缓存；
- 只进行有界重写/分解，不无限自纠错。

## 03.11 SQLite 任务队列而不是 Redis/Celery

服务器网络受限，Redis 不是稳定前置依赖。入库任务需要的核心能力只是持久化状态、单机 worker、失败重试和重启恢复，SQLite 足够。

选择 SQLite 的收益：

- 无额外服务；
- 重启后任务仍在；
- 状态可以直接查询；
- 适合低频文档上传。

代价是跨机器并发、精确租约、高吞吐和可观测性有限。若未来出现多实例部署或大量入库任务，再引入 Redis/Celery/Kafka 才有证据。

## 03.12 SQLite 业务存储的职责分离

会话/反馈、用户、入库任务、科研空间并非强行塞进单表，而是按服务生命周期使用不同 SQLite 文件。这样迁移和备份简单，但不应描述成企业级数据库架构。

如果未来需要多实例写入、复杂查询和严格事务，应迁移 PostgreSQL；当前没有为假设中的规模提前承担运维成本。

## 03.13 SSE 而不是 WebSocket

聊天主链主要是服务端向浏览器单向推送进度、token、来源和完成信号。SSE：

- 基于 HTTP，代理和调试简单；
- 浏览器消费事件方便；
- 自动按文本事件分帧；
- 不需要维护双向长连接协议。

WebSocket 接口可以作为兼容能力，但不是主链。只有协同编辑、客户端实时控制任务等强双向需求出现时，WebSocket 才更合适。

## 03.14 摘要与 Mem0 双层记忆

摘要解决单会话上下文过长，Mem0 解决可选跨会话偏好。两者分离：

- 摘要属于图状态，默认开启且只压缩用户可见消息。
- Mem0 默认开启，失败不阻塞请求，写入在响应后后台执行；项目事实仍不能绕过证据验证直接沉淀。

长期记忆不能替代知识库。用户历史说过的内容不自动获得与正式文档相同的可信等级。

## 03.15 显式 Deep 而不是自动升级

自动判断复杂度并不等于能判断 Deep 是否值得。V2 显示 Deep 召回和引用覆盖更高，但 premise 更差、延迟与 token 大幅增加。

因此产品策略是：

- Normal 默认；
- 用户显式 opt-in；
- Deep 选择只对一轮生效；
- 关闭开关时确定性提示 offline；
- 不用 Planner 悄悄升级。

这是质量、成本和用户控制权共同决定的策略。

## 03.16 为什么 Deep 只有三个角色

Researcher、Analyst、Reviewer 分别对应搜证、成论、审查。最终写作复用已有 Generation Agent，因为再增加 Writer Agent 会重复生成能力和 Prompt 维护。

Reviewer 最多一次修订，避免形成不可终止回环。固定拓扑也便于把每阶段输入输出写进 trace 和评测。

## 03.17 为什么没有 GraphRAG

当前失败主要来自未入库、关键词/语义召回、重排、前提判断和评测器问题，没有证据显示“跨多跳实体关系无法表达”是首要瓶颈。冻结数据只有 40 chunks，构建图抽取、实体消歧和图存储属于高成本变量。

当同时满足以下条件时才重新评估 GraphRAG：

1. 有足够多文档和稳定实体关系。
2. 建立专门的多跳/关系问题基准。
3. 现有 Hybrid 在该基准持续失败。
4. 失败能归因于关系连接，而非缺文档或 ACL。

## 03.18 MCP 与 A2A 的定位

MCP 只为 Operation Agent 提供受限工具，filesystem server 的目录白名单是 `data/knowledge`。A2A 只实现 Agent Card 与简化消息兼容层。

二者都是扩展性验证，不是核心卖点。MCP 不可用时返回空工具，A2A 也没有完整任务取消、推送和身份委托。准确描述完成度比协议名数量更重要。

## 03.19 决策记录模板

未来任何架构变化都应回答：

```text
问题：当前哪项可观察指标失败？
证据：日志、测试或 benchmark 是什么？
最小方案：能否只改一个变量？
替代方案：至少比较哪两种做法？
成功标准：改动前预声明什么 gate？
回滚：失败时如何恢复？
文档：哪些架构、评测和运维说明需要同步？
```

这套模板能防止“看到开源项目有某功能，所以也接入”成为架构理由。
