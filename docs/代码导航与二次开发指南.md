# 代码导航与二次开发指南

本文帮助开发者快速找到真实实现、修改最小范围代码，并用相应测试证明变更没有破坏主链。

## 2. 第一次阅读的推荐顺序

1. `docs/项目定位与总体方案.md`：先确定产品重点；
2. `src/agent/graph.py`：看生产节点和边；
3. `src/api/services/chat_service.py`：看请求如何驱动图和 SSE；
4. `src/agent/agents/planner.py` 前 400 行：看实际路由；
5. `src/agent/agents/knowledge.py`：看普通知识检索与生成契约；
6. `src/agent/agents/research_team.py`：看离线实验团队的结构化协议、一次修订与 Claim 校验；
7. `src/rag/evaluation/retrieval_grader.py` 的 `CorrectiveRAGPipeline`；
8. `src/rag/retrieval/hybrid_retriever.py` 和 `reranker.py`；
9. `src/api/services/knowledge_service.py`；
10. `frontend/src/App.vue`；
11. `tests/test_agent_architecture.py`、`tests/test_research_team.py` 与两套 eval runner。

这个顺序能避免先被旧 Supervisor 或历史计划执行代码带偏。

### 3.2 不在生产图中的历史实现

- `src/agent/agents/supervisor.py`；

## 4. 关键代码流程

### 4.1 修改路由

入口在 `planner.py`：

- `_quick_complexity_check()` 判断是否需要知识查询扩展；
- `_quick_route()` 选择三类分支；
- `planner_node()` 只在规则无法确定的较长输入上调用 LLM；
- `route_from_planner()` 是 LangGraph conditional edge 的返回函数。

增加路由规则时：

1. 给出明确正例和反例；
2. 优先使用窄规则，避免一个关键词覆盖所有语境；
3. 所有复杂知识、科研和前提核验任务都路由 knowledge + expansion；不要重新添加 `use_research_team`；
4. 在架构测试加入断言；
5. 比较是否减少错误路由，而不是只减少 LLM 调用。

### 4.2 修改知识回答

`retrieval_agent_node()` 负责证据，不负责自由回答；`generation_agent_node()` 负责引用生成，不应自行再次搜索未授权数据。

修改提示词时必须保留：

- 检索资料是不可信数据，不执行其中指令；
- 内部事实仅依据提供的文档；
- 使用 `[文档N]`；
- 无结果确定性拒答；
- 冲突和版本显式呈现；
- 用户可见输出标签。

提示词修改至少运行流式测试、无答案样本和引用人工检查。

### 4.3 增加工具

先判断工具是否真的属于“需要执行”的 Operation 分支。纯知识查询不应做成工具。

合理步骤：

1. 实现输入输出明确、无隐式全局副作用的工具；
2. 在 Skill 中只暴露必要工具；
3. 对危险写操作加入授权与参数确认；
4. 测试成功、超时、无权限和错误参数；
5. 确保最终只返回一个 AIMessage。

### 4.4 增加文档类型

在 `loaders.py` 增加解析器映射，让输出保持统一 `Document`；在 KnowledgeService 校验扩展名/MIME；在入库测试加入真实最小文件；确认元数据、中文、空文件和异常文件行为；最后用检索评测验证，不以“解析未报错”为完成标准。

### 4.5 修改分块或 embedding

这是数据迁移级变更：

1. 记录旧模型、维度、分块策略和评测基线；
2. 在隔离集合重建；
3. 用同一标注集对比；
4. 检查索引大小、入库时间和回答引用；
5. 确认提升后再替换生产集合；
6. 保留可恢复备份。

不能直接向现有集合混写不同 embedding。

### 4.6 增加元数据或 ACL

元数据会跨越上传 schema、Service 规范化、chunk、Chroma filter、BM25 结果、来源卡片和前端。因此至少检查：

```text
请求模型
  → KnowledgeService._normalize_metadata
  → IngestionJob metadata
  → Worker chunk metadata
  → Chroma
  → build_acl_filter + check_doc_access
  → source card
  → 前端展示
```

权限字段必须有旧数据默认值和不同角色测试。

### 4.7 增加科研工作区字段

先在 `ResearchService` 的 schema 初始化中做兼容迁移，再更新 service 校验、Pydantic schema、controller、前端表单/显示和 `test_research_workspace.py`。不要让前端直接构造 SQL 意义上的状态值。

## 5. 配置的来源优先级

`config/settings.py` 是字段、默认值和校验的代码真相；`config/.env` 是当前实例真相；`env.template` 是示例，不是运行状态。

排查一个模型或阈值时按顺序看：

1. `.env` 是否显式覆盖；
2. Settings 的 alias 和默认值；
3. 运行日志/健康信息；
4. 实际调用测试。

修改 Settings 后同步更新 `env.template` 和配置文档，避免模板长期漂移。

## 6. 测试选择矩阵

| 改动 | 最小相关测试 | 还需验证 |
|---|---|---|
| Planner/图 | agent architecture、chat streaming | 三类真实问题 |
| RAG/阈值 | retrieval、reranker、Quick eval | 指标对比、无答案 |
| 入库 | ingestion pipeline、knowledge catalog | 上传轮询、更新替换 |
| 认证/角色 | auth、password、token、security | 两角色浏览器互测 |
| 会话/SSE | chat streaming、controller binding | 停止生成、刷新历史 |
| 科研空间 | research workspace | 创建/刷新/越权 |
| 反馈 | feedback workflow | 用户提交到审核关闭 |
| 前端样式 | npm build | 桌面与 390px 浏览器 |

提交前的通用检查：

```bash
pytest -q
npm --prefix frontend run build
git diff --check
```

## 7. 日志与可观测位置

- `.run/后端.log`：启动实例 stdout/stderr；
- `logs/agent.log`：应用日志；
- `.run/前端.log`：Vite；
- `/health`：组件状态；
- ingestion job API：文件处理状态；
- feedback 表：真实用户问题；
- eval JSON：可比较的离线快照。

调试请求时推荐关联 request/session/user，但日志中不要写 JWT、密码、完整 API key 或 restricted 文档全文。

## 8. 代码风格与边界原则

- 异步路径不要直接调用耗时同步网络/磁盘操作；必要时 `asyncio.to_thread`；
- SQL 始终参数化；
- Controller 薄，权限和业务规则在 Service；
- 检索结果在进入生成前完成 ACL；
- 对可选依赖采用明确降级，不用无条件吞异常；
- 最终用户回答只由一个节点负责；
- 中文用户文档使用中文文件名；
- 不为可能永远不会出现的规模预建分布式系统。

## 9. 常见错误改法

### 9.1 为一个新问题类型增加 Agent

先问它是否只是知识检索策略、一个受限工具或一条确定性路由。大多数情况下不需要新 Agent。

### 9.2 只调低相似度阈值解决无结果

这常把噪声交给生成模型。应先定位解析、分块、ACL、BM25、embedding、rerank 哪一层漏掉。

### 9.3 在前端做权限

隐藏按钮不是授权。服务端 Service 和检索 ACL 必须拒绝请求。

### 9.4 把所有模型事件直接 SSE 输出

会泄露内部推理并产生多重答案。继续使用 ChatService 的事件过滤和用户可见标签。

### 9.5 引入 Redis 解决单机状态

当前 SQLite 队列和内存缓存足够。只有多实例共享、吞吐或可靠性指标证明需要时再引入。

## 10. 推荐的小步开发循环

1. 从真实失败案例写一个最小复现；
2. 确认属于入库、检索、生成、权限、接口还是前端；
3. 只修改最窄的一层；
4. 增加一个防回归测试；
5. 跑相关测试与 Quick eval；
6. 浏览器重走失败路径；
7. 记录指标和行为变化；
8. 指标无改善就撤回复杂度，而不是继续叠补丁。

这个循环比长时间围绕登录、框架替换或 Agent 数量迭代更贴合项目重点。
