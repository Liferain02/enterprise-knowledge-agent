# 评测、测试与质量保障

本项目把质量拆为三层：代码是否正确、检索是否找到正确证据、最终产品是否对真实用户有用。只看单元测试或只看一个 RAG 指标都不够。

## 1. 质量模型

```text
工程正确性
  ├─ 单元/集成测试
  ├─ 架构契约
  └─ 前端构建与类型检查
          ▼
检索质量
  ├─ Recall / Precision / F1
  ├─ MRR / NDCG / MAP / Hit
  ├─ CRAG 决策
  └─ 无答案与对抗输入
          ▼
回答与产品质量
  ├─ 引用是否支持结论
  ├─ 权限是否正确
  ├─ 延迟与流式体验
  ├─ 真实浏览器任务
  └─ 用户反馈闭环
```

## 3. 架构契约测试

架构测试不是普通函数测试，而是防止系统悄悄退回高成本旧设计。它应持续保护：

- Planner 是唯一业务路由入口；
- 生产图只有 knowledge、operation、general 三个业务分支；
- 知识分支固定先 Retrieval 再 Generation；
- 所有分支汇入唯一 finalizer；
- `supervisor`、`execute_plan`、`save_to_mem0` 不出现在编译图；
- 一般复杂知识、科研与前提核验请求都设置查询扩展，生产图不包含固定三角色团队；
- 显式固定团队没有 Supervisor/动态 Worker，Reviewer 最多触发一次修订且没有回边；normal 路由不变；
- 最终只有一个用户可见 AIMessage；
- 版本来源能传到最终状态。

如果测试因为有意架构升级而失败，应先更新架构文档和评测设计，再更新断言；不应直接删除测试。

## 4. RAG 评测数据集

`tests/eval/eval_dataset.py` 保存与仓库样本文档对应的标注查询。当前约 20 条普通查询，覆盖：

- 实验室规章与日常流程；
- 项目资料；
- 组会与科研活动；
- 论文知识；
- 应当拒答的无答案问题。

`tests/eval/run_rag_eval.py` 还会加入 7 类对抗输入，例如不存在的内部事实、错误前提、重复字符、零宽字符、纯标点、超长重复文本和中英文混合查询。

普通主链评测使用匿名 `UserContext`、Hybrid Retriever 和 Qwen Rerank；五路消融另行显式运行 CRAG。这样既贴近默认产品路径，也能保留对已关闭组件的可复现负结果。

## 5. 检索指标

指标实现在 `src/rag/evaluation/retrieval_metrics.py`。计算前会按逻辑文档去重，避免同一源文件的多个 chunk 人为抬高命中率。

### 5.1 Recall@K

前 K 个结果覆盖了多少相关文档：

```text
Recall@K = 命中的相关文档数 / 全部相关文档数
```

适合观察漏召回。多资料汇总问题尤其重视 Recall。

### 5.2 Precision@K

前 K 个结果中有多少是相关的：

```text
Precision@K = 命中的相关文档数 / K
```

适合观察噪声。生成上下文有限时 Precision 很重要。

### 5.3 F1@K

Recall 与 Precision 的调和平均，用于避免只优化其中一侧。

### 5.4 MRR

使用第一个相关结果排名的倒数。正确文档排第一得 1，排第二得 0.5。适合单一明确答案问题。

### 5.5 NDCG@K

考虑不同相关等级和位置折损，衡量排序质量。比简单命中更能评价 rerank 是否把强相关资料提前。

### 5.6 AP/MAP

AP 衡量单个查询在各个相关命中位置上的综合精度，MAP 是多查询平均。适合比较两套检索配置的整体排序稳定性。

### 5.7 Hit@K

前 K 中只要出现至少一个相关文档就记 1。它直观，但信息较粗，不能单独作为上线门槛。

## 6. CRAG 与无答案评测

评测记录 HIGH、MEDIUM、LOW、NO_RESULTS 的分布，并检查应拒答样本是否真的拒答。

无答案准确率至少需要区分两种错误：

- 假阳性：知识库没有证据，但系统高置信回答；
- 假阴性：知识库有明确证据，但系统拒答。

安全的初期系统可容忍少量假阴性，但不应长期以“全部拒答”换取漂亮的无答案准确率。因此必须与普通查询 Hit/NDCG 一起看。

## 7. 上下文指标与回答指标

当前命令中的 context metrics 主要基于关键词覆盖，不等同于 RAGAS 的严格 Faithfulness，也不证明最终每个结论都由引用支持。`--no-ragas` 只是兼容旧命令的别名。

仓库另有 `src/rag/evaluation/evaluator.py`，包含 LLM 辅助的 faithfulness、answer relevancy、context recall/precision 能力，但主综合检索脚本的核心报告仍以检索指标为主。

当前最值得补齐的评测是：

1. 声明级引用覆盖率：回答中的可验证声明有多少带引用；
2. 引用支持率：引用文本是否真的支持该声明；
3. 冲突呈现正确率：存在版本冲突时是否明确说明；
4. 权限泄漏率：不同角色是否可能获得不可见内容；
5. 答案任务完成率：用户是否无需二次追问即可完成目标。

这些指标应先用小规模人工标注建立基线，再考虑自动裁判，避免让另一个模型的偏好变成唯一真值。

## 8. 执行评测

### 8.1 准备知识库

先确认 `.env`、Qwen API、embedding 和 rerank 配置可用，然后按需运行：

```bash
python tests/eval/ingest.py
```

可用 `python tests/eval/ingest.py --help` 查看目录、清理、视觉处理等选项。对现有共享库运行清理参数前必须确认目标，因为这会改变向量数据。

### 8.2 快速评测

```bash
python tests/eval/run_rag_eval.py --dataset quick --top-k 5
```

Quick 每类取一个普通样本，并保留对抗样本，适合改动后的短反馈。

### 8.3 完整评测并保存 JSON

```bash
python tests/eval/run_rag_eval.py \
  --dataset full \
  --top-k 10 \
  --output data/评测结果.json
```

如只看核心检索指标：

```bash
python tests/eval/run_rag_eval.py --no-context-metrics
```

输出 JSON 应和代码版本、模型名、阈值、知识库 hash 一起记录，否则两次数字不可可靠比较。

### 8.4 Historical Development Eval V1

```bash
python tests/eval/run_research_team_eval.py --dataset full --dry-run
python tests/eval/run_research_team_eval.py \
  --dataset full \
  --checkpoint /tmp/复杂科研评测断点.json \
  --output data/复杂科研开发评测结果.json \
  --report data/复杂科研开发评测报告.md
```

41 条数据覆盖 cross_scope、multi_evidence、temporal_conflict、recommendation、false_premise 和 supported_premise。报告必须按类别输出，不能只看全局平均。前提指标只对 9 条 premise 样本计算；普通样本写 null。

Citation 正则兼容 `[文档1] / [文档 1] / [文档   1] / [S1] / [S 1]`。引用 support 是词汇重叠 proxy，不是事实蕴含；最终答案级语义评分见 `data/深度研究盲评表.md`、`data/深度研究盲评分数.json` 与 `data/深度研究盲评结论.md`。

41 条现作为 Development Eval：B 关键词/引用覆盖/support 为 0.939/0.516/0.970，Deep 为 0.963/0.683/0.936；Deep P50 为 28.6 秒。开发集只能诊断和冻结，不用于最终上线门禁。

### 8.5 Historical Blind Holdout V1

实现冻结并记录 SHA-256 后才创建 18 条新问题，六类各 3 条。一次性运行器拒绝覆盖已有结果：

```bash
python -m tests.eval.run_deep_research_blind_eval
```

脚本比较 B normal 与 C Deep，生成自动报告、候选顺序随机化的答案级盲评表和独立映射。该 18 条数据和映射现在已经被查看，只能当作 `Historical Blind Holdout V1` 和 `Regression after inspection`，不得继续用它调参后声称 blind generalization。

### 8.6 Deep Research V2 检索与盲测

V2 先运行 26 条 retrieval-only Development Benchmark，再运行 41 条答案级 Development Eval。完成源码、配置、测试和生产 gate 冻结后，才创建 26 条 Blind V2。

```bash
# Development：可重复，只用于诊断
python -m tests.eval.run_deep_research_retrieval_eval
python tests/eval/run_research_team_eval.py --dataset full

# Blind V2：一次性运行器，已有正式产物时会拒绝覆盖
python -m tests.eval.run_deep_research_v2_blind_eval
```

Retrieval runner 保存 query、subquestions、rewrite history、raw/reranked/final candidates、rank、Hit@K、Recall@K、MRR、coverage、延迟和失败归因。对 H08/H16 相关资料的检查结论是 `missing_document`：Nu、Quicksand、Argo、AIFM 文件在磁盘上，但不在冻结的 40 chunks / 18 documents Chroma snapshot 中。由于基准没有证明通用 Named Evidence Anchor 有净收益，本轮没有改 Retrieval。

Blind V2 的映射必须保持密封。评分者只打开 `data/深度研究V2盲评表.md`，不打开 `data/深度研究V2盲评密封映射.json`。候选只标记为甲/乙；由于文风可能泄露方案，这是 label-blind，不是 double blind。

## 9. 常规 RAG 历史实测基线

最近一次 Quick + 对抗真实运行的参考快照：

| 项目 | 结果 |
|---|---:|
| 总查询数 | 11 |
| 普通查询 Hit@5 | 100% |
| 普通查询 NDCG@5 | 约 0.9167 |
| 普通查询 MAP | 约 0.8889 |
| 无答案拒答 | 100% |
| P99 延迟 | 约 6.97 秒 |

真实浏览器中，简单知识问答约 4.45 秒，复杂查询扩展约 9.41 秒。数字受网络、模型服务和缓存影响，只能作为当前环境基线，不能写成 SLA。

其中一个错误前提查询可能命中语义相关的实验记录并得到较高相关分。这说明“检索相关”不等于“问题前提正确”，需要在回答级评测中单独覆盖 false-premise 检测。

## 10. 已知评测实现问题

当前综合脚本中存在 `result.cag_low_count` 的字段拼写问题，而数据类字段是 `crag_low_count`。这会使 LOW 计数在部分汇总中保持默认值。阅读该数字前应先修正并增加回归断言。

这不影响文档相关性排名本身，但会影响 CRAG 决策分布报告。修复时应只改字段名并跑 Quick/单测，不需要重构评测框架。

## 11. 真实浏览器验收清单

自动化通过后，至少用浏览器完成以下路径：

1. 注册、登录、刷新页面、退出和重新登录；
2. 新建会话，询问一个明确知识问题，打开来源；
3. 问一个不存在的内部事实，确认拒答；
4. 问一个对比/列举问题，确认结果完整且延迟可接受；
5. 在生成中点击停止；
6. 上传支持格式，观察 pending 到 completed；
7. 上传重复文件和不支持文件，确认提示明确；
8. 用不同权限账号查看项目文档；
9. 创建项目、实验和任务，再刷新确认持久化；
10. 点踩一条回答，审核端查看并处理；
11. 390px 窄屏检查菜单、长标题、来源和输入框；
12. 后端/模型异常时确认页面不会永久加载。

真实验收必须使用鼠标点击和键盘输入，因为焦点、滚动、按钮禁用和流式中断问题通常无法从 API 测试发现。

## 12. 上线门槛建议

不过度设计的最小上线门槛可以是：

- 全量自动化测试通过；
- 前端生产构建通过；
- 核心角色权限用例无泄漏；
- 固定评测集关键指标不低于上一基线；
- 无答案和提示注入样本没有高风险回归；
- 真实浏览器核心 12 项通过；
- 数据库与 Chroma 已备份且恢复步骤可执行。

不要仅因为平均分提高就上线：单个权限泄漏、错误引用或无法停止的 SSE 回归都可能比平均 NDCG 更重要。
