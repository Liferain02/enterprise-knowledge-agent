# 选择性深度研究多智能体实现与评测

本文描述 Selective Deep Research 的生产代码与历史 V1 评测。它不是默认回答链，也不是自动多 Agent 路由：调用者必须在聊天请求中显式设置 `research_mode=deep`。未设置或设置为 `normal` 时，系统保持原来的 Query Expansion → Retrieval → Generation，不增加任何模型调用。

> 当前结论请以根目录《实验室科研助手_秋招版评测收口说明.md》为准。本文的 Development/Blind 数据是冻结历史记录，只用于解释评测方法和 Deep 的边界；不应当作新的待办或全局产品收益结论。

文档基线：2026-08-13。模型、Embedding、Reranker、知识库、ACL、切块与框架均沿用项目既有配置。

## 1. 当前产品决策

系统保留两种清晰模式：

| 模式 | 入口 | 适用问题 | 工作流 | 默认 |
|---|---|---|---|---|
| `normal` | 请求不传或显式传 `normal` | 普通知识问答、制度、单事实、一般对比 | Planner → ACL RAG → Generation | 是 |
| `deep` | 请求显式传 `deep` | 多证据综合、时间/冲突、证据化建议、前提核验、Research Brief | Researcher → Analyst → Reviewer → 最多一次修订 → 既有 Generation | 否 |

Historical Blind V1 的答案级盲评曾只在 `temporal_conflict` 类观察到净收益：Deep 平均 6.00/6，normal 为 4.67/6，3 条中 Deep 胜 2 条。这是历史信号，不是 V2 的新盲测结论。V2 自动指标显示文档召回和引用覆盖提高，但 premise 安全指标从 Normal 的 0.667 降到 Deep 的 0.167，已触发预声明红线。因此当前只能保持原有窄边界：

- 允许用户显式选择 Deep；
- 不自动把任何问题升级为 Deep；
- 不替换 normal；
- 不增加前端复杂自动路由；
- 不宣称 Deep 对所有科研问题更好；
- 不在 V2 独立人工盲评完成前扩大产品声明或自动适用范围。

## 2. 明确不做什么

本实现没有引入 Supervisor、第四个 Agent、动态 Worker、Agent 自由协商、Agent 间长期记忆、Blackboard、消息队列、Redis、Kafka、GraphRAG、新向量库、新模型或新 Agent 框架。Reviewer 没有循环回边，Researcher 不绕过 ACL，Finalizer 不是新 Agent。

## 3. 请求入口

非流式与流式请求模型都有同一个字段：

```json
{
  "message": "综合近期 RDMA 资料，分析冲突并给出下一步研究建议",
  "session_id": "research-001",
  "research_mode": "deep"
}
```

Pydantic 只接受 `normal | deep`，默认 `normal`。控制器原样传入 `ChatService.achat()` 或 `ChatService.achat_stream()`。`DEEP_RESEARCH_ENABLED` 是部署门禁；盲测达标后模板和默认配置为 true，运维仍可设为 false 立即下线 Deep，不影响 normal。

项目没有自动判断后悄悄进入 Deep。`route_from_planner()` 只检查显式状态：

```python
if state.get("research_mode", "normal") == "deep":
    return "research_agent"
```

其余 Planner 逻辑保持不变。

## 4. 生产图

```text
maybe_summarize
  → retrieve_mem0_memories
  → planner
      ├─ normal knowledge → retrieval_agent → generation_agent ──────┐
      ├─ operation → operation_agent ────────────────────────────────┤
      ├─ general → general_agent ────────────────────────────────────┤
      └─ explicit deep → research_agent                              │
                            → analyst_agent                           │
                            → reviewer_agent                          │
                                ├─ PASS ───────────────────────┐      │
                                └─ REVISE / NEED_MORE_EVIDENCE │      │
                                          → research_revision  │      │
                                               （最多一次）      │      │
                                                             ▼      │
                                                deep_research_generation
                                                             │      │
                                                             └──────┤
                                                                    ▼
                                                          finalize_response
                                                                    ▼
                                                                   END
```

关键边界：`research_revision` 直接去 `deep_research_generation`，绝不返回 Reviewer；`deep_research_generation` 复用 `knowledge.py` 中已有的 `generation_agent_node()`，不执行第二次检索。

## 5. 状态协议

Deep 只在现有 `AgentState` 增加业务字段，不建数据库：

| 字段 | 生产者 | 消费者 | 内容 |
|---|---|---|---|
| `research_mode` | API/调用入口 | Router | `normal` 或 `deep` |
| `research_question` | Researcher | 后续节点 | 原始问题 |
| `evidence_package` | Researcher | Analyst/Reviewer/Revision/Generation | ACL 校验后的证据 |
| `analysis_report` | Analyst/Revision | Reviewer/Generation | 结构化 Claim Map |
| `review_report` | Reviewer | Revision/Generation | 声明、前提、冲突复核 |
| `research_revision_count` | Revision | Router/诊断 | 只允许 0 或 1 |
| `research_team_metrics` | 全阶段 | Eval/诊断 | 调用、token、耗时 |
| `research_trace` | 全阶段 | Eval/诊断 | 端到端阶段轨迹 |

## 6. Researcher

入口：`research_agent_node()`。

### 6.1 有限拆分

复用现有 `QueryDecomposer`，最多 4 个子问题。结构化调用失败时使用 `_fallback_subquestions()`，不会创建角色或无限扩展。

```text
MAX_SUBQUESTIONS = 4
MAX_TARGETED_QUERIES = 2
MAX_EVIDENCES = 12
MAX_EVIDENCE_CHARS = 800
```

### 6.2 只使用既有检索

每个子问题调用与 Normal 相同的 `_retrieve_documents()`，并固定 `needs_expansion=False`，因为问题已经在 Researcher 中拆分。默认链是 ACL Hybrid → Qwen Rerank；只有显式设置 `CRAG_ENABLED=true` 的实验才增加 Grading/Rewrite。

### 6.3 ACL

Pipeline 的 ACL 过滤后，Researcher 再逐文档调用 `check_doc_access()`。匿名或缺失用户上下文时使用 public 权限，而非全库权限。被拒绝的文档不会进入 EvidencePackage、Claim、生成上下文、来源卡片或 trace。

### 6.4 EvidencePackage

```text
EvidencePackage
  original_question
  subquestions[0..4]
  evidences[0..12]
    source_id             S1..Sn
    subquestion
    title
    source                仅安全文件名
    excerpt               最多 800 字符
    score
    metadata              白名单字段
    time_info
    conflict_warnings
  missing_evidence
  conflicts
  acl_checked
```

证据按 `source + 正文前缀` 去重并按分数排序。`_documents_from_package()` 用同一顺序重建前端来源，保证 S1..Sn 与 `[文档1..n]` 一致。

## 7. Analyst

入口：`analyst_agent_node()`。Analyst 不能检索、不能创建 Agent，只读 EvidencePackage。

```text
Claim
  claim_id
  text
  claim_type: fact | comparison | inference | recommendation
  source_ids
  confidence

AnalysisReport
  claims                 最多 12
  comparison
  uncovered_source_ids
  limitations            最多 4（规范化后）
  draft_answer            正常要求留空
```

Prompt 要求 6～10 条紧凑 Claim；每条都必须绑定 EvidencePackage 中真实存在的 S 编号。`uncovered_source_ids` 用于诊断“检索到了但没有进入 Claim”的证据流失。

Qwen 的 wire format 偶尔使用 `claim_text`、`claim_content`、`content`、`category` 等字段。Pydantic alias 只做字段兼容；缺失类型默认 fact 后再按“建议/推断”等通用语义规范化，不会补造证据。

## 8. Reviewer

入口：`reviewer_agent_node()`。只允许：

- `PASS`；
- `REVISE`；
- `NEED_MORE_EVIDENCE`。

ReviewReport 包含逐 Claim 结果、`premise_assessment`、直接前提证据编号、冲突/ACL 状态和最多 2 个补检索 query。

前提协议使用四态：

- `supported`：资料直接确认问题范围；
- `unsupported`：资料直接给出相反规则、状态或机制；
- `insufficient`：资料既不支持也不反驳。
- `not_applicable`：用户任务不是明确的前提核验。

`_is_premise_task()` 先判断问题是否真的要求核验可判真命题。普通比较、总结、建议和“两份资料是否冲突”不属于 premise task；即使模型返回 `unsupported`，也会确定性归一为 `not_applicable`，并清空相关 source IDs 与误报。

“表达绝对”本身不是反证，“可能存在未记载例外”也不能推翻明确制度。supported/unsupported 必须绑定 `premise_source_ids`。Qwen 偶尔把枚举返回成 `{status: supported}`，field validator 会提取枚举值；无法解析时安全降级。

LLM Review 之外，程序固定拒绝不存在的 source_id、无引用 Claim 和未通过 ACL 的 package。Reviewer 明确否决的 Claim 在 Generation 前删除。

## 9. 一次修订

`REVISE` 只有在 Reviewer 给出至少一个 `supported=false` 的结构化 `ReviewItem`，或明确标记现有
证据冲突尚未处理时，才让 Analyst 根据 ReviewReport 重写一次。只有笼统 `REVISE`、没有可定位
问题时会归一化为 `PASS`，并在 trace 中记录原始决策和跳过原因。`NEED_MORE_EVIDENCE` 最多再检索
2 个目标 query，然后重写一次。之后调用 `_validate_claims_for_finalization()`：

- source_id 不存在 → 删除；
- source_ids 为空 → 删除；
- `acl_checked=false` → 删除全部；
- 被删除内容只作为 limitation 数量记录，不进入最终事实。

没有第二轮 Review，所以最大延迟有确定上界，也避免“Reviewer 不满意 → 无限回环”。

这一门槛来自冻结 V2 的失败归因：21 个 `REVISE` 中有 16 个没有任何被拒 Claim、没有未处理冲突，
`overall_instruction` 也为空，却仍执行了完整 Analyst 修订。按旧 trace 静态计算，这 16 次修订合计
占 89.7 秒、49,046 input token 和 9,379 output token。它只是反事实成本估计，不是新质量结果；
新实现必须在 Development/V3 对照中确认跳过空修订不会降低答案质量。

## 10. 复用 Generation Agent

`deep_research_generation_node()` 不是第四个 Agent，它是适配器：

1. 应用 Reviewer 明确否决；
2. 再做确定性 Claim 校验；
3. 将 EvidencePackage 映射为 `文档1..n`；
4. 把合法 Claim Map、前提结论、冲突与局限放进 `retrieval_context`；
5. 调用已有 `generation_agent_node()`；
6. 使用 `config={tags: [user_visible_answer]}` 进入原 SSE；
7. 标记 `used_agent=deep_research`。

Generation 被要求严格输出七段 Research Brief：

1. 研究问题
2. 已有证据
3. 关键事实
4. 冲突/不确定项
5. 推断
6. 下一步研究建议
7. Sources

事实/比较必须就近 `[文档N]` 引用；推断和建议必须明确标注；无内容写“无”，不能用常识补内部事实。前提结论由适配器确定性加在顶部，避免最终自由生成说丢 Reviewer 结果。

normal 调用同一 Generation Agent 时不传格式说明，仍为原 500 字限制；Deep 才传 Research Brief 指令和 1400 字上限。因此 normal 行为没有被全局改写。

## 11. 阶段 trace

`research_trace.stages` 记录：

- `researcher`：query、subquestions、检索 ID/标题、EvidencePackage、延迟/调用/token；
- `analyst`：全部 Claim、未覆盖 S 编号、证据转 Claim 覆盖率、延迟/调用/token；
- `reviewer`：完整 ReviewReport、延迟/调用/token；
- `revision`：修订前后 Claim、被丢弃 Claim、最终合法 Claim、补检索次数；
- `generation`：Reviewer 丢弃项、validated claims、最终答案、Claim 引用覆盖、延迟/调用/token。

它完全落在现有 state/eval JSON 中，没有引入监控平台或消息系统。V2 还增加了 `retrieval | analysis | review | generation | knowledge_gap | acl | none` 统一失败归因，以及 query 改写历史、被拒 Claim 原因、修订前后 Claim 和最终有效 Claim 覆盖 proxy。

## 13. Historical Blind Holdout V1 的冻结

实现冻结清单位于 `data/深度研究实现冻结清单.json`，记录关键文件 SHA-256。冻结后才创建 `tests/eval/deep_research_blind_dataset.py`：18 条新问题，六类各 3 条，不复制开发集。

一次性运行器 `run_deep_research_blind_eval.py` 拒绝覆盖已有产物。比较 B 与 C，并在看到结果前固定生产门槛。结果：

| 方案 | 成功 | 关键词 | 引用覆盖 | 支持 proxy | 召回 | 前提 | ACL | P50/P95 | 调用 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| B normal | 18/18 | 0.836 | 0.567 | 0.994 | 0.787 | 0.667 | 0 | 7.2/10.2s | 2.00 |
| C Deep | 18/18 | 0.931 | 0.677 | 0.992 | 0.769 | 1.000 | 0 | 26.0/36.5s | 7.44 |

自动 support 只是分词重叠回归代理，不是事实蕴含，也不是上线主指标。

## 14. Historical Blind V1 答案级盲评与门禁

每题 B/C 顺序固定随机化为候选甲/乙，先按正确性、完整性、证据依据分别 0～2 打分并落盘，再打开独立映射。未调用额外 Judge API。评分者是本次实现审查者，不是独立第三方人类，这是结果限制；正式大规模上线前建议由课题组成员复核评分表。

| 方案 | 正确性 | 完整性 | 证据依据 | 总分 | 胜出题数 |
|---|---:|---:|---:|---:|---:|
| B normal | 1.722 | 1.667 | 1.889 | 5.278/6 | 4 |
| C Deep | 1.778 | 1.722 | 1.833 | 5.333/6 | 4 |

按类别：

| 类别 | B | C | C 胜出 |
|---|---:|---:|---:|
| false premise | 5.67 | 6.00 | 1/3 |
| multi evidence | 5.33 | 5.67 | 1/3 |
| recommendation | 4.67 | 3.67 | 0/3 |
| research brief | 5.33 | 4.67 | 0/3 |
| supported premise | 6.00 | 6.00 | 0/3 |
| temporal conflict | 4.67 | 6.00 | 2/3 |

预先门槛要求至少一个类别 C 高 1.0/6 且胜 2/3；全集正确性/证据依据不得回退 0.2；前提自动准确率不得低于 B；18 条必须全成功、ACL=0。`temporal_conflict` 满足类别门槛，其他安全门槛也通过，所以显式 Deep 开放。

该结论现仅是 V1 历史决策证据，不得当作 V2 生产门禁已通过。V2 已证实 H08/H16 对应的 Nu、Quicksand、Argo、AIFM 根本不在 40 chunks / 18 documents 的 Chroma snapshot 中，归因为 `missing_document`，不是多 Agent 角色不够。禁止用第四 Agent、动态协商或新基础设施掩盖证据缺口。

## 16. 当前限制

1. Deep P50 约为 normal 3.6 倍，只适合显式复杂任务。
2. 检索没命中目标论文时，多 Agent 无法补证据；必须诚实写缺口。
3. 关键词、引用覆盖和 support 都是自动代理指标。
4. 当前盲评不是独立领域专家评审。
5. 前端已增加最小的“普通 / 深度研究”选择；默认普通，仅对当前一次请求生效，发送、刷新和新会话后都恢复普通。
6. `is_complex_research_task()` 仅作为离线/诊断窄规则，不参与显式 Deep 路由。
7. 非前提任务的多余“前提核验”已用四态边界修复；但 V2 Blind 明确 premise 任务的自动准确率仅 0.167，这是当前不可掩盖的安全限制。

## 18. V2 当前收口

V2 不再用已查看的 V1 Holdout 调参，而是依次完成 26 条 retrieval-only Development Benchmark、41 条 Development Eval、实现与门禁冻结、26 条新 Blind V2 的一次性 B/C 运行。V2 自动结果为：

| 方案 | 关键点 | 引用覆盖 | 文档召回 | premise | P50/P95 | calls |
|---|---:|---:|---:|---:|---:|---:|
| B Normal | 0.865 | 0.507 | 0.679 | 0.667 | 6.6s/9.1s | 2.00 |
| C Deep | 0.913 | 0.727 | 0.811 | 0.167 | 27.5s/33.0s | 7.77 |

Deep 的输入/输出 Token 均值为 12590/2304，Normal 为 2071/367。这些数字是自动代理指标，不是人工答案质量结论。由于 premise safety gate 已失败，当前状态固定为“实现与自动评测完成，未宣布 Deep 全局收益”。新的 Retrieval 和 Knowledge Evolution 结果见根目录《实验室科研助手_秋招版评测收口说明.md》。

## 17. 防止过度设计的维护规则

- normal 永远是默认；
- Deep 只由显式字段进入；
- 固定三角色，不加第四角色；
- Reviewer 最多一次修订；
- 不因单题失败增加循环；
- 不改变 ACL、Embedding、Reranker、切块、模型和检索框架；
- 新问题先定位到 Researcher/Analyst/Reviewer/Generation 哪一阶段，再决定是否修；
- 新版本必须使用新 Holdout，不能对本轮 Blind Holdout 调参。
