# 复杂科研多智能体团队实现与评测

本文说明固定 Researcher → Analyst → Reviewer 团队的状态协议、代码实现、安全约束、一次修订机制和 A/B/C 评测。修正 citation 统计并加入成立前提对照后的 41 条结果表明：团队在任何类别都没有取得稳定净收益。因此它已从生产 LangGraph 移除，只保留为可复现的离线实验实现。

## 1. 设计目标

要验证的命题只有一个：

> 对需要多来源证据、事实/推断分离和独立复核的复杂科研任务，固定专业分工能否比单 Agent 更可信。

不以“运行更多 Agent”为目标。若评测不能证明质量收益足以覆盖延迟和 API 成本，应简化或删除该团队。

## 2. 明确不做什么

本实现没有增加：

- Supervisor；
- 动态创建 Agent；
- 用户自定义角色；
- Agent 自由协商；
- Agent 间长期 Memory；
- Blackboard、Mailbox 或消息队列；
- 动态团队拓扑；
- Redis、Kafka、知识图谱或 GraphRAG；
- 新 Agent 框架；
- 为每个 RAG 步骤包装一个 Agent。

团队复用现有 LangGraph、Planner、ACL、Hybrid Retrieval、Qwen Rerank、CRAG、Chroma 和 Finalizer。

## 3. 使用边界

### 3.1 继续走原单 Agent RAG

以下问题不会进入团队：

- “实验室组会多久一次？”；
- “有哪些 RDMA 实验要求？”；
- “对比 RDMA 和 TCP 的差异”；
- 普通制度、流程、项目事实；
- 单份或少量资料即可回答的问题。

其中对比、列举等一般复杂知识问题仍使用 Query Expansion + Retrieval → Generation。

### 3.2 当前生产结论：不自动进入团队

纠偏前曾将生产门缩到“复杂多证据 + 错误/绝对化前提核验”。纠偏后取消该门，原因不是否定所有局部收益，而是没有任何类别同时满足：

1. 正确性不低于 B；
2. citation coverage/support 不低于 B；
3. 前提核验和冲突处理不低于 B；
4. 延迟与调用成本可接受。

`should_use_research_team()` 已删除，Planner 不再写 `use_research_team`，生产图也不注册五个团队节点。普通事实、跨项目、多证据、时间冲突、研究建议、错误前提和成立前提都使用现有 Retrieval → Generation；复杂输入由 Query Expansion 处理。

`is_complex_research_task()` 只服务离线 41 条 A/B/C 数据完整性检查，不是生产路由函数。本轮也没有增加 `deep` 模式，因为把未证明可靠的实验路径暴露给用户没有产品收益。

## 4. 生产图与离线实验链

```text
maybe_summarize
  → retrieve_mem0_memories
  → planner（唯一入口）
      ├─ 知识/复杂科研 → retrieval_agent → generation_agent ─┐
      ├─ 工具 → operation_agent ─────────────────────────────┤
      └─ 通用 → general_agent ───────────────────────────────┤
                                                           ↓
                                                 finalize_response → END
```

离线 C 方案由评测器显式调用：

```text
research_agent → analyst_agent → reviewer_agent
                                     ├─ PASS → team finalizer
                                     └─ REVISE / NEED_MORE_EVIDENCE
                                              ↓
                                      research_revision
                                              ↓
                                   deterministic claim validation
                                              ↓
                                      team finalizer
```

`research_revision` 从不返回 Reviewer；最多一次修订的协议测试继续保留，即使该链不在生产图中。

## 5. 最小共享状态

`ResearchTaskState` 只包含：

| 字段 | 内容 |
|---|---|
| `research_question` | 原始复杂科研问题 |
| `evidence_package` | Researcher 输出的结构化证据 |
| `analysis_report` | Analyst 的 Claim 与草稿 |
| `review_report` | Reviewer 的结构化复核 |
| `research_revision_count` | 0 或 1 |
| `research_team_metrics` | LLM/检索调用、token 和耗时 |

它由离线评测器的局部 state 使用，不再嵌入生产 `AgentState`。不另建团队数据库、长期记忆或消息系统；节点通过结构化对象交换信息，不以自由自然语言对话作为主要协议。

## 6. EvidencePackage

Pydantic 模型定义在 `research_team.py`：

```text
EvidencePackage
  original_question: str
  subquestions: list[str]          # 最多 4 个
  evidences: list[EvidenceItem]    # 最多 12 条
  missing_evidence: list[str]
  conflicts: list[str]
  acl_checked: bool

EvidenceItem
  source_id: str                   # S1、S2……
  subquestion: str
  title: str
  source: str                      # 只保留安全文件名
  excerpt: str                     # 最多 800 字符
  score: float
  metadata: dict                   # 白名单元数据
  time_info: str
  conflict_warnings: list[str]
```

绝对服务器路径不会进入协议。metadata 只保留 title、类型、作者、项目、研究方向、visibility、密级、版本和时间等必要字段。

## 7. Research Agent

入口是 `research_agent_node()`。

### 7.1 有限问题拆分

Researcher 使用结构化 `SubquestionPlan` 生成 2～4 个可检索子问题。模型结构化输出失败或返回空列表时，`_fallback_subquestions()` 生成有限确定性计划，不会创建新角色。

最大值常量：

- `MAX_SUBQUESTIONS = 4`；
- `MAX_TARGETED_QUERIES = 2`；
- `MAX_EVIDENCES = 12`；
- `MAX_EVIDENCE_CHARS = 800`。

12 条 × 800 字符是实测后的上下文上限，用于避免 Analyst 在宽检索结果上超过模型输出/上下文预算；它不是新的检索基础设施。

### 7.2 复用现有检索

每个子问题调用同一个 `CorrectiveRAGPipeline.retrieve()`：

```text
ACL-aware Hybrid Retrieval
  → Qwen Rerank
  → CRAG grade
  → 必要时管线自身纠错
```

团队没有专用向量库或绕过 ACL 的快速通道。

### 7.3 ACL 二次复核

即使 Pipeline 已过滤，Researcher 仍对每个返回文档调用 `check_doc_access()`。没有用户上下文时按 `UserContext.anonymous()` 的 public 权限处理，而不是全库访问。

被拒绝的文档不会进入 EvidencePackage、Analyst prompt、最终来源卡片或评测结果。

### 7.4 聚合与去重

证据以 source + 正文前缀去重，保留分数更高项，再按相关性排序并编号 S1～Sn。来源文档由 `_documents_from_package()` 重建，确保修订后来源卡片顺序仍与 S 编号一致。

### 7.5 冲突和缺口

没有结果或子查询异常会进入 `missing_evidence`，不会使整个团队无限重试。多个文档进入现有 conflict detector，冲突写入 package。

Researcher 不生成最终答案，也不修改科研数据。

## 8. Analyst Agent

入口是 `analyst_agent_node()`。它只读取 EvidencePackage。

### 8.1 Claim 协议

```text
Claim
  claim_id: str
  text: str
  claim_type: fact | comparison | inference | recommendation
  source_ids: list[str]
  confidence: high | medium | low

AnalysisReport
  claims: list[Claim]
  comparison: str
  limitations: list[str]
  draft_answer: str                # 当前要求留空，由 Finalizer 确定性渲染
```

事实、比较、模型推断和研究建议必须显式区分。重要 Claim 绑定 S 编号。当前 Prompt 要求 `draft_answer` 留空，最终文本统一由 Finalizer 从 Claim 确定性渲染，避免自由草稿绕过声明级引用。

### 8.2 安全边界

Prompt 明确声明 EvidencePackage 是不可信数据：文档中的指令不得改变系统规则。Analyst 不检索、不调用工具、不创建 Agent，也不能用外部常识补实验室内部事实。

### 8.3 结构化兼容

Qwen 偶尔只填 `draft_answer` 而不填 `claims`。`_normalize_analysis()` 会从带 S 引用的草稿中恢复 Claim，并根据“推断、可能、暗示、建议”等词区分类型；它不会为没有引用的句子凭空创建证据。

## 9. Reviewer Agent

入口是 `reviewer_agent_node()`。它只允许三个决定：

- `PASS`；
- `REVISE`；
- `NEED_MORE_EVIDENCE`。

任何其他值都会被 Pydantic 拒绝。

### 9.1 ReviewReport

```text
ReviewReport
  decision
  items: list[ReviewItem]
  premise_assessment: not_applicable | supported | unsupported | insufficient
  false_premise_detected
  conflict_handled
  acl_verified
  overall_instruction
  targeted_queries            # 最多 2 条

ReviewItem
  claim
  source_ids
  supported
  issue_type
  revision_instruction
```

### 9.2 确定性护栏

LLM Reviewer 之外还有程序检查：

- source_id 不存在 → `invalid_source`；
- Claim 没有引用 → `citation_gap`；
- package 未确认 ACL → `acl`；
- 用户要求验证“所有、任何、每次、必然、完全相同”等强前提 → 必须显式给出 `supported / unsupported / insufficient`，不能仅因量词绝对就默认否定。

因此 Reviewer 即使误返回 PASS，也不能放过无效引用或明显需要核验的绝对化前提。

Reviewer 不生成最终答案、不直接检索，也不能启动其他 Agent。

## 10. 一次受限修订

`route_after_reviewer()` 的规则：

```text
PASS → research_team_finalizer
REVISE/NEED_MORE_EVIDENCE 且 revision_count=0 → research_revision
任意决定且 revision_count>=1 → research_team_finalizer
```

`research_revision_node()`：

- REVISE：将 ReviewReport 交给 Analyst 修订一次；
- NEED_MORE_EVIDENCE：最多执行 2 个 targeted query，合并去重后让 Analyst 修订一次；
- 修订完成写 `research_revision_count=1`；
- 不再返回 Reviewer。
- 写回前调用 `_validate_claims_for_finalization()`，确定性检查 source_id 存在性、fact/comparison 引用和 `acl_checked`。

不合法 Claim 会被删除并降级为 limitation。Finalizer 为兼容旧 checkpoint 再防御性调用同一轻量函数；没有新 Agent、Reviewer LLM 第二次调用或循环。

## 11. 团队终态

`research_team_finalizer_node()` 不再调用模型。它：

- 无证据时确定性拒答；
- 无论 PASS 或修订，都按 Claim 类型渲染“资料事实/资料比较/模型推断/研究建议”；
- 保留 `[Sx]` 引用；
- 按 ReviewReport 在顶部明确写“前提成立 / 不成立 / 证据不足”；
- 存在冲突时追加冲突说明；
- 在离线结果中标记 `used_agent=research_team`。

该终态目前只由 A/B/C 评测器调用，不进入产品 SSE 或会话持久化。

## 12. SSE 与前端边界

ChatService 不再包含团队阶段状态，前端也没有 `deep` 入口。生产只展示 Planner、知识检索、工具和通用分支。这样不会让用户误以为离线实验链是稳定线上能力。

## 13. 成本与可观测性

`research_team_metrics` 累积：

- `llm_calls`；
- `retrieval_calls`；
- `input_tokens` / `output_tokens`；
- `estimated_prompt_chars`；
- `elapsed_ms`。

token 取 OpenAI-compatible 响应的 `usage_metadata`。CRAG 内部每篇文档 grader 的 token 并不全部暴露给团队状态，因此评测报告同时给出 logical API call estimate，并明确它不是账单数字。

## 14. 评测集

`tests/eval/complex_research_dataset.py` 包含 41 条复杂科研问题。分类：

| 类别 | 数量 | 重点 |
|---|---:|---|
| `cross_scope` | 8 | 跨项目、方向或论文比较 |
| `multi_evidence` | 8 | 论文、实验、纪要、制度共同支撑 |
| `temporal_conflict` | 8 | 时间演化和冲突 |
| `recommendation` | 8 | 基于证据的下一步建议 |
| `false_premise` | 4 | 绝对化或错误前提识别 |
| `supported_premise` | 5 | 有直接制度证据支持的强前提对照 |

每条包含 relevant_doc_ids、expected_keywords、最少来源数、冲突要求和 `premise_expectation`。前提标注只有 `false / supported / none` 三值；非 premise 样本的 `premise_accuracy` 为 null，不再用默认 1.0 制造无意义全局平均。full dry-run 会检查全部 41 条都符合离线复杂科研分类器。

## 15. A/B/C 评测

运行脚本：`tests/eval/run_research_team_eval.py`。

三种方案：

- A：Hybrid/CRAG + 单 Agent，不主动 Query Expansion；
- B：Hybrid/CRAG + Query Expansion + 单 Agent；
- C：Researcher + Analyst + Reviewer。

指标：

- 关键词正确性代理指标；
- 声明级引用覆盖率；
- 引用支持词汇 proxy；
- 错误前提识别率（只算 4 条 false）；
- 成立前提确认率（只算 5 条 supported）；
- premise overall（只算上述 9 条）；
- 冲突处理正确率；
- ACL 泄漏数；
- 目标文档 recall；
- P50/P95 延迟；
- 可观测 token；
- 逻辑 API 调用估计。

命令：

```bash
# 只校验 41 条数据，不调用模型
python tests/eval/run_research_team_eval.py --dataset full --dry-run

# 每类一条，共 6 条，执行 A/B/C
python tests/eval/run_research_team_eval.py --dataset quick

# 全量 41 条
python tests/eval/run_research_team_eval.py --dataset full

# 单案例调试
python tests/eval/run_research_team_eval.py --case-id C33 --variants C
```

输出默认是 `data/复杂科研评测结果.json` 和 `data/复杂科研评测报告.md`。

### 15.1 Citation 纠偏

旧正则只识别 `[文档1]` 和 `[S1]`，漏掉模型真实输出中大量 `[文档 1]`。当前正则为：

```python
r"\[(?:文档\s*(\d+)|S\s*(\d+))\]"
```

它覆盖 `[文档1]`、`[文档 1]`、`[文档   1]`、`[S1]` 和 `[S 1]`。测试直接验证 coverage 和 support，不改变模型回答格式。旧的 36 条 citation 数字全部废止，不再用于项目结论。

### 15.2 Citation support 的含义

自动 support 通过 Claim 与引用证据的分词重叠计算，只是 regression proxy，不等价于严格事实蕴含。18 条人工语义抽检为 17/18，唯一错误是将“下一步要回答的问题”写成“已经明确区分的结论”。详见 `data/复杂科研引用人工抽检.md`。

## 16. 全量 41 条纠偏结果与生产决策

2026-08-12，在相同 Qwen、知识库、Reranker 和检索配置上完成 41×3，含受 Reviewer 规则影响的 9 条 premise C 复测；累计墙钟 1629.8 秒：

| 方案 | 成功 | 关键词正确性 | 引用覆盖 | 引用支持 proxy | false premise | supported premise | premise 总体 | 文档召回 | ACL | P50/P95 | 平均输入/输出 Token | 调用 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| A Hybrid 单 Agent | 41/41 | 0.915 | 0.518 | 0.966 | 1.000 | 1.000 | 1.000 | 0.598 | 0 | 6.0/7.4s | 1450/385 | 1.98 |
| B Expansion 单 Agent | 41/41 | 0.939 | 0.516 | 0.970 | 1.000 | 1.000 | 1.000 | 0.632 | 0 | 7.0/8.9s | 2142/396 | 1.98 |
| C 固定团队 | 41/41 | 0.911 | 0.469 | 0.777 | 1.000 | 0.600 | 0.778 | 0.705 | 0 | 17.1/23.4s | 8195/904 | 7.07 |

按类别的完整六张表见生成报告。最关键的对比：

- `cross_scope`：B 正确性/coverage/support 为 1.000/0.586/1.000，C 为 0.875/0.322/0.562；
- `multi_evidence`：C 文档召回和 coverage 略高，但正确性 0.917 低于 B 的 1.000，延迟约 12.8s 对 7.4s；
- `temporal_conflict`：C 正确性、coverage、support、冲突处理都低于 B；
- `recommendation`：C coverage 略高，但正确性和 support 更低，延迟约 17.5s 对 6.4s；
- `false_premise`：C 正确性 0.875、冲突处理 1.000 高于 B 的 0.625/0.750，但 coverage/support 仅 0.260/0.438，低于 B 的 0.402/0.750，P50 约为两倍；
- `supported_premise`：C 正确性、coverage、召回较高，但只确认 3/5；A/B 确认 5/5，故前提核验不可靠。

因此没有类别取得稳定净收益。生产默认统一使用 B 类路径；C 保留为离线实验以解释为什么没有为了简历保留无效复杂度。

## 17. 保留或删除判据

建议只有同时满足以下条件才长期保留：

1. ACL 泄漏始终为 0；
2. 复杂任务引用覆盖/支持率相对 B 有稳定提升；
3. 错误前提和冲突处理不低于 B；
4. 正确性不下降；
5. 用户能接受约 20～30 秒的复杂分析延迟；
6. 真实科研问题人工复核确认建议确由证据支撑。

本轮结果不满足第 2、4 项，且成立前提可靠性低于 B，所以已从生产图删除团队节点和路由，而不是继续修 Prompt 让数据更好看。实验实现仍保持三角色、一次 revision 和确定性 Claim Validation，便于复现实验结论。

本轮后冻结 Agent 架构：没有新增第四个 Agent、Supervisor、动态 Worker、GraphRAG、Redis、Kafka、MCP、消息系统或新 Agent 框架。除非真实用户或新评测暴露明确问题，不再扩展拓扑。
